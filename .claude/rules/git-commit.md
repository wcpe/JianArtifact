# Git 提交与历史治理规范

> 适用于本仓库的提交信息、开发分支提交整理、主线合并与发布历史。

## 1. 提交信息规范（强制）

### 1.1 语言与 Conventional Commits

- 标题（Description）与正文（Body）必须使用简体中文，禁止英文、日文等非中文正文。
- 遵循 Conventional Commits；type 与 scope 使用英文小写。常用 type：`feat`、`fix`、`refactor`、`docs`、`chore`、`test`、`build`、`ci`、`perf`、`style`。
- 禁止在提交信息中添加任何 AI 签名、AI 尾注、作者署名或工具来源，例如 `Generated with ...`、`Co-Authored-By: ...`。

标题格式：

```
<type>(<scope>): <中文描述>
```

- `<scope>` 是可选的英文小写模块或能力域。本项目常用 scope：`server`、`web`、`wiki`、`ui`、`devmock`、`api`（OpenAPI 契约）、`protocol`（Raw/Maven/npm 等协议实现）、`repository`、`storage`、`migration`（Nexus 迁移）、`auth`、`persistence`、`config`、`deploy`、`build`、`ci`、`docs`。
- `<中文描述>` 简洁说明本次做了什么，必须使用简体中文，结尾不加句号。

正文格式：

- 标题与正文之间保留空行，正文使用简体中文，可用 `-` 列出要点。
- 正文说明“为什么改”和“改动要点”，不要逐行复述 diff。

正确示例：

```
feat(auth): 实现基于令牌的登录鉴权

- 统一令牌签发与校验，避免各接口重复处理鉴权
- 受保护接口由中间件校验令牌，失败时返回 401
```

错误示例：

```
feat(auth): add token-based login
```

### 1.2 禁止用阶段词代替改动内容

提交按功能点描述，不按开发阶段、时间批次或版本批次描述。最终提交的标题与正文禁止用 `Phase 0`、`P0`、`P1`、`P2`、`MVP`、`Sprint`、`第一期`、`本次迭代` 等词代替具体改动；这些词不能说明提交本身做了什么。

正确：

```
feat(auth): 实现令牌刷新接口
```

错误：

```
feat: 完成 MVP 第一期核心功能
```

## 2. 开发分支允许频繁提交

- `feature/*`、`fix/*`、`refactor/*` 等短生命周期开发分支应频繁、及时提交安全检查点，不得为了追求表面上的历史整洁而长期堆积大量未提交变更。
- 优先直接形成可保留的逻辑提交。需要把后续修正归入既有提交时，可以临时使用 `fixup!` 或 `squash!`，但它们只能存在于尚未共享的本地开发分支，并且必须在发 PR 或合入主线前整理掉。
- 临时 `WIP`、提交信息拼写修补和同一实现的跟随式修复不得未经整理直接或长期进入 `main` / `master`。
- 临时检查点可以尚未满足最终提交的完整粒度与验证门，但不得包含凭据、隐私数据等禁止内容，也不得推送或交给协作者继续开发；整理后的最终提交必须满足下文全部要求。

## 3. 最终逻辑提交的粒度与质量门（强制）

每个最终提交必须同时满足以下条件：

- **单一意图**：只完成一个功能点、一个修复、一次重构或一项文档治理；不把无关改动混在一起。
- **不混类型**：不得在同一提交中混合 `feat`、`fix`、`refactor` 等不同意图；顺手发现的问题另建对应类型的提交。
- **可独立理解**：仅查看该提交的说明与 diff，就能理解为什么改、改了什么。
- **可独立回滚**：撤销该提交不会被迫连带撤销无关能力。
- **可构建**：提交落地后代码能够编译或构建，不留下半截实现。
- **验证门通过**：最终提交前，本次影响范围内的格式化、静态检查、构建、单元测试、集成测试和必要的实机验收必须通过；具体判据见 `testing-and-quality.md`。验证门未全绿不得形成最终提交。

提交过大、包含多个意图或无法独立回滚时，必须按逻辑拆分。提交数量不是目标；提交边界以“一个可以独立理解和回滚的变更意图”为准，由行为、职责、依赖和回滚关系决定，不得按文件数量、开发时间、会话轮次、阶段编号或版本号机械划分。

一个中等规模需求可以由实现、测试、兼容性调整和耐久文档等多个逻辑提交组成；同一文件可以分属多个逻辑提交，多个文件也可以共同构成一个逻辑提交。

## 4. 提交历史整理与合并策略（强制）

### 4.1 发 PR 或合入主线前整理全部提交

发 PR 或合入 `main` / `master` 前必须审查分支上的全部提交，而不只看最后一次提交或最终 diff，并按逻辑重排、归并或拆分历史：清理 `WIP`、`fixup!`、`squash!`，修正提交信息拼写，把同一实现的跟随式修复归入所属逻辑提交，并把混合无关意图、无关需求或不同 Conventional Commit 类型的过大提交拆开。整理只能在尚未共享的本地分支上进行。

整理完成后，每个提交都必须满足单一意图、可独立理解、可独立回滚、可构建和影响范围验证门通过。开发期临时检查点可以被改写或吸收；最终逻辑提交则是供评审、合并、发布和长期追溯的稳定历史。

### 4.2 主线与 PR 合并策略

- `main` 或 `master` 主线只保留最终逻辑提交，不保留 `WIP`、`fixup!`、`squash!`、拼写修补或纯跟随式修复提交。
- 合并时优先采用能够保留整理后逻辑提交的 rebase 后 fast-forward、受控 rebase 或其他保留清晰提交序列的方式；选择方式的目标是得到可审查、可定位、可回滚的主线历史。
- 单一意图的小型 PR 可以整理为一个逻辑提交；包含多个独立意图的 PR 必须保留为多个逻辑提交，不得为了“一 PR 一提交”强行压缩。
- 禁止使用 Squash and merge 把整个版本压成单个提交；禁止把大型或多意图 PR 压缩成一个提交。版本历史应由多个按能力、修复、重构和治理划分的逻辑提交组成。
- 禁止制造“完整版本一次提交”的大提交。版本号不是提交边界，发版也不能替代此前逻辑提交的整理。

### 4.3 发布提交与标签

正式版本由此前已经进入主线的多个 `feat`、`fix`、`refactor`、`test`、`docs`、`build` 等逻辑提交组成。发版时另建独立 release commit，并在该提交上创建独立 tag：

```
chore(release): 发布 X.Y.Z
vX.Y.Z
```

release commit 只包含版本号、CHANGELOG 定稿以及发布所必需的元数据，不夹带功能、修复、重构或大范围格式化。`vX.Y.Z` tag 与独立 release commit 共同标记发布点；不得把整个版本的实现压成一条 release 大提交。

### 4.4 公开历史禁止重写

- 已 push、已被协作者基于其继续开发，或已被正式版本标签引用的历史禁止重写；不得对这类提交执行 rebase、squash、amend 或 force push。
- 已发布版本发现问题时创建新的 `fix` 提交；需要撤销既有改动时优先使用 `git revert`，保留原提交与撤销原因。
- 只有尚未共享的本地开发分支可以通过 rebase、squash、amend 等方式重排、拆分或压缩临时提交；一旦共享，改用追加提交或 revert。
- 严禁对 `main` 或 `master` 执行 force push，包括 `git push --force` 与 `git push --force-with-lease`。

## 5. 文档入库边界（强制）

判据：活文档，也就是长期维护并作为真源的文档，应当入库；做完即弃的易朽过程稿留在 `.tmp/`。

应当入库的耐久文档：

- 产品与需求：`README.md`、`CHANGELOG.md`、`docs/PRD.md`。
- 架构与契约：`docs/ARCHITECTURE.md`、`docs/adr/*.md`、`docs/API.md`。
- 协作治理：`docs/CONTRIBUTING.md`、`.claude/rules/*.md`。

严禁入库的易朽过程稿：

- 实施计划、里程碑、路线图，例如 `实施计划.md`、`PLAN.md`、`roadmap.md`。
- 过程性报告，例如 `IMPLEMENTATION.md`、`执行报告.md`、`分析.md`、`audit-*.md`。
- AI 助手过程性笔记、交流稿、思路记录。

文档与代码的同步要求见 `docs/CONTRIBUTING.md` 与 `.claude/rules/doc-sync.md`。

## 6. 提交操作底线

- 禁止跳过或绕过 hooks，包括使用 `--no-verify`；hook 失败时必须修复原因后重新提交。
- 提交前确认未包含 `.env`、凭据、密钥、隐私数据或不应入库的大型二进制。
- 未经用户明确要求，不自动提交、不自动推送。
