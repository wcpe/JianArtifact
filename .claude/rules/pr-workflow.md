# PR 工作流规范（强制）

> 主线只接受**经 PR 合入**的变更；PR **一律使用 Squash merge**。
> 与 `git-commit.md`（提交信息与历史治理）配套：本文件管「怎么进主线」，那个文件管「提交怎么写」。

## 1. 主线保护：禁止直接提交

- `main` / `master` **禁止直接提交、禁止直接推送**：所有变动——包括文档、配置、格式化、发版元数据——都必须先建分支、发起 PR，经评审与门禁通过后合入。
- 禁止对主线 force push（含 `--force-with-lease`），见 `git-commit.md` §4.4。
- 无例外：不因「改动很小」「只是文档」「先打通再补流程」而直推主线。

## 2. 分支与 PR 粒度

- 分支命名：`feat/*`、`fix/*`、`refactor/*`、`docs/*`、`chore/*`，短生命周期，合入后删除。
- 一个 PR 承载**一个可独立评审与回滚的意图**（可包含实现 + 测试 + 文档 + 契约重生成）。
- PR 分支上的提交仍按 `git-commit.md` §3 的单一意图组织（便于逐提交评审）；**合入时会被压缩**（见 §3），因此不要把 PR 当成提交粒度单位。
- PR 描述必须写清：为什么改、改动要点、验证证据（质量门/测试/实机验收）、影响面与回滚方式。

## 3. 合并策略：一律 Squash merge

- 所有 PR 使用 **Squash merge**：分支上的提交被压缩为**一条**落在主线上的提交（「一 PR 一提交」）。
- squash 提交的**标题必须带 PR 编号**，形如 `feat(web): 页面骨架收敛 (#123)`：让主线提交能直接跳回对应 PR 的讨论与评审记录。
- squash 提交的**正文必须由合并者自行总结**，写清「为什么改 / 改动要点 / 验证证据」；**禁止直接使用 PR 标题、PR 描述、PR 评论或分支提交正文**。PR 里的过程讨论、逐条回复与历史细节属于 PR，不属于主线历史。
- 标题的 type/scope 与正文语言仍按 `git-commit.md` §1：Conventional Commits + 简体中文描述，禁止任何 AI 签名、AI 尾注或作者署名。
- **禁止 Merge commit（`--no-ff`）**，**禁止 Rebase merge**：不让主线出现网状历史或分支回放产生的重复提交。
- 主线历史因此是线性序列；`git log --first-parent` 与常规 log 等价。
- 仓库设置层面同样只保留 squash（关闭 merge commit 与 rebase merge），避免绕过规则合并。

## 4. 发布

- 发版按 `git-commit.md` §4.3：独立 release commit（`chore(release): 发布 X.Y.Z`）+ 该提交上的独立附注 tag `vX.Y.Z`。
- release commit 同样**经 PR 合入**；tag 在合入后于主线对应提交上创建。
- 禁止把整个版本的实现压成一条 release 大提交。

## 5. PR 门禁（合入前必须全部通过）

| 门             | 判据                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------- |
| 质量门         | `scripts/check.ps1`（Windows）/ `scripts/check.sh`（Linux）全绿，见 `testing-and-quality.md` |
| CI             | PR 触发的 `ci.yml` 全绿：质量门 + CodeQL + 依赖漏洞扫描                                      |
| 隐私与敏感内容 | 见 §6，命中即阻断                                                                            |
| 文档同步       | 满足 `doc-sync.md`：契约、CHANGELOG、PRD、ROADMAP 与代码一致                                 |
| 提交整理       | 分支上的提交已按 `git-commit.md` §4.1 整理（无 `WIP`/`fixup!`/`squash!`/拼写修补）           |
| 合并提交信息   | squash 标题带 PR 编号（`(#123)`）；正文为合并者自写的总结，未照搬 PR 标题 / 描述 / 评论      |

## 6. 禁止提交的内容（强制）

以下内容**禁止**出现在任何提交（包括开发分支的临时检查点）里；发现即视为阻断项：先从暂存区移除，再检查是否已进入历史或远端。

- **绝对路径**：本机 / 构建机的绝对路径，例如 `D:\ProjectsGo\...`、`/c/Users/<name>/...`、`/home/<user>/...`、`/root/...`。文档与示例一律用仓库相对路径或 `<占位>`；URL 不算绝对路径。
- **隐私信息（PII）**：真实姓名、邮箱、手机号、身份证号、银行卡号，内部人名与账号，客户或第三方数据。
- **凭据与密钥**：口令、Token、API Key、JWT 密钥、私钥块、连接串里的 `user:pass@`。
- **IP 地址与内网信息**：真实公网 / 内网 IP（`10.`、`172.16-31.`、`192.168.`）、内网域名（`.corp`/`.internal`）、内部主机名与端口拓扑。测试与示例一律使用文档保留地址（`203.0.113.0/24`、`example.com`、`localhost`）。
- **被 `.gitignore` 忽略的文件与内容**：`.env*`、`*.pem`/`*.key`/`*.p12`、`id_rsa*`、构建产物、缓存目录（`.tmp/`、`.gomodcache/`）、大二进制等。需要模板时只提交 `*.example` 占位。

自查方式：提交前对 `git diff --cached` 逐条核对上述五类；CI 侧由 PR 门禁的敏感内容扫描兜底（检测口径与修复指引见 `privacy-guard` 技能：报告只写标记码，不写明文）。
