# 发布门禁与版本窗口

> 适用于本项目所有正式版本（`vX.Y.Z` tag）的发布与后续版本窗口开启。AI 代理与人类协作者都须遵守。

## 1. 发布门禁（强制）

**任何正式版本发布前必须通过全部验收门**——不满足则不打 tag、不发 release：

1. 质量门通过：`bash scripts/check.sh` 全项绿（前端 + 后端 + govulncheck）。
2. CI 全绿：推 main 触发的 `release.yml` 质量门 5/5 通过。
3. 该版本声明的实机验收门全部通过（定义在 `docs/ROADMAP.md` 对应版本段的"门禁"），且须用户确认。
4. 冒烟验收：已发布产物（GHCR 镜像 / Release 二进制）可运行、前端内嵌渲染正常、e2e 链路绿。

**流程**：先提交非发布改动 → 等 CI 绿 → 实机验收通过 → 提交发布 commit + 打 tag → 推送。

## 2. 版本窗口（强制，且必须等用户确认）

正式版本发布完成后**不自动、不立即**开启下一版本窗口：**窗口开启的时机与版本号只有用户能定**。过早开窗会把「下一版本是多少」这个决策预支掉（可能该是 patch、也可能是别的 minor 或 rc），确认前就写进 `VERSION`，之后很难无痕改回。

流程：

1. 发布 PR 合入并打好 tag 后**停下**，等待用户明确确认下一版本号（含主题）。
2. 用户确认后，才以**独立 PR** 提交 `chore(release): 开启 X.Y.Z 开发窗口`，同一提交内完成：
   - `VERSION` 与 `apps/server/cmd/jianartifact/main.go` 的 `version` 默认值更新为确认后的版本号（二者恒一致）；
   - `docs/ROADMAP.md` 把该版本标注为**进行中**，并写入用户认可的主题；
   - `CHANGELOG.md` 顶部保留空「未发布」模板。
3. 从发布完成到窗口开启之间：新开发改动照常走分支与 PR、条目进 CHANGELOG 未发布段，但**不得修改 `VERSION`**；这样即使窗口尚未开启，也不会把新改动错标成已发布版本。

禁止：

- 发布完成后顺手开窗（无论是否拆成独立 PR）；
- 未经用户确认自行选定下一版本号并写入 `VERSION` / `main.go` / `ROADMAP`。

## 3. 禁止

- 禁止在验收未通过时打 tag 或发 release（质量门/实机门任一未过 = 未通过）。
- 禁止**未经用户确认**就开启版本窗口（见 §2）；也禁止确认之后长期拖着不落地——确认后应及时以独立 PR 完成开窗。
- 禁止 CI 外手动构建产物作为正式发布（正式产物必须源自 CI）。
