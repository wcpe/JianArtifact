## 2. 历史交付

## 3. 当前 0.8.0 开发窗口

### 3.1 功能范围

- Docker/OCI、Cargo、PyPI、Go modules、NuGet 及其 Nexus 迁移扩展。
- 按格式启停、统一制品操作、可恢复 blob 回收和 v2 原子 operation。
- 发布账号防护、额度、不可变 Release 和完整认证审计。
- 搬迁转向一致性备份包：热备份 / 冻结窗口双模式生成、内容寻址 blob 快照、带时效签名的无登录下载、导入三通道（CLI / URL 拉取 / 分片上传）与「暂存 + 重启替换」。
- 写入冻结窗口：运行时可冻结、有界 TTL、超时自动解冻，冻结期间界面显著提示。
- 管理控制台信息架构、当前节点审计、业务仪表盘、当前主机监控和页面缓存。
- 端口级安全防护：允许访问域名白名单、回源 Token 校验与服务内置 TLS。
- Linux arm64 构建资产、声明式格式启停和 Windows 原生质量门。
- 实时复制通道（原级联树、逐跳凭据、集群页面与邻接监控）按 FR-138 整体退役，不再属于本窗口范围。

### 3.2 搬迁边界

```text
源节点                                          目标节点
  生成一致性备份包（manifest.json + VACUUM INTO 快照 + blobs.index + 内容寻址 blob）
     │  ── 传包：签名链接下载 / 分片上传 / URL 拉取 / CLI 直拷 ──▶
     │                                            导入：校验包格式、db 摘要与 blob 抽样摘要
     │                                            暂存目录 + 写 restore.pending
     └────────────────────────────────────────────▶ 重启：先生成 pre-restore-<ts>/ 备份，再原子替换库
```

- 包内**只含数据，不含密钥**：排除复制凭据密钥、JWT 密钥、迁移凭据密钥与 `-wal`/`-shm`；`manifest.kind` 固定为 `jianartifact-node-backup`，与 Nexus 迁移 `bundle/` 外部导入包严格区分。
- 切换窗口靠**冻结窗口 + 增量差包**压到分钟级：冻结 → 生成差包 → 传输 → 导入 → 起服 → 切 DNS。
- blob 集合以快照库 `asset` 表为准而非扫描目录；blob 内容寻址可加，运行中即可直接合并。
- 不做节点角色、配对仪式、水位 / 代次 / 拓扑控制，也不做自动选主或双主写入。

备份包生成、下载、导入三通道与冻结窗口均已开发实现并有端到端演练证据；详细的包格式与通道契约见 [`specs/0.8.0-node-backup-and-relocation.md`](specs/0.8.0-node-backup-and-relocation.md) 与 [`adr/0027`](adr/0027-package-based-node-backup-and-relocation.md)。

### 3.3 当前状态

当前 M2 的协议、迁移、制品生命周期、备份包搬迁和控制台 FR 均已有工作区实现或既有交付实现；PRD 以“开发完成，待用户验收”区分尚缺真实证据的功能，以“开发完成，验收通过，待发版”区分已过自动化/隔离门或已完成真机演练的功能，以“已退役（FR-138）”标记随复制通道退场的 FR。测试通过不等于真实发布通过。2026-09-13 已在 t1 隔离测试站完成搬迁链路真机演练：热备份生成与深度校验、签名链接无登录下载（sha256 一致 + Range 206 + 篡改/无签名 401）、写入冻结窗口（写 503 `write_frozen` / 读与登录放行 / `until>24h` 400）、三通道导入（CLI / URL 拉取含 SSRF 拒绝 / 分片上传）与重启原子替换（`pre-restore-<ts>/` 保留、`restore.pending` 消费、规模与登录一致）均已通过；同时发现两项阻塞缺陷（已于 2026-09-14 修复并复验，见 §4.6）。同日另完成端口防护验收：内置 TLS 双监听实测通过（TLSv1.3 + HTTPS 真实登录/读配置，移除配置后端口关闭）；回源 Token 在**非回环**路径上实测通过（固定白名单内 Host 时：无 Token → 404、正确 Token → 200、错误 Token → 404；业务接口带正确 Token 但无凭据 → 401），并据此确立「用例必须固定 Host ∈ allowedHosts 以隔离两个守卫」的验收口径，见 §4.3。

## 4. 0.8.0 整期验收门禁

### 4.1 质量和契约

- Windows 原生 `make check` / `scripts/check.ps1` 通过；包含前端格式、类型、lint、测试、构建、Go vet/lint/race/vuln、契约和静态构建。
- `api/openapi.yaml`、生成 Go 类型、前端 client 和 devmock 一致；生产构建不包含 Mock 数据或 Mock worker。
- 所有 0.8.0 新接口、配置、迁移和安全行为有对应 spec、测试和 CHANGELOG 记录。

### 4.2 制品与协议

- Raw/Maven/npm 及新增格式的原生客户端读写/删除语义经真实服务验收。**（2026-09-13 用户决定：Docker/Cargo/PyPI/Go/NuGet 的真实客户端验收豁免，改以协议层自动化 + 公网真实拉取路径为准）**
- 大文件始终流式；blob 哈希、引用计数、隔离回收和失败恢复一致。
- 统一资产操作和 operation envelope 不出现半批次、错误引用或不可恢复的 blob 删除。

### 4.3 恢复与搬迁

- 备份生成双模式可用：热备份不停服（独立连接 `VACUUM INTO` 取快照，不占用业务主连接池）；冻结窗口模式先停写再取快照，CLI 的 frozen 模式假定服务已停并显式提示。
- 无登录拉包：`/api/v1/backups/{id}/download` 的签名链接在有效期内容器外新机器无需登录即可拉取，并支持 Range 断点续传；过期或篡改的链接必须失效。
- 导入三通道各自可用：CLI 直拷贝；URL 拉取（拒绝回环 / 私网 / 链路本地 / 云元数据，每次拨号重新解析并对重定向重新校验）；分片上传（按磁盘推导续传、缺片补片、重复片幂等、可取消）。
- 重启替换安全：替换前先生成 `pre-restore-<ts>/` 备份，`restore.pending` 消费后清除；目标非空判据排除内置 `anonymous` 主体；规模护栏（快照 8 GiB / blob 总量 50 GiB / 条目 500 万）在写盘前生效。
- 写入冻结窗口有界：`until` 不得晚于 `now+24h`（否则 400），否则用 `ttlSeconds`（缺省 7200，钳到 [60, 86400]），**不提供无限期冻结**；冻结期业务与管理写入返回 503 `write_frozen`，读方法、`POST /api/v1/auth/login`、维护命名空间与导入 / 上传路径放行。
- 增量差包：只携带新增 blob 与新 db，`manifest.expected` 与本地集合并集比对；基线缺失时明确拒绝且不留残留文件，被差包引用的基线不可删除。
- 端口防护三件套的真机口径（2026-09-14 t1 实测确立）：
  - **回源 Token 的用例必须固定 `Host ∈ allowedHosts`**——否则非回环请求会先被主机白名单拦成同样的 404，"不带 Token 得 404"无法区分是哪个守卫生效，会假通过。
  - 完整取证三连：固定白名单内 Host 时「不带 Token → 404」「正确 Token → 200」「错误 Token → 404」；业务接口另加一条「正确 Token 但不带凭据 → 401」（证明确实穿过 Token 守卫到达鉴权层）。
  - 回环恒放行是设计语义（本机运维与健康检查），因此该维度只能在**非回环**路径上验；同机反代或隧道发布时对端恒为回环，守卫不产生防护效果。
- 内置 TLS：配置 `JIAN_TLS_ADDR`/`JIAN_TLS_CERT`/`JIAN_TLS_KEY` 后 HTTP 与 HTTPS 双监听（已实测 TLSv1.3 + 真实登录/读配置），移除配置后 TLS 端口关闭且 HTTP 不受影响。
- 以上需真实服务演练证据（本机 + 远端运输），测试通过不替代演练。

### 4.4 控制台和运维

- 「迁移与备份」页（`?tab=backups` 深链）正确呈现备份列表的状态 / 方式 / 大小 / 规模 / 创建时间，生成中可轮询进度，并能发起 URL 导入与分片上传。
- 冻结期间界面给出显著提示（冻结状态与截止时间），避免遗忘解冻。
- 不显示令牌、环境变量、内部地址或原始错误；搬迁不再有跨节点观测维度。
- FR-120 仅验证当前实例主机 CPU、内存、磁盘、网络、进程和 `/readyz`，不从邻居采集数据。
- 真实浏览器复核：设置页（域名白名单与回源 Token）、迁移与备份页、审计中心与主机监控页。

### 4.6 真实演练发现的缺陷（已于 2026-09-14 修复并 t1 复验）

以下两项在搬迁主链路的真实演练中复现，属**代码缺陷**（文档口径为「重复片幂等覆盖」「包登记与实际状态一致」）。均已于 2026-09-14 修复、补齐失败用例并在 t1 复验通过：

- **B1 · 备份包被还原后自身登记状态被误标 failed**（影响 FR-132 / FR-134）：
  - 复现：热备份生成包 P（其内嵌快照取自生成中的库，此时 P 的登记行仍是 `generating`）→ 导入 P 并重启 → 启动期「清理遗留生成中包」把目标节点上的 P 标为 `failed / 服务重启，备份生成被中断`。未参与还原的同批基线包仍为 `done`。
  - 现象：P 的包文件与侧车索引完好（深度校验通过、签名下载 sha256 一致、导入还原成功），仅登记状态错误；后果是**在目标节点无法基于 P 继续生成增量差包**（报「基线包不可用，状态为 failed（需 done）」），堵死「落地后再做差包」的搬迁续跑路径。
  - 修复：`ReconcileStartup` 改为按「归档是否完整可读」收口——manifest 身份正确即判 `done` 并回填大小与计数，归档缺失才判 `failed`。
  - 复验（t1）：生成 `bk-20260913-231116-361d4e` → 导入并重启 → 该包 `status=done / size=1591962`；此前被堵死的「基于还原后的包生成差包」现已成功（差包 `bk-20260913-231123-7692a5`，1,578,780 B）。
  - 用例：`TestBackupReconcileStartupKeepsRestoredPackageDone`（归档完整 → done；归档缺失 → failed）。
- **B2 · 分片重传被「累计超额」误拒**（影响 FR-137）：
  - 复现：`POST /backups/uploads` 建会话（`totalBytes=1557313`）→ 首片 PUT `chunks/0` 返回 200 → 重传同一分片返回 **400**：`参数校验失败：累计分片 1557313 + 本次 1557313 超过声明总字节 1557313`。
  - 现象：与「续传按磁盘推导、重复片幂等覆盖」的既定口径不符——磁盘上已存在的同序号分片被计入累计字节，导致网络抖动后的重试被拒；客户端必须自行判断「该片是否已存在」才能绕开。
  - 修复：累计字节校验先扣除本次 index 在磁盘上的既有字节（覆盖语义），再与声明总字节比较。
  - 复验（t1）：会话 `up-20260913-231223-6c04b5` 首片 200 → 重传同片 **200**，`uploadedChunks` 仍为 `[0]`（修复前为 400）。
  - 用例：`TestBackupUploadRetransmitSameChunkIsIdempotent`。

遗留观察（非阻塞）：若通过 URL 拉取或分片上传导入、且归档未落到目标节点的 `backups/` 目录，该类包的登记仍会判 `failed`（`OpenReader` 要求包文件存在）。后续可考虑让导入把归档一并归入 `backups/`，使登记与文件始终一致。
确定性复现步骤与日志/响应体证据见 `.tmp/acceptance-version-v0.8.0-20260913.md`。
