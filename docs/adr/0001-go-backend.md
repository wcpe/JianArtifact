# ADR-0001：后端采用 Go 重写（替代旧 Rust 实现）

## 状态
已接受

## 背景
JianArtifact 的前身用 Rust 实现制品仓库后端。本次重写要在保留旧项目 UI 组件库与产品形态的前提下，选定新的后端语言与生态。核心约束：单二进制交付、易于团队维护、丰富的 HTTP / 制品协议生态、跨平台交叉编译、无重型运行时依赖。

## 决策
后端改用 **Go**，Web 框架用 **Gin**，数据访问用 **sqlx**，口令哈希用 **argon2**，会话令牌用 **JWT(HS256)**。

## 理由
- Go 原生支持静态编译与交叉编译，天然契合单二进制、多平台（含 arm64 / Windows）发布目标。
- 标准库 `net/http`、`io`、`embed` 与成熟生态直接支撑流式大文件、前端资源内嵌等制品仓库刚需。
- 相较 Rust，Go 的心智负担与编译时长更低，团队上手与长期维护成本更可控；对本项目"以 IO 与协议协调为主、计算密集度不高"的负载，Go 的性能足够。
- Gin + sqlx 是轻量、可控、无过度抽象的组合，符合"简单优先"不变量。

## 后果
- 正面：交付形态简单（见 ADR-0005），CI / 交叉编译链路短；生态覆盖各制品协议客户端行为验证。
- 负面 / 约束：放弃 Rust 的编译期内存安全保证，需以 `go vet`、`golangci-lint`（警告即失败）、`govulncheck` 与充分测试补足；并发正确性靠规范（禁主线程 / 持锁 IO）与 race 检测保障。

## 备选方案
- **续用 Rust**：编译期安全最强，但重写目标之一即降低维护门槛，且团队生态取向偏 Go，落选。
- **Node.js / TypeScript 后端**：与前端同语言，但单二进制交付、大文件流式与 CPU 稳定性不如 Go，落选。
- **Java / Kotlin**：生态成熟（Nexus 本身即 JVM），但需 JVM 运行时、违背单二进制零依赖目标，落选。
