# ADR-0004：API 契约设计优先，OpenAPI 为唯一真源

## 状态
已接受

## 背景
前后端分属 Go 与 TypeScript 两个工程，管理 API 面较大且随版本演进。需要一种机制防止前后端接口漂移，并让契约变更可评审、可测试。可选路线为"代码优先生成文档"或"设计优先手写契约再生成代码"。

## 决策
采用**设计优先**：手写 `api/openapi.yaml` 为**唯一真源** → `oapi-codegen` 生成 Go server 接口与类型；前端据同一份 OpenAPI 生成 client，`packages/devmock` 据同一契约做 Mock 与比对。

## 理由
- 契约先于实现，接口设计可在编码前评审，前后端并行开发有稳定契约。
- 单一真源 + 双向生成，从机制上消除"文档与实现不一致"；契约比对测试将漂移变成 CI 可捕获的失败（质量不变量）。
- devmock 与 OpenAPI 自动比对，让前端在后端未就绪时也能对齐真实契约。

## 后果
- 正面：接口稳定、漂移可拦截、前后端解耦并行；契约即测试基线。
- 负面 / 约束：契约变更需先改 `openapi.yaml` 再 `task gen` 重生成，流程更重；生成产物不得手改。协议端点（Raw/Maven/npm 等原生客户端交互）多为二进制流与原生路由，不完全适合 OpenAPI 描述，这部分以协议兼容测试而非契约生成保障。

## 备选方案
- **代码优先（从 Go 注解 / 反射生成 OpenAPI）**：省一次手写，但真源在代码、前端易滞后、评审前置性弱，落选。
- **gRPC / Protobuf**：强类型契约，但制品协议客户端与浏览器管理端以 HTTP/JSON 为主，引入 gRPC 收益不抵成本，落选。
