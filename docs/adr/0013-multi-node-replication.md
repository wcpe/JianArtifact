# ADR-0013：多节点复制架构（双向拉取 + 变更日志 + LWW）

## 状态

提议中

## 背景

按实际部署需求（FR-83~86，插队 0.7.0）：一个公网主机（腾讯云 CDN，上传限制 ~800MB）与一个内网主机（Cloudflare Tunnel，上传限制 100MB）组成主备制品库。要求双向同步、主写 + 备临时写、全量数据（制品 / 仓库 / 用户 / ACL / 令牌 / 配置）最终一致、删除双向传播、实时增量 + 首启全量。

**关键约束**：同步必须走 HTTP 协议（用户明确"做协议而非 SSH 复制"），且**只能 GET 拉取、禁止 PUT 推送**——Cloudflare Tunnel / CDN 的上传体积限制只作用于请求体（上传），对响应体（下载）无大小限制（官方文档：connection-limits 仅限制响应头 128KB / URL 16KB，无响应体上限）。因此任何把制品"推送"到对端的行为都会撞上传限制，拉取（GET）则完全不受限。

现状基础：元数据真源 SQLite（ADR-0002），blob 内容寻址存文件系统；写路径集中在 domain 层（AssetService / RepositoryService / UserService / TokenService / SettingService）；当前无分布式协调、无事务化写路径（除 acl / offline_index 外基本单条 SQL）。

## 决策

**多节点复制采用"变更日志 + 双向拉取 + last-writer-wins"的最终一致模型**：

1. **变更日志（repl_change 表）**：本地每次业务写（put / delete）落一条变更日志，含全局递增 `seq`、写入节点 `node_id`、操作 `op`、实体类型 `entity_type`、实体键 `entity_key`、变更后数据 JSON `data`、时间戳 `ts`。日志与业务写**非同一事务**（业务写成功后追加日志；崩溃丢日志靠定期对账兜底，见决策 6）。

2. **双向拉取协议（全部 GET）**：节点主动向对端 `GET /api/v1/cluster/sync/pull?since=<seq>` 拉取增量变更；变更中的 blob 按需 `GET .../blob/<hash>` 流式拉取（只拉本地缺失）。首启经 `GET .../full` 全量初始化。**全程无 PUT / POST 推送**。

3. **对等拓扑**：节点间对称，各持有 `node_id`（唯一）与对端列表（URL + 同步令牌）；主备只是部署角色，复制机制无主从依赖。

4. **last-writer-wins 冲突解决**：每个实体以 `(ts, node_id)` 排序裁决——应用对端变更时，若本地该实体的最近变更 `(ts, node_id)` 更新，则跳过；否则覆盖。删除以 tombstone 变更表达，LWW 同规则。

5. **时间戳**：`ts` 为写入节点本地时钟（RFC3339Nano）。时钟漂移通过 `node_id` 字典序打破同 ts 平局；最终一致由定期对账兜底，不追求强一致。

6. **对账兜底（FR-85）**：节点定期（默认每 N 分钟）比对双方 `seq` 水位，落后即补拉；新对端配置后自动触发全量初始化。**弥补"日志与业务写非同一事务"可能丢失的变更。**

## 理由

- **GET 拉取**是唯一不受 Cloudflare / CDN 上传限制约束的通道，直接满足"复制不得触发 100MB / 800MB 上传限制"的核心约束；双向都从对方拉，天然规避推送。
- **变更日志 + seq 水位**比"定期全量比对"实时性高（事件触发即时拉取），比"每写即推"简单（无对端可达性依赖，断网自动积压、恢复自动续拉）。
- **LWW + tombstone + 对账**以最简机制达成最终一致；用户已确认接受 last-writer-wins（不要求强一致 / 事务性复制）。
- **日志非事务追加**避免大规模重构现有写路径（现有 domain 写路径基本无事务）；代价是崩溃窗口可能丢日志，由对账兜底——对"制品仓库最终一致"场景可接受（与 ADR-0002"SQLite 单写者"定位一致）。

## 后果

- 正面：复制全程 GET 不受上传限制；机制简单、无分布式协调依赖；双向对称、断网恢复自动续拉。
- 负面 / 约束：
  - 复制是**最终一致**（非强一致）：短暂窗口内两节点数据可能不同（取决于拉取频率）。
  - 时钟漂移可能造成 LWW 误判（用 node_id 打破平局，靠对账修复）。
  - 变更日志随数据量增长需定期 GC（保留足够覆盖对账窗口即可；具体策略 FR-83 定）。
  - 令牌 / 凭据类数据同步需谨慎：仅同步**引用名 / 摘要**，明文密钥不入库、不同步（延续 ADR-0002 / SECURITY 约定）。
- 前置：本决策不依赖外部中间件（无 MQ / 无协调器），符合"默认零外部依赖"。

## 备选方案

- **PUT 推送**（每写即推送到对端）：直接触发 Cloudflare 100MB / CDN 800MB 上传限制，大制品同步失败——**否决**。
- **SSH / rsync 文件级复制**：用户明确不要（非协议），且 SQLite 文件在 WAL 下需一致性快照、跨网络部署复杂——**否决**。
- **定期全量比对对账**：实现简单但实时性差、数据量大时开销高；作为兜底保留，不作为主通道。
- **外部分布式协调 / 消息队列**：引入外部依赖，违背默认形态，且对最终一致场景过度设计——**否决**。
