# ADR-0014：原子制品操作与 Blob 回收

## 状态

已被 ADR-0019 取代

## 背景

v0.7.0 的删除仅移除 `asset` 元数据并保留内容寻址 blob，批删允许部分成功，复制按单条制品最终一致。v0.8.0 需要在共享 blob 下实现引用归零立即回收、批量操作全成或全不成，并让集群对端不暴露半完成操作。

SQLite 事务与文件系统没有共同事务。直接先删 blob 会在数据库提交失败时损坏仍存在的资产；先提交数据库再删 blob 会在物理删除失败时留下孤儿内容，均不满足要求。

## 决策

1. 所有本地 `asset.blob_hash` 引用变更均经注入的节点级 `AssetMutationCoordinator` 执行，禁止直接调用资产仓储写入。覆盖协议发布、代理缓存写入、格式派生 metadata 所关联的 asset、管理操作、仓库删除、迁移写入、复制应用都在此范围；仅改变格式索引但不改变 blob 引用的写入仍必须与同一操作的 asset 计划共同提交。协调器串行化同节点的引用变更，并在短 SQLite 写事务中重新计算引用数和完整计划。
2. blob 引用以单个节点的全部活动 `asset.blob_hash` 为准。仅在协调器确认计划提交后无任何活动引用的 hash 才可回收；共享 blob 不得提前删除。协调器持久化 `prepared`、`staged`、`committing`、`completed`、`rolling_back` intent 和完整前镜像，所有状态转换均为短 SQLite 事务；文件移动、恢复和删除一律在 SQLite 写锁外执行。
3. 归零 blob 通过同一文件系统内原子移动进入持久化暂存区。`prepared` 期间资产仍从原位置读取；`staged` 期间旧资产的读路径按 intent 从暂存位置读取；`committing` 与 `rolling_back` 期间受影响路径由读门等待终态，不能按旧 asset 行直接打开原路径。物理回收失败、数据库失败或进程崩溃时，协调器按前镜像恢复暂存 blob 和业务状态；只有完成物理清理后标记 `completed` 的操作才向读路径、审计查询和复制拉取公布新视图。不得在 SQLite 写锁内执行文件 IO，也不得让未完成操作返回半旧半新的内容。
4. 批量删除、移动与重命名均使用 UUIDv7 `operationId`，并持久化来源节点、排序后的实体键、项目数、SHA-256 清单摘要和统一版本元组 `(ts,node_id)`。本地逐制品落审计和复制记录，但整批以一个完成边界发布；对端收齐、校验清单后使用同一操作引擎在单个事务中应用。
5. 对端若发现任一清单实体已有更新版本，拒绝原批次而不部分应用。接收节点对每个 item 比较远端与本地版本元组，tombstone 与 put 同为可比较实体状态：较高元组的完整状态胜出，相等但内容不同视为损坏并拒绝。接收节点以严格高于两侧最大值的新统一版本元组、排序后的全部赢家状态和新 `operationId` 持久化 successor 操作，再通过既有 GET pull 发布；不得复用或部分修改原批次。接收审计同时保留本地复制服务身份、来源节点和原始操作者快照，绝不复制口令或令牌。
6. 操作仅限 hosted 仓库。Raw 支持任意文件或目录删除、移动和单项重命名；Maven/npm 仅允许其格式感知删除，不支持管理端移动或重命名。

## 后果

- 成功操作不保留归零 blob，失败或崩溃不损坏仍被引用内容；未完成操作的受影响读请求只会读取同一旧视图或等待终态。
- 复制仍是 GET 拉取和最终一致，但单个已发布批次在每个节点均原子可见。
- 需要新增持久化 intent、读门、暂存恢复、批次复制协议、清单冲突 successor、并发引用线性化和覆盖异常路径的测试；不能在现有 `AssetService.Delete` 中直接调用文件删除。
- 旧批删接口不再允许部分成功，保留为弃用兼容入口并委托统一引擎。
