# ADR-0023：主备级联树单向复制与受控人工提升

## 状态

开发完成，待用户验收（v0.8.0 尚未发布；本开发窗口直接修订本 ADR）。本 ADR 取代 ADR-0013 的全互联双向复制决策；FR-121 的逐跳凭据细节由 ADR-0026 同步约束。

## 背景

ADR-0013 的对等双向拉取和 LWW 冲突模型允许任一节点生成并回流业务变更，且全互联配置会让拓扑、凭据和故障恢复复杂化。生产制品库需要唯一权威写入源，同时需要支持多个地域或边缘节点分层分发，不能要求每个节点知道完整集群拓扑。

复制仍必须经 HTTP GET 拉取，以避免 CDN、Tunnel 的上传限制；现有 v2 operation envelope 的完整性、blob 校验和 watermark 语义继续适用。

## 决策

### 1. 采用有向级联树

集群是有向无环的级联树：

- 根节点是唯一 `primary`，负责业务写入；
- 每个非根节点只有一个直接上级；
- 每个节点可以有零个或多个直接下级；
- 下级始终主动向直接上级发起 v2 GET pull，上级不主动连接或推送下级；
- 每个节点只维护直接上级和直接下级的配对信息，不维护、不要求展示全局拓扑。

严格的 `primary → standby → standby` 单链是级联树中每层只有一个下级的特例。

### 2. 业务写入权与中继能力分离

业务角色继续使用 `primary`、`standby`、`disabled`：

- `primary` 是唯一业务写节点，生成根源复制流；
- `standby` 永远拒绝本地业务、管理和协议写入；其中启用中继能力的 standby 可以为直接下级提供复制源，但只能提供自己已经完整接收和校验的上游数据；
- `disabled` 不参与复制，保持单节点行为。

中继 standby 不把上游数据重新记录为本地业务变更，不生成 successor，不把本地历史反向带回上游。中继能力必须显式启用，不能因普通 standby 收到一次拉取请求而自动开放。

### 3. 复制链路保持 GET-only 与 v2

每条父子边只提供三类经专属凭据保护的 GET：能力协商、v2 records 拉取和按哈希流式拉取 blob。子节点必须先确认直接上级具有兼容的中继能力和 v2 operation envelope 能力，失败时不应用数据、不推进 watermark，也不得自动绕过直接上级连接更高层节点。

所有 operation envelope、普通 change、原始 `sourceNode`、stream generation、`seq` 和 `operationId` 在中继过程中保持不变。下级看到的是根源流的原始顺序，而不是中继节点重新生成的本地序列。

### 4. 中继使用独立的持久化入站/转发日志

本地业务 `repl_change` 继续只表示本节点产生的业务源变更，不能直接承担中继日志。每个具备中继能力的 standby 增加独立的 relay/inbox 记录，至少保存：

- 根源 stream generation、source node 和 source seq；
- record 类型、operation envelope 或普通 change 的完整载荷；
- 所有 blob 哈希与依赖；
- 接收、完整校验、原子应用和可转发状态；
- 直接上游和直接下游的边界信息。

只有已经完整取得依赖、校验所有 blob、完成本地原子应用的记录，才能被直接下级拉取。当前工作区以 `replication_relay_record` 保存根源 stream/source seq 作为 inbox，以 `replication_relay_frontier.forwardable_seq` 在整轮成功后原子推进下游可见 record/blob 前缀，并以保守策略保留 relay blob；失败轮次可以留下不可见 inbox 供重试，但不得推进下游 latest/hasMore，也不得通过 blob GET 绕过。父流 generation、watermark 与 valid 围栏原子持久化，失效状态跨重启保持；同 stream/seq 的载荷不可变。子边观测按直接 child 分开保存。按直接下级确认水位定向回收、人工重新挂接演练仍是发布前验收项，旧 watermark 不得继续使用。

### 5. 凭据逐跳配对

父节点只为自己的直接下级创建、验证、撤销和轮换凭据；子节点只保存绑定直接父节点的本地密文。凭据不跨层转发、不复用、不授予管理或业务写权限。根 primary 不需要知道孙节点，relay standby 也不需要知道孙节点之后的拓扑。

### 6. 故障恢复仍受控，不自动换父

本期不提供自动选主、自动换父或双主写入。中间节点故障时，其下游保持明确的父节点不可用状态；需要恢复时由运维先围栏旧写入源，再核验水位和哈希，执行人工提升或人工重新挂接。改变父节点或提升为新的 primary 必须生成新的 stream generation，并按受控回填流程处理旧 watermark；旧节点重新加入必须使用全新数据目录。

## 理由

- 级联树将根节点的连接和出口压力限制在直接下级，支持分层、跨地域和边缘分发；
- 每个节点只管理相邻边，避免全互联网状配置和全局拓扑依赖；
- 保留单一业务写权威，避免 standby 业务变更回流和 LWW 覆盖主数据；
- 复用 GET-only、v2 原子 operation、blob 校验和 watermark 语义，兼容现有 CDN/Tunnel 传输边界；
- 中继日志与本地业务日志分离，防止转发数据形成环路或污染源端变更历史。

## 后果

- 需要新增 relay/inbox 持久化模型、连续前缀判定、边级 watermark、blob 保留和 stream generation；
- standby 的复制源接口已扩展为“具备中继能力的已认证父节点”，但仍不能开放业务写入；
- 链路延迟会随层数累加，中间节点故障会影响其全部下游；
- 重新挂接、提升和历史回填必须由运维明确执行，不能让节点凭旧 watermark 自动接续到新父节点；
- 集群页面和监控只能展示本节点及直接邻接边，不能声称掌握孙节点或全局健康状态。

## 备选方案

- 保留当前一主多备星型：实现简单、故障隔离更好，但 primary 必须直接服务所有 standby；保留为小规模部署的可用简化拓扑。
- 保留全互联双向 LWW：不能保证唯一写入权威，且拓扑和冲突复杂，否决。
- 无状态透明代理：中继不保存已接收记录，难以保证本地已应用前缀、blob 保留和断点一致性，否决为正式路径。
- 自动选主或自动换父：需要可靠围栏和协调边界，当前单二进制范围内无法安全提供，否决。
