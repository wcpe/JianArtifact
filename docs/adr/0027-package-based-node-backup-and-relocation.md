# ADR-0027：以一致性备份包取代实时复制通道作为节点搬迁手段

## 状态

开发中（v0.8.0 尚未发布）。本 ADR 记录搬迁手段的转向：备份包的生成、登记、下载与恢复路径。相关影响：
- 取代 ADR-0023（主备复制）与 ADR-0026（逐跳拉取凭据）在"节点搬迁"这一用途上的定位；
- 复制通道本身的代码退役安排见"后果"一节，属于独立清理工作，不在本期落地。

## 背景

原方案把节点搬迁建模成实时复制：一个静态 primary 向 standby 单向 GET 拉取，拓扑是一棵手工维护的级联树，另有逐跳凭据、水位、代次与人工提升流程。

实际使用下来，这套模型对"把一套实例从 A 机器搬到 B 机器"这个真实需求是过度的：

- **搬迁是一次性事件，而复制是为持续同步设计的。** 一次性事件却要付出持续运行的成本：拓扑、水位、凭据轮换、邻接监控、孤儿轮次清理、角色提升，全部都要维护。
- **失败模式多且难以自证。** 拷贝凭据、水位错位、代次复用、忘记围栏旧 primary，任何一步出错都表现为"数据不一致"，而不是明确报错。
- **搬迁完成后原节点通常直接退役。** 用户明确表示原有集群可以直接退役——既然目标机器接手后旧机器不再参与服务，就不需要长期维持一条复制边。
- **数据边界本来就是"一个 SQLite 加上一堆内容寻址 blob"。** 这两个东西天然可以打成一致快照，不需要通过变更流重建。

## 决策

### 1. 搬迁的传输单位是"一致性备份包"，不是复制流

备份包是 `${JIAN_DATA_DIR}` 下一个自包含的 tar.gz：

```
manifest.json            包元数据与摘要
jianartifact.db          VACUUM INTO 产出的一致性快照
blobs.index              每行 "<sha256> <size>"，用于核对与求差
blobs/<xx>/<yy>/<hash>   仅快照库 asset 表引用到的 blob
```

`manifest.kind` 固定为 `jianartifact-node-backup`，与 Nexus 迁移用的 `bundle/` 离线包（OPERATIONS.md §3.2）明确区分。搬迁流程退化为四步：**生成包 → 传包 → 导入包 → 校验**，没有角色、水位、代次或拓扑。

### 2. 包内只有数据，不含任何密钥或节点本地配置

排除 `replication-credential.key`、JWT 密钥、迁移凭据密钥、环境文件、`-wal`/`-shm` 与 blob 临时/隔离目录。理由：密钥属于节点身份而非可搬迁的业务数据；把一个节点的密钥复制到另一个节点会制造两个共享身份，破坏"一个节点一份身份"的边界。

代价是新机器需要人工重新配置密钥与域名。这个代价被接受——它换来的是"包泄露也不等于密钥泄露"。

### 3. 热备份用 `VACUUM INTO`，且必须走独立连接

- 用 `VACUUM INTO` 而不是拷文件：它产出一个已 checkpoint 的单文件一致性快照，WAL 下的并发写不会让快照落在半个事务上。
- **必须另开一条连接执行**：应用主池（`persistence.Open`）是 `SetMaxOpenConns(1)`，在主池上跑 `VACUUM INTO` 会在整个快照期间独占唯一的连接，把全部业务查询排到后面——对大库等同于服务停摆。WAL 下读不阻塞写，独立连接不抢主池。
- **blob 集合以快照库的 `asset` 表为准，而不是扫 `blobs/` 目录**：目录里可能残留未被任何资产引用的 blob（回收前的中间态），扫目录会把它们打进包造成虚大；而 `asset` 表是"哪些内容还能被下载"的权威定义。
- blob 写入路径是"写临时文件 → 校验 sha256 → 原子 rename"，因此**出现在最终路径的 blob 必定完整**；快照之后新写入的 blob 不被快照引用，自然排除在集合外。

### 4. 下载走带时效的签名链接，而不是会话

管理接口统一用 `Authorization: Bearer` 认证，普通 `<a href>` 下载带不上这个请求头；而搬迁场景要求新机器能直接粘贴一个地址把包拉过去。

因此签发一个只绑定"某单个包 + 明确截止时间"的 HMAC 令牌（`?exp=<unix>&token=<hmac>`），签名密钥由启动密钥派生而非复用。**包本身不加密**：包内不含密钥，加密的收益低于它带来的口令分发与脚本化障碍。风险由"HTTPS + 短有效期"承担，并写进文档。

### 5. 恢复走"暂存 + 重启替换"，覆盖需二次确认

运行中无法安全替换 SQLite 文件。因此导入分两段：

1. 校验（manifest 可识别版本、db 摘要、blob 抽样摘要）后解包到 `restore-staging/`，并写 `restore.pending` 标记；
2. 下次启动时执行替换：先给现有数据做 `pre-restore-<ts>/` 备份，再原子替换 db，然后清除标记。

blob 是内容寻址且可加的，可以运行中直接合并；只有 db 需要重启替换。目标非空时要求显式确认，且**默认保留 pre-restore 备份**作为回滚退路。

### 6. 集群功能退役

原复制通道（FR-115/119/121 及其页面、CLI、诊断读模型）不再作为搬迁路径，整体退役。

## 理由

- **把"持续同步"降级为"一次性搬运"，删掉了一整类状态**：没有水位就没有错位，没有代次就没有复用，没有拓扑就没有换父，没有角色就没有提升事故。
- **可自证**：包的完整性由 manifest 摘要与逐 blob sha256 判定，导入前后都能独立校验，不依赖对端行为。
- **停机窗口可控**：热备份在线完成；增量差包（同一基线包的 blob 集合求差）只携带新增 blob 与新 db，切换窗口只需覆盖"冻结 → 生成差包 → 传输 → 导入 → 起服"。
- **复用既有存储语义**：blobstore 已经是内容寻址 + 原子落盘 + 已实现过"读 tar 跳过已存在、新 blob 走临时文件 rename"的回滚快照逻辑，导入路径不必从零写。

## 后果

- **正面**：搬迁路径的状态面、失败模式与运维负担显著减少；包可离线搬运（U 盘、对象存储、任意文件通道），不要求两机网络互通；备份本身即搬迁材料，不需要额外维护一套"备份"和一套"同步"。
- **负面**：
  - 失去准实时的持续同步能力。需要长期双向/持续复制的场景不再被支持，只能靠周期性包搬运。
  - 新机器必须人工重配密钥与对外地址。
  - 包为明文，泄露等于业务数据泄露；必须强制 HTTPS 并对链接设定短有效期。
  - 导入需要一次重启，无法做到"不停服切换"。
- **后续约束**：
  - 新增任何"把数据带到另一个节点"的机制都应回到本 ADR 的包模型，不得重新引入节点角色与水位。
  - 退役复制通道时必须逐项确认共享代码的归属（原子 operation envelope 服务于审计与制品操作、`BusinessWriteGate` 复用为冻结闸门），不得一刀切删除。
  - 集群数据表默认保留不 DROP：不可逆且收益为零。

## 备选方案

1. **保留复制通道，另加备份包**：两套机制并存，但复制通道的维护成本与失败模式并未消除，用户已明确要求退役。落选。
2. **在运行中直接替换 SQLite 文件（不停服恢复）**：需要暂停所有连接并处理 WAL 边界，任何遗漏都表现为静默损坏；且必须引入连接池级冻结，风险高于一次重启。落选。
3. **包口令加密**：包内不含密钥，加密的边际收益主要是防"包泄露"，而这一风险可由 HTTPS + 短有效期链接大幅降低；代价是导入必须交互式输口令，破坏 CLI 脚本化。落选（保留为将来可选项）。
4. **按仓库选择性打包**：包内必须保持"db 与 blob 互相自洽"才能恢复；选择性打包会让 db 引用到包内不存在的 blob，需要额外的裁剪逻辑与一致性证明。落选。
5. **扫 `blobs/` 目录决定包内容**：会把未引用的残留 blob 打进包，且无法证明与 db 自洽。落选（改为以快照库 `asset` 表为准）。
