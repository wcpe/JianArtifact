# ADR-0031：服务端可信关联和事务型安全事件

## 状态

已接受（用户已批准正式规格）；待分批实现，当前仅 FR-165 基础模块开发中，不代表各入口已全部接入或上线。

## 背景

[当前架构](../ARCHITECTURE.md) 分别保存管理/协议审计、运维告警和制品原子操作 outbox。既有审计保留历史价值，但部分成功审计在 handler 尾部尽力记账，当前请求 ID 可以沿用外来值；这些事实不足以证明真实提交、可靠同源或持续可观测。

[ADR-0015](0015-protocol-authentication-and-credential-references.md) 第 7 项已提出稳定主体和禁止秘密入审计。本决策只取代该项中请求来源与结果的采集、落库语义，并扩展为各入口共享；不改变其 TLS/出站/引用政策与发布限制。

[ADR-0024](0024-atomic-physical-blob-reclamation.md) 仍描述最终快照删除失败时撤销已经完成的业务。现行协调器把完成事务后的快照清理当作重试。本决策**取代 ADR-0024 中提交后清理可撤销成功的语义**；不取消其提交前同卷暂存、隔离和可恢复回滚。证据引用对回收的独立扩展见 [ADR-0033](0033-incident-restrictions-and-recovery-gate.md)。

## 决策

1. 服务端在鉴权前生成自己的请求 ID，关联来源只接受显式信任的代理链；IP 用规范地址/网络查询，不把伪造的头、UA 或相近时间当身份。后台固化原请求可信来源快照和发起授权；worker 地址/身份不替代原始来源，终提交按当前规则裁决。
2. 新增追加式安全事件、对象明细和可核对水位，区别事件时间、入库时间、响应观察、授权和业务提交。保留旧 `audit_log` 及其确认机制；旧记录不补造新事实，不做旧证据重写。
3. 必须可靠记账的业务成功、关键明细和必要回执，与业务状态共享同一短 SQLite 事务。制品用现有协调器的最终事务；用户、会话、Token、权限及处置使用对应的事务仓储，不在 handler 中事后猜成功。
4. SQLite 提交前的文件暂存、原件回收、补偿和启动恢复仍属协调器。完成提交后，快照只做可重试清理；通知消费、响应中断或清理失败不会撤销成功或另造成功事实。不得宣称跨介质有原子事务。
5. 安全字段采用白名单，无请求正文、令牌预览、秘密和摘要。历史敏感字段不传播到新调查、通知、导出。拒绝洪峰纳入有限预算，显式标有证计数/不可计数缺口；事件失败阻止关键写，不让拒绝变成接受。
6. 安全事件本身不等同案件、处置、回执或通知。下游只消费已提交事件，使用稳定 ID 去重、持久水位续读；不把成功响应、投递接收或用户已阅读混为一件事。

## 理由

- 把写入状态和安全事实放同一事务，可以区分故障时的“未执行”与“已执行但响应丢失”，无需依赖异步投递是否恰好一次。
- 业务链上已有统一制品完成事务和 operation outbox；保留其用途又不复活复制通道，可减少跨系统一致性复杂度。
- 单实例 SQLite 的拒绝洪峰不能无限逐请求写；优先可靠提交与撤销，并用显式缺口避免让调查把没有记录当作未发生。
- 代理判断和关联 ID 是同一上下文的边界。将原生协议、管理 API 与后台语义对齐，才可让下游选择可靠关联而非猜测。

## 后果

- 新写路径必须明确是关键事务还是可丢失观察，并携带同一字段词表。有关字段、错误、预算和初始覆盖以 [FR-165](../specs/security-trusted-audit.md) 为准。
- 代理头与外来请求 ID 兼容需受控迁移；应用日志/客户端链路若曾依赖回显需改用响应服务端 ID，不能保留客户端值作主关联。
- 审计不可写会牺牲关键写的可用性；服务必须能分辨该失败与普通拒绝，准备重查已确认回执；运行中不能把同次已成功的提交撤掉掩饰故障。
- 需要监控持久水位、缺口、清理重试和保留容量。性能与真实代理、故障顺序需独立验证；主机管理员可改本地存储，不声称抗其篡改。
- 不更新历史 ADR 决策正文。后继接受并实现时，维护者加旧 ADR 状态/取代链接，在架构与契约真源同步其范围。

## 备选方案

- **保持尽力写审计**：实现简单，但业务可成功且无安全证据，不能用于撤销、处置和发布关键事实。
- **先落审计再做业务**：崩溃会留下并未实际提交的成功事实；双写补偿不等价于统一事务。
- **将所有请求逐条同步写入或引入外部消息队列**：前者挤占关键撤销资源，后者增加协调和部署依赖，均不能替代最终事务裁决。
- **复用旧审计全量回填**：无法生产从未采集的来源或主体事实，并扩大历史敏感数据传播，否决。
