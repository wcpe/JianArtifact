# 功能规格：定时任务调度器

> 状态：开发完成，待用户验收　·　关联 PRD：FR-44　·　分支：feat/job-scheduler　·　依赖：无（FR-40 / FR-41 反向依赖本能力）

## 1. 背景与目标

**问题**：后端已有 4 处各自实现的周期机制，触发语义各写各的，没有统一落点：

| 机制                                  | 位置                                                                    | 现有触发语义                                                |
| ------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------- |
| 分钟聚合落库 + 每日清理（运营仪表盘） | `domain/operations_observability.go` `OperationsDashboardService.Start` | minute + day 两个 ticker；启动不扫描历史数据                |
| 下载统计落库 + 过期清理               | `domain/asset_download.go` `AssetDownloadService.Start`                 | minute + day 两个 ticker；启动不扫描                        |
| 主机监控分钟采样                      | `domain/operations_observability.go` `HostMonitoringService.Start`      | minute ticker；启动不扫描                                   |
| 孤立 blob 定时清理                    | `cmd/jianartifact/main.go` `startBlobGCTask`                            | 固定间隔（`JIAN_BLOB_GC_INTERVAL`，0 禁用）；启动不立即扫描 |

每新增一类"周期 X"（如 FR-41 的保留/清理作业、FR-40 的周期化自动备份）就要再手写一个 ticker，失败隔离、禁用语义、状态可见性都得各写一遍。

**目标（对用户）**：

- 为"周期作业"提供**唯一落点**：注册名称 + 间隔 + 执行函数，其余（循环、停止、失败隔离）由调度器统一负责；
- 语义**一次性固化**：启动不立即执行（不扫描历史数据）、间隔 ≤ 0 即禁用、单作业失败不影响其他作业、同一作业不自我重叠；
- 作业运行状态**进程内可见**（上次执行时间、上次错误、次数），为 FR-39（Prometheus 指标）提供现成数据面；
- 为 FR-40（周期化自动备份）与 FR-41（GC / 保留 / 配额 / 存储清理）扫清前置依赖。

## 2. 需求（要什么）

- **调度器**（进程内，无外部依赖）：
  - 注册作业：名称（日志与状态标识）、间隔、`func(ctx) error` 执行函数；
  - `Start(ctx)`：随 context 取消优雅停止（与既有后台循环一致）；
  - **启动不立即执行**：首次执行在第一个间隔到期后（对齐 `startBlobGCTask` 与 0.8.0「启动不扫描历史数据」基调）；
  - **禁用语义**：间隔 ≤ 0、名称为空或执行函数为空 → 该作业不注册，静默跳过（对齐 `JIAN_BLOB_GC_INTERVAL=0` 的既有禁用约定）；
  - **失败隔离**：单个作业返回错误 → 记中文日志并计数，不影响其他作业与后续周期；作业 panic → 隔离并计数，不拖垮进程；
  - **不自我重叠**：同一作业上一次未执行完，不叠加下一次（见 §3.2 的定时语义）。
- **作业状态面**：`Status()` 返回每个作业的名称、间隔、执行次数、失败次数、最近开始/结束时间、最近错误、是否正在执行。
- **纳入既有作业（行为等价）**：把孤立 blob 清理从 `startBlobGCTask` 迁入调度器，保持"不启动即扫 / 按间隔执行 / 取消即停"三项既有行为不变。
- **范围外（本期不做）**：
  - 迁移其余 3 处服务内部循环（dashboard 聚合、下载统计、主机采样）——它们与其功能的生命周期绑定，迁移须按 [0.8.0-host-monitoring.md](0.8.0-host-monitoring.md#L25) 的**等价行为**约束单独验证，留作后续增量；
  - 作业历史持久化（进程内状态即可，作业本身幂等，失败下个周期自然重试）；
  - 新作业本身（备份 / 保留 / 压实 / 校验）——由 FR-40 / FR-41 / FR-46 落地；
  - HTTP API、web 页面、新环境变量（不为未来预留空壳）。

## 3. 设计（怎么做）

### 3.1 模块与依赖

```
cmd/jianartifact/main.go 装配：scheduler.New() → Register(...) → Start(ctx)
  ↓
internal/scheduler（新叶子包，零内部依赖）
  ├─ Job{Name, Interval, Run}
  ├─ Scheduler{Start(ctx), Status()}
  └─ JobStatus（状态快照）
```

- 放 `internal/scheduler` 而非 `domain`：这是与领域无关的通用能力（对照 `blobstore` / `auditctx` 等能力包），domain 与 cmd 均可导入，避免 domain 再背一个通用设施。
- 依赖方向：叶子包，不依赖任何 `internal/*`，不触碰架构不变量 §2 禁止的重型件（无 MQ / 无外部锁 / 无分布式协调）。

### 3.2 定时语义（单作业循环）

```
run(ctx, job):
  for {
    select ctx.Done → return
    等待 interval（timer，每次重新起算）
    执行 job.Run(ctx)：recover 包裹；成功/失败都记状态
  }
```

- 用**每轮重新起算的 timer** 而非长跑 ticker：作业耗时超过间隔时不会"补跑"（ticker 会缓冲一个 tick 造成连发）；语义是「上次结束后至少再等一个间隔」，天然满足不自我重叠。
- 每作业一个 goroutine：作业之间天然并行且互不阻塞；共享状态（次数 / 时间 / 错误）用互斥保护，`go test -race` 覆盖。
- 作业执行函数接收 `ctx`，长作业应尊重取消；调度器在 `ctx` 取消后不再触发新周期。

### 3.3 状态面

```go
type JobStatus struct {
    Name       string
    Interval   time.Duration
    Runs       int64     // 已执行次数（含失败）
    Failures   int64     // 失败次数（含 panic）
    Running    bool      // 是否正在执行
    LastStart  time.Time // 零值 = 尚未执行
    LastFinish time.Time
    LastError  string    // 最近一次错误描述，空 = 最近一次成功
}
func (s *Scheduler) Status() []JobStatus  // 快照，返回副本，不泄漏内部状态
```

- 本期仅进程内提供；FR-39 落地时直接读取导出为 Prometheus 指标，不重复造状态。

### 3.4 装配改造（blob GC 纳入）

- `main.go`：删除 `startBlobGCTask`，改为构造调度器并注册 `blob-gc` 作业（间隔取 `cfg.BlobGCInterval`）；作业闭包保留原日志文案。
- 既有 cmd 层测试 `blob_gc_test.go` 的三个断言（不启动即扫 / 按间隔触发 / 取消即停）改为经调度器验证，保证**等价替换**。

### 3.5 日志

- 沿用现有 `log.Printf` 中文风格：作业失败记 `定时任务 <名称> 执行失败：<原因>`；panic 记 `定时任务 <名称> 发生 panic：<值>`（含堆栈）。
- 不引入新日志框架；成功不逐周期刷日志（作业自身按需输出业务日志）。

## 5. 验收标准

- **调度语义（单测，`-race`）**：
  - 启动不立即执行：`Start` 后首个间隔内零次执行；
  - 按间隔执行：短间隔（毫秒级）下按周期触发；
  - 禁用：间隔 ≤ 0 / 空名称 / 空执行函数不注册（不出现在 `Status()`）；
  - 取消即停：`ctx` 取消后不再触发；
  - 失败隔离：一个作业持续报错，其他作业照常按周期执行；
  - panic 隔离：作业 panic 后进程存活、计数递增、后续周期继续；
  - 不自我重叠：执行耗时超过间隔时执行不叠加（相邻两次开始间隔 ≥ 上次耗时）；
  - 状态正确：`Runs` / `Failures` / `LastStart` / `LastError` 与实际执行一致。
- **等价替换（cmd 层）**：blob GC 作业「不启动即扫 / 按间隔触发 / 取消即停」三项断言全绿（既有测试改写后保持覆盖）。
- **质量门**：`scripts/check.ps1` 全绿（前端 format/lint/typecheck/test/build + Go gofmt/vet/golangci-lint/`go test -race`/govulncheck）。
- **真实运行（集成维度）**：以真实二进制 + 临时数据目录启动，配置短间隔（如 `JIAN_BLOB_GC_INTERVAL=1`），人为放置孤立 blob，验证按周期回收且日志正常、进程无异常退出；证据随 PR 附上。

## 6. 风险 / 待定

- **不新写 ADR 的理由**：本能力落在既有决策内——进程内、零新依赖、无外部接口变更，不与任何已接受 ADR 冲突（blob 回收语义仍归 [ADR-0014](../adr/0014-atomic-asset-operations-and-blob-reclamation.md) / [ADR-0024](../adr/0024-atomic-physical-blob-reclamation.md)，本规格只管"何时触发"）；对照先例，0.8.0 的分钟采样与保留清理同样未立 ADR。如审核认为"统一调度器"属需长期固化的架构模式，可改为补一条 ADR。
- **其余循环迁移时机**：dashboard 聚合 / 下载统计 / 主机采样的内部循环保持现状；迁移它们必须整体等价（含启动不扫描、保留窗口、日志行为），建议在 FR-41 落地时按需一并评估，避免为统一而统一。
- **timer 与 ticker 的差异**：长作业（耗时 > 间隔）下 timer 语义比 ticker 少一次"补跑"，属有意选择（不自我重叠优先）；对现有 blob GC 作业（远快于间隔）无行为差异。
- **包位置**：`internal/scheduler`（本稿）与 `domain`（先例 `ReplicationScheduler`）均可；选前者是为避免 domain 承载通用设施，如需归入 domain 可在审核时调整。
