# 功能规格：Prometheus 指标导出

> 状态：开发完成，待用户验收　·　关联 PRD：FR-39　·　分支：feat/prometheus-metrics　·　依赖：FR-44（定时任务调度器，提供作业状态面）

## 1. 背景与目标

**问题**：本实例的观测数据已经很全（制品协议请求与缓存命中、下载计量、主机采样、审计、以及 FR-44 交付的调度器作业状态），但**只进 SQLite 供自有控制台展示**——外部监控系统（Prometheus / 告警规则 / Grafana）拿不到任何数据，运维只能"人眼看控制台"，无法做阈值告警与趋势留存。

**目标（对用户）**：

- 暴露标准 `/metrics` 端点（Prometheus 文本暴露格式），一次配置即可被标准抓取器采集，无需任何第三方服务；
- 首版覆盖三类可立即回答运维问题的信号：**制品协议请求**（有没有流量、有没有错误、缓存命中如何）、**定时任务作业**（清理等维护任务是否在跑、是否持续失败）、**进程运行时**（协程 / 堆 / GC 是否异常）；
- 口径与既有安全约定一致：匿名可见但不泄露指纹信息（对齐 `/healthz`、`/readyz` 与 `/api/v1/status` 的版本脱敏规则）。

## 2. 需求（要什么）

- **端点**：`GET /metrics`，返回 Prometheus 文本暴露格式（`text/plain; version=0.0.4`）。
- **指标（首版，全部进程内、抓取零数据库查询）**：
  - `jianartifact_protocol_requests_total{method,status,cache_result}`（counter）：制品协议请求完成计数，复用既有协议指标钩子（`WithProtocolMetric`）；`cache_result` ∈ `hit` / `miss` / `unknown`。
  - `jianartifact_scheduler_job_runs_total{job}`、`jianartifact_scheduler_job_failures_total{job}`（counter）；`jianartifact_scheduler_job_running{job}`、`jianartifact_scheduler_job_last_run_timestamp_seconds{job}`、`jianartifact_scheduler_job_last_run_failed{job}`（gauge，仅在该作业已执行过时输出）——来源为 FR-44 的 `Scheduler.Status()` 快照。
  - `jianartifact_runtime_goroutines`、`jianartifact_runtime_heap_bytes`、`jianartifact_runtime_gc_total`（gauge / counter）：进程运行时，渲染时即时读取。
- **标签基数受控**：`method` 只登记已知方法（`GET`/`HEAD`/`PUT`/`POST`/`DELETE`/`OPTIONS`/`PATCH`），其余归 `other`；`status` 只登记合法三位码，异常值归 `other`；`cache_result` 固定三值。禁止把请求路径、仓库名、用户等无界值做标签。
- **匿名口径**：`security: []`（与 `/healthz`、`/readyz` 一致），但**不输出版本等指纹指标**（对齐 `OPERATIONS.md` 的版本脱敏规则）。
- **零新增依赖**：文本暴露格式为仓库内手写渲染（`# HELP` / `# TYPE` / 标签转义 / 稳定排序），不引入指标 SDK。
- **契约同步**：`/metrics` 进入 `api/openapi.yaml`（响应用 `text/plain`），`task gen` 重生成 Go 接口与前端 client，devmock 同步端点，契约比对测试保持全绿。
- **范围外（首批不做）**：
  - DB 派生指标（主机监控样本、下载趋势、存储用量）——抓取路径不得查询 SQLite；
  - 请求时延直方图（需要桶设计与采样口径，另立增量）；
  - 管理面请求计数（若做需按路由模板做标签，避免基数爆炸）；
  - Grafana 面板 / 告警规则文件 / 新配置项。

## 3. 设计（怎么做）

### 3.1 模块与依赖

```
httpserver（运维端点，与 /healthz、/readyz 同级；不进 /api/v1）
  ↓
internal/metrics（新叶子包）
  ├─ 计数器 / 仪表注册与更新（并发安全）
  ├─ 文本暴露渲染器（纯函数：快照 → 文本）
  └─ gin handler（GET /metrics；来源 = 本包计数器 + scheduler 快照 + 运行时即时读取）
```

- 叶子包、零内部依赖；调度器快照经**接口注入**（`func() []scheduler.JobStatus`），避免包间反向依赖。
- 契约：`api/openapi.yaml` 增 `/metrics`（`security: []`，200 → `text/plain`），`task gen` 生成后接线。

### 3.2 插桩点（不新增中间件）

- `main.go` 既有 `WithProtocolMetric` 钩子内累加协议请求计数（每请求一次原子加，不写库、不落盘）；
- 调度器指标在渲染时从 `Scheduler.Status()` 读取（注册时注入取数函数）；
- 运行时指标在渲染时读取（`runtime.NumGoroutine` 与内存统计）。

### 3.3 渲染与格式

- 稳定排序（指标名，其次标签序列）；每个指标一组 `# HELP` / `# TYPE`（`counter` / `gauge`）；
- 标签值转义（`\`、`"`、换行）；数值为整数时直出、为浮点时按最短往返表示；
- **固定指标族即使暂无样本也输出 HELP / TYPE**（抓取端据此发现指标），样本行只反映真实数据、不虚构：尚无协议请求时不输出请求样本，未执行的作业不输出最近执行时间与失败结论；未接入调度器时整组作业指标不输出。

## 5. 验收标准

- **渲染（单测）**：HELP / TYPE 与样本配对；标签转义正确；排序稳定；空快照输出合法；未知方法与异常状态码归 `other`。
- **计数与并发（单测，`-race`）**：协议计数按标签累加；`/metrics` 渲染与计数更新并发无数据竞争。
- **契约**：openapi ↔ devmock 一致性检查通过；生成产物与契约同步（`task gen` 后无未生成差异）。
- **真实运行（集成维度）**：真实二进制启动后 `GET /metrics` 返回 200 与 `text/plain; version=0.0.4`；输出包含三类指标；连续两次抓取计数单调不减；匿名可访问且**不含版本**；维护作业执行一次后 `scheduler_job_runs_total` 递增。
- **质量门**：`scripts/check.ps1` 全绿（前端 + Go 全链路 + govulncheck）。

## 6. 风险 / 待定

- **鉴权口径**：本稿选匿名（与 `/healthz`、`/readyz` 同口径、抓取最简）。若审核认为指标外泄不可接受，可改为默认 `bearerAuth`（Prometheus 抓取侧支持 `bearer_token`），此时可考虑恢复版本指标；两种口径的实现差异仅在契约 `security` 与处理器鉴权，改动小。
- **为何不做 DB 派生指标**：逐次抓取查询 SQLite 会把监控流量放大成数据库负载（与"抓取零开销"目标冲突）；主机样本、下载趋势等若确需暴露，应由调度器周期任务预热进内存后由渲染读取。
- **`last_success` 未单列**：调度器状态面当前只有"最近一次执行 + 是否失败"，仅能表达"最近一次是否成功"；若后续需要"距上次成功"类告警，需在 FR-44 状态面补 `LastSuccess` 字段（小改动，随需增补）。
- **不新写 ADR 的理由**：不引入新技术与服务（纯标准库 + 一个运维端点），落在既有决策内（契约唯一真源、零外部依赖、运维端点先例）；如审核认为需长期固化"指标暴露口径"，可改为补一条 ADR。
