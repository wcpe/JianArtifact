# 功能规格：存储治理（配额 / 清理作业 / 代理缓存保留 / 运维作业面）

> 状态：开发完成，待用户验收　·　关联 PRD：FR-41　·　分支：feat/fr41-storage-governance　·　依赖：FR-44（[定时任务调度器](0.11.0-job-scheduler.md)，本功能的清理作业落点）、FR-39（[Prometheus 指标导出](0.11.0-prometheus-metrics.md)，拒绝计数所在指标面）、[ADR-0024](../adr/0024-atomic-physical-blob-reclamation.md)（引用归零→同步物理回收语义，本功能不改变它）

## 1. 背景与目标

**问题**：磁盘与数据库此前都没有上限，也没有例行治理手段：

| 缺口                     | 具体表现                                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 无仓库容量配额           | 仓库表与配置里没有容量字段，raw / maven / npm / oci / pypi / nuget / cargo 的发布路径**零上限**，单个仓库可以把盘写满                       |
| 回收过程与元数据长期残留 | `blob_quarantine` 与 `asset_mutation` / `asset_mutation_item` 的终态行只增不减；`<blob 根>/tmp/oci-upload` 的上传暂存文件只在进程启动时清理 |
| 代理缓存无保留策略       | 代理仓库缓存过的内容永久留在盘上，即使上游早已更新或该内容长期无人使用                                                                      |
| 运维面缺失               | 周期清理作业既看不到清单、也不能手动触发，只能"等下一个周期"                                                                                |
| 清理类审计缺口           | 既有的 Maven 空目录清理端点（批量物理删除入口）不写审计                                                                                     |

**目标（对用户）**：

- **能给仓库设"最多占多少"**：超出上限的写入被拒绝（而不是"只告警"或"转只读"），使磁盘占用可预估（NFR-05）；
- **代理缓存能按时间自动淘汰**：默认关闭、按仓库显式开启，删除走既有资产删除通道，不引入第二套回收语义；
- **回收残留与元数据不再只增不减**：隔离区空目录、终态元数据、过期上传临时文件有例行清理；
- **清理可见、可手动触发**：管理员可查作业清单与状态、可手动触发一次，并留痕；
- **拒绝可观测**：发布拒绝按月原因计数暴露到 `/metrics`，可对"配额被打满"设告警。

## 2. 需求（要什么）

**范围内（本批交付）**：

1. **仓库级存储配额** `quotaBytes`（字节）与 `quotaAssets`（制品数）——0 / 缺省 = 不限；越限拒绝写入（429 `quota_exceeded`）；
2. **清理作业** `storage-cleanup`——终态元数据裁剪、空隔离目录清理、过期 OCI 上传临时文件清理、代理缓存保留；一个作业、四件事、各自可独立禁用；
3. **代理缓存保留** `cacheRetentionDays`——仓库级、**仅 proxy**、**默认关闭**；
4. **运维作业面**——`GET /api/v1/maintenance/jobs` 与 `POST /api/v1/maintenance/jobs/{name}/run`（仅管理员）；
5. **指标** `jianartifact_publish_rejections_total{reason}`——`reason` 为**闭集枚举**，v1 只有 `quota`；
6. **契约与前端**——仓库读写两侧的三个新字段、两个维护接口进入 `api/openapi.yaml` 并同步 devmock；仓库表单/详情可编辑上限与保留天数，列表与详情按用量/上限四态着色；
7. **顺带治理**——Maven 空目录清理端点补 `repo.cleanup` 审计（成功与失败都记），响应结构保持兼容。

**范围外（本批不做，理由见 §4）**：制品历史版本 / "保留最近 N 版"、软删除 / 回收站 / 异步 GC、S3 或其他 blob 后端、周期 SQLite `VACUUM`、实例级 / 用户级总容量配额、**`proxy` 仓库的存储配额**、把观测三循环迁入调度器、审计归档与 `revoked_token` 清理、清理复制期历史表、**`pending_gc` 滞留件回收**、作业管理页面。

## 3. 设计（怎么做）

### 3.1 仓库级存储配额

#### 3.1.1 配置与生效范围

- 字段落在既有的 `repository.config` JSON 列（`quotaBytes` / `quotaAssets` / `cacheRetentionDays`）：**无新表、无迁移**，旧行解码即为零值。
- 更新语义按**指针**判定：缺省 = 不修改，显式 `0` = 改为不限 / 关闭（对齐 `immutableRelease` 的既有范式）。
- 校验（域层 `validateConfig`，违规 → 400）：配额负数非法；**非 `hosted` 仓库（`group` 与 `proxy`）都不接受非 0 配额**——`group` 只是成员的读取聚合视图、不承载写入；`proxy` 的缓存写入发生在**读取回源**路径上，该路径既没有准入预检、也没有流式早拒（详见 §3.1.3），配额强制尚未完整覆盖，故一并先拒绝，避免"设了但永不生效"。
- **生效范围**：配额判定（准入预检 + 流式早拒）只对 `hosted` 仓库执行——判定服务按名解析仓库后，非 `hosted` 直接放行；由于配置层已拒绝非 `hosted` 的非 0 配额，`proxy` / `group` 上不存在可用的配额配置，这条放行只是防御性兜底。

#### 3.1.2 计量口径（与物理占用不等价，必须明示）

- 维度一：**逻辑字节** `SUM(asset.size)`；
- 维度二：**制品计数** `COUNT(*)`；
- 两者复用仓库列表已有的同一套聚合（即 `Repository.artifactCount` / `Repository.totalSize` 的口径），不另写 SQL。
- **与去重后的物理占用不等价**：blob 内容按 hash 去重存储，同一份字节被多个仓库引用时，每个仓库各自按逻辑字节计入；去重 blob 无法按仓库归属，因此配额**不能**用来推算磁盘占用。

#### 3.1.3 判定时序（四级，缺一不可）

| 级别                        | 位置                               | 语义                                                                                 |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------ |
| 1. 已知长度预检             | 协议发布入口，**在读取请求体之前** | 已知 `Content-Length` 时直接给结论；不合格立即 429，**不读流**                       |
| 2. 流式限额读取器早拒       | 长度未知的流式上传                 | 用限额感知读取器把读取限制在上限内，越限**立即中断**，不允许"先写满 GB 再拒绝"       |
| 3. **提交点事务内权威复检** | 资产写入**同一事务**的完成钩子     | 按事务视图重新判定（已含本次写入），越限即整批回滚并返回同一个 429。**这是权威判定** |
| 4. 拒绝后回收               | 既有失败路径                       | 已落盘的暂存 blob 交给 `RemoveIfUnreferenced` 回收，`blob-gc` 兜底，不产生新的孤立件 |

- 覆盖写按**净增量**计量：预检用 `当前占用 − 被覆盖旧大小 + 本次大小`；制品数只在**新增路径**时增件（覆盖写不改变件数）。
- 长度未知且路径尚未解析（如 multipart 还没读出文件名）时，预检返回**整仓上限**作为安全上界（宁可少拒不可误拒），精确判定交给路径解析后的预检与提交点复检。

#### 3.1.4 并发语义（不引入第二套预留）

- **不引入 `used + reserved` 预留机制**：那会让存储配额与既有发布额度成为两套并存的预留体系，复杂度和误解成本都更高，而收益仅为"更早拒绝"——早拒已由第 1/2 级承担。
- 并发上传可能**都通过预检**，但提交点由 SQLite 单写者串行化，因此：
  - **已提交状态永不越界**（权威不变式）；
  - **最多一个在途上传在提交点被拒**（同一个 429）——这是明确接受并写入规格的边界。

#### 3.1.5 有意语义（可预期，不是缺陷）

- 判定的是"**提交后占用 ≤ 上限**"。因此当管理员把配额调低到低于当前占用后，**连"缩小体积"的覆盖写也会被拒**（保守：先要回到限内）。这是有意且可预期的。
- **删除项永不被配额阻断**：只判定写入项；否则调低配额后连删除都锁死。

#### 3.1.6 豁免（迁移导入与备份恢复）

- 迁移导入与备份恢复属管理员批量操作，经非持久化标记 `Asset.QuotaExempt`（随资产对象流入提交点，不落库）显式豁免；提交点跳过其写入项判定。
- 豁免发生时**记中文日志**（含仓库 id 与项数，不含任何文件系统路径），供运维追溯。
- 协议发布路径**不得**设置该标记。

#### 3.1.7 响应与错误

- 越限错误为 `StorageQuotaError`，同时满足 `errors.Is(err, ErrQuotaExceeded)`，因此沿用既有发布额度错误的映射：**HTTP 429 + 错误码 `quota_exceeded`**，覆盖 raw / maven（含网页表单上传）/ npm（含 packument 覆盖写）/ oci / pypi / nuget / cargo 全部发布入口。
- 消息含仓库名与"当前占用 / 上限"两组数字（按实际配置的维度拼接），**不含任何文件系统路径**（对齐 `docs/API.md` 的错误响应约束）。
- 仓库不存在或类型不承载写入时不判定，交由既有 404 / 409 逻辑处理。

### 3.2 清理作业 `storage-cleanup`

- 注册为 FR-44 调度器的周期作业：**启动不立即执行**（首次在第一个间隔到期后）、**失败隔离**、**不自我重叠**——全部继承调度器语义，不另写循环。
- 间隔由 `JIAN_STORAGE_CLEANUP_INTERVAL`（秒）控制，**默认 86400（24 小时）**；显式 `0` 即禁用（作业不注册、也不出现在作业清单里）；缺省 / 非数字 / 负数回落默认值。
- 一个作业四件事，**各自独立**：单类失败不跳过其余，全部错误合并上报为一次作业失败；部分成功时先记"存储治理清理部分完成：…"日志便于定位卡在哪一步。

| #   | 清理项           | 判定条件                                           | 开关                                                         |
| --- | ---------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| 1   | 终态元数据裁剪   | 见下                                               | `JIAN_STORAGE_METADATA_RETENTION_DAYS`（天，默认 7，0 禁用） |
| 2   | 空隔离目录清理   | 隔离区根下**一级子目录**、**为空**、mtime 早于宽限 | **无开关**（固定宽限 1 小时）                                |
| 3   | 过期上传临时文件 | `<blob 根>/tmp/oci-upload` 下 mtime 早于阈值       | `JIAN_STORAGE_TEMP_MAX_AGE_HOURS`（小时，默认 24，0 禁用）   |
| 4   | 代理缓存保留     | 见 §3.3                                            | 仓库级 `cacheRetentionDays`（默认关闭）                      |

**第 1 项的候选集（三条语句同一集合、同一事务）**：`asset_mutation.status ∈ {completed, rolled_back}` 且 `updated_at < 截止时间`，**且该操作下不存在任何非终态的隔离记录**（`blob_quarantine.status NOT IN (deleted, restored)`）；删除顺序为"终态隔离记录 → 操作明细 → 操作行"。两个条件都不可放宽：

- 在途状态（`prepared` / `staged` / `committing` / `rolling_back`）表示操作尚未结束或仍需启动恢复推进，**绝不裁剪**；
- 一个 `completed` 操作完全可能仍挂着 `pending_gc` 的隔离记录（物理回收失败留下的滞留件）。孤立看终态行是不够的——删掉父行会连带删掉这条唯一记录，让隔离文件变成"有字节、无元数据"的永久垃圾且再也无法回收。**宁可保留元数据，也不裁剪**。

**第 2 项为什么没有开关**：`Stage` 的落盘顺序是"先 `MkdirAll` 建操作目录、再 rename 隔离文件进目录"，两步之间存在一个"目录已存在但为空"的极短窗口。宽限期是**防误删护栏而非可调策略**：一个能被运维调成 0 的开关正好能打开这个窗口，把在途操作的隔离目录删掉。固定 1 小时远长于任何单次资产操作，既不会误删在途目录，也能让成功回收后的空壳目录在下一轮被收走。非空目录（含在途隔离文件或回滚快照）无法删除、直接跳过，因此**绝不会连带删除任何 blob 字节**；删除失败（占用 / 权限）只跳过，不使作业失败。

**第 3 项只碰一个专用目录**：`<blob 根>/tmp/oci-upload`（OCI 分块上传暂存的唯一落点）。普通 blob 写入的 `tmp/blob-*`、备份恢复的 `tmp/restore-*`、隔离区与活动 blob 都不在其内；按 mtime 判定，仍在写入的上传会话 mtime 持续更新、不会命中阈值；删不掉的残留（如 Windows 上仍被占用的句柄）计入 skipped 并记日志，留待下一轮，不作为作业失败。

#### 3.2.1 与 `blob-gc` 的职责边界

| 作业                      | 处理对象                                                                       | 依据                                       |
| ------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------ |
| `blob-gc`（既有）         | **活动目录**中的无引用 blob                                                    | 活动目录遍历明确跳过 `tmp` 与 `quarantine` |
| `storage-cleanup`（本批） | **隔离区**（空目录）+ **终态元数据** + **`tmp/oci-upload`** + **代理缓存保留** | 只碰上述命名空间与终态状态                 |

两者按**目录命名空间**与**元数据状态**天然互斥，同一 hash 不会被两条路径同时处理。

#### 3.2.2 本批不做：`pending_gc` 滞留件回收（留待后续增量）

计划原本把"用启动恢复的同一条既有代码路径把 `blob_quarantine` 中的 `pending_gc` 滞留件推进到终态"列为本作业的第一件事，**本批最终没有做**，原因是前置能力缺口（不是取舍）：

- 操作引擎的**写门是私有字段**，公开面只有"取读锁"与"取写锁并真的执行一次资产变更"两种，**没有"在写门下执行任意函数"的原语**，也没有"在途 operationID"的注册表 / 集合；`Recover` / `RecoverReceived` 不是在途判定接口——它们的语义前提正是"进程刚启动，本地不存在任何在途操作"，而这恰是定时作业无法假设的不变量。
- 启动恢复的前半段以"全部 intent 都是崩溃遗留"为前提做恢复 + 标记回滚：从定时器调用它会与**正在进行的操作直接冲突**（把隔离中的 blob 从活操作脚下恢复走，并把仍将提交的操作标成已回滚）。
- 启动恢复的后半段取 `pending_gc` / `staged` 记录、靠"操作是否已完成"过滤。但 `pending_gc` **恰恰是在途窗口内写入的状态**（先标 `pending_gc`，之后才 finalize），因此该查询结果里确实可能含活操作的记录；已提交但尚未完成快照清理的操作还会与清理竞争同一份回滚快照与隔离文件——**没有写门入口就无法消除这个窗口**。

结论：不自己发明一套文件删除逻辑（硬做会破坏 ADR-0024 的回滚原子性），滞留件回收整体留待后续增量（前置能力：操作引擎提供"在写门下执行、且能判定操作是否在途"的入口，或把回收动作收敛进操作引擎自身）。**现状不会因此变差**：滞留件仍与今天一样由启动恢复处理。本批实际执行的四件事都不会触碰任何仍在途的文件。

#### 3.2.3 支撑索引（迁移 0045）

清理作业每轮跑两条跨库范围查询，此前都无可用索引，库一大就退化成每轮全表扫：

- `idx_asset_mutation_status_updated (status, updated_at)`——对应候选集判定；`status` 在前使"终态等值族"的行走同一条索引序，`updated_at` 的范围裁剪只扫待裁区间，**"绝不碰在途"这条安全约束在查询计划层就兑现**；
- `idx_asset_repo_updated (repository_id, updated_at, path)`——对应代理缓存淘汰查询（`WHERE repository_id=? AND updated_at<? ORDER BY updated_at, path LIMIT ?`）；末尾带 `path` 使排序完全由索引顺序满足，**按序取够上限条即可停**（只建到 `updated_at` 时并列行仍需临时排序）。
- 不重建既有索引（本批只做加法，避免计划回归）；迁移为纯建索引、无历史回填、不支持 down。

### 3.3 代理缓存保留

- 配置：仓库级 `cacheRetentionDays`，**仅 `proxy` 可设**（`hosted` / `group` 带非 0 值一律 400），`0` / 缺省 = **关闭（默认）**，负数非法。
- 判定：该 proxy 仓库内 `asset.updated_at`（**最后一次写入**）早于 `当前时间 − 保留天数 × 24 小时`的资产，最旧的优先。
- **不追踪命中**：读取 / 下载不刷新 `updated_at`，因此"很久没被写入"的缓存会到期删除，即使偶有访问——这是有意语义，安全性由"代理缓存可从上游重新拉取"承担。
- 删除**走既有资产删除通道**（引用归零 → 同一操作内同步物理回收，ADR-0024 语义不变），不引入异步 GC；并发删除 / 覆盖导致的缺失按"已消失"处理，其余错误如实上报但不中断本轮。
- **每轮删除有硬上限 200 个**（跨仓库共享）：代理缓存虽可重新拉取，但一次删爆会引发上游流量洪峰，故先用上限收敛每轮删除量，达到上限时记日志、剩余部分由后续轮次继续收敛。
- **审计口径**：系统发起的删除**只记日志**（每个有删除的仓库一行，含仓库名、删除数与保留天数；达上限时另有汇总行），不写审计；写审计的是**运维动作**——手动触发作业（`maintenance.job_run`）与通过 API 修改策略（`repo.update`，detail 带 `cacheRetentionDays`）。

### 3.4 运维作业面

| 接口                                       | 语义                                                                                                                                             |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/v1/maintenance/jobs`             | 返回本进程**已注册**作业的清单与状态快照（名称、间隔秒数、是否运行中、累计执行 / 失败次数、最近开始 / 结束时间、最近错误）。只读，不触发任何作业 |
| `POST /api/v1/maintenance/jobs/{name}/run` | 手动触发一次。**202 只表示已受理**，不等待执行完成；是否跑完 / 失败看清单接口的 `running` / `failures` / `lastError`                             |

- 作业清单由注册决定：**间隔 ≤ 0 被禁用的作业不注册，也不出现在清单里**，因此"某个作业没有出现"等价于"该作业在本实例被禁用"。计数自进程启动累计，重启归零；未执行过时的时间与错误字段缺省（序列化为 null）；空清单序列化为 `[]`。
- 触发**不改变既有调度语义**：作业正在运行（含周期触发的那一轮、含本接口上一次触发尚未结束的那一轮）时返回 **409 `job_running`**，不排队、不并发重入、后续不补跑；名称未注册返回 **404 `not_found`**；非管理员 **403**、未登录 **401**；作业调度器未接线时返回 503 `unavailable`（兼容分支，生产装配恒为已接线）。
- 成功触发写审计动作 `maintenance.job_run`（entityType `maintenance_job`、entityKey 为作业名、detail 记来源=手动触发）；触发失败的响应**不回显内部实现细节**。
- `/api/v1/maintenance/` 在写入冻结窗口的放行清单内，故冻结期间仍可查清单与手动触发。
- **本批没有配套管理页面**：这两个接口是**纯 API**（纳管页面留待后续增量）。
- 顺带：既有 Maven 空目录清理端点作为"唯一的批量物理删除运维入口"，现在**成功与失败都写审计**（动作 `repo.cleanup`），响应结构保持兼容。

### 3.5 指标

- 新增 `jianartifact_publish_rejections_total{reason}`（counter）：发布被拒绝的累计次数，按原因分区。
- **`reason` 是闭集枚举**：v1 只有 `quota` 一个取值，覆盖"发布额度拒绝"与"仓库存储配额拒绝"两类（二者共用既有的 429 `quota_exceeded` 口径）。**闭集之外的取值被直接忽略**（保证标签基数受控、暴露面与规格一致）；**新增取值必须先改本规格与 [0.11.0-prometheus-metrics.md](0.11.0-prometheus-metrics.md)、同步测试与 `docs/OPERATIONS.md`**，不允许实现期就地塞入自由字符串。
- 累加点：预检与提交点的拒绝由配额服务自行累加；**限额读取器在流中的早拒**发生在读取器内部、配额服务观察不到，由协议层显式补报，并以"是否已有具名的配额错误"排除重复计数。
- 清理作业自动获得既有 `jianartifact_scheduler_job_*` 指标族（执行 / 失败次数、运行中、最近执行时间与最近是否失败），无需新契约。
- 不新增任何按仓库 / 路径打标签的指标。

### 3.6 契约与前端

- 契约（唯一真源 `api/openapi.yaml`）：`/api/v1/maintenance/jobs` 与 `/api/v1/maintenance/jobs/{name}/run` 两个路径 + `MaintenanceJob` / `MaintenanceJobList` / `MaintenanceJobRunResult` / `MaintenanceJobNameParam`；`Repository` / `CreateRepositoryRequest` / `UpdateRepositoryRequest` 三个字段（`quotaBytes` / `quotaAssets` / `cacheRetentionDays`）。生成物与 devmock 同步，契约一致性测试把关。
- 前端：仓库创建表单与详情配置页签可编辑三个字段（字节维度按 B / MB / GB 带单位填写与回显、留空或 0 = 不限，非数字与负数在提交前拦截）；仓库列表用量列与详情页头徽章对"用量 vs 上限"按 `unlimited / ok / near(≥90%) / over(≥100%)` 四态着色并给出文案（非管理员只见只读徽章，不见配置页签）；已超限仓库给出"写入会被 429 拒绝"的明确提示。中英双语键集一致（编译期同键约束 + i18n 键集测试）。

## 4. 明确不做（连同理由）

| 不做的事                                      | 理由                                                                                                                                       |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 制品历史版本 / "保留最近 N 版"                | 需要版本历史表 + 删除语义变更，属存储边界变更 → 先立 ADR，另立增量（当前 asset 是硬删、`UNIQUE(repository_id,path)` 覆盖写，无版本可留）   |
| 软删除 / 回收站 / 异步 GC                     | ADR-0024 明确否决（归零 blob 必须在操作成功返回前物理回收）                                                                                |
| S3 或其他 blob 后端抽象                       | 属 FR-37，需先立 ADR                                                                                                                       |
| 周期 SQLite `VACUUM`                          | 在线的整库重写，风险大于收益                                                                                                               |
| 实例级 / 用户级总容量配额                     | 用户级发布额度已存在（`publish_policy`）；实例级无明确需求                                                                                 |
| 把观测三循环（分钟 / 小时 / 每日）迁入调度器  | 纯重构、无用户可见收益，风险不划算；记入后续增量                                                                                           |
| 审计日志归档 / 导出、`revoked_token` 过期清理 | 属各自 FR 的未定空白，本批不接管                                                                                                           |
| 清理复制期历史表                              | 明令保留（PRD：复制历史默认保留、不 DROP）                                                                                                 |
| `pending_gc` 滞留件回收                       | 前置能力缺口（操作引擎无"在写门下判定是否在途"的入口）；硬做会破坏 ADR-0024 的回滚原子性。见 §3.2.2                                        |
| 作业管理 / 触发的管理页面                     | 本批只交付运维 API；页面属后续增量                                                                                                         |
| `proxy` 仓库的存储配额                        | 代理缓存写入在读取回源路径上（无预检、无早拒），配额强制尚未覆盖该路径；本批在配置层直接拒绝非 0 配额（见 §3.1.1），待后续增量支持后再放开 |

## 6. 验收标准

**配额（自动化）**

1. 已知 `Content-Length` 的发布在**读取请求体之前**被判拒（越限时请求体未被读走）；
2. 长度未知的流式上传**在超过上限处立即中断**，不会"先落盘再拒绝"；
3. 提交点越限时**整批回滚**：既有内容与元数据一个字节都不变；
4. 覆盖写按**净增量**判定，覆盖旧大小不虚增占用；
5. 制品数上限生效：新增路径超限被拒，覆盖写不因件数判定被误拒；
6. 并发上传只会有一个在提交点被拒，**不存在越界的已提交状态**；
7. 迁移导入 / 备份恢复路径**豁免**配额（可正常导入超限仓库）；
8. 未设上限 / 不存在的仓库 / 非 hosted 仓库的发布**不受影响**；
9. 全协议（raw / maven / npm / oci / pypi / nuget / cargo）越限统一 **429 + `quota_exceeded`**，消息含占用与上限、**不含文件系统路径**；
10. 配置校验：配额负数 400、非 `hosted`（`group` / `proxy`）非 0 配额 400、更新请求缺省字段不被清空、显式 0 表示改为不限。

**清理作业（自动化）**

11. 只裁剪**终态且早于保留期**的操作元数据，且**该操作下无任何非终态隔离记录**；在途操作行一个不删；
12. 保留期显式 0 时**完全不裁剪**（禁用语义）；
13. `pending_gc` 等非终态隔离记录**不被触碰**（本批不做滞留件回收）；
14. 空隔离目录只在**为空且早于固定宽限**时被删；非空目录与在途目录保留；
15. 只删 `tmp/oci-upload` 下早于阈值的文件，该目录之外的任何文件不受影响；
16. 代理缓存保留**默认关闭**时一个资产都不删；开启后只删早于保留期的资产；每轮删除量不超过上限（跨仓库共享）；
17. 作业语义：启动不立即执行、按间隔执行、取消即停、间隔 0 / 负值不注册、单作业失败隔离。

**运维作业面与指标（自动化）**

18. 两个接口均要求管理员（未登录 401 / 非管理员 403）；清单返回所有已注册作业与状态形状，空清单为 `[]`；
19. 手动触发返回 202 + `{name, started:true}` 并写 `maintenance.job_run` 审计；未知名 404、运行中 409、异常 500 且不回显内部细节；
20. 通过接口触发**真实调度器**时，同一作业不会被并发重入；
21. 连续越限发布后 `/metrics` 的 `jianartifact_publish_rejections_total{reason="quota"}` 单调递增；清理作业出现 `jianartifact_scheduler_job_*{job="storage-cleanup"}`；闭集外的 reason 被忽略。

**前端（自动化）**

22. 四态判定与阈值（`<90%` 正常、`≥90%` 接近上限、`≥100%` 已超限、0 / 缺省恒为不限）与"取两个维度里更严重的一个"；
23. 字节维度带单位回显 / 保存**互为逆运算**（读既有上限后原样保存不改变数值）；空串与 0 表示不限并显式提交 0；
24. 负数 / 非数字在提交前被拦截并给出可读提示，不发保存请求；保存失败保留已填值并提示；
25. 非管理员可见只读配额徽章但不出现配置页签；接近 / 超限状态在列表与详情都有对应文案。

**契约与质量门**

26. openapi ↔ devmock 契约一致；`task gen` / `pnpm gen` 后无未生成差异；中英文案键集一致；
27. `scripts/check.ps1`（前端 format/lint/typecheck/test/build + Go gofmt/vet/golangci-lint/`go test -race`/govulncheck）全绿。

**实机验收（需用户确认通过，手动步骤）**

28. 真实实例设定小配额后真实上传越限 → 得到 **429 `quota_exceeded`**，消息含当前占用与上限、不含文件系统路径；仓库既有内容仍可正常下载；把配额调回限内后写入恢复；
29. 临时把清理间隔调成秒级 → 日志出现"存储治理清理完成：…"（或"部分完成"）且计数与实测动作一致；人为种入终态元数据行、空隔离目录、过期 `tmp/oci-upload` 文件各一轮后被清掉，**有引用的 blob 一个都没被误删**；
30. `GET /api/v1/maintenance/jobs` 能看到 `blob-gc` 与 `storage-cleanup`；把 `JIAN_STORAGE_CLEANUP_INTERVAL` 设为 0 重启后 `storage-cleanup` **不在清单里**（禁用等价于不注册）；`POST .../run` 返回 202、运行中再触发返回 409、未知名 404、非管理员 403；审计中心能看到 `maintenance.job_run` 与 `repo.cleanup`；
31. 代理缓存保留实测：某 proxy 仓库设为 1 天后只淘汰超期缓存（每轮不超过上限），设回 0 后不再删除；系统发起的删除**只出现在日志**、不产生审计条目；
32. 验收后把实例环境档还原为部署基线，并复跑 `scripts/acceptance-spotcheck.py` 抽查全绿。

## 7. 风险 / 待定

- **配额只对 `hosted` 生效**：`proxy` / `group` 在配置层就被拒绝非 0 配额（400，见 §3.1.1），因此不存在"设了但不生效"的静默陷阱；代价是代理仓库本批完全不能设配额——要在 `proxy` 上真正生效，需把回源写入路径纳入配额强制（准入预检 + 流式早拒），另立增量。
- **非 hosted 仓库不提供配额输入**：管理端只在仓库类型为 `hosted` 时渲染并提交 `quotaBytes` / `quotaAssets`（group / proxy 隐藏而非灰显），避免管理员填了必然被后端 400 的值。
- **逻辑字节 ≠ 物理占用**：规格与契约都明示此差异；若运维要按"磁盘实际占用"设阈值，本批口径不适用。
- **"最多一个在途上传在提交点被拒"是有意接受的边界**：不引入预留机制换取实现与心智的简单；若未来要求"任何情况下都不让用户先传完再被拒"，需要新的预留设计。
- **`pending_gc` 滞留件仍依赖进程重启**：本批未闭环该缺口（见 §3.2.2），运维排障时"隔离区有滞留文件但作业没清掉"属预期现象。
- **代理缓存保留不追踪命中**：可能删掉偶被读取但长期未写入的缓存（可重新拉取）；"按访问时间淘汰"需要额外的访问时间戳列，另立增量。
- **不新写 ADR 的理由**：本批不改变 blob 布局与"引用归零→同步物理回收"语义（删除仍走既有资产变更通道），只是在既有语义之上加策略与治理面，落在既有决策内（ADR-0024 与 ADR-0002 继续有效）；对照先例，0.8.0 的保留清理与 0.11.0 的调度器同样未立 ADR。若审核认为"仓库级配额判定时序"需长期固化，可改为补一条 ADR。
- **`Asset.QuotaExempt` 是非持久化字段**：豁免信息不落库，因此"某次导入被豁免"只能靠日志追溯，不进审计（若需审计豁免，另立增量）。
