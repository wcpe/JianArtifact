# 功能规格：周期化自动备份与恢复演练（FR-40）

> 状态：待开发　·　关联 PRD：FR-40（续 FR-132–FR-137）　·　分支：feat/fr40-auto-backup-and-drill　·　依赖：[ADR-0027](../adr/0027-package-based-node-backup-and-relocation.md)（备份包模型）、FR-44 调度器

## 1. 背景与目标

- **现状**：v0.8.0 已交付完整的**按需**备份包能力——热备份 / 冻结窗口双模式生成、增量差包、带时效签名的无登录下载、三通道导入（CLI / URL 拉取 / 分片上传）、写入冻结窗口。但**备份必须人工触发**：没有周期化自动备份，也没有恢复演练 / 校验报告。
- **缺口（本条要补的两件事）**：
  1. **周期化自动备份**：按配置间隔自动生成备份包，不需要人记得点；
  2. **恢复演练与校验报告**：能验证「这份备份包真的能恢复」，并留下可查的报告，而不是只有一个 `ok` / `error` 字符串。

**目标（对用户）**：

- 配好间隔后，系统按周期自动生成备份包（默认**关闭**，需显式开启）。
- 自动备份**不会把磁盘打满**：保留策略随本批一并交付（这是自动备份的隐性硬依赖，见 §1.1）。
- 能对任意备份包发起**恢复演练**：在隔离的临时目录里真解包、真校验，产出结构化报告（含逐项结论与耗时），并可查历史。
- 管理界面能区分手动 / 自动来源、查看校验报告、配置自动备份。

### 1.1 为什么保留策略必须同批交付

`backups/` 目录目前**既无 GC 也无任何配置项**（全仓仅 `backup_service.go` 引用该目录，`storage-cleanup` 作业不覆盖它）。若只加「每日自动备份」而不加保留策略，磁盘会被自己打满——这是自动备份的**隐性硬依赖**，不解决则功能本身不可用。

## 2. 需求（要什么）

### 2.1 周期化自动备份

- 新增环境变量 `JIAN_BACKUP_AUTO_INTERVAL`（**默认 0 = 关闭**，单位秒），经既有调度器（FR-44）注册为 `backup-auto` 作业。
- 自动备份固定使用 **hot 模式**（不停服）；frozen 模式需人工控制停机窗口，不适合无人值守。
- **不生成差包**：自动备份每次生成**完整包**（差包依赖指定基线，无人值守下基线选择不可控且易形成长链）。
- 来源可区分：`backup_package` 新增 `origin` 列（`manual` / `auto`），列表可分辨。

### 2.2 保留策略

- 两条配置，**同时生效、取更严格者**（哪个先触发就按哪个淘汰）：
  - `JIAN_BACKUP_KEEP_LAST`（默认 7）：保留最近 N 份**自动**备份；
  - `JIAN_BACKUP_RETENTION_DAYS`（默认 30）：保留最近 N 天的**自动**备份。
- **只淘汰 `origin='auto'` 的包**：手动备份是人工决策产物，不自动删除。
- 复用既有 `HasDerived` 约束：**被差包引用为基线的包不得删除**（跳过而非报错，并在报告中注明跳过数）。
- 淘汰是作业的收尾步骤，随自动备份作业一起跑；首个自动备份生成后立即应用一次保留策略。

### 2.3 恢复演练与校验报告

- 新增「恢复演练」能力：对指定备份包，在**隔离临时目录**内：
  1. 校验包完整性（复用 `archive.Reader.Verify`，支持浅 / 深两级）；
  2. 真解包（复用 `Extract`）；
  3. 对解出的 SQLite 快照做一致性检查（`PRAGMA quick_check` + 关键表行数比对）；
  4. 校验 blob 内容摘要（深校验时）；
  5. 产出**结构化报告**：包 id、级别、开始 / 结束时间、耗时、各项结论、失败原因。
- 报告**可查历史**：落库保存，列表可查（而不是只有一次性响应）。
- **绝不调用 `RestoreService.Stage`**：它会写 `restore-staging/` 与 `restore.pending`，污染节点并在下次重启触发真正的替换。演练必须是只读路径。

### 2.4 界面（交付面含前端）

- 备份列表区分手动 / 自动来源；
- 可对某包发起演练并查看报告（含历史）；
- 可查看 / 修改自动备份配置与保留策略。

### 2.5 范围外（不做）

- 备份包加密与异地自动同步（超出本条）；
- 自动备份的差包链管理（本批固定完整包）；
- 演练结果的趋势分析 / 告警联动（仅留指标与报告）；
- 手工备份的自动保留策略（不自动删人工产物）。

## 2A. 追加八：未管理包导入 / 上传语义修正 / 孤儿回收

### 2A.1 背景

实机核查测试站时发现：`/opt/jianartifact/data/backups/` 有 144 个 `.tar.gz`，而 API 只登记 36 个——差额 110 个包在磁盘上占 33MB，却因为"列表读登记表"而在界面上完全不可见，既不能用也不能删。

台账核查同时暴露两个设计缺口：

1. **上传通道的语义过重**：`BackupUploadService.Complete` 直接调 `StartLocalImport` → 写 `restore.pending`，于是"上传一个包"等于"提交一次覆盖本机数据的恢复"。用户没有校验的机会——而恢复是要替换全部用户、仓库、制品的动作。
2. **没有任何机制回收"有包体、无登记"的残留**：`blob-gc` 只管活动 blob 目录，`storage-cleanup` 只管隔离区与终态元数据，二者都不碰 `backups/`。

### 2A.2 需求

- **R1 上传只入库**：上传备份包不再发起恢复，只把包收进备份列表；恢复是入库之后的独立动作，可先校验。
- **R2 导入未管理包**：列出服务器上"磁盘有包体、登记无记录"的包，支持**单选与多选**，逐个校验后导入管理列表。
- **R3 孤儿回收**：无人认领的残留由新作业回收，带宽限期与身份校验，不与 R2 冲突。

### 2A.3 设计

**差集口径只有一处**：`BackupAdoptService.Scan()` 同时服务 R2 与 R3。两者各自算一套差集迟早会不一致（刚导入的包被判成孤儿删掉）。

- `Scan()`：读 `backups/` → 只认 `<id>.tar.gz`（跳过 `.tar.gz.snap` 与 `.index`）→ 用 `repo.List` **翻页**取全部已登记标识（不能用 `ListRetentionCandidates`，它写死 `origin='auto' AND status='done'`，会把手动包与生成中的包误判为未管理）→ 求差集 → 对每个候选调 `readPackageFile` 做完整 `Manifest.Validate`。
- `Adopt(fileIDs)`：逐个校验 → 以**归档内 manifest 的 packageId** 登记（文件名可被人工改，manifest 才是包的真实身份；不一致时重命名包体）→ 补 `.index` 侧车 → `status=done`、`origin=manual`。单个失败不中断整批。
- `AdoptUploaded(sourcePath)`：上传通道复用同一套校验与登记，区别是来源在 `backup-uploads/<id>/` 且需要先 `MkdirAll`（全新实例第一次走上传时 `backups/` 还不存在）。同名包已存在时**明确拒绝**而不是覆盖。
- `BackupOrphanCleanupService.Run()`：基于 `Scan()` 的候选，两道护栏——**宽限期**（mtime 早于 `now-grace`，默认 1h，不允许配 0）与**身份校验**（只回收合法本产品包；无法识别的归档计入 `Invalid` 不删）。单轮上限 500 个。

**为什么 origin 必须是 manual**：标成 `auto` 会让保留策略把这个包当成周期备份淘汰掉。手工放进来/导入的包必须由人决定去留。

**为什么宽限期不能是 0**：零宽限会让"拷入 → 界面导入"这个操作窗口消失，用户刚放进去的包会在下一轮被删。

### 2A.4 接口与配置

| 端点                        | 方法 | 说明                               |
| --------------------------- | ---- | ---------------------------------- |
| `/api/v1/backups/unmanaged` | GET  | 列出未管理包（仅管理员）           |
| `/api/v1/backups/adopt`     | POST | 批量导入，返回逐项结果（仅管理员） |

| 环境变量                              | 默认    | 说明                                |
| ------------------------------------- | ------- | ----------------------------------- |
| `JIAN_BACKUP_ORPHAN_CLEANUP_INTERVAL` | `86400` | 回收间隔（秒）；`0` 禁用            |
| `JIAN_BACKUP_ORPHAN_GRACE_HOURS`      | `1`     | 宽限期（小时）；`0`/负数/非法回落 1 |

作业名 `backup-orphan-cleanup`，可从既有 `POST /api/v1/maintenance/jobs/{name}/run` 手动触发。

### 2A.5 界面

- 「上传包恢复」改名「上传备份包」；移除「覆盖已有数据 / 深度校验」两个开关（它们属于恢复动作）。
- 新增动作条入口「导入未管理的包」→ 内联面板：候选表 + 复选框（单选/多选/全选）+ 导入所选 + 结果摘要。
- 待重启生效时**只有**「从 URL 恢复」被挡住并解释原因；上传与导入未管理包只入库、不写 `pending_restart`，因此不受影响。

### 2A.6 验收

单测：扫描差集口径、导入幂等、非法包与路径穿越拒绝、批量部分失败、GC 宽限期、侧车一并回收、不碰 `.snap`、不碰已登记包、不删无法识别的归档。

实机：上传 `.tar.gz` → 列表多一行且**无** `pending_restart`；扫描出历史残留 → 多选导入 → 可校验/演练；触发 GC → 剩余残留被回收、已导入的不受影响。

## 2B. 追加九：间隔时间单位与"恢复抹掉备份列表"修复

### 2B.1 需求

- **N1 间隔支持多单位**：自动备份间隔不应只能用秒输入。要能直接表达"每 30 秒""每 5 分钟""每 2 小时""每天""每周""每月""每年"。
- **N2 恢复不得抹掉备份列表**：用户报告"备份包会跟着恢复一起被覆盖掉，导致备份包都丢失了"。

### 2B.2 N2 的根因与修复

**根因**：`backup_package` 登记表与被恢复的数据库是**同一个文件**，而备份包体在数据目录下、不在快照内。`ApplyPendingRestore` 原子替换整个 db 后，登记表退回旧快照的内容，于是"磁盘上有包、列表里没有"。而 restore 恰恰是最需要备份兜底的时刻。

**实测证据**：测试站恢复后 API 登记只剩 3 个，磁盘上却有 42 个包体、51 个 pre-restore 回滚目录。

**修复**：`ApplyPendingRestore` 在替换数据库后调用 `restoreBackupRegistrations`，以**磁盘为准**补回登记：

- 只补"包体能打开且 `manifest.Validate` 通过"的包——这是"能否使用"的最低门槛；
- 已在登记里的跳过，因此幂等；
- 包体已不存在的旧登记不补（本来也没法用）；
- 来源记为 `manual`：手工/历史留下的包不该被保留策略当成周期备份淘汰；
- 任何失败都只返回 0 而不让启动失败——恢复本身已成功，补登记是尽力而为的补救。

补回条数写入 `RestoreOutcome.ReRegistered` 并出现在启动日志摘要里，运维能看到"这次恢复找回了多少备份"。

### 2B.3 N1 的设计

**存储口径不变**：权威值仍是秒（`setting.backup_auto_interval`），不引入迁移。本功能只改变"人的表达方式"。

新增 `domain/duration_unit.go` 作为唯一的换算实现：

- `ParseDurationExpression("5m")` → 秒；裸数字按秒（保持旧配置含义不变）。后缀支持 `s/m/h/d/w/mo/y` 及英文全称。
- `DurationToParts` 把秒拆成"最适合显示"的数值与单位，供界面回填；**天优先于周**（7 天显示为"7 天"，否则用户认不出自己填的值）；只做整数拆分，不产生"1.5 天"。
- `ComposeDuration` 做溢出保护与上限钳制（超上限**钳制**而非报错：填"1 年"的意图是"尽量久"）。
- `0` 恒等于关闭，与单位无关。

**`m` 与 `mo` 必须区分**：`m` 是分钟、月写 `mo`。把 `1m` 当成一个月会有 43200 倍偏差，这是本功能最危险的坑，有专门单测守护。

**接口层**：`PUT /api/v1/settings` 接受 `backupAutoIntervalExpr`（字符串，优先级高于秒字段）；响应回显 `backupAutoIntervalExpr` / `backupAutoIntervalValue` / `backupAutoIntervalUnit`——拆分规则只在后端实现一处，前端直接回填两个控件。

**界面**：`AutoBackupConfigModal` 的间隔字段改为 `NumberInput + Select`，并实时显示"等于 N 秒"，让单位换算当场可见。

### 2B.4 验收

单测：表达式解析（全单位 + 边界 + 溢出 + 负数）、单位拆解优先级、往返一致性、`m`/`mo` 区分、`validateBackupSettings` 与表达式的配合、`resolveBackupAutoInterval` 的优先级。

回归：`TestApplyPendingRestoreKeepsBackupRegistrations` —— 已验证在禁用修复后会失败，确认它真的能抓到这个 bug。

实机：恢复一次后备份列表不减少；间隔填"1 天"保存后回显为「1 天」且作业按 86400 秒运行。

## 2C. 追加十一：包内容预览与自动备份默认开启

### 2C.1 包内容预览

**问题**：恢复是不可撤销的整份覆盖，而界面只给抽象计数（"多少制品、多少仓库"）。用户无法判断包里到底是不是自己需要的那个包，恢复因此成了赌博。

**实现**：`GET /api/v1/backups/{id}/preview`

- 返回仓库清单（名称/格式/类型）、账号清单（用户名/角色/状态）、制品路径样例（最多 50 条）、制品总数、blob 总字节、manifest 摘要。
- **账号清单不含口令哈希或任何密钥**：预览的用途是"看清有什么"，没有理由把敏感字段带到界面上。
- **纯只读**：把归档内的 db 条目单独解到临时目录，以 `mode=ro` 打开查询，查完删除；不改包体、不写备份目录、不产生标记。有专门的单测守住"预览后包体与备份目录条目数不变"。
- 样例上限 50 条：真实实例可能有几万制品，全量序列化既慢又没人看。

界面：列表「⋯」菜单第一项「查看包内容」（排在获取链接之前），打开预览弹窗。

### 2C.2 自动备份默认关闭（追加十二修正）

**结论**：默认间隔保持 `0`（**关闭**）。曾一度改为 `24h`，实测反馈后回退——这是有意的判断修正，不是回退疏漏。

**理由**：备份是**全量**包，每份大小≈整个数据目录。默认开启会在用户毫无预期时持续消耗磁盘。实测存在 **20GB 数据 / 40GB 磁盘**的配置：默认开几天即可写满，而盘满会连带把服务写挂。两者代价不对称——默认关闭、没备份可由运维事后补配置修复；盘被写满则是运行故障。两害相权，默认关闭。

**保留策略不构成容量保证**：`BACKUP_KEEP_LAST` 是"最多留几份"的上限。7 份 × 20GB = 140GB 仍可能远超可用磁盘。因此本追加同时引入**容量估算**：

- `GET /api/v1/settings` 增加 `backupLatestPackageBytes`（最近一次**成功**备份包的实际大小）。
- 配置弹窗内按「最近一次包大小 × 保留份数」实时显示预计占用，并在说明里点明"份数 × 单份大小不得超过可用磁盘"。
- 取"最近一次"而非平均值：数据量通常增长，旧平均值会低估当前占用。

**仍可显式开启**：界面设非 0 间隔，或 `JIAN_BACKUP_AUTO_INTERVAL=<秒>`。非法值回落默认（关闭），与"0 即关闭"口径一致。

## 3. 设计（怎么做）

### 3.1 模块与依赖

```
config（4 个新环境变量）
  ↓
cmd/jianartifact/auto_backup_job.go（作业注册，照 storage_cleanup_job.go 范式）
  ↓
domain/backup_service.go（Generate 复用）+ 新增 domain/backup_drill_service.go（演练）
  ↓
repository（backup_package 加 origin 列 + 新增 backup_verification 表）
  ↓
api（新端点：演练发起 / 报告查询）+ 契约重生成 + 前端
```

**分层归属**（已在调研中确认）：

- 自动备份落在**调度器作业**（`cmd/jianartifact/`），**不**做成 domain 自跑 goroutine——后者会绕过 FR-44 的禁用语义、失败隔离与 `/maintenance/jobs` 可见性。
- 演练落在 **domain 服务**，CLI 与 API 共用同一实现。

### 3.2 数据模型（迁移 `0047`）

- `backup_package` 加列 `origin TEXT NOT NULL DEFAULT 'manual' CHECK (origin IN ('manual','auto'))`（对齐 `backup_import.origin` 先例）。既有行默认为 `manual`，语义正确。
- 新增 `backup_verification` 表记录演练报告：
  - `id INTEGER PK AUTOINCREMENT`
  - `package_id TEXT NOT NULL REFERENCES backup_package(package_id) ON DELETE CASCADE`
  - `level TEXT NOT NULL CHECK (level IN ('shallow','deep'))`
  - `ok INTEGER NOT NULL`
  - `started_at` / `finished_at TEXT`、`duration_ms INTEGER`
  - `checks_json TEXT NOT NULL DEFAULT '{}'`（逐项结论）
  - `error_summary TEXT NOT NULL DEFAULT ''`
- 演练报告随包级联删除（包没了，报告无意义）。

### 3.3 作业流程

```
backup-auto 作业被触发（间隔 JIAN_BACKUP_AUTO_INTERVAL）
  → 串行化检查（复用既有 beginGenerate 语义，生成中则跳过本轮并记日志）
  → Generate(hot, 完整包, origin=auto)
  → 应用保留策略（份数 + 天数，取更严格；保护 auto 之外的包与 HasDerived 基线）
  → 记日志与指标
```

失败不得影响下一轮（调度器已提供失败隔离）。

### 3.4 演练流程

```
POST /api/v1/backups/{id}/drill {level?}   # 省略即 deep：浅校验会漏判被静默篡改的内容
  → 校验包存在且状态 done
  → 建临时目录（独立，不碰 data 目录）
  → Reader.Verify(deep?) → Extract → SQLite quick_check + 行数比对
  → 写 backup_verification 记录
  → 清理临时目录（无论成败）
```

耗时可能较长（深校验要逐 blob 读），API 采用 **202 + 轮询**，与既有 `createBackup` 同风格；CLI 走同步等待。

## 7. 追加实现（超出本规格初版范围）

> 本节记录规格初版交付**之后**由用户追加提出的两点，均已实现。列出是为了让后来者看清"为什么与 §3.5 当初的结论不一致"——不是文档自相矛盾，而是需求变了。

### 7.1 操作列按钮被压成残片（缺陷）

§3.5 交付后用户实测反馈"页面里的操作按钮会被裁切"。定位：表格 `layout=fixed` + 操作列写死 144px，但三个按钮自然宽度合计约 175px；flex 容器压缩按钮后 Mantine 的 `Button-label` **静默**把文字压到 3px（「校验」），表现为"按钮被裁切"。

修复三层：按钮 `flexShrink: 0`（禁止压缩，宁可整列溢出由外层横向滚动承载）、操作列按实测给足 176px 并重分配其余列宽、窄视口折叠为图标按钮。

### 7.2 自动备份配置允许后台修改（需求变更）

§3.5 的结论是"间隔改动需重启生效、界面只做只读说明"，理由是当时后端未暴露配置读写端点。用户随后明确要求「需要允许后台配置」，因此：

- 三项配置纳入既有 **settings 通道**（`GET/PUT /api/v1/settings`），参数为 `backupAutoInterval` / `backupKeepLast` / `backupRetentionDays`，三者的 `0` 均为合法取值（关闭 / 不限制）。
- **不改调度器**：`backup-auto` 作业改为 30 秒心跳常驻、每轮重读配置自行判到点，实现**保存即生效**。心跳粒度（30s）即最小可配粒度。
- 环境变量降级为**首次部署初值**（整组缺失时才写入），此后以数据库为准。
- 语义变化（必须在文档与界面如实说明）：作业现在**始终注册**，因此「维护作业」页总能看到 `backup-auto`；**看到它不等于自动备份已启用**，是否备份取决于间隔是否为 0。
- 保留策略服务的阈值改为可被作业每轮覆盖（`BackupRetentionService.SetOptions`，加锁保护读改写）。

### 7.3 配置卡挤占备份列表高度（缺陷）

§7.2 把配置卡从只读说明改成受控表单后，卡片从约 60px 涨到 365px 且带 `flexShrink: 0`；本页可用高度 768px 减去冻结卡与间距后，三个 `flex: 1` 区块（备份列表 / 从 URL 导入 / 分片上传）各只剩约 80px，备份列表作为页面主体只能显示约一行——用户实测反馈「高度压缩的看不清了」。

修复：配置卡**默认折叠**。摘要放进标题行（`OpsSection` 的 `meta`）、展开开关放进标题行右侧（`actions`），折叠时 `body` 内边距置 0——因此折叠态**只剩标题行**，展开后才渲染表单。这与 §3.5 及 `OpsSection` 的既有约定一致——说明与编辑入口不应常驻占用列表高度。

实测（1280×900 视口，页面可用高 768px）：

| 状态                     | 配置卡   | 备份列表容器    |
| ------------------------ | -------- | --------------- |
| 修复前（常驻表单）       | 365px    | 80px（约 1 行） |
| 仅折叠、摘要仍留在卡内   | 103px    | 167px           |
| 摘要移入标题行后（当前） | **49px** | **185px**       |
| 对照：main 上无此卡      | —        | 206px           |

中间那行说明「折叠」本身不够：折叠态若仍渲染 `body`，光是它的上下内边距就要 32px，而这一页每一像素都在跟列表抢高度。

- 折叠态摘要必须说清「自动备份当前是否在跑」：间隔为 0 时显示「自动备份已关闭」，而不是「每 0 秒备份一次」。
- 保留 `flexShrink: 0`：折叠后已不再抢空间，展开时也不被压扁。
- 折叠是纯展示态，**不影响热生效路径**：折叠态仍会读取 settings（摘要取最新值），保存逻辑不变。
- 测试在 jsdom 里量不出布局高度，因此守卫的是根因本身——断言配置卡**默认处于折叠态**，以及摘要随服务端值（含 0）正确渲染。两条守卫均经变异验证：把 `expanded` 默认值改为 `true` 后三条用例转红；让 devmock 丢弃 `backupAutoInterval` 后「保存后回读」断转红（`expected '0' to be '60'`）。
- `GET/PUT /api/v1/settings` 是非契约端点（手写而非生成），devmock 需手工同步字段——本次即发现它完全不认识这三项，导致 Mock 下摘要显示前端归一化兜底的默认值、保存只弹提示而值退回。

> **本节的折叠方案已被 §7.4 取代。** 折叠只缓解了"常驻表单"这一种发作，展开态仍会挤压列表（实测表格可视区只剩 19px）。§7.4 改为整页信息架构重排：配置等会改变高度的内容一律进 Modal，页面上不再有"可展开的常驻卡"。

### 7.4 整页信息架构重排（§7.3 的结构性取代）

> **§7.3 的折叠方案已被本节取代。** 折叠只治了"常驻表单"这一个发作；§7.3 交付后的界面复核又发现：**展开态仍会挤压**——中文 1280×900 下列表卡 185→76px、表格可视区仅 **19px**；英文 1100×900 下列表卡与另两张卡各只剩 **33px**（只看得到标题栏）。根因不是某一处间距，而是**「可展开的常驻卡」与「多个 `flex:1` 区块」共存于视口锁定容器**：任何区块扩张都必须从别的区块身上抢，堵一次冒一次。据此改为整页重排。

#### 结构（追加五后的最终形态：两段式 + 动作条挂标题行 + 统一事件表）

经过四轮结构调整（§7.4 首版三段式 → 追加二两段式 → 追加三任务台四段式 → 追加四聚合 → 追加五动作收编；
其中追加二与追加四都是两段式，区别在导入区是弹窗还是内联），
最终形态按「先按时间摊开发生过什么，操作入口就在这张表的标题行上」组织：

```
┌ ①附 内联导入区（flexShrink:0；收起时 display:none，仍挂载）──────┐
│ ⇧ 从 URL 导入 / 上传本机文件                    [收起]           │
│   ［表单本体：就地点「从 URL 导入」/「上传本机文件」展开］          │
└──────────────────────────────────────────────────────────────┘
┌ ① 关键事实（flexShrink:0）───────────────────────────────────────┐
│ 最近成功备份 13:00 │ 下次自动备份 已关闭 │ 最近校验 通过 │ 占用 │ 保留策略 │
└──────────────────────────────────────────────────────────────┘
┌ ② 备份与导入事件（flex:1 —— 独占全部剩余高度）────────────────────┐
│ 备份与导入事件 8  [生成备份包][冻结写入][从URL导入][上传][设置][说明]│
│  统一事件表（区块内滚动，吸顶表头）                              │
│  bk-…a1b2c3  [本机包]  手动  热备份  已完成  70MB  13:00  —  [⋯] │
│  imp-…g7h8i9 [导入记录] 上传   —     失败    10MB  20:00  错误  — │
└──────────────────────────────────────────────────────────────┘
```

**追加五改了什么**（用户复核追加四后提出「顶上两块太突兀了 需要收纳成按钮放到 备份与导入事件」）：
原先那**两张常驻动作卡**（约 173px，含三行说明文字）整体收成**标题行右侧的一排按钮**——
`生成备份包` / `冻结写入`（冻结态转为橙色的 `解冻写入`） / `从 URL 导入` / `上传本机文件` /
`自动备份设置` / `说明`。页面因此由三段收敛为**两段**，省下的 173px 全部给事件表。

**卡里的说明文字没有被删，只是换了载体**：那三行（"冻结写入后打一份完整的快照包…"、
"把已有备份包传到目标实例…"、冻结状态）迁进 `OpsHelpButton` 的「说明」气泡——该组件本就为此而生
（其注释写明"说明内容对操作不是必需的，常驻卡片会一直占用纵向空间"）。实现上**刻意复用原有文案键**
（`startTitle` / `startHint` / `moveTitle` / `moveHint` / `freezeStatus*`），只新增气泡标题
`actionBarHelpTitle`；若另写一套新文案，旧键会变成零引用，等于把说明悄悄删掉。

**冻结状态不再单列一只常驻 `StatusPill`**：它与按钮本就一一对应（可写 ↔ 「冻结写入」、
已冻结 ↔ 「解冻写入」），收成一行后由按钮自身的橙色变体与文案体现，自动解冻时间挂在该按钮的
`title` 上（用 `formatStamp` 过的可读时刻，不是裸 ISO）。**解冻入口必须常驻可达**这一条不变——
冻结期间若没有它，就会形成「已冻结 → 按钮禁用 → 打不开弹窗 → 永远解不了冻」的死锁（此前踩过）。

**追加四改了什么**：① 待处理提示条整个删除；② 导入与传输弹窗整个删除；③ 备份包列表与导入记录表
合并为**一张按事件时间倒序混排的统一事件表**；④ 两条导入通道改为**就地展开**（不再开弹窗）。

**为什么把包与导入记录合成一张表**：它们回答的是同一个问题——「这台机器上的备份与搬迁，先后
发生过什么」。拆成「页面里的一张表 + 弹窗里的一个标签页」只会逼用户来回对照；混排后一次搬迁的
时间线（打一份包 → 传到那边 → 那边导入 → 待重启生效）能在一屏里顺着读下来，正是"按事件顺序更好
分清"的落点。

**混排不会出现「同一件事两行」**——两类对象**不相交**：本机包登记在 `backup_package` 表；
导入记录是把别处的包收进来（走 `RestoreService.Stage` 暂存、写 `restore.pending`），记录里的
`packageId` 是包内携带的**源机器**标识，不会进入本机备份包列表。两张表后端都按
`ORDER BY created_at DESC, id DESC` 返回，前端 `mergeBackupEvents` 用同一口径重排（平局按标识
降序），因此**不依赖数组到达顺序**——两个列表各自异步返回，若平局时沿用输入顺序，同一份数据可能
两次渲染出不同次序。

**待处理提示条为什么可以删**：它当初存在，是因为「待重启生效」「导入失败」「写入仍冻结」散在
看不见的地方（记录藏在弹窗里），必须有一条汇总把用户引过去。记录常驻可见之后，前两类直接在对应
行的状态单元格里给结论（`pending_restart` 行显示「需重启服务后生效」、`failed` 行显示错误摘要），
汇总层就成了多余的中间人；第三类（冻结）在动作条的「解冻写入」按钮上——追加五之前是「立即备份」
卡上的常驻 `StatusPill`，收成一行按钮后由该按钮自身的橙色变体与文案体现（见上）。
代价是失去了"一眼看到有几件事等我"的汇总，但换来的是一张表里每行都能对上具体对象——
前者在旧版里本来就常常只起到"再点一次才看到明细"的作用。**角标一并删除**：它依赖的
"需注意计数"现在等于"表里可以自己数的行"，再挂一个数字只会与表内容重复。

**一卡一个主按钮的层级差异在动作条上靠 `variant` 保留**（追加五后不再有卡片）：主路径
`生成备份包` 与 `从 URL 导入` 用 `filled`，其余用 `default`——否则一排同款式按钮又看不出该先按哪个。
设计稿里搬迁卡原本全是默认样式按钮，实现首版照抄后经设计比对发现并修正
（比对过程记录属过程稿，按 `doc-sync` §5 不入库；结论即本节所述）。

三条原则：

1. **不再有「可展开的常驻卡」，也不再有「会变高度的常驻区块」**。会改变自身高度的东西（配置、
   冻结表单、生成向导、演练报告）一律进 **Modal**——Modal 默认 portal 到 `document.body`，
   **根本不参与页面的 flex 布局**。这是从结构上消灭"展开即挤压"，而不是再调一次间距。
   唯一的例外是内联导入区，它是页面流里唯一会增高的一块（`flexShrink:0`，位于 ③ 之前），
   展开时 ③ 整体下移、页根出滚动条，而**不改变 ③ 自身的高度**——这正是旧版"展开即挤压"的反面。
   追加五把动作条挂到 ③ 的标题行后，它**不再单独占一行高度**，标题行本身的增高（窄视口折行）
   由 `Group wrap="wrap"` 承载，实测 1440 宽下仍是 55px。
2. **每类内容只出现一次，不留双份实现**：页面流里不再有第二处导入记录表或第二处导入入口。
3. **状态常驻、写操作就地展开**：只读状态（五个事实、写入冻结与否）留在页面上随时可见；
   表单本身只在点了按钮之后占据页面。写入冻结状态是**唯一**从常驻徽章降级为按钮语义色的状态
   （追加五），因为它与那个按钮一一对应，单列一遍是同一事实的第二次表述。

#### 关键事实四项取值的来源（以及被刻意排除的东西）

这一条决定该块可不可信，故逐项写明：

| 事实         | 来源                                                                                      | 刻意排除                                                                                                                                                                                                                 |
| ------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 最近成功备份 | 备份列表里 `status=done` 且 `createdAt` 最大的一条                                        | 不依赖后端返回顺序，显式比较（改排序不会静默取错）                                                                                                                                                                       |
| 下次自动备份 | 用户配置的间隔（`settings.backupAutoInterval`） + **最近一个 `origin=auto` 包**的生成时刻 | **不用 `maintenance/jobs` 的 `intervalSeconds`**——`backup-auto` 注册的是固定心跳、每轮重读配置判断是否到点，那是心跳粒度而非备份间隔，拿它算会算出一个错的时刻；也不混入手动包，否则手动备份一次就会把"下次"推后一个间隔 |
| 最近校验     | 最近一个已完成包的**落库**演练报告                                                        | 不借 `/verify` 的即时结论冒充历史；读不到报告时如实显示「尚未校验」                                                                                                                                                      |
| 占用         | 当前列表内已完成包的 `sizeBytes` 求和 + 包数                                              | **不写成"磁盘占用"**——没有全局用量端点，这只是这一页能看到的那些包，故同时给出包数                                                                                                                                       |

间隔为 0 时如实显示「已关闭」——这正是 0 的语义，不能显示成「每 0 秒备份一次」（详见 `status.ts`
的 `useAutoBackupSummary`，三个 0 各自成句）。保留策略摘要从已删除的常驻状态条迁到本事实条第 5 项，
信息一条未丢。

**「下次自动备份」的三个分支必须各说各的话**（实机验收发现并修正）：① 间隔为 0 → 「已关闭」；
② 间隔 >0 且**尚无自动包** → 「等待首次执行」（`factNextPending`）；③ 间隔 >0 且**算出的时刻已过**
（等下一轮心跳来跑）→ 「即将执行」（`factNextDue`）。②与③曾共用 `factNextPending` 一句文案，但
③ 的场景下实例上**已经有自动包**了，说"等待首次执行"是假话；且 30 秒这类短间隔下几乎总走 ③，
用户会看到一个与表格自相矛盾的结论（表格里明明列着 `origin=auto` 的包）。分支 ③ 也**不能**给出
一个未来时刻——已过点就没有"下次时刻"可说，只能如实说"即将执行"。

**已知局限（未在本轮修）**：本事实条只在备份列表 / 导入记录 `reload` 时重算，而这两个 reload
只在**存在非终态记录**时按 `POLL_INTERVAL_MS` 轮询。因此自动备份稳定运行时页面会静止：短间隔
（如 30 秒）下先显示一个未来时刻，等它过去后若页面一直开着，该值不会自行变成「即将执行」，而是
停在一个已经过去的时刻，直到用户触发一次刷新。要根治需引入与数据无关的定时重算，属本页刷新
策略的范畴，留给后续（当前如实记录，不假装它已解决）。

#### 为什么把「从 URL 导入」与「分片上传」合成同一个内联区

它们**本来就是同一条流水线**：都产出 `BackupImport` 记录，只差 `origin`（`url` / `upload`）。合并前 `BackupUploadCard` 完成上传后要 `dispatchEvent(REFRESH_EVENT)` 去**让另一张卡**刷新——这个跨卡耦合本身就是"它们该是一张卡"的证据。追加四更进一步：两者共用一个内联展开区，按 `channel` 切换，同一时刻只显示一个表单。

**内联区必须常驻挂载（隐藏只置 `display:none`）**：分片上传面板要在挂载时探测"上次是否有未完成的上传会话"（`localStorage` 里的 `uploadId` → `GET` 拉回 `uploadedChunks`）。条件卸载会让探测永远跑不到，续传提示与"只补缺失片"全部失效——这与它在 `Collapse`（首版）、Modal（追加二）里踩过的坑是同一个：父级一旦真卸载，子树的副作用就停摆。同理，`activity` 模式会在隐藏时让 React 停掉子树副作用，故也**不能**用 Mantine 的隐藏机制，只能自己写字面 `display:none`。两个通道**各自**也常驻挂载：切到另一个通道再切回来，已填的 URL / 校验摘要都还在。

**展开规则**：点按钮就地展开；点**已展开的那个**按钮收起（再点一次 = 撤销）；点另一个切过去。上传进行中禁止收起（进度条与取消按钮都在面板里，收起来等于把唯一的进度反馈藏掉），按钮置 `disabled` 并给出原因。

#### 上传通道必须暴露 `overwrite` / `deep`（缺陷修复）

**现象**：把下载来的备份包传到已有数据的实例上，界面报"上传成功"，随后导入记录变成 `failed`，错误是"目标实例非空，导入前请开启「覆盖已有数据」"——但**界面上根本没有那个开关**。

**根因不在后端**：契约的 `CompleteBackupUploadRequest` 一直带 `sha256` / `overwrite` / `deep`，服务端也早已透传（`backup_upload_handlers.go`）。**缺陷纯在前端**——URL 导入通道有这两个开关，上传通道从未暴露，两条形式不一致。

**为什么必须前置而不是等失败**：`target_not_empty` 在**异步 Stage 内**判定，HTTP 早已返回 202，失败只体现在记录终态。用户看到的是"上传成功、随后记录变失败"，无从知道差在哪。因此开关与说明必须摆在提交按钮旁（上传通道放在"选择文件"上方），而不是失败后再让用户猜。

#### 导入成功后的刷新：只有一个通道

URL 导入与分片上传都走**同一个** `REFRESH_EVENT`（`useAsync` 监听），组件不接受"完成回调"。
理由是踩过的坑：同一件事有两个刷新通道，容易出现一个刷了另一个没刷的错位。这条对事件表尤其关键——
事件表只在**其内已出现非终态记录**时才开始轮询，若提交成功后不主动刷新，页面会卡在"提示已受理、
表里却看不到那一行"。

#### 统一事件表的几处取舍

- **类型徽章用 outline，不用 light**：它回答的是"这是什么"，与"它现在怎么样（状态）""它从哪来（来源）"是两个维度，共色会被误读。用文字（「本机包」/「导入记录」）而非仅图标，因为混排表里最容易混淆的恰是这两类对象。**不靠标识前缀**（`bk-` / `imp-`）让人猜。
- **来源列单独也能区分两类**：手动与自动只可能是本机包，URL / 上传 / CLI 只可能是导入记录。
- **「包含」列（制品数 / 仓库数）并入标识单元格第二行**，腾出的宽度给新增的「错误」列：失败原因要能就地读到，而"包含多少"是次要信息，截断可接受。信息一条没丢。
- **导入记录没有独立的「进度」列**：进度条（`fetching`）与「需重启服务后生效」（`pending_restart`）都挪进状态单元格——它们都是状态的补充说明，跟着状态徽章走才不会被误读。
- **导入记录行没有动作**（操作列显示 `—`）：契约里没有删除导入记录的端点，记录本身是这条流水线的账。
- **操作列仍只留一个「⋯」**：六个按钮平铺会把行高从 40px 撑到 98px（按钮折成三行），一屏少看四条记录，而其中三个是低频动作。

但"陈旧行 → 裸后端文案"确实不够清楚。现改为在该 404 场景给出可操作提示（「该备份包可能已被保留策略删除……刷新列表即可看到最新状态」）并附「刷新」按钮——它刷新外层备份列表并关闭弹窗，因为该行已经不存在了。其余错误（500 / 网络失败）仍走 `AsyncBoundary` 的通用错误渲染（自带重试），不混为一谈。

#### 本轮新发现并修复的三处

1. **解冻死锁**：冻结按钮在已冻结时必须禁用（再冻一次没有意义），若解冻也只放在冻结 Modal 里，就会形成「已冻结 → 按钮禁用 → 打不开弹窗 → 永远解不了冻」。解冻**没有表单**（只有一次 `confirmDanger` 二次确认），弹窗化的理由对它本不成立，故移到状态条上——与状态徽章同行，看到「已冻结」的同时就看到「解冻写入」。
2. **上传区 idle 文案与状态相反**：`uploadStarted`（「已开始上传，进度见下方」）被用作 idle 占位符，尚未选文件的用户会以为上传已在跑。已改为引导文案并删除该零引用键。
3. **导入区空状态复用备份包文案**：两处都显示「暂无备份包」，用户分不清说的是哪个对象。已新增 `importEmpty` / `importEmptyHint`。

### 7.5 恢复进度 / 一键重启 / 冻结提示 / 校验反馈 / 陈旧行（追加七）

界面复核提出五个问题，本节逐一记录**根因**与**修法**——其中第 5 条是真 regression（功能看起来坏了），其余四条是反馈缺失。

#### 问题 5（真 bug）：复制链接会失败

**现象**：点「复制链接」失败。**根因不是剪贴板**（浏览器 `NotAllowedError: Document is not focused` 是次要因素），而是**界面显示的是陈旧行**——该包已被保留策略淘汰，后端返回 **404 `not_found`「备份包不存在」**。裸报此错让用户以为功能坏了。

**为什么列表会陈旧**：页面此前**只在存在非终态记录时**才轮询（`importsRunning` / `hasRunning`）。自动备份每 30 秒生成新包并淘汰旧包，而**新增与淘汰都是终态变化**，不会让任何记录进入非终态 ⇒ 页面开着不动时列表永不更新，`auto` 行会一直指着已删除的包。这与先前「演练卡在进行中」是**同源问题**：都因"页面不知道后端状态已经变了"。

**修法（两处，双管齐下）**：

1. **本迭代已加**：`AUTO_LIST_REFRESH_MS = 10_000`——存在自动备份配置（`autoInterval > 0`）时，列表按 10 秒慢节奏自动刷新；`hasRunning` 时由更快的 1.5 秒轮询覆盖，**不叠加两个定时器**。节奏取 10 秒是权衡：比生成间隔（默认 30s）从容，又足以让陈旧行在用户动手前消失。
2. **本迭代已加**：`handleStaleRow(err, actionName)` 把 404 统一转为可操作提示（「该备份包已被淘汰，列表已刷新，请重试」），已接入 `onGetLink` / `onVerify` / `onDelete` / `onRestore` 四处。处置顺序是**先刷新列表再提示**——只提示不刷新的话，用户很容易再点同一行、再失败一次。

> **`onRestore` 这一处是实机验收时才补上的**（原计划里已列出，但首轮实现漏了）。触发场景很典型：用户看到列表 → 点开「用这个包恢复」→ 读完确认说明 → 再按「开始恢复」，而测试站是 30 秒间隔 + 保留 2 份，这中间包**已被淘汰**，后端返 404。不接这一条就会退化成裸报「备份包不存在」——与用户先前反馈的「复制链接会失败」是**同一个观感问题**。非 404（如 409 需要勾选覆盖）仍走普通错误提示，不误判为"这一行陈旧"。

> 注：test 阶段 `AUTO_LIST_REFRESH_MS` 的轮询会与既有"非终态快轮询"分工，二者互斥（`hasRunning` 时不启用慢轮询）。

#### 问题 1：恢复没有进度

**现状**：恢复受理后**只弹了一个 toast**（「已受理，正在校验与暂存；完成后需重启服务生效」），此后再无反馈。用户不知道在跑、跑到哪、失败没有。

**关键事实（决定了修法的可行性）**：`BackupImport` 记录**本就带进度字段**（`status` / `fetchedBytes` / `totalBytes` / `blobCount`），状态机 `queued → fetching → staging → pending_restart → done|failed`，且四条恢复通道（URL / 上传 / 本机包 / CLI）共用同一种记录。**进度数据早已存在，只是恢复路径没 surface**。

**修法**：新增 `RestoreProgressModal`，四条通道共用一个弹窗（差别只在 `origin`）：

- 状态徽章 + origin + `importId`；逐阶段说明（`restoreStage_<status>`）。
- **只有 `fetching` 且有 `totalBytes` 才画百分比进度条**；其余进行中阶段一律"转圈 + 阶段文案"。理由：暂存与深校验的耗时与包体积同阶，**编不出真实百分比**，画一个假的比不画更误导。
- 失败时就地展示 `error` 原文 + 刷新按钮；包已被淘汰（404）交回外层统一处置。
- 到达 `pending_restart` 时给出**真正的最后一步**：建议冻结 + 一键重启入口（见问题 2 / 3）。
- 到达终态时通知外层刷新一次；**只在进行中才轮询**（1.5 秒），终态即停，避免白打接口。

**四通道如何接上这个弹窗**（一处刻意保留的架构决定）：`UrlImportPanel` 与 `BackupUploadPanel` 此前**明确拒绝**过 `onImported` 回调，理由写在 `UrlImportPanel` 文件头——"同一件事有两个刷新通道，容易出现一个刷了另一个没刷的错位"。本次沿用该判断：**通道仍只有一个**，只是把"顺手要打开的进度弹窗"当作载荷捎带在同一个全局刷新事件上（`dispatchRefresh(importId)`），监听方按需取 `detail.importId`。CLI 通道**没有前端调用点**（由运维在服务器执行），退化为"列表里可见的一行"——这是不改后端所能做到的最好覆盖。

#### 问题 4：校验 / 深度校验没有反馈

**现状**：行内「⋯」→「校验 / 深度校验」只是 `await verifyBackup(...)` 然后 toast。用户看不到"正在校验什么、到哪一步"。

**关键约束（决定了修法只能是"列检查项 + 给结论"）**：后端 `verify` 是**同步**接口——一次返回最终结论（`ok` / `blobs` / `assets` / `error`），**没有中间进度可拉**（对比 drill 是 202 + 轮询）。且响应**不含分项 checks**。

**修法（不改后端）**：新增 `VerifyModal`：

- 打开即列出**真实会执行的检查项**（顺序与 `archive.Reader.Verify` 的实现步骤一一对应：清单一致性 → 数据库快照 → 对象索引 → 归档完整性；深校验额外加"逐对象内容摘要"）。**不得凭空增删**——它是"将要做什么"的如实说明。
- 进行中给**不确定进度（`Loader`）+ 阶段文案**，**不画百分比**：同步接口没有真实进度，编一个 60% 比不显示更不可信。
- 完成后**就地展示结论**（通过 / 未通过与原因、对象与制品规模、耗时），而不是让结论随 toast 消失。
- **浅校验必须显式写明"不核对对象内容"**：否则"校验通过"会被读成"这份包没问题"，而它对"结构完好但内容被篡改"的包照样判通过——那是深校验才管的事。

#### 问题 2：一键重启（已确认方案：调 systemctl，失败降级给命令）

**设计**：新增 `POST /api/v1/maintenance/restart`（仅管理员）。核心是两条：

1. **先回 202 再重启**：重启会杀掉当前进程，若先重启则响应发不出去，前端只能看到连接断开。实现为"延迟约 1.8 秒的后台执行 + 立刻返回"。
2. **能力探测 + 失败降级（绝不假装成功）**：同步预检（`LookPath` + `sudo -n systemctl restart --dry-run <unit>`，3 秒超时 + 单元名字符集白名单）；不通过则返回 **HTTP 200** + `supported:false` + `reason` + `command`。降级是**正常业务结果**，不是错误——用 4xx/5xx 会把可操作信息埋进错误路径。

配置项：`JIAN_RESTART_UNIT`（默认 `jianartifact`）+ `JIAN_RESTART_SCOPE`（`system` / `systemd-user` / `docker`，默认 `system`）。**命令注入是本功能最高风险点**：单元名只从环境变量读取、绝不从请求体读取，且须匹配 `[A-Za-z0-9._@-]`；字符集校验针对的不是执行侧（`exec.Command` 传参不经 shell），而是 `command` 字段——它会被运维**复制到终端粘贴执行**，那一侧真有 shell。

前端 `RestartControl`：可用则「立即重启服务」为主按钮（二次确认后调用，随后**轮询公开健康端点 `/api/v1/status` 探活**，成功即刷新数据）；不可用则显示可复制命令 + 原因。探活首个请求延迟 1.5 秒发出——重启命令有约 2 秒延迟，立刻探必然还是旧进程，会让"服务已回来"在被杀掉之前误报成功。探活上限 60 秒，超时如实告知手动刷新。

**明确不做**：不做"重启后自动恢复页面状态"（跨进程无从追踪），只做探活 + 提示。

#### 问题 3：恢复前建议冻结（已确认：不强制 + 提示）

在恢复确认弹窗（`RestoreFromPackageModal`）与进度弹窗的"待重启"区块里各加一处：一句说明 + 一个**可点的冻结入口**（复用既有 `WriteFreezeModal`）；已冻结时改为提醒"重启后记得解冻"（否则实例一直只读）。

**不强制的原因（写进实现注释）**：强制会让"忘记解冻"直接把实例变成只读，代价大于收益；且恢复本身是"暂存 + 重启时原子替换"，**一致性已由机制保证**。

#### 恢复生效后弹窗必须收尾（实机验收发现，原计划未预见）

恢复生效会把**整个数据库替换成包里的快照**，而那条导入记录正写在**被替换掉的那个库里**——重启完成后它自然消失。这带来一个原计划没预料到的界面状态：进度弹窗随后的轮询会拿到 404，若按通用错误渲染成"读不到记录"，**说的与事实正好相反**（用户刚刚恢复成功）。

处置（两个分支都要，缺一不可）：

- 进度弹窗把这条 404 单独识别为**"恢复已生效"**收尾态（`restoreAppliedTitle` / `restoreAppliedBody`）+「知道了」出口。它必须渲染在 `AsyncBoundary` **之外**——boundary 见到 error 就渲染通用错误态，会把"其实是成功"的呈现挡掉。这一支覆盖"维护者在服务器上手敲命令重启"：页面无从察觉，只能等轮询撞上 404。
- 走界面上的「立即重启服务」时，探活成功即**顺手关掉弹窗**（这次恢复已经落地，弹窗再无话可说）。这一支覆盖"从界面点重启"，界面更干净。

> 实测记录（测试站完整链路）：恢复受理 → 待重启 → 点「立即重启服务」→ 二次确认 → 探活；随后 `ActiveEnterTimestamp` 由 `12:50:53` 变为 `12:59:15`、`restore.pending` 已被消费、`restore-status` 回到 `pending:false`——**数据确实被替换**。

#### 「待重启」说明弹窗也要有一键重启（实机验收发现）

`restore.pending` **不允许叠加**：一次恢复暂存成功后，后续恢复一律被 409 `restore_pending` 拒绝，必须重启才能继续。而这个状态**跨页面刷新一直存在**——页面重开、或过一阵子再回来，用户从橙色导入按钮进到的就是那个「待重启」说明弹窗。

原先该弹窗只有一条**要用户自己复制**的命令（`RESTART_COMMAND` 常量），而一键重启按钮只存在于"刚受理完那一刻"才打开的进度弹窗里。于是：**用户真正需要一键重启的场景（回到页面、状态仍在），按钮恰好不在**。现已把 `RestartControl` 也放进这个弹窗（保留原有可复制命令作为保底，且复用原有文案键而不另写一套）。

> 触发这次发现的实机现象：前一次恢复仍处 `pending_restart` 时再发起第二次恢复，界面表现为"点了没反应"——实为后端 409 正确拒绝（\`{"code":"restore_pending","message":"已存在待生效的备份恢复，请先重启服务完成替换"}\`）。后端行为正确，但界面把用户引到了一个**没有出口**的地方。
