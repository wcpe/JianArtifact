# 功能规格：用户组与更细粒度权限动作

> 状态：**开发完成，待用户验收**（阶段五：文档同步）　·　关联 PRD：FR-36（P2，PRD 记为「已交付@未发布」）　·　分支：feat/fr36-user-groups　·　依赖：[ADR-0002](../adr/0002-sqlite-filesystem-storage.md)（schema 由迁移管理）、[ADR-0008](../adr/0008-auth-session-model.md)（会话模型）、[ADR-0029](../adr/0029-external-identity-providers.md)（外部身份源，本期不扩展）

## 1. 背景与目标

- **问题**：授权主体只有「单个用户」一种形态，动作只有 `read` / `write` / `admin` 三档（见 `0001_init.sql:52-58`）。给十个人开同一个仓库的读权限，就要写十条几乎一样的 ACL；人员变动要逐条增删，审计时也无法回答"某仓库究竟对谁开放"。动作粒度同样过粗：`write` 一把同时给出「上传发布」与「删除」，无法只授予发布、也无法只授予删除；改 ACL 的权限等同于 `admin`。

**目标（对用户）**：

- 引入**用户组**：组作为授权主体，一条 ACL 可授予整组；成员变动只改 `user_group_member`；
- 动作集由三档扩展为六档（`read` / `write` / `publish` / `delete` / `acl_manage` / `admin`），可分别授予"只能发布""只能删自己负责的路径前缀之外不授予""只能改本仓库 ACL"；
- 既有用法**不回退**：既有 `subject_id` 行全部解释为"用户主体"，无需数据回填即可继续工作；
- 本规格只覆盖**数据基座与语义口径**（阶段一）与随后的领域/接口实现（阶段二），目录侧组映射等一律不做。

**期次归属**：FR-36 属 **M3（企业认证、存储与运维）**（见 [ROADMAP.md](../ROADMAP.md) §6）。此前它在三处被明确列为范围外，本期即兑现这些声明：

- [ADR-0029](../adr/0029-external-identity-providers.md) §"范围外"：目录组 → 角色 / ACL 映射属 FR-36；
- [0.11.0-external-identity-providers.md](0.11.0-external-identity-providers.md) §2：用户组与更细粒度权限动作（FR-36）不做；
- [0.6.0-anonymous-access.md](0.6.0-anonymous-access.md) §2：细粒度权限动作扩展（FR-36）不做。

## 2. 需求（要什么）

- **用户组**：管理员可建组（名称唯一、可选描述）、增删成员、删除组；一个用户可属多个组。
- **组作为 ACL 主体**：仓库 ACL 的条目可以是"用户 × 动作"或"组 × 动作"两种形态；同仓库下同一主体同一动作只允许一条（避免重复授权与语义歧义）。
- **动作集**：`read` / `write` / `publish` / `delete` / `acl_manage` / `admin`，蕴含关系见 §3.3；`write` 仍是"常规写"的粗粒度便捷档（蕴含 `read` / `publish`，**不蕴含 `delete`**）。
- **生效口径**：判定某用户能否对某仓库执行某动作时，先按其**直接用户条目**判定，再按其**所属各组**的条目判定，两者取并集（并集语义：任一命中即通过，不存在"禁止优先"）。
- **生命周期清理**：删除用户 → 其成员关系与其用户主体 ACL 条目一并消失（CASCADE）；删除组 → 成员关系与该组的 ACL 条目一并消失；删除仓库 → 其全部 ACL 条目消失（既有 CASCADE 不变）。
- **可审计**：仓库 ACL 列表接口能区分"这是用户条目还是组条目"并给出组名，管理员能看出"某仓库为什么对某人开放"。
- **范围外（不做）**：目录组 → 角色 / ACL 映射（LDAP 组 / OIDC claim / SCIM）；多 IdP、SLO、MFA；管理面端点的细粒度授权（仍沿用既有 `IsAdmin` 守卫，本期不把 `acl_manage` 接到管理端点）；协议侧（git / npm / mvn）经外部身份源鉴权；路径级 / 前缀级授权；组嵌套（组内套组）。

### 3.2 数据模型（迁移 `0046`）

三处结构改动（详见 `apps/server/internal/persistence/migrations/0046_user_groups.sql`）：

**新增 `user_group`**

| 列            | 类型与约束                                | 说明                       |
| ------------- | ----------------------------------------- | -------------------------- |
| `id`          | `INTEGER PRIMARY KEY AUTOINCREMENT`       | 组主键                     |
| `name`        | `TEXT NOT NULL UNIQUE`                    | 组名唯一，作为人类可读标识 |
| `description` | `TEXT NOT NULL DEFAULT ''`                | 可选说明                   |
| `created_at`  | `TEXT NOT NULL DEFAULT (datetime('now'))` | 与其它表的既有口径一致     |

**新增 `user_group_member`**

| 列           | 类型与约束                                                     | 说明                 |
| ------------ | -------------------------------------------------------------- | -------------------- |
| `group_id`   | `INTEGER NOT NULL REFERENCES user_group(id) ON DELETE CASCADE` | 删组即清理成员关系   |
| `user_id`    | `INTEGER NOT NULL REFERENCES user(id) ON DELETE CASCADE`       | 删用户即清理成员关系 |
| `created_at` | `TEXT NOT NULL DEFAULT (datetime('now'))`                      | 加入时间             |
| —            | `PRIMARY KEY (group_id, user_id)`                              | 同一成员不重复       |

另建 `idx_user_group_member_user (user_id)`：承载"某用户属于哪些组"的反查，这正是鉴权时的热路径（一次判定要展开该用户的所有组）。复合主键的最左列是 `group_id`，无法服务该反查。

**改造 `acl`（SQLite 不支持 ALTER 改 CHECK / 加带约束的列，故按仓库既有先例 `0020_repository_formats.sql` 的「建新表 → 复制 → 删旧 → 改名 → 重建索引」范式重建）**

| 列                 | 类型与约束                                                                                 | 说明                      |
| ------------------ | ------------------------------------------------------------------------------------------ | ------------------------- |
| `id`               | `INTEGER PRIMARY KEY AUTOINCREMENT`                                                        | 列名与语义不变            |
| `repository_id`    | `INTEGER NOT NULL REFERENCES repository(id) ON DELETE CASCADE`                             | 不变                      |
| `subject_id`       | `INTEGER REFERENCES user(id) ON DELETE CASCADE`（**可空**）                                | 用户主体；组主体行为 NULL |
| `subject_type`     | `TEXT NOT NULL DEFAULT 'user' CHECK (subject_type IN ('user','group'))`                    | 本行主体是用户还是组      |
| `subject_group_id` | `INTEGER REFERENCES user_group(id) ON DELETE CASCADE`（可空）                              | 组主体；用户主体行为 NULL |
| `action`           | `TEXT NOT NULL CHECK (action IN ('read','write','publish','delete','acl_manage','admin'))` | 由三档放宽到六档          |

**为什么 `subject_type` 与 `subject_group_id` 两列并存，而不是把 `subject_id` 复用成"主体 ID"**：

1. **向后兼容**：复用会让"用户 7"与"组 7"在同一列里撞车，必须靠 `subject_type` 才能分辨——那 `subject_id` 的语义就从"用户 ID"退化成"多态 ID"，所有既有查询（`AclRepo.ListByRepo` / `Replace` / `HasPermission` 与 `repository_delete_journal.go:73` 的回滚插入）都要同时带上类型条件，一处漏写即产生**跨类型误授权**（把组 7 的权限判给用户 7）。
2. **外键能落地**：分开后两列各带各的 `REFERENCES ... ON DELETE CASCADE`，由 SQLite 直接兑现"删用户清用户条目、删组清组条目"；复用一列则无法建外键，清理逻辑必须全部搬进应用代码，且任何一条漏写的删除路径都会留下悬空主体。
3. **可空性即校验**：配合 CHECK（见下）可强制"用户行与组行二者恰有其一"，不会出现两列都填或都不填的中间态。

**UNIQUE 约束的口径**（关键，SQLite 对 NULL 的语义在这里是陷阱）：原 `UNIQUE(repository_id, subject_id, action)` 在引入可空列后**不再有效**——SQLite 的唯一索引把 NULL 视作互不相同，多行 `subject_group_id IS NULL` 之间永不冲突；若简单改成 `UNIQUE(repository_id, subject_id, subject_group_id, action)`，则同一用户在同一仓库可被插入无数条相同的 `read`（每行 NULL 都"独一无二"），重复授权无从阻止。因此改为**两条 partial unique index**，各自只约束一种主体、且该主体下的键列全部非空：

```sql
CREATE UNIQUE INDEX idx_acl_user_grant
  ON acl (repository_id, subject_id, action) WHERE subject_type = 'user';
CREATE UNIQUE INDEX idx_acl_group_grant
  ON acl (repository_id, subject_group_id, action) WHERE subject_type = 'group';
```

配合表内 CHECK 约束 `(subject_type='user' AND subject_id IS NOT NULL AND subject_group_id IS NULL) OR (subject_type='group' AND subject_group_id IS NOT NULL AND subject_id IS NULL)`，保证两条索引的键列在各自分区内非空、NULL 陷阱不成立。

索引：保留并重建 `idx_acl_repository (repository_id)` 与 `idx_acl_subject (subject_id)`（后者名字沿用旧名、语义不变——它只服务用户主体，因为组主体行的 `subject_id` 恒为 NULL，不会进入该索引的有用区间）；新增 `idx_acl_group_subject (subject_group_id)` 服务组主体的反查与级联清理。

### 3.3 动作集语义与蕴含关系

| 动作         | 含义                                                                        |
| ------------ | --------------------------------------------------------------------------- |
| `read`       | 浏览、下载、搜索该仓库内容                                                  |
| `write`      | 常规写：粗粒度便捷档，蕴含 `read` / `publish`；**不蕴含 `delete`**（见 §6） |
| `publish`    | 只管上传 / 发布新版本；不授予读取、不授予删除                               |
| `delete`     | 只管删除资产；不授予读取、不授予发布                                        |
| `acl_manage` | 只管**该仓库**的 ACL 变更；不授予任何内容读写，也不提升为全局管理员         |
| `admin`      | 该仓库的全部权限，蕴含上述全部                                              |

蕴含表（判定动作 → 能使之通过的已授权动作集合，即 `AclRepo.satisfyingGrants` 展开的 `action IN (...)`）：

| 判定         | 满足集合                    | 说明                                                                              |
| ------------ | --------------------------- | --------------------------------------------------------------------------------- |
| `read`       | `read`, `write`, `admin`    | `publish` / `delete` / `acl_manage` **不蕴含** read：只发发布权的人不应因此读全仓 |
| `publish`    | `publish`, `write`, `admin` | 保留 `write ⊇ publish`，既有"能写就能发"的直觉不变                                |
| `delete`     | `delete`, `admin`           | **`write` 不蕴含 `delete`**：删除是破坏性动作，需单独授予（见 §6 的取舍说明）     |
| `write`      | `write`, `admin`            | `write` 是具体授权档，不被 `publish` / `delete` 反向蕴含                          |
| `acl_manage` | `acl_manage`, `admin`       | 严格隔离：管 ACL 不等于能读内容                                                   |
| `admin`      | `admin`                     | 最高档；未列入集合即表示不被任何更低档蕴含                                        |

未登记的动作（含空串）一律退化为「只由自身满足」，避免未知动作被宽泛授权放行。

**组主体的判定**（阶段二）：`HasPermission` 的一次判定 = 「用户主体条目」∪「该用户所属各组的条目」，任一命中即通过；组内成员关系变化**即时生效**（无缓存、无快照），与既有"改 ACL 立即生效"的口径一致。

### 3.4 删除与清理语义

- **删除用户**：`user_group_member.user_id` 与 `acl.subject_id` 均 `ON DELETE CASCADE` → 成员关系与该用户的 ACL 条目自动消失。
- **删除仓库**：`acl.repository_id` CASCADE → 全部条目消失（既有行为不变）。
- **删除组**：`user_group_member` 按 `group_id` CASCADE 清理；**该组在 `acl` 中的条目也一并删除**（`acl.subject_group_id` 同样 `ON DELETE CASCADE`）。理由：ACL 条目本身不是可独立存在的资源，组这个主体消失后留下"指向已不存在的组"的行只会产生两类危害——(a) 悬空条目在列表接口里无法展示组名，成为管理员无法解释的僵尸授权；(b) 若将来发生 ID 复用（SQLite 的 `AUTOINCREMENT` 保证不复用 rowid，但语义上仍不应依赖这一点），悬空条目会被后来新建的组"继承"，构成静默提权。删组是一次管理员显式动作，连带删除其授权条目是**最安全且可预期**的语义；需要保留授权时，管理员应先建新组再迁移。
- **重命名组**：组名唯一，改名不影响 ACL（引用的是 `id`）。

## 5. 验收标准

- **迁移（阶段一可验）**：全新库 `Migrate()` 后 `user_group` / `user_group_member` 存在且可查询；`acl` 具备 `subject_type` / `subject_group_id` 且 `action` 接受六值；在含既有 ACL 行的库上升级后行数与 (repository_id, subject_id, action) 三元组**逐条不变**、`subject_type` 全为 `user`。
- **唯一性（负例）**：同一用户同仓库同动作插入两条 → 被 `idx_acl_user_grant` 拒绝；同一组同仓库同动作插入两条 → 被 `idx_acl_group_grant` 拒绝；两种主体各自独立，不与对方冲突。
- **组主体判定（阶段二）**：组成员因组授权而通过判定；移出组后立即不通过；同时存在用户条目与组条目时取并集。
- **蕴含（阶段二，六档 × 两态）**：按 §3.3 蕴含表逐格验证，重点负例——`publish` 不蕴含 `read`、`delete` 不蕴含 `read`、`acl_manage` 不蕴含任何内容读写、**`write` 不蕴含 `delete`**（授予 `write` 的账号不得能删）、`write` 不被 `publish` 或 `delete` 反向蕴含。
- **级联（阶段二）**：删用户 → 其成员关系与用户 ACL 条目清空；删组 → 成员关系与该组 ACL 条目清空；删仓库 → 其全部条目清空；三者均无悬空行。
- **既有行为不回退（阶段二）**：0.11.0 的三档用法（read / write / admin 的既有判定结果）在升级后逐条一致；匿名访问（FR-66，`anonymous` 主体）与 public 仓库放行逻辑不受影响。**协议层删除例外**：它由「仅全局管理员」放开为可授予的仓库级 `delete` 动作（全局管理员分支保留），是有意的放开，见 §6。
- **质量门**：`scripts/check.ps1` 全绿。
- **实机验收清单（需用户确认）**：以真实浏览器完成——①建组并加两名成员；②对某私有仓库只授予该组 `publish`，验证成员**能发布但不能列出/下载**该仓内容；③对另一仓库授予 `delete`，验证成员能删但不能发；④授予 `acl_manage`，验证成员能改该仓 ACL 但读不到内容、且**不能**进入管理面其它端点（仍受 `IsAdmin` 限制）；⑤删除该组，验证其 ACL 条目清空、原成员权限即时失效；⑥既有（升级前建立的）用户级 read / write / admin 授权在升级后表现不变。**单元 / e2e 全绿不替代本清单**，需用户在自有环境确认。

## 6. 风险 / 待定

- **`write ⊇ delete` 的取舍：最终选定**不蕴含**（已落定）**：收口为**删除必须与写分离**——`delete` 是唯一不可逆的破坏性动作，把它绑在 `write` 上等于「凡是能写某个路径的人都能把整仓历史删掉」，这会让本期「细粒度」的最大收益落空。代价是升级后若某账号确实需要删除，管理员须显式补一条 `delete` 授权。
  **对既有升级用户的实际影响（已核实代码，非推测）**：FR-36 之前协议层删除是**仅全局管理员**（`raw.go` 的 `requireAdmin`、批量删除的 `requireAssetOperationAdmin`），且既有 `HasPermission` 只认 `read` / `write` / `admin` 三档、把其余动作一律映射到 `admin`。也就是说**此前不存在"靠 `write` 授权就能删除"的路径**——`write` 事实上从未蕴含过删除。因此 `write` 收紧为不含 `delete` **不会让任何既有账号失去删除能力**：能删的人（全局管理员）照旧能删，不能删的人原本也不能删。`delete` 的净变化是**放开**（从"只有全局管理员"扩到"可授予任意主体/组的仓库级动作"），不是收紧。管理员真正需要做的是：把"给账号加全局管理员才能删"这类越权配置，改配为仓库级 `delete` 授权。若后续出现「既要 write 又要 delete」的高频组合，以 UI 层面的复合授权档解决，而不是回滚蕴含关系。
- **`subject_id` 由 NOT NULL 改为可空**：`Acl` 行模型与所有 `INSERT` 必须显式处理 `subject_type`；阶段二任一处沿用旧的"只写三列"语句，都会靠默认值生成 `user` 主体行（不会误判，但组授权会静默失效）。这是本期最易漏改的点，需以测试锁定。
- **组名唯一性的作用域**：本期组是全局的（不按仓库隔离）。优点是可跨仓复用；代价是组名在多团队场景下可能撞车。若后续出现该诉求，再考虑命名空间或改为显示名 + 唯一标识分离。
- **性能**：一次判定要展开用户所属各组（一次 `user_group_member` 查询 + `IN (...)`）。组规模与用户所属组数都很小（企业场景典型为个位数），本期不做缓存；如出现"数百组"场景，再评估物化展开。
- **范围风险**：目录组 → ACL 映射最容易被顺手做进来（它看起来只是"多一个字段"），本稿明确不做，属后续增量。
- **备份口径**：两张新表是元数据，已计入备份包计数白名单；备份包经 `VACUUM INTO` 整体快照产出（无按表清单），导入侧无需另配清单——但升级前后跨版本恢复（旧包 → 新库）的 ACL 语义需阶段二确认。
