# 功能规格：group 回源预算解耦（两阶段）

> 状态：草拟　·　关联 PRD：FR-154（增强 FR-110）　·　分支：feature/fr154-group-two-phase-budget　·　依赖：FIX-1（group 不可判定返回码分离）

## 1. 背景与目标

### 1.1 用户可见现象

生产 group 仓库（`maven-public`）下，某个上游分组的 POM **全部 200**，同坐标的 jar **全部 404**：

- 与版本无关，**只与制品体积相关**：280KB / 1.7MB / 1MB 的 jar 正常，15MB 的 universal jar 必挂。
- 每次失败耗时约 3s，且**每次重试都重复这 3s**——不会自愈，也不会被 404 负缓存收敛。
- 对客户端表现为「这个制品不存在」，于是 Gradle/Maven 直接回退下一仓库或构建失败。

优先级 P2（PRD 已登记 FR-154）。本条是 FR-110（group 聚合读性能，见 [0.7.1-group-read-latency.md](0.7.1-group-read-latency.md)）的**增强**：FR-110 把成员超时从 10s 收到 3s 换来「缺失制品快速 404」，代价是把「大制品的完整下载」也塞进了这 3s 里。

### 1.2 根因链（已由代码验证闭合）

1. [asset_service.go](../../apps/server/internal/domain/asset_service.go#L1338) 的 `groupGet` 对每个 proxy 成员用 `context.WithTimeout(groupCtx, groupMemberTimeout)` 派生成员预算，而 `groupMemberTimeout = 3 * time.Second` 是硬编码常量（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1242)）。
2. `proxyGet` → `fetchProxyAsset` 的语义是「取响应头 → `putStagedBlob(body)` 流式把**整个** body 落盘 → upsert → 再从本地读返回」（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1041-L1092)）。因此这 3s 实际覆盖**完整下载**。15MB 制品需约 5MB/s 稳定回源带宽才能在这 3s 内完成。
3. [client.go](../../apps/server/internal/upstream/client.go#L158) 的 `fetch` 用 `http.NewRequestWithContext(ctx, ...)` 构造请求，因此 group 的 3s context 到期会让 `resp.Body.Read` 失败，`putStagedBlob` 报错。
4. `groupGet` 收集成员结果时，任何 `resolveErr` 都只做 `uncertain.Store(true)`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1342-L1347)），最后**无条件** `return nil, nil, ErrNotFound`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1364-L1370)）。`uncertain` 只决定「要不要写负缓存」，不改变返回码。
5. 因不确定的路径不写负缓存（[negative_cache.go](../../apps/server/internal/domain/negative_cache.go#L13-L19)），下次请求重新探测、重新超时，于是表现为「永久 404，每次约 3s」。

### 1.3 目标

**一句话**：3s 只回答「是否值得等这个成员」，**不回答**「能不能下完」；一旦确认该成员确实持有该制品，落盘改用回源整体超时（`JIAN_UPSTREAM_TIMEOUT`，默认 30s，见 [config.go](../../apps/server/internal/config/config.go#L86)、[config.go](../../apps/server/internal/config/config.go#L651-L662)、装配点 [wiring.go](../../apps/server/cmd/jianartifact/wiring.go#L112)）。

必须同时保持的不变量：

- **I1** 无响应上游仍在 3s 量级被跳过；真实缺失路径仍在 3s 量级返回 404（FR-110 收益不退化）。
- **I2** 已确认存在的成员，落盘预算为回源整体超时，而不是成员超时。
- **I3** 成员顺序语义不变（见 §3.5）。
- **I4** 同路径回源至多一次，single-flight 不回退。
- **I5** 真实缺失路径的负缓存行为不变；「确认命中但落盘失败」**不得**写负缓存。

## 2. 需求（要什么）

### 2.1 预算分离（核心）

- 阶段一（探测）：`groupMemberTimeout`（3s）**只约束「该成员是否及时给出响应」**，不约束响应体传输。
- 阶段二（落盘）：一旦确认该成员持有该制品，落盘预算交由回源整体超时（`JIAN_UPSTREAM_TIMEOUT`，默认 30s，运行时可改）。
- 3s 的**唯一**判据是「该成员的确认信号是否在预算内到达」；只要到达，即使响应体还需要很久，也不再按成员预算取消。
- 不新增配置项：本 FR 不把 `groupMemberTimeout` 配置化（那是 FR-156 的范围），也不改 `JIAN_UPSTREAM_TIMEOUT` 的语义。

### 2.2 确认命中后的落盘与失败返回

- 「确认命中」的判据：拿到上游 2xx 响应头。既有实现已经在这一刻认定「上游可达」（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1082) 在落盘**之前**就 `recordSuccess`），本条沿用同一口径，不引入新判据。
- 确认命中但落盘失败（超时 / 传输中断）：必须返回「不可判定」类错误链，经 FIX-1 的返回码分离映射为 **504**（超时）或 **502**（其余上游故障）；**不得**返回 404，**不得**写负缓存。

### 2.3 与 FIX-1 的分工（不重复定义）

| 归属                | 职责                                                                                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **FIX-1**           | 「不可判定 → 502/504、确认不存在 → 404」的**返回码分离**：`groupGet` 全失败时不再无条件 `ErrNotFound`，按 `ResolveFailure` 判定上抛错误。返回码表在 FIX-1 内定义。                      |
| **本 FR（FR-154）** | 「确认阶段与落盘阶段**预算分离**」：让 `ResolveFailure` 有机会被判成 Unclear/Confirmed，并保证落盘失败产出**可被正确分类的错误**（超时 → `ErrUpstreamTimeout`，其余 → `ErrUpstream`）。 |

两件事缺一不可：只做 FIX-1 而预算不分离，则「确认」永远来不及发生，仍然全是 Uncertain→404 或全 502/504；只做预算分离而 FIX-1 缺席，则落盘失败仍会被吞成 404，用户看到的仍是「制品不存在」。本 spec 引用 FIX-1 的返回码结论，不在此重复。

### 2.4 范围内

- `groupGet` 的成员预算模型（单一 3s → 两阶段）。
- 判定「已确认命中」的信号通道，及其在成员 goroutine 内的取消/等待语义。
- 确认命中后落盘失败的错误分类（保证可被映射为 504/502）。
- 相应单元/集成测试、`-race` 验证。

### 2.5 范围外

见 §6.3（含：不做自动重试、不做分片下载、不改组成员顺序语义、不做跨节点负缓存）。

## 3. 设计（怎么做）

### 3.1 现状锚点（改造点定位）

| 位置                                                                               | 现状                                                                        | 本 FR 的作用点                                              |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------- |
| [asset_service.go](../../apps/server/internal/domain/asset_service.go#L1242)       | `groupMemberTimeout = 3 * time.Second` 硬编码                               | 值不变，**语义**改为「确认预算」                            |
| [asset_service.go](../../apps/server/internal/domain/asset_service.go#L1338)       | `context.WithTimeout(groupCtx, groupMemberTimeout)`                         | 改为 `context.WithCancel` + 独立计时器（见 §3.3）           |

| [client.go](../../apps/server/internal/upstream/client.go#L82-L87)                 | `http.Client{Timeout: JIAN_UPSTREAM_TIMEOUT}`                               | 这就是阶段二的预算来源，**无需新机制**                      |

### 3.2 候选路径 A：拆出「确认存在」接口

**做法**：把「确认存在」与「取得内容」拆成两个独立操作。

- 新增 upstream 层能力（**新增，非既有**）：「只取响应头、不读 body」，例如 `HeadWithCredential(ctx, baseURL, path, credentialRef) (http.Header, error)`，复用 `Do` 的出站安全策略与凭据注入。注意既有 `ProbeWithCredential`（[client.go](../../apps/server/internal/upstream/client.go#L217)）只探测 remoteURL **根地址**，不适用于制品路径，不能直接复用。
- `resolve` / `proxyGet` / `fetchProxyAsset` 的内部契约随之变更：需要多一个「只确认」模式（例如 `confirmProxyAsset`），返回「成员是否持有该路径」，不落盘、不 upsert。
- 阶段一（`groupGet`）：对每个成员调用「确认」模式，3s 内返回 2xx 即视为该成员命中。
- 阶段二：对胜出成员调用既有 `proxyGet` 走完整落盘，此时**不再**施加成员预算，只受回源整体超时约束。

**路径 A 的代价（必须写清）**：

- **请求数翻倍**：每个缓存未命中路径要打两次上游（HEAD + GET）。若上游不支持 HEAD 或 HEAD 与 GET 语义不一致（部分私有仓库/带鉴权重定向的上游），必须回落 GET——回落即等于「先完整下载再丢弃」，把浪费放大到整份制品。
- **single-flight 跨两阶段会被打断**：`sf.Do` 在函数返回时即释放 key（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1004-L1032)），阶段一结束就释放，因此并发请求会在「确认完成、落盘未完成」的窗口内重复进入阶段一。要维持「同路径回源至多一次」，必须额外引入**确认结果的短窗缓存**（TTL 数秒）+ 阶段二内的二次复查，并定义其失效语义；这是净新增状态，不是既有能力。
- **「最快成功」的含义被改写**：见 §3.5，可能胜出一个「头很快、body 很慢」的成员。
- 契约变更面更大：`resolve` / `proxyGet` / `fetchProxyAsset` 三个内部契约同时改动，回归面覆盖 group / proxy / OCI / 格式元数据回退（[format_metadata_service.go](../../apps/server/internal/domain/format_metadata_service.go#L1064) 也直接调用 `fetchProxyAsset`）。

### 3.3 候选路径 B（推荐）：首字节看门狗

**做法**：仍是**同一次 GET**，把 3s 从「总预算」改为「首个响应头的看门狗」。

关键前提（已核实）：`readResponse`（[session.go](../../apps/server/internal/upstream/session.go#L298-L312)）拿到响应头就返回 `(body, header)`，**不预读** body；因此「响应头到达」这个时点在 `fetchProxyAsset` 里天然可观测，无需另造探针。

实现要点：

1. **成员 ctx 不再带 deadline**：[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1338) 改为 `context.WithCancel(groupCtx)`。之所以不能用 `context.WithTimeout` 再加长 deadline：子 context 的 deadline 只能收紧、无法延长，父级 3s 一旦到点就无法撤回。
2. **新增确认信号（复用既有 ctx 记录器范式）**：建议命名（实现期可调）`WithUpstreamStarted(ctx) (context.Context, <-chan struct{})` 与 `markUpstreamStarted(ctx)`，与 `WithResolveFailure` / `WithCacheOutcome` 同一风格；未挂载时为无操作，因此代理直连、后台任务、格式元数据回退等调用方**无需感知**。发送点放在 `fetchProxyAsset` 拿到 header 之后（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1082) 附近，即 `recordSuccess` 之后、`putStagedBlob` 之前）。
3. **成员 goroutine 结构**：`resolve` 放到内层 goroutine，外层 `select` 三路竞速：

```
memberCtx, mCancel := context.WithCancel(groupCtx)   // 无 deadline
defer mCancel()
memberCtx, started := WithUpstreamStarted(memberCtx)
memberCtx = WithResolveFailure(memberCtx)

go func() { asset, rc, resolveErr = s.resolve(memberCtx, j.member, path, depth+1); close(done) }()
timer := time.NewTimer(groupMemberTimeout); defer timer.Stop()

select {
case <-started:   // 已确认该成员持有该制品 → 撤销阶段一预算，余下交给回源整体超时
case <-done:      // 成员已给出结论（含快速 404）：按既有逻辑处理
case <-timer.C:   // 3s 内既无响应头也无结论 → 判为不可判定，跳过该成员
    mCancel()
    uncertain.Store(true)
}
<-done            // 必须等内层真正退出，避免 goroutine 泄漏与数据竞态（-race）
```

4. **计时与取消细节**：
   - 计时器必须独立于 ctx（这就是路径 B 唯一的新技术点）；不能靠「派生一个更长的 ctx」实现。
   - `timer.C` 触发后**必须** `cancel` 成员的 ctx，让 `resp.Body.Read` 立即失败并释放连接，否则该成员会继续占着上游连接与 goroutine。
   - 「同时就绪」偏向**宽容侧**：实现时先做一次非阻塞检查 `started`，再进入 `select`。误取消的代价是「把可下载的制品判成缺失」（正是本次要修的故障），多等代价只是一个回源整体超时，两者不可对称。
   - `started` 只需触发一次（`sync.Once` 语义即可），多次触发不允许阻塞或 panic。

### 3.4 推荐与理由

**推荐路径 B。**

- **语义最贴合目标**：「3s 只回答是否值得等」在路径 B 里就是字面实现——看门狗只管首包，落盘预算回到 `http.Client.Timeout`（既是既有机制，也是运维可调的 `JIAN_UPSTREAM_TIMEOUT`）。
- **single-flight 天然不变**：探测与落盘仍在**同一个** `sf.Do` 临界区内（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1003-L1036)），「同路径回源至多一次」无需任何新状态，直接满足 I4。
- **请求数不变**：仍是 1 次 GET，不依赖上游是否支持 HEAD，不给上游增加额外 RTT 与负载。
- **顺序语义不变**：胜出判据仍是「谁先完成」，与 FR-110 的「并行回源取最快成功」一致（见 §3.5 的严格说明）。
- **改动面最小**：`resolve` / `proxyGet` / `fetchProxyAsset` 的签名与语义都可保持不变，只新增一个 ctx 信号 + `groupGet` 内的等待结构；`format_metadata_service.go` 等既有调用方零改动。
- **与 PRD 措辞一致**：FR-154 正文写「拿到响应头即算命中、不落盘」。路径 B 同样满足——**确认判据就是响应头**，确认阶段本身不写入任何字节（`putStagedBlob` 属于阶段二）；与路径 A 的差别只在于不为「确认」另发一次请求，而是把同一次 GET 的后续字节继续用于落盘。

**未被选中路径 A 的代价**：请求数翻倍与 HEAD 兼容性风险；必须新增「确认结果短窗缓存」才能守住 I4；胜出判据从「下载完成」前移为「响应头到达」，会把「头快体慢」的成员选为胜者（在它落盘失败时，另一个本可成功的成员已被取消，只能返回 504）；内部契约三处同时变更，回归面明显更大。若后续出现「必须在 3s 内确定成员归属、但绝不能开始传输」的新需求（例如按成员优先级做严格仲裁），再考虑路径 A。

### 3.5 成员顺序语义

结论：**路径 B 下完全不变。**

- **本地快查**：阶段一仍按 `Members` 配置顺序串行 `localGet`，先命中先返回（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1280-L1292)）——不受本 FR 影响。
- **回源并行**：仍是「首个成功即取消其余」；多个成员几乎同时成功时，既有的 `results` 收集循环按下标最小者返回（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1356-L1363)），本 FR 不改这段。
- 严格说明一处**措辞**上的差别：路径 B 里「成功」的定义仍是「该成员已把内容落盘并可 `localGet` 读到」，**没有**变成「响应头到达」。这是选择路径 B 的直接收益之一——胜者一定是可用的。若走路径 A，「成功」会变成「确认存在」，胜出判据随之前移，可能出现「胜出成员落盘失败、而更快可用的成员已被取消」的退化；要避免就得再定义「多成员同时确认时的仲裁与回退」，那是本 FR 之外的额外设计。

### 3.6 确认命中但落盘失败时如何返回

要求：**504（超时）/ 502（其余上游故障），不得 404，不得写负缓存。**

- 落盘阶段的失败发生在 [asset_service.go](../../apps/server/internal/domain/asset_service.go#L1083-L1086)：`putStagedBlob(body)` 出错后**原样返回**，当前没有经过 `mapUpstreamErr`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1428-L1439)）。这是必须补的一处：body 读取超时的错误若不包装成 `ErrUpstreamTimeout`，上抛后会被协议层落到 `default` 分支映射成 **500**（[raw.go](../../apps/server/internal/protocol/raw.go#L633-L646) 的 `writeAssetErr`），既不是 504 也不是 404，验收无法通过。
- 因此实现要求：落盘失败按 `upstream.IsTimeout`（[client.go](../../apps/server/internal/upstream/client.go#L254-L266)）判定——超时包装 `ErrUpstreamTimeout`，其余包装 `ErrUpstream`；对 `upstream.ErrNotFound` / `ErrGone` 的既有分类保持不动。
- 分类结果交给 FIX-1 的返回码分离逻辑（§2.3）映射成 504/502；本 spec 不重复返回码表。
- 「确认命中」的成员失败时，该成员**必须**记为 `ResolveFailureUncertain`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L116-L124) 的既有语义：一旦 Uncertain 不会被后续 Confirmed 覆盖），从而保证：不写负缓存（I5）、下次请求仍会重试、不会把可下载的制品长期锁成 404。
- 协议层已具备两条通路：普通制品走 `writeAssetErr`（[maven.go](../../apps/server/internal/protocol/maven.go#L233-L241) → [raw.go](../../apps/server/internal/protocol/raw.go#L633-L646)）；**注意** maven 的 SNAPSHOT 分支在解析失败时直接写 404（[maven.go](../../apps/server/internal/protocol/maven.go#L208-L231)），不经过 `writeAssetErr`——该分支是否也要跟随 FIX-1 分离返回码，见 §6.2 待定 1。

### 3.7 并发、single-flight 与资源

- **请求取消**：`groupCtx` 派生自请求 ctx。客户端断开 → 全部成员 ctx 取消 → `sf.Do` 内的下载随之中断；`sf.Do` 返回即释放 key，不留悬挂。
- **是否会出现「确认了但没落盘」的悬挂状态**：路径 B **不会**。确认只是**单次请求内的 in-memory 信号**，不写任何持久或共享状态；不存在「已确认、待落盘」的可观测中间态。落盘进行中的中间产物是既有机制：
  - 写失败时 `blobstore.put` 统一删除临时文件（[store.go](../../apps/server/internal/blobstore/store.go#L98-L103)、[store.go](../../apps/server/internal/blobstore/store.go#L109-L115)）；
  - 已 rename 落盘但元数据未提交的内容由**暂存保护 + GC 兜底**（[store.go](../../apps/server/internal/blobstore/store.go#L81-L86)、[store.go](../../apps/server/internal/blobstore/store.go#L120-L127)），由 `ReleaseStaged` 或后续 GC 回收。
  - 因此**禁止**为了记录「已确认」而写入 asset 行或任何占位记录——那才会制造真正的悬挂状态（资产可见但内容缺失）。
- **single-flight 取消/清理语义**：`sf.Do` 使用**首个调用者**的 ctx。若首个调用者的成员看门狗在 3s 触发并取消，正在共享下载的其它 group 请求也会一同失败——这是既有行为（当前同样如此），本 FR 不改变、也不需要额外补偿；两个请求都会得到同一「不可判定」结论。
- **goroutine 生命周期**：看门狗路径必须先 `mCancel()` 再 `<-done`，任何提前 `return` 都必须以 `<-done` 收尾，否则 `-race` 会报出对内层变量的竞态，并可能泄漏 goroutine。
- **嵌套 group 成员**：若成员本身是 group，内层任一成员的响应头会让外层的 `started` 提前触发。语义上仍正确（确实已确认存在），但会让外层的确认预算提前放宽；见 §6.1 风险。

### 3.8 复用而不重复设计

以下能力**已存在**，本 FR 直接复用，不新增同类机制：

- `ResolveFailureStatus` 的 Confirmed / Uncertain 二分与 ctx 传递范式（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L82-L124)）。
- `proxyHealth` 的 `shouldBlock` / `beginUpstream` / `releaseProbe` / `recordFailure` / `recordSuccess`（[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L196)，[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L222)，[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L253)）——成员预筛与半开闸门行为不变。
- single-flight（`s.sf.Do`，key = `repoID\0path`）与 404 负缓存（键 `repoID\0path`，TTL 60s，[negative_cache.go](../../apps/server/internal/domain/negative_cache.go#L11)）。
- `JIAN_UPSTREAM_TIMEOUT` 的解析与动态更新（`upstream.Client.SetTimeout` / `Timeout`，[client.go](../../apps/server/internal/upstream/client.go#L124-L139)）。
- 相关架构决策见 [ADR-0010](../adr/0010-proxy-cache-singleflight-group-routing.md)（proxy 回源缓存、single-flight 与 group 路由）。

## 5. 验收标准

### 5.1 单元与集成（须全绿）

- **大制品成功**：`httptest` 慢上游夹具——立即 `WriteHeader(200)` + `Flush()` 给出响应头，随后按约 **5MB/s** 分块写 15MB body（分块间 sleep）；group 读**成功**返回，字节数 = 15MB，内容与 sha256/sha1/md5 和上游一致。
  - 注：现有测试助手 `newAssetService` 的回源客户端是 `upstream.NewTestClient(5*time.Second)`（[asset_service_test.go](../../apps/server/internal/domain/asset_service_test.go#L34-L41)），5s 对本用例过紧，需另建 30s 超时的客户端（或加一个助手变体）。
- **确认命中但落盘超时 → 504**：上游立即回 200 头、body 长期滴流；回源客户端超时设为 1s。断言：错误链满足 `errors.Is(err, domain.ErrUpstreamTimeout)`，且**不**满足 `errors.Is(err, domain.ErrNotFound)`；同路径第二次请求仍会回源（上游命中计数 +1，证明**未写负缓存**）。协议层若已有 maven/raw handler 测试夹具，补一条 504 状态码断言。
- **真实缺失不退化**：单成员 404 的 group，`Resolve` 返回 `ErrNotFound`，耗时与 FR-110 基线同量级（3s 内），且负缓存照常写入。
- **无响应上游不拖慢**：一个成员挂起（`<-r.Context().Done()`）、另一个成员快速 404，整体在 **3s 量级**返回，且挂起成员的上游只被请求 1 次。断言的是**耗时上界**；错误身份按 FIX-1 后的语义为该成员的不可判定结果（超时 → 504 一侧），不再要求整体返回 404。对照用例 `TestResolveGroupFast404WithHangingMember`（[asset_service_resolve_test.go](../../apps/server/internal/domain/asset_service_resolve_test.go#L356-L387)）的 <5s 断言进一步收紧。
- **single-flight 不回退**：N 个并发请求读同一 group 同路径大制品，上游各成员命中计数为 1，所有响应体一致。
- **既有测试继续通过**：`asset_service_resolve_test.go`（含 `TestResolveGroupOrderedHit`、`TestResolveGroupFast404WithHangingMember`、`TestResolveGroupFuseSkipsUnreachableMember`、`TestResolveGroupParallelHitFromLaterMember`、负缓存三例）与 `proxy_half_open_test.go` 全绿。**注意**：这几条用例的错误身份断言已随 FIX-1 从「404」改为「504/502」，回归保护的是它们的**耗时上界、上游命中次数、阻断状态与恢复语义**，不是旧的 404 返回值；本 FR 不得把它们改回 404。
- **质量门**：`go test -race ./...` 与 `bash scripts/check.sh` 全绿。

### 5.2 实机验收（需用户确认）

> **仅在本地环境与测试站进行，禁止部署到正式站。** 正式站的大制品回源验证由用户在其确认后另行安排，不属于本次交付的前置条件。

手动复验步骤（测试站/本地）：

1. 起实例，配置一个 group 仓库（如 `maven-public`），其中一个 proxy 成员指向含 15MB universal jar 的上游；`JIAN_UPSTREAM_TIMEOUT` 保持默认 30s。
2. `curl -sS -o /dev/null -w '%{http_code} %{time_total}\n' <group>/<15MB jar 路径>` → 期望 **200**，耗时约与 `体积 ÷ 实际带宽` 相符（数秒到数十秒皆正常）。
3. 校验和比对：`curl <group>/<该 jar>.sha1` 与上游的 `.sha1` 内容一致；本地 `sha1sum` 与之一致。
4. 同坐标的 `.pom` 仍 200（回归）。
5. 缺失路径对照：`curl` 一个确实不存在的 jar → 3s 量级 **404**，且第二次请求同样快（负缓存生效）。
6. 无响应上游对照：临时把一个成员指向不可达地址，确认 group 读不被该成员拖到远超 3s（整体秒级）。
7. 重复步骤 2 两次，确认第二次走本地缓存、耗时明显下降（内容未被反复回源）。
8. 观察日志：不应出现对该 15MB 路径的 `context deadline exceeded` / 负缓存写入记录。

## 6. 风险 / 待定

### 6.1 风险

- **整体响应时长上界变大**：路径 B 下若某成员「头很快、body 很慢」，group 整体响应会长到接近 `JIAN_UPSTREAM_TIMEOUT`（默认 30s）。这是本 FR 的**有意取舍**（正确性优先于延迟），且预算由运维可调；但不熟悉的运维可能把它当成新故障，需在 `docs/OPERATIONS.md` 写清。
- **body 读取错误的映射缺口**：现状 `putStagedBlob` 失败原样返回（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1083-L1086)），不经过 `mapUpstreamErr`；若实现期漏补分类，症状会从「404」变成「500」，验收项会失败。已列为任务。
- **看门狗与取消的并发正确性**：新增内层 goroutine + 三路 select 是典型数据竞态高发区，必须 `-race` 覆盖「同时就绪」「取消时内层尚未退出」两条路径。
- **嵌套 group 成员的信号穿透**：内层任一成员的响应头会让外层 `started` 提前触发，外层的确认预算被提前放宽。语义可接受，但会让「外层成员整体不可达」的判定变慢到内层预算之和；见待定 3。
- **落盘超时仍会触发该成员的 auto-block**：`fetchProxyAsset` 的 `default` 分支会把上游失败计入 `recordFailure`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1075-L1078)）。注：body 读取阶段的失败**不会**走该分支（`recordSuccess` 已在落盘前调用），但**响应头阶段**的慢/超时仍可能让整个 proxy 成员进入 40s 阻止窗口，连带该成员其它路径。这属于 FR-155 的范围，本 FR 不改，但实机验收时若观察到「大制品失败后同成员其它制品也 502」，应归因到 FR-155 而非本 FR。
- **测试时长**：3s 确认预算与 15MB@5MB/s 的下载都是真实墙钟时间，新增用例会让 `go test` 变长（数十秒量级）；不引入可注入的假时钟（会偏离「真实路径验证」的初衷）。

### 6.2 待定

1. **maven SNAPSHOT 分支的返回码**：[maven.go](../../apps/server/internal/protocol/maven.go#L208-L231) 在 SNAPSHOT 时间戳解析与字面路径解析都失败时**直接写 404**，不经过 `writeAssetErr`。本 FR 不扩到该分支（属 FIX-1 / 后续修正范围），需在 FIX-1 落地时确认是否一并收敛，否则 SNAPSHOT 大制品仍可能表现为 404。
2. **`started` 信号的命名与挂载点**：spec 给出的 `WithUpstreamStarted` / `markUpstreamStarted` 只是建议；挂载点在 `fetchProxyAsset` 内、`recordSuccess` 之后，实现期若发现更合适的边界（例如放在 `upstream` 层），需保证「未挂载时零副作用」。
3. **多成员确认时的仲裁**：路径 B 下「最快完成落盘者胜」已足够；若未来要求「必须按成员优先级而非速度选定来源」，需要引入确认候选集与顺序仲裁，届时评估是否转向路径 A。
4. **是否需要为落盘阶段单独设上限**：当前直接复用 `JIAN_UPSTREAM_TIMEOUT`（不新增配置）。若实机发现「30s 不够下完特大型制品」，优先由运维调大该值，而不是新增第二套超时配置；若确实需要，另立 FR。
5. **与 FR-156 的对接（确认预算单一来源）**：`groupMemberTimeout` 后续会配置化。本 FR 落地时，看门狗的计时**必须**只读这一个来源（当前的常量 / 未来的配置字段），不得在 `groupGet` 里再硬编码一份 3s，否则配置化后会出现「配置改了但看门狗没变」的静默分歧。同理，FR-156 注入的值只作用于**确认阶段**，不得覆盖落盘阶段的回源整体超时。

### 6.3 范围外（不做）

- **不做自动重试**：确认命中但落盘失败时**不**在内部换成员重试、也不隐式重发上游请求；直接返回 504/502，由客户端重试（重试不会被负缓存挡住，符合 I5）。
- **不做分片下载 / 断点续传**：不引入 Range 请求、不合并分段、不做边下边发的流式透传（当前语义是「先落盘再返回」）。
- **不改组成员顺序语义**：本地快查按成员配置顺序优先、回源并行取最快成功、并列时按下标最小——全都不动（§3.5）。
- **不做跨节点负缓存**：负缓存仍是单节点内存态（[negative_cache.go](../../apps/server/internal/domain/negative_cache.go#L20-L25)），不随复制同步、不共享、不集群一致。
- **不改 `groupMemberTimeout` 的可配置性**：仍是硬编码 3s，配置化属 FR-156。
- **不改 auto-block / 断路器分类**：把「回源慢」排除出不可达判据属 FR-155。
- **不动 maven-metadata.xml 合并的 5s 预算**（[maven.go](../../apps/server/internal/protocol/maven.go#L281-L283)）：那是另一条链路的独立预算。
- **不新增管理界面元素**：解析结果可观测属 FR-157。
