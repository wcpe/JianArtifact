# 功能规格：维护与清理控制台（清理任务队列 / 定向清理 / 管理页面）

> 状态：草拟（待用户审核）　·　关联 PRD：FR-160 / FR-161 / FR-162 / FR-163　·　分支：integration/release-batch-0.13.0
> 依赖：既有 `GET /api/v1/maintenance/storage-health`（只读体检，本批前置）与 `GET/POST /api/v1/maintenance/jobs*`（作业清单与手动触发）

## 1. 背景与目标

线上判断"有没有可回收的垃圾"此前只能登机器 `find` / `du`。测试站实测：**21 个空分片目录**、**10 MB 中断上传残留**、3 个 `pre-restore` 回滚备份——都是真实存在的垃圾，但既没有界面也没有安全的手动清理入口；仅有的三个清理作业（`blob-gc` / `storage-cleanup` / `backup-orphan-cleanup`）只能整体触发、默认每日一次，粒度粗且不可见。

本批交付一个**面向管理员的维护与清理控制台**：看得见垃圾、看得见清理进度与历史、能以受控方式清理。

属于 M3 的运维可见性延伸（清理能力已在 M3 由作业形式交付，本批补齐"人可操作 + 可追溯"的一面）。

## 2. 需求（要什么）

### FR-160 清理任务队列（落库）

- 每次破坏性清理都落一条**任务记录**，含 kind / 状态 / 进度 / 释放字节 / 时间 / 失败原因。
- 状态机：`queued → running → succeeded | failed`；**进程重启时把残留的 `running` 标为 `interrupted`**（如实说明"上次没跑完"，绝不伪装成功）。
- **全局单并发**：已有 `running` 任务时，新的清理请求返回 `409 cleanup_running`，不排队、不并发。
- 历史可查：分页列表 + 单任务详情（进度）。
- 范围内：任务记录、状态机、进度查询、重启收口。
- 范围外：任务取消、任务重试、按任务回滚已删除内容（删除本身不可逆）。

### FR-161 定向清理（预览 + 执行）

四类可回收垃圾，**先预览、后执行**：

| kind            | 目标               | 判定口径                                                                          |
| --------------- | ------------------ | --------------------------------------------------------------------------------- |
| `empty_dirs`    | 活动 blob 分片空壳 | `data/blobs` 下不含任何普通文件的叶子目录（跳过 `tmp` / `quarantine`）            |
| `stale_uploads` | 中断的分片上传     | `data/backup-uploads/<session>` 中**无活动会话**且目录 mtime 早于 idle 阈值的会话 |
| `pre_restore`   | 恢复前回滚备份     | `data/pre-restore-*`，按"保留最近 N 个"，**永远保留最新一个**                     |
| `quarantine`    | 隔离区待回收 blob  | `data/blobs/quarantine/<op>/<hash>` 中**不被待生效恢复引用**的条目                |

- `POST /api/v1/maintenance/cleanup/preview` `{kind, keepLast?}`：**纯只读**，返回 `{kind, items[{path, bytes}], itemCount, freedBytes}`。
- `POST /api/v1/maintenance/cleanup` `{kind, items?, keepLast?}`：异步，**202** + `{taskId}`；进度与历史走 FR-160。
  - `items` 省略 = **整类全收**；给出 `items` = **只收列出的那些**（逐项勾选），但服务端**重新校验每一项仍在白名单与当次预览口径内**，不接受客户端自带路径直接删除。
  - **该操作只把目标移入回收站（FR-163），不做物理删除**——误点时可用 `restore` 原样取回。
- 范围内：四类清理（移入回收站）、两种粒度（整类 / 逐项）。
- 范围外：孤儿 blob（归 `blob-gc` 作业）、业务数据（asset / blob 在用内容）任何形式的清理、以及物理删除（归 FR-163 的彻底删除）。

### FR-163 回收站（可逆）

一句能力：所有定向清理先进回收站，**可恢复、可彻底删除、有保留期**。

- 存储：`data/trash/<entryId>/<原始相对路径>`，按条目隔离，避免同名冲突；数据库记录原始绝对路径、kind、字节数、移入时间、所属任务。
- 状态：`staged → (restored | purged)`；`staged` 期间占用磁盘但**不计入业务数据**。
- 端点（非契约，仅管理员）：
  - `GET /api/v1/maintenance/trash`：分页列表（kind / 原始路径 / 字节 / 移入时间 / 可恢复性）
  - `POST /api/v1/maintenance/trash/restore` `{ids[]}`：恢复指定条目；**目标位置已存在则跳过并如实报冲突**，不做覆盖
  - `POST /api/v1/maintenance/trash/purge` `{ids[]}`：物理删除指定条目（**不可逆**）
  - `POST /api/v1/maintenance/trash/purge-all`：清空回收站（**不可逆**，需确认词）
- **保留期**：`JIAN_TRASH_RETENTION_DAYS`（默认 7 天）；到期条目由新作业 `trash-gc` 自动物理删除。设 0 = **不自动清理**（只保留手动彻底删除）。
- **容量护栏**：回收站总量超过 `JIAN_TRASH_MAX_BYTES`（默认 2 GiB）时，`cleanup` 直接拒绝并提示先清理回收站——避免"清理"把磁盘顶满。
- 范围外：跨实例同步、按内容去重、回收站内的搜索。

### FR-162 维护与清理页面（前端）

- 新路由 `/maintenance`（`RequireAuth + RequireAdmin`），侧栏「管理」分区加入口。
- 四个区块：
  1. **存储体检**：渲染体检全部指标；四类各带 `[预览清理]`。
  2. **清理任务**：进行中任务的进度条 + 历史列表（kind / 状态 / 释放字节 / 耗时 / 失败原因）。
  3. **回收站**：条目列表（kind / 原始路径 / 大小 / 移入时间 / 剩余保留天数）+ `[恢复]` / `[彻底删除]` / `[清空回收站]`。
  4. **维护作业**：作业清单（间隔 / 最近执行 / 失败次数 / 是否运行中）+ `[立即执行]`。
- **三层防护**（作用于 `cleanup` 与 `purge` 两类破坏性动作）：预览清单（可逐项勾选）→ 二次确认弹窗（写清条目数与预计释放）→ **输入确认词「清理」**才可提交。
- **恢复不做三重防护**：恢复是**反向**操作（把东西放回去），只需一次点击 + 轻确认，否则误删后想取回还要过三道关，反而助长误操作。
- `[立即执行]` 触发既有作业**仍为物理删除**（`blob-gc` / `storage-cleanup` / `backup-orphan-cleanup` 是 M3 已交付的既有行为，不进回收站），界面上必须**明确标注"该操作不可恢复"**，与走回收站的 `[预览清理]` 在视觉与文案上区分开。
- 范围内：上述四区块、三层防护、窄屏可用。
- 范围外：自动清理策略配置（仍由环境变量 + 作业控制）、清理结果的推送通知。

## 3. 设计（怎么做）

### 数据模型（迁移 `0052`）

> **编号定案（`0052`）**：本批与「上游健康分钟表」一度占用同一个号——两批都从 `main` 的
> `0050` 起算，各自取了 `0051`。迁移器按「版本号是否已记录」判断跳过，同号第二个**永远不会执行**，
> 且迁移连续性测试会直接报「版本号重复」。现按「proxy 线保留 `0051`、本批递增」定案：
> `0051_upstream_health_minute.sql` 不动，本表改为 `0052_clean_task_and_trash.sql`，编号
> `0050 → 0051 → 0052` 连续。
>
> 部署时留意测试站的既有记录（**先看这段，别急着「修」**）：那边 `schema_migrations` 里 `0051`
> 记的是上游健康分钟表、`0052` 记的是本批建表，两张表都已存在。因此本批部署后 `0052` 被视为
> 已应用而跳过——这是**预期行为**。不要为了「对齐版本号」去删记录或丢表：那会连带丢掉回收站里的
> 验收数据，并让另一批的 `0051` 记录一起错位。
>
> **需求编号定案（`FR-160`~`FR-163`）**：本批与代理线一度在 `FR-158` / `FR-159` 上撞号——两条线
> 都从 `main` 的 `FR-153` 之后起算。按「proxy 线保留、本批递增」定案后，本批四条取
> `FR-160`~`FR-163`，紧接代理线的 `FR-159`，**不留空号**。
>
> 为什么强调不留空号：一度把本批写成 `FR-162`~~`FR-165`，理由是「proxy 占了 154~~159，
> 那本批就从 162 起」——但 `160` / `161` 本身是空的，那样写会凭空造出一段无归属的空洞，
> 读 PRD 的人会立刻问「160/161 去哪了」，未来也可能被误当成保留号。**编号还没合并进
> `main` 时，它的取值是完全自由的，就该取最紧的连号，没有理由留洞。**

```sql
CREATE TABLE clean_task (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  kind             TEXT NOT NULL,              -- empty_dirs|stale_uploads|pre_restore|quarantine
  status           TEXT NOT NULL,              -- queued|running|succeeded|failed|interrupted
  total_items      INTEGER NOT NULL DEFAULT 0,
  processed_items  INTEGER NOT NULL DEFAULT 0,
  freed_bytes      INTEGER NOT NULL DEFAULT 0,
  error_message    TEXT,
  created_at       TEXT NOT NULL DEFAULT (datetime('now')),
  started_at       TEXT,
  finished_at      TEXT
);
CREATE INDEX idx_clean_task_status ON clean_task(status);
CREATE INDEX idx_clean_task_created ON clean_task(created_at);

-- 回收站条目：一次 cleanup 的每一项一条记录，restore / purge 都以此为准。
CREATE TABLE trash_entry (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id          INTEGER NOT NULL REFERENCES clean_task(id) ON DELETE CASCADE,
  kind             TEXT NOT NULL,
  original_path    TEXT NOT NULL,              -- 移入前的绝对路径，供恢复还原
  trash_path       TEXT NOT NULL,              -- 回收站内的落盘位置
  is_dir           INTEGER NOT NULL DEFAULT 0,
  bytes            INTEGER NOT NULL DEFAULT 0,
  status           TEXT NOT NULL,              -- staged|restored|purged
  created_at       TEXT NOT NULL DEFAULT (datetime('now')),
  resolved_at      TEXT
);
CREATE INDEX idx_trash_entry_status ON trash_entry(status);
CREATE INDEX idx_trash_entry_created ON trash_entry(created_at);
```

字段形式与 `migration_task` 对齐（status / 进度 / 错误 / 时间戳），不另造抽象。

### 回收站机制（FR-163）

- **移入而不是删除**：`cleanup` 逐项 `rename` 到 `data/trash/<entryId>/`，同盘 rename 是原子的、不复制字节；跨界（跨文件系统）时退化为 copy + 校验 + unlink，并如实记录。
- **恢复**：把 `data/trash/<entryId>/...` 移回 `original_path`。**目标已存在则跳过该条并计入 `conflicts[]`**——绝不覆盖（覆盖等于一次删除）。
- **彻底删除**：仅删 `data/trash/<entryId>/` 与其记录；**不触碰** `original_path`。
- **保留期与容量**：见 FR-163 的两项环境变量；`trash-gc` 作业按保留期回收，默认每日一次。
- **为什么回收站不记录空目录以外的东西**：四类清理本来就只针对"已确认可回收"的目录/文件，把它们的**原位置**记下来就足以完全复原；不需要内容级快照（那会把回收站变成备份系统）。

### 领域层

- `CleanTaskRepo`（仓储）：`Create / MarkRunning / UpdateProgress / MarkSucceeded / MarkFailed / MarkInterruptedOnStartup / List / Get`。
- `CleanupService`（领域）：
  - `Preview(kind, keepLast)` → 只读扫描，产出待删清单。
  - `Execute(kind, items, keepLast)` → 建任务记录（`queued`）→ 后台 goroutine 执行 → 逐项更新进度 → 终态。
  - `ReconcileStartup()` → 把 `running` 全部标 `interrupted`（启动早期调用，与既有 `ReconcileStartup` 同处）。
- **单并发守卫**：进程内互斥 + 数据库 `running` 检查双保险（重启后 DB 里不会残留 `running`，因为启动即收口）。

### 安全边界（本批最高风险点）

1. **路径白名单根**：只允许 `data/blobs`（空目录）、`data/backup-uploads`（会话目录）、`data/pre-restore-*`（整目录）、`data/blobs/quarantine`（op/hash）。用具名根集合判定，**不做字符串前缀比较**（避免 `../` 与相似前缀绕过）。
2. **不跟随符号链接**：删除前 `Lstat` 判定，遇到 symlink 直接跳过并计入 `skipped`。
3. **执行时重校验**：`items` 由客户端回传时，逐项重新走 `Preview` 口径，不在清单内的**拒绝执行整批**（不做"部分信任"）。
4. **业务数据零接触**：四类都只涉及"已确认可回收"的目录/文件，任何 `asset` 行与在用 blob 都不在候选集内。
5. `pre_restore` **永远保留最新一个**，即使 `keepLast=0`。
6. `stale_uploads` 的 idle 阈值复用既有上传会话的过期口径，不新造常量；**有活动会话的目录绝不删**。

## 5. 验收标准

### 自动化（必须全绿）

- **重启收口**：写入一条 `running` 任务后重启进程 → 该记录变 `interrupted`，不出现"永远 running"。
- **单并发**：存在 `running` 时再次触发 → `409 cleanup_running`，且不新增 `running` 记录。
- **预览只读**：预览前后逐项比对磁盘，**无任何文件被删除或改动**（变异验证：让 Preview 顺手删一项，用例必须转红）。
- **可逆性（本批新增的硬不变量）**：`cleanup` 之后原始路径消失、`trash` 里出现对应条目；`restore` 之后**内容与清理前逐字节一致**（对目录递归比对）。变异验证：把 `stage` 改成直接 `RemoveAll` → 用例必须转红。
- **恢复不覆盖**：目标位置已存在时该条跳过并出现在 `conflicts[]`，且**原目标内容未被改动**。
- **彻底删除不碰原位置**：`purge` 只删回收站副本与记录，`original_path` 无论存在与否都不被触碰。
- **容量护栏**：回收站超 `JIAN_TRASH_MAX_BYTES` 时 `cleanup` 拒绝，提示先清理回收站。
- **保留期**：`JIAN_TRASH_RETENTION_DAYS=N` 时，`trash-gc` 只删超过 N 天的 `staged` 条目；设 0 时不自动清理。
- **白名单逃逸**：`../` 路径、白名单外目录、符号链接 → 拒绝或跳过，且**不产生删除**（变异验证：换成字符串前缀比较后用例转红）。
- **逐项勾选**：`items` 只删列出的项；混入一个不在预览清单的路径 → 整批拒绝。
- **业务零影响**：任一类清理前后，`asset` 行数与在用 blob 数不变。
- **pre-restore 保底**：`keepLast=0` 时仍保留最新一个目录。
- **stale_uploads 安全性**：存在活动会话时该会话目录不被删。
- 前端：三层防护顺序可验证（未输入确认词时确认按钮 disabled；取消不发请求）；任务进行中轮询推进、终态停止轮询；四类按钮与体检数字一致。

### 实机（需用户确认）

- 在测试站对**真实的 21 个空分片目录**与 **10 MB 中断上传**跑通：预览数量与执行结果一致、`freed_bytes` 与 `du` 差值吻合、业务数据无变化。
- 浏览器复核 `/maintenance` 页三个区块与三层防护交互。

> **手工造隔离区数据时的硬约束（已在测试站踩过一次）**：`blob_quarantine.blob_hash`
> 必须是**合法 sha256（64 位十六进制）**。写入非法值（如 `aabbccdd`）后再重启，启动流程的
> 「恢复遗留资产操作」会因「非法的 blob 哈希」直接拒绝启动——表现为**服务起不来并无限重启**，
> 而报错发生在迁移之后、监听之前，日志里只有一行业务错误，很容易被误判成二进制有问题。
> 另外：`status='staged'` 的记录会被启动恢复流程接管（判为需回滚并改成
> `rolled_back`/`restored`），所以「隔离区跳过」这条判据**不能靠重启前写库来验证**——
> 必须在服务运行期写入，随即查询预览，否则数据会先被启动流程消化掉，看起来像判据失效。

## 6. 风险 / 待定

- **回收站不是备份系统**：它只记录"原位置"，用于撤销一次清理动作；文件内容本身没有额外副本，若原清理后又发生同名写入，`restore` 会因目标存在而跳过（不覆盖）。这一点必须写进界面文案，避免被当成备份来依赖。
- **回收站也会占盘**：默认保留 7 天、上限 2 GiB，超限时拒绝新清理而不是偷偷淘汰（静默删除等于绕过用户确认）。
- **触发既有作业仍是物理删除**：`blob-gc` / `storage-cleanup` / `backup-orphan-cleanup` 是 M3 已交付行为，不进回收站；界面必须标注"不可恢复"，与走回收站的清理明确区分。若后续要求作业也进回收站，需单独立 FR（会改变自动清理的磁盘回收目标）。
- **隔离区**：可能是失败回滚的中间态。当前口径是"只收不被待生效恢复引用的条目"，若实现中发现该判据不可靠，则**降级为只展示、不提供清理入口**并回报。
- **stale_uploads 的 idle 阈值**：对齐既有上传会话过期口径；若既有口径不存在，需新定常量并回写到本规格。
- **跨文件系统 rename**：`data/trash` 与目标同在一个数据目录下，正常情况同盘；若运维把 `JIAN_DATA_DIR` 下的 `trash` 做成单独挂载，rename 会失败，实现时需退化到 copy + 校验 + unlink 并记录。
- **前端轮询**：仅在有 `running` 任务时轮询，终态立即停止（避免把运维页变成持续负载）。
