# 功能规格：代理解析结果可观测（FR-157）

> 状态：草拟　·　关联 PRD：FR-157　·　分支：feature/fr157-proxy-resolve-observability　·　依赖：FIX-1（失败原因分类）

## 1. 背景与目标

解析失败「是不是确认不存在」这个判定，代码里**已经有了**，只是从来没有对外露过：

- [asset_service.go](../../apps/server/internal/domain/asset_service.go#L82-L92) 定义了 `ResolveFailureStatus` 与两个取值 `ResolveFailureConfirmed`（已确认上游或本地资源不存在）与 `ResolveFailureUncertain`（失败可能由离线、阻止窗口或上游故障导致）；
- 分类经请求上下文传递并回读：[`recordResolveFailure`](../../apps/server/internal/domain/asset_service.go#L116-L124) / [`ResolveFailureFromContext`](../../apps/server/internal/domain/asset_service.go#L107-L114)；
- 但它的**唯一消费点**是「要不要写 404 负缓存」——见 [groupGet 的收尾分支](../../apps/server/internal/domain/asset_service.go#L1364-L1370)（`uncertain` 为真则不写，否则写）与 [fetchProxyAsset 的上游错误分支](../../apps/server/internal/domain/asset_service.go#L1062-L1079)；
- 除此之外，这个判定**不进 API 响应、不进日志、不进指标**。

因此运维面对一条 404 时无法回答：这是「上游确认没有这个制品」，还是「某个成员超时 / 被熔断 / 离线被跳过，可能只是暂时不可用」？只能靠猜或者去翻上游访问日志。

**目标（对用户）**：

1. **指标上分得开**：解析失败按 `confirmed` / `uncertain` 分区计数，让「异常失败占比」变成可告警的曲线。
2. **单次失败查得清**：当一次解析被判定为「不可判定」时，留下一条带仓库、路径、触发成员与错误类别的中文诊断行，能直接看出「是超时还是不存在的结论」。
3. **负缓存看得见、清得掉**：目前 [negative_cache.go](../../apps/server/internal/domain/negative_cache.go) 只有 `hit` / `add` / `remove`，没有任何查看或清理入口；排查「明明上游有了却还是 404」只能重启进程。

**边界（本 FR 只做可观测，务必先读）**：本 FR **不改返回码**（Confirmed → 404 / Uncertain → 502、504 的映射属 FIX-1 与 FR-154）、**不改超时策略**（`groupMemberTimeout`、`JIAN_UPSTREAM_TIMEOUT` 不动）、**不改阻断语义**（`proxyHealth` 状态机与退避曲线不动）。任何一处行为改变都不属于 FR-157。

## 2. 需求（要什么）

### 2.1 解析结果指标

- 新增 counter，按解析失败结论分区：`confirmed` / `uncertain`，闭集枚举。
- 新增 gauge，报告当前负缓存条目数（无标签）。
- 与既有 `jianartifact_upstream_block_events_total{reason}` / `jianartifact_upstream_blocked_repositories` **互不重命名、互不合并**：前者是「阻断状态机事件」维度，本条是「请求解析结果」维度，口径见 `docs/specs/0.12.0-upstream-circuit-breaker.md` §3.3。
- 沿用既有指标族约定：即使无样本也输出 `# HELP` / `# TYPE`。
- **范围外**：按仓库 / 路径打标签（违反标签基数约束，见 [ARCHITECTURE.md 指标导出](../ARCHITECTURE.md#L100)）；解析**成功**计数（已由 `jianartifact_protocol_requests_total` 覆盖）；负缓存命中率指标。

### 2.2 解析失败诊断

- 当一次解析最终被判为 `uncertain` 时，输出**一条**中文诊断行（不是每个成员一条），包含：仓库名、路径、结论、触发成员及其类别、上游 host、耗时。
- `confirmed`（正常的 404 流量）**不输出诊断行**——否则爬虫与错误配置的客户端会把日志刷满。
- 诊断信息不得包含凭据、上游认证信息、内网地址细节（见 §3.6）。

### 2.3 负缓存可视化与清理

- 能查看当前负缓存：条目总数、TTL、条目摘要（仓库、路径、写入时间、剩余 TTL）。
- 能清理：全清 / 按仓库清 / 按仓库+路径精确清。
- **先补条目上限**再做暴露（理由见 §3.5）；无上限的映射直接对外可视化，等于把一个无界增长的结构挂在查询接口后面。

### 2.4 范围外（不做）

- 不做全链路追踪（tracing）、不做持久化负缓存、不做诊断中心 UI、不做按路径的指标标签。
- 不改返回码、不改超时、不改阻断语义（见 §1 边界）。

## 3. 设计（怎么做）

### 3.1 三种可观测形态：数据来源与生命周期

| 形态       | 数据来源                                                   | 生命周期                               | 能回答的问题                              |
| ---------- | ---------------------------------------------------------- | -------------------------------------- | ----------------------------------------- |
| 指标       | 顶层解析出口读回的 `ResolveFailureStatus` + 负缓存实时条数 | 进程内累计，重启归零                   | 「最近一小时不可判定失败占多少」          |
| 诊断日志   | 同一结论 + 解析过程中累积的成员明细                        | 单次请求，写一次即弃（进既有日志采集） | 「这一条为什么不是确认不存在」            |
| 负缓存 API | `negativeCache` 的内部映射快照                             | 条目 TTL 60s，纯内存，重启即清         | 「这个路径现在被钉成 404 了吗，是谁写的」 |

三者的共同前提是同一个已有判定，不新增第二套「为什么失败」的逻辑——这是本 FR 不重复造轮子的关键。

### 3.2 指标

**新增指标（拟）**：

| 指标名                                | 类型    | 标签                                      | 说明                                   |
| ------------------------------------- | ------- | ----------------------------------------- | -------------------------------------- |
| `jianartifact_resolve_failures_total` | counter | `resolution` ∈ {`confirmed`, `uncertain`} | 解析失败的结论分区计数                 |
| `jianartifact_negative_cache_entries` | gauge   | 无                                        | 当前负缓存有效条目数（清理过期后统计） |

标签名刻意取 `resolution` 而非 `status`：既有 `jianartifact_protocol_requests_total{status}` 的 `status` 是 HTTP 状态码，同名不同义会让 PromQL 阅读者误判。两个取值直接对应 `ResolveFailureStatus` 的两常量，**`ResolveFailureUnknown` 不计样本**（没有结论就不是失败结论）。

**基数**：2 条序列；仓库名 / 路径 / 成员名一律不进标签，与 [metrics.go 里 `blockedRepositoriesFamily` 无标签的理由](../../apps/server/internal/metrics/metrics.go#L373-L388)同源。

**采样点唯一（容易做错的地方）**：`recordResolveFailure` 会在递归层、成员层（[groupGet 给每个成员单独挂 recorder](../../apps/server/internal/domain/asset_service.go#L1334-L1341)）和同一请求的多个阶段被多次调用，且语义是「一旦 uncertain 就不再被覆盖」。因此**不得在 `recordResolveFailure` 内部累加指标**，否则一次请求会被计成多次。指标只在**顶层解析出口**记一次：即 `Resolve` / `ResolveWithRepo` / `ResolveIndex` 失败返回处（[asset_service.go L876-L902](../../apps/server/internal/domain/asset_service.go#L876-L902)），读回最终结论后累加。

**顶层出口必须自己保证有 recorder**：现状是**只有协议层**（[maven.go](../../apps/server/internal/protocol/maven.go#L141-L163)）会给 ctx 挂 `WithResolveFailure`，其余调用点 `ResolveFailureFromContext` 直接返回 `Unknown`。所以顶层出口要在「ctx 上尚无 recorder」时自行挂一个（只挂不覆盖），否则这些路径的失败永远读不到结论、指标系统性漏计。

**早期返回不计入**：`Resolve` / `ResolveWithRepo` 对空路径与尾斜杠路径直接 `ErrNotFound`（[L876-L892](../../apps/server/internal/domain/asset_service.go#L876-L892)），不写任何结论。这部分**保持原状、不进指标**——在此处补一个 `Confirmed` 会连带改变 maven 的 `notFound` memo 行为（该 memo 读的正是同一个结论），属于本 FR 边界之外的语义改动。

**接入范式**：与 [proxy_health.go 的 `UpstreamBlockRecorder`](../../apps/server/internal/domain/proxy_health.go#L60-L65) 完全同构——`domain` 定义小接口，装配层注入 `*metrics.Registry`，`nil` 表示不记录；不得让 `domain` 反向依赖 `api` 或 `metrics`。Gauge 取数走 `metricsExposition.SetBlockedRepositories` 那种回调范式（见 [wiring.go L329-L341](../../apps/server/cmd/jianartifact/wiring.go#L329-L341)），由 `AssetService` 暴露一个只读内存的方法（对齐 `BlockedUpstreamCount`，[asset_service.go L238-L241](../../apps/server/internal/domain/asset_service.go#L238-L241)）。

**与阻断事件的边界**：一条上游超时**可能同时**让 `jianartifact_upstream_block_events_total{reason="upstream_error"}` 加一、让 `jianartifact_resolve_failures_total{resolution="uncertain"}` 加一。这不是重复计数，是两个不同事实（状态机发生了一次阻止事件 / 这个请求的解析结论是不可判定），**但它们不可相加、不可互相推导**，须在 OPERATIONS 口径里写明。FR-155 若为阻断事件新增 `upstream_timeout` 取值，那是 `upstream_block_events_total{reason}` 的闭集扩展，**不迁移到本指标**；本指标的取值集合保持 `confirmed` / `uncertain` 两值不变。

### 3.3 诊断读取：日志 vs 管理 API

两个方案都评估过，结论是**只做日志，不做「最近解析失败」管理 API**。

**推荐方案 (a)：结构化诊断日志**

- 触发条件：**仅 `uncertain`**。`confirmed` 是正常 404 流量，逐条记录会造成日志洪水（扫描器、Gradle 反复探测缺失子模块都是这个形态）。
- 输出位置：顶层解析失败出口（§3.2 的同一处），一个请求一行。
- 需要把成员明细带上来：`WithResolveFailure` 挂的记录器（[L96-L104](../../apps/server/internal/domain/asset_service.go#L96-L104)）当前只存一个 `status` 字符串，需**追加**明细字段（成员名 + 类别，带条数上限防内存膨胀）；`recordResolveFailure` 的「uncertain 不被覆盖」语义保持不变，`ResolveFailureFromContext` 签名不变，因此 [maven.go 里既有消费点](../../apps/server/internal/protocol/maven.go#L141-L163)无需改动。
- 行格式沿用仓库既有风格（`log.Printf` + 中文 + 严重级前缀，见 [restart_service.go](../../apps/server/internal/domain/restart_service.go#L282-L285) 的 `ERROR` / `INFO` 写法）。

```text
WARN 代理解析不可判定 repo=<仓库名> path=<路径> resolution=uncertain elapsed_ms=<N>
     member=<成员名>:<类别> member=<成员名>:<类别> upstream_host=<scheme://host>
```

- 类别闭集（拟，全部来自既有代码分支，不是新分类）：
  - 回源侧：`timeout`（`ErrUpstreamTimeout`）、`gone`（410）、`upstream_error`（其余 `ErrUpstream`）；
  - 跳过侧：`offline`（成员 `Online=false`）、`blocked`（`shouldBlock` 命中）、`member_unknown`（成员名解析失败）、`not_proxy`（成员类型非 proxy）；
  - 兜底：`unknown`。
- **为什么不选 (b) 管理端「最近解析失败摘要」**：它需要在进程内新增一个有界环形缓冲（容量、过期、并发、重启归零语义都要定），再走一遍契约 + `task gen` + devmock + 鉴权 + 测试，**而它能回答的「为什么这条 404」日志已经能回答**，且日志本来就在既有日志采集里、天然带时间轴与聚合能力。为一个与日志等价的只读视图新增一类有状态内存结构与一份契约，是典型的为可观测造仪表盘。负缓存不同：清理动作**只能**通过 API 做，日志给不了，所以只有它为 API 花了额度（§3.4）。

### 3.4 负缓存查看与清理 API

**拟新增两个端点**（契约真源 `api/openapi.yaml`，摆在既有维护端点组里，与 [`/api/v1/maintenance/jobs`](../../api/openapi.yaml#L2110-L2128) 同一分组）：

```text
GET  /api/v1/maintenance/negative-cache
DELETE /api/v1/maintenance/negative-cache
```

鉴权：沿用根级 `security: bearerAuth`（[openapi.yaml L13-L14](../../api/openapi.yaml#L13-L14)），处理器内 `requireAdmin` —— 与 [`RecheckRepositoryConnection`](../../apps/server/internal/api/repository_handlers.go#L397-L426) 完全同构。

**GET 查询参数**：`repo`（仓库名，可选）、`path_prefix`（可选）、`limit`（可选，默认 100，上限 500）。

**GET 响应 `NegativeCacheSummary`**：

| 字段                                          | 类型              | 说明                                                          |
| --------------------------------------------- | ----------------- | ------------------------------------------------------------- |
| `total`                                       | integer           | **过滤前**的有效条目总数（清理过期后统计）                    |
| `ttlSeconds`                                  | integer           | 当前负缓存 TTL                                                |
| `maxEntries`                                  | integer           | 条目上限（§3.5 前置改动引入）                                 |
| `items[]`                                     | array             | 过滤后按写入时间升序的前 `limit` 条                           |
| `items[].repositoryId` / `items[].repository` | integer / string  | 仓库 ID 与名称                                                |
| `items[].path`                                | string            | 制品路径（原样，理由见 §3.6）                                 |
| `items[].writtenAt`                           | string(date-time) | 写入时间（`repositoryId` + `path` 唯一确定条目，无需额外 id） |
| `items[].remainingSeconds`                    | integer           | 剩余 TTL                                                      |

**DELETE 语义**：无参数 = 全清；仅 `repo` = 按仓库清；`repo` + `path` = 精确清。响应 `{ "removed": <int> }`。仓库不存在 → 404；参数非法 → 400。

**审计**：清理是管理员对运行态记忆的破坏性动作，按既有范式写一行审计（`h.AuditLog`，对齐 `repo.recheck`）；**查看不写审计**（只读、无副作用）。

**前端**：**本期只做 API，不做 UI**。理由：负缓存是 60s 生命周期的进程内性能缓存，清理是排障时的一次性动作；为它造一个页面要连带导航项、i18n 中英文案、空态与表格交互，收益远低于一句 `curl`。等真的出现「运维必须自助操作」的诉求再做页面，届时以真实交互需求驱动设计比现在拍脑袋更省。

**需要重新生成的产物**：

- 契约：`api/openapi.yaml` 新增两路径与两个 schema；
- Go 侧：`cd apps/server && task gen`（oapi-codegen 重生成 `internal/api/api.gen.go` 的类型与 `ServerInterface` 方法）；
- TS 侧：`pnpm --filter @jianartifact/devmock gen`（重生成 `schema.gen.ts`，前端 `api/types.ts` 经其复用自动获得新类型）；
- 文档：`docs/API.md` 端点分组、`docs/OPERATIONS.md` §1.4 指标口径（[L268-L278](../OPERATIONS.md#L268-L278)）与排障条目、`docs/specs/README.md` 索引。

### 3.5 负缓存容量：必须先补上限（前置改动）

现状（[negative_cache.go](../../apps/server/internal/domain/negative_cache.go)）：`map[string]time.Time`，无任何上限；过期条目**只在同键命中时**被顺带删除（`hit` 中的 `delete`），写入（`add`）不做任何清理。

这带来两个必须先处理的问题：

1. **过期条目会长期残留**：一个 404 路径若之后再也没有被请求，其条目过期后**永远不会被删除**，直到进程重启。高基数缺失路径的站点（爬虫、错配客户端）上这是持续增长的内存，且增长量与时间成正比。
2. **查询接口要遍历全表**：可视化的 `total` 与过滤必须在 `negativeCache.mu` 下走一遍映射；无上限时，一次管理查询最坏会与所有读请求抢锁。有上限后才能保证遍历代价有界。

**结论：必须先补上限保护，再暴露查看/清理**。最小方案（不引入 LRU 这类被 [0.7.1-404-negative-cache.md](0.7.1-404-negative-cache.md) §2 列为范围外的复杂策略）：

- 引入 `maxEntries`（常量 + `SetNegativeCacheMaxEntries` 测试钩子，对齐既有 `SetNegativeCacheTTL`，[asset_service.go L243-L244](../../apps/server/internal/domain/asset_service.go#L243-L244)）；
- `add` 时若已达上限：**先做一次全量过期清理**；仍满则**淘汰写入时间最早的一条**；
- 淘汰只影响命中率，不影响正确性——负缓存本就是纯优化，丢掉条目最坏是多一次回源；
- 默认上限取值与「是否经环境变量外露」列入 §6 待定（TTL 配置化属 FR-156 口径，本 FR 不抢它的配置面）。

### 3.6 脱敏与安全（对齐 NFR-06）

| 字段                       | 处理                                                                   | 理由                                                                                                                                                                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 完整路径                   | **日志与 API 均给原样**，但须转义控制字符（CR/LF 等）并截断至 512 字符 | 管理员本就能通过 [`GET /api/v1/repositories/{name}/assets`](../../api/openapi.yaml#L1180-L1201) 看到全量 `AssetSummary.path`（[schema](../../api/openapi.yaml#L5068-L5092)），诊断里给路径不构成新增暴露面；但路径来自客户端，不转义会造日志注入（伪造诊断行）               |
| 上游 URL                   | **只输出 `scheme://host`**                                             | `RemoteURL` 已被校验为无 userinfo、无 query、无 fragment（[repository_service.go L535-L541](../../apps/server/internal/domain/repository_service.go#L535-L541)），故不含凭据；但 path 段常含团队/项目名，属不必要暴露。仓库自建域名可能落内网，host 仍保留——否则诊断失去意义 |
| `credentialRef`            | **不输出名称，只表达「已配置 / 未配置」**                              | 它是指向环境变量 `JIAN_UPSTREAM_CREDENTIAL_<名称>` 的引用名，NFR-06 的脱敏清单覆盖凭据与其用户名，引用名无诊断价值                                                                                                                                                           |
| Authorization / 上游响应体 | **绝不输出**，连摘要也不给                                             | NFR-06 明文禁止；诊断只需要「超时 / 4xx / 5xx」这类类别                                                                                                                                                                                                                      |
| 成员名                     | **可输出**                                                             | 成员是仓库（管理端可见对象），排障必须知道是哪个成员拖垮了结论                                                                                                                                                                                                               |
| 用户名 / 令牌 / 请求头     | **不输出**                                                             | NFR-06 明文禁止                                                                                                                                                                                                                                                              |

响应与日志**共用**一个格式化助手（新增），避免两处各写一套裁剪逻辑后走样；仓库内目前未发现可复用的 host 脱敏工具（`url.Parse` 调用点均为校验用途），需新增。

### 3.7 模块与依赖

```text
config（不新增配置项；maxEntries 默认值待定）
  ↓
cmd/jianartifact/wiring.go（注入 metrics.Registry 到解析失败记录器 + 负缓存条目数取数回调）
domain（negative_cache.go 上限与快照/清理；asset_service.go 顶层出口记录指标与诊断行）
  ↓
metrics（新增 counter + gauge，沿用 /metrics 暴露与「无样本也出 HELP/TYPE」）
  ↓
api（新增两个维护端点 → task gen → mock_handler 适配 → devmock gen）
```

依赖方向仍为 `api → domain → repository/blobstore/upstream`，`domain` 不感知 `metrics` 与 `api`，符合 [ADR-0010](../adr/0010-proxy-cache-singleflight-group-routing.md) 与分层单向依赖约束。

## 5. 验收标准

### 5.1 单元与集成（须全绿）

- **能区分 confirmed 与 uncertain**：构造「上游 404 的缺失路径」→ 结论 `confirmed`、指标 `resolution="confirmed"` 加一、**无**诊断行；构造「成员上游 hang 超过 `groupMemberTimeout`」→ 结论 `uncertain`、指标 `resolution="uncertain"` 加一、诊断行含 `cause`/类别为超时且**不**出现 `confirmed` 字样的误导表述。
- **一次请求只计一次**：group 多成员同时失败时，`confirmed`/`uncertain` 计数各只加一（钉住采样点唯一，防递归层与成员层重复累加）；未经协议层挂 recorder 的调用路径（直接 `ResolveWithRepo`）也能正常计数（钉住顶层自挂载）。
- **负缓存查看**：写入条目后 GET 能看到对应 `repository` / `path` / `writtenAt` / `remainingSeconds`；`repo` 与 `path_prefix` 过滤生效；`total` 为过滤前总数；`limit` 上限生效。
- **负缓存清理后立即回源（关键）**：用计数的假上游钉住——清理同路径后再请求，上游确实被再访问一次（不是返回缓存 404）；按仓库清与全清各自只影响目标范围。
- **端点鉴权与错误**：非管理员 → 403；仓库名不存在 → 404；`limit` 超上限 → 400 或截断（按契约实现二者择一并钉住）。
- **新指标**：无样本时仍输出 `# HELP` / `# TYPE`（沿用既有约定）；闭集外取值被忽略（不新增序列）；`jianartifact_resolve_failures_total` 与 `jianartifact_upstream_block_events_total` 在同一次上游故障下各自累加、互不改写标签或数值。
- **脱敏断言**：诊断行与 API 响应中不出现 `credentialRef` 名称、`Authorization`、上游 URL 的 path/query；构造含换行与控制字符的请求路径 → 日志仍是单行（注入防守）。
- **上限（若本 FR 补了上限）**：`maxEntries=3` 时连续写入 4 条不同路径，条目数不超过 3，且被淘汰的是写入时间最早的一条；过期条目在 `add` 触发清理时被真实删除（内存不随时间无限增长）。
- 全量质量门（`scripts/check.sh`）与 `-race` 全绿。

### 5.2 实机验收（需用户确认）

> **硬约束：只在本地与测试站进行，禁止部署正式站。**

1. 本地起一个实例 + 一个「慢上游」（可用带 `sleep` 的临时 HTTP 服务或受控代理），配置一个 proxy 仓库指向它，另配一个 group 仓库包含该成员。
2. 请求 group 仓库下一个只有慢上游才有的路径，使其触发成员超时；对照诊断输出，确认它明确指向**超时 / 不可判定**，而不是「不存在」（这是本 FR 的核心价值）。
3. 请求一个上游明确返回 404 的路径：确认结论为 `confirmed`、**没有**产生诊断行；`GET /api/v1/maintenance/negative-cache` 能看到该条目。
4. 把该路径在上游补上（或让上游开始返回内容），**不清理**负缓存 → 观察仍返回 404；`DELETE /api/v1/maintenance/negative-cache?repo=<名>&path=<路径>` 后立即请求 → 命中新内容。这是「负缓存可清」的用户可见证明。
5. `curl /metrics`：确认 `jianartifact_resolve_failures_total` 出现且两个取值随上述操作增长，`jianartifact_negative_cache_entries` 随条目增减变化；确认与 `jianartifact_upstream_block_*` 并存且口径不混淆。
6. 确认诊断行与 API 响应中不含上游凭据、Authorization 头，上游 URL 只到 host。

## 6. 风险 / 待定

**风险**

- **日志量**：`uncertain` 在「整个上游不可用」时会持续产生。本 spec 规定按请求记一行（不按成员），但若一个高频路径每次都被判不可判定，仍可能放大日志。是否需要限速 / 采样需实机观察后再定，先不引入采样（会破坏「这条为什么 404」的确定性）。
- **上限改动在热路径**：`add` 在满上限时会做一次全量过期清理（持全局锁、O(n)），并发下可能短暂阻塞读路径。仅在满时触发、上限有界，风险可控，但必须 `-race` 验证并观察实机锁竞争。
- **采样点唯一性易被破坏**：只要有人在 `recordResolveFailure` 里顺手加一行指标累加，一次 group 请求就会被计成多次（成员层各有 recorder）。须由测试钉住。
- **`OPERATIONS.md` 现有一处引用与契约不一致**：[L276](../OPERATIONS.md#L276) 提到用 `/api/v1/operations/alerts` 定位自动阻止仓库，但 `api/openapi.yaml` 中并无该路径（告警实际在仪表盘响应的 `alerts` 字段）。本 FR 不依赖该端点，也不在其上扩展；若后续要把诊断与告警串起来，需先修正该处措辞。

**待定（需拍板）**

- **`maxEntries` 默认值与是否外露为环境变量**：本 spec 倾向先写常量 + 测试钩子（不新增环境变量），默认值需按典型缺失路径基数实测后定（初值建议 10000 量级）。TTL 配置化属 FR-156，本 FR 不抢它的配置面。
- **FIX-1 的交付形态**：本 spec 假定 FIX-1 会把「错误类别」（超时 / 其他上游故障）随解析结论一并可得。若 FIX-1 只做返回码映射而不暴露类别，诊断行的 `cause` 需在本 FR 内从 [`mapUpstreamErr`](../../apps/server/internal/domain/asset_service.go#L1428-L1439) 的分支处自行采集——这两种做法对本文第 2、3 节的需求结论无影响，只影响实现落点，开工前需确认。
- **审计动作命名**：拟用维护类动作名（区别于 `repo.recheck` 的仓库维度），需对齐既有审计口径后定稿。
- **上游 host 是否需进一步打码**：本 spec 结论是保留 host（否则诊断无意义，且该地址本就存在于实例配置中）。若安全评审认为内网 host 也不得入日志，需改为按仓库名反查代替 host，届时诊断可读性下降，需重新评估。
- **诊断行是否需要带 request id**：现有协议指标钩子已有请求上下文，若日志采集侧主张按请求串联，可补一个短 id；本期默认不加（YAGNI）。
