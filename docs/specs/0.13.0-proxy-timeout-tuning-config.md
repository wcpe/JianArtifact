# 功能规格：group 成员超时与负缓存 TTL 配置化

> 状态：草拟　·　关联 PRD：FR-156　·　分支：feature/fr156-proxy-timeout-tuning　·　依赖：FR-154（超时语义先定稿）

## 1. 背景与目标

proxy/group 读路径上有两个决定「失败有多快、失败多久被记住」的数值，目前都是**硬编码常量**，运维与现场调优只能改代码重编：

| 常量                 | 位置                                                                               | 现值  | 语义                                                                |
| -------------------- | ---------------------------------------------------------------------------------- | ----- | ------------------------------------------------------------------- |
| `groupMemberTimeout` | [asset_service.go#L1242](../../apps/server/internal/domain/asset_service.go#L1242) | `3s`  | group 逐成员并行解析时每个成员的最大等待时间                        |
| `negativeCacheTTL`   | [negative_cache.go#L11](../../apps/server/internal/domain/negative_cache.go#L11)   | `60s` | 同 `(repoID, path)` 确认不存在后，TTL 内直接返回 404、不再回源/探测 |

两者的默认值都是**针对典型网络的一次权衡**，落到不同现场会各自失准：

- **`groupMemberTimeout` 取 3s 偏紧**：跨地域或经代理的成员，正常响应就可能超过 3s，于是被当成「不可判定」跳过，表现为「制品明明有却报 404/504」。FR-154 已经把「确认阶段」和「落盘阶段」拆开，正是为了让 3s 只覆盖确认、不切断 15MB 这类大制品的下载；但**光拆阶段还不够**——确认阶段给多少秒仍然只能改代码。
- **`negativeCacheTTL` 取 60s 偏长且不可关**：group 层负缓存不因成员后续上传而失效（这是 [0.7.1 规格 §6](0.7.1-404-negative-cache.md#L52) 已记录的既有权衡），因此上游新发布一个制品后，最长 60s 内同路径仍是 404。排查现场问题时，运维需要一个「关掉它，看真实行为」的开关；而这个开关目前**不存在**。

目标：把这两个数值变成可配置项，沿用仓库既有的配置范式（缺省与非法值回退默认、设置项运行时生效不需重启），并给出「负缓存可以彻底关掉」的明确语义。

为谁：自建多节点/跨地域部署的运维（需要调大确认预算），以及排查「制品存在但 404」问题的现场支持（需要临时关掉负缓存）。

阶段：M3 收尾后的运维可调性补强（0.13.0 窗口）。

## 2. 需求（要什么）

- **R1 两个新配置项**：`JIAN_GROUP_MEMBER_TIMEOUT`（秒，默认 3）与 `JIAN_NEGATIVE_CACHE_TTL`（秒，默认 60，**显式 0 = 关闭负缓存**）。
- **R2 非法值口径对齐既有范式**：缺省 / 非数字 / 超出取值范围的输入**回退默认值，不报错、不阻止服务启动**（口径同 [`upstreamTimeout()`](../../apps/server/internal/config/config.go#L651-L662)）。
- **R3 负数口径显式化**：`JIAN_GROUP_MEMBER_TIMEOUT` 的 0 与负数一律回落 3s（本项**无禁用语义**，理由见 §3.2）；`JIAN_NEGATIVE_CACHE_TTL` 的负数回落 60s（**不**视为关闭，理由见 §3.2）。
- **R4 节点本地**：两项均为节点本地配置，**不入库复制、不进节点备份包的配置面**（当前复制通道已随 FR-138 退役，分类仍须写对）。
- **R5 运行时生效**：走设置页（对齐 FR-89 既有模式），保存后**不需重启**即改变行为；环境变量降级为「首次播种的初值」。
- **R6 负缓存的关闭必须是真关闭**：`JIAN_NEGATIVE_CACHE_TTL=0` 时，同路径连续请求每次都回源，且负缓存内存表**不再增长**（不能只是「写入后立刻过期」）。
- **范围内**：配置解析、装配注入、设置页读写与热生效、负缓存 `setTTL` 语义修正、对应自动化测试。
- **不做（范围外）**：按仓库 / 按上游 / 按成员的差异化超时；负缓存的持久化或分布式化；TTL 的策略引擎（自适应、按路径正则、按制品类型）。详见 §6。

## 3. 设计（怎么做）

### 3.1 配置项定义（`internal/config`）

沿用既有三件套：`Env*` 常量 + `default*` 常量 + 无参解析函数，并在 `Load()` 里赋到 `Config` 字段。命名范式对齐 [`EnvCapacityCacheTTLSeconds`](../../apps/server/internal/config/config.go#L78) / [`capacityCacheTTL()`](../../apps/server/internal/config/config.go#L537-L539) 与 [`EnvUpstreamTimeout`](../../apps/server/internal/config/config.go#L28) / [`upstreamTimeout()`](../../apps/server/internal/config/config.go#L651-L662)。

| 配置项             | 环境变量                    | 默认  | 解析函数               | 0 的语义              | 负数的处理 |
| ------------------ | --------------------------- | ----- | ---------------------- | --------------------- | ---------- |
| group 成员确认预算 | `JIAN_GROUP_MEMBER_TIMEOUT` | `3s`  | `groupMemberTimeout()` | 回落 3s（无禁用语义） | 回落 3s    |
| 负缓存 TTL         | `JIAN_NEGATIVE_CACHE_TTL`   | `60s` | `negativeCacheTTL()`   | **关闭负缓存**        | 回落 60s   |

```go
// Config 新增两字段（对齐既有字段的注释口径）
GroupMemberTimeout time.Duration // group 并行解析时每个成员的确认阶段上限；非正数已在解析期回落默认
NegativeCacheTTL   time.Duration // 404 负缓存 TTL；0 = 关闭负缓存，负数已在解析期回落默认 60s
```

解析实现直接复用现成的两个 helper，不新写解析逻辑：

- `groupMemberTimeout()` → [`envPositiveDurationOr`](../../apps/server/internal/config/config.go#L575-L588)（缺省/非数字/负数/显式 0 全部回落 fallback）。
- `negativeCacheTTL()` → [`envDurationOr`](../../apps/server/internal/config/config.go#L562-L573)（缺省/非数字/负数回落 fallback，**显式 0 原样返回**）。

> **命名提示**：`groupMemberTimeout()` 与 domain 包的同名常量 `groupMemberTimeout` 分处两个包，Go 允许，且与 `searchTimeout()`/domain `searchTimeoutDefault` 的同名范式一致。若评审认为跨包同名会误导读者，可改用 `groupMemberResolveTimeout()`——**待定项见 §6**。

**为什么 group 成员超时没有禁用语义**：0 秒预算等于「每个成员都立刻超时」，group 读会 100% 退化为不可判定失败，这不是有意义的配置，只因手误就会让整个 group 仓库不可用。口径与 [`auto_blockBase()`](../../apps/server/internal/config/config.go#L505-L506)、`searchTimeout` 一致：`envPositiveDurationOr`，取 0 无意义。

**为什么负缓存 TTL 的负数不当成关闭**：关闭是一个**明确的运维意图**，应当用显式的 `0` 表达。把负数也解读为关闭，等于「一次手误（例如想写 600 却写错成 `-600`）静默变成负缓存全关 → 每次请求都回源/探测 group 全成员」，这是**放大上游压力**的静默行为，恰好落在最不该静默的地方。因此负数按非法值回退 60s，与 [`capacityCacheTTL()`](../../apps/server/internal/config/config.go#L518-L539) 的既有口径完全一致。

#### 3.1.1 是否需要上限保护

**建议加上限，且与设置页的既有边界对齐为 3600s，超限夹取并打一条中文警告。** 具体：

- 上限取值复用 [`maxConfigSecs = 3600`](../../apps/server/internal/api/settings_handlers.go#L21-L26)（设置页秒级配置的既有上界），避免出现「环境变量能配 86400、界面最多 3600」两个入口口径不一致。
- 夹取方式对齐 [`sqliteMaxConns()`](../../apps/server/internal/config/config.go#L551-L560)：夹到上限 + `fmt.Fprintf(os.Stderr, "警告：…")` 留痕，不报错退出。

理由（与 `capacityCacheTTL` **明确不夹取**的取舍不同，需要说明为什么这次不一样）：

|            | 容量缓存 TTL（既有：不夹取） | 负缓存 TTL（本次：建议夹取）                                                                               |
| ---------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 过大的后果 | 展示数字滞后（新鲜度）       | **新制品长期 404**（正确性感知）                                                                           |
| 自愈方式   | 进程重启即自愈               | group 层负缓存**不因成员上传而失效**（[0.7.1 §6](0.7.1-404-negative-cache.md#L52)），只能等 TTL 过期或重启 |
| 结论       | 不做隐藏二次加工             | 夹取 + 警告（挡数量级笔误：60 打成 6000/60000）                                                            |

即：判据不是「配置值应当可预期」这一条单独成立与否，而是「笔误的后果是否可被人及时察觉」。容量缓存滞后一眼能看出来；负缓存把制品藏住一小时以上，现场通常先怀疑上游或权限，排查成本高。**这是一个待拍板项**——若更看重「不隐藏改写运维显式值」，则该限制可只落在设置页（`validateSecs` 天然 1–3600），环境变量侧不夹取，见 §6。

### 3.2 作用域：节点本地，不入库复制

两项都**不参与复制**，需要显式加入 [`isNodeLocalSetting`](../../apps/server/internal/domain/setting_service.go#L274-L284) 的白名单（该函数是 switch 列表 + `repl:` 前缀判定，新键不带 `repl:` 前缀，必须显式列出）：

- `groupMemberTimeout` 是「**本节点的回源网络条件**给多少确认预算」——同一 group 里不同节点到同一上游的时延本就不同，把一个节点的预算复制到另一个节点没有意义。
- `negativeCacheTTL` 是「**本进程内存态缓存**的存活期」——负缓存本身就是进程内 `map[string]time.Time`（[negative_cache.go#L21-L25](../../apps/server/internal/domain/negative_cache.go#L21-L25)），另一个节点根本没有这份缓存，复制该值只会把本节点策略强加给它。

先例：备份三键 [`SettingKeyBackupAutoInterval` 等](../../apps/server/internal/domain/setting_service.go#L135-L139) 出于完全同构的理由（「这台机器怎么用自己的盘」）被列为节点本地。

注意当前的实际状态：复制通道已随 FR-138 退役，装配层注入的是 [`domain.NoopChangeRecorder{}`](../../apps/server/cmd/jianartifact/wiring.go#L177)，`recordChange` 实际不会落任何变更日志。**但这不构成「分类可以随便写」的理由**——`isNodeLocalSetting` 的语义价值恰恰在于「若复制能力回归，这些键不会被静默错复制」。分类写错今天没有任何症状，是最典型的一类埋雷。

### 3.3 运行时生效：走设置页（对齐 FR-89），环境变量降级为播种初值

**推荐走设置页**，不采用「仅环境变量」。理由：

1. PRD FR-156 正文已明确写明「设置项运行时生效、**不需重启**」，这是需求本身的一部分，不是可选项。
2. 这两项的价值恰在**现场调**：跨地域部署调大确认预算、排查 404 时临时关负缓存，改环境变量意味着重启服务——把一个「看一眼是不是负缓存的问题」的诊断动作变成一次停服。
3. 仓库已有完整先例：回源超时（FR-89）就是「env 初值 → setting 表 → 回调热生效」的同构链路，见 [`OnUpstreamTimeoutChange`](../../apps/server/cmd/jianartifact/wiring.go#L495-L499) 与 [`PutSettings` 中的回调调用](../../apps/server/internal/api/settings_handlers.go#L262-L264)。

**环境变量的角色**：从「唯一真源」降级为**首次播种的初值**——启动时若 setting 表无该键，用环境变量值写入；此后以 setting 表为准。这与备份三项的注释口径逐字一致（[setting_service.go#L126-L134](../../apps/server/internal/domain/setting_service.go#L126-L134)），也复用现成的播种函数 [`seedSettingDefault`](../../apps/server/cmd/jianartifact/wiring.go#L417) 与既有播种代码块（[wiring.go#L179-L196](../../apps/server/cmd/jianartifact/wiring.go#L179-L196)，回源超时的写法 `strconv.Itoa(int(cfg.UpstreamTimeout.Seconds()))` 在 L183）。

#### 3.3.1 设置键与读取口径

新增两个设置键，命名沿用既有风格（snake_case、无 `jian_` 前缀、按主题成组）：

```go
// proxy/group 读路径调优两项（节点本地、运行时可改）。
const (
	SettingKeyGroupMemberTimeout = "group_member_timeout"   // group 成员确认阶段上限（秒），非正数回退默认
	SettingKeyNegativeCacheTTL   = "negative_cache_ttl"     // 404 负缓存 TTL（秒），0 = 关闭
)
```

**读取口径必须区分「键缺失」与「值为 0」**，这是本设计最容易出错的一点：

- `groupMemberTimeout`：用 [`secsSetting`](../../apps/server/internal/domain/setting_service.go#L241-L252)（缺失/非数字/非正数 → 0），装配层只在 `secs > 0` 时应用，否则保留环境变量/默认值。**直接照抄** [`UpstreamTimeoutSecs` 的读取用法](../../apps/server/cmd/jianartifact/wiring.go#L193-L195)。
- `negativeCacheTTL`：**不能**用 `secsSetting`（它把 0 也归零成「未配置」，与「0 = 关闭」直接冲突），也**不能**直接用 [`nonNegativeIntSetting`](../../apps/server/internal/domain/setting_service.go#L159-L171)（它接受 0，但**缺失时也返回 0**，于是一个被删掉的键会静默变成「关闭负缓存」）。
  因此新增一个带存在性的读取方法（**新增符号，命名待实现时定稿**）：

  ```go
  // NegativeCacheTTLSecs 返回负缓存 TTL（秒）与「键是否已配置」。
  // ok=false 表示键缺失或值非法，调用方应回退环境变量/默认值；
  // 只有 ok=true 且 secs==0 才是「显式关闭」。
  func (s *SettingService) NegativeCacheTTLSecs() (secs int, ok bool)
  ```

  这样「关闭」与「未配置」彻底分开，不依赖播种顺序或播种成功与否。

`SettingsUpdate` 追加两个 `*int` 字段，`settingValues` 追加两个分支（**0 是合法值，照写不跳过**——对齐备份三项在 [settingValues#L313-L322](../../apps/server/internal/domain/setting_service.go#L313-L322) 的既有注释与写法）。

### 3.4 与 `negativeCache.setTTL` 现有语义的冲突（必须改）

现状：[`setTTL`](../../apps/server/internal/domain/negative_cache.go#L32-L39) 的守卫是 `if d > 0 { c.ttl = d }`，即 **`<=0` 被忽略**，注释也写着「测试与调优用；<=0 忽略」。这与「0 = 关闭负缓存」直接冲突，必须改。改造点有三处，缺一不可：

1. **`setTTL` 守卫拆开 0 与负数**：`d < 0` 继续忽略（保留「非法值不动现值」的防御，配置层已回退默认，这里是第二道保险）；`d >= 0` 一律写入，**包括 0**。
2. **`add` 在关闭态下直接返回**（[negative_cache.go#L58-L62](../../apps/server/internal/domain/negative_cache.go#L58-L62)）：`ttl <= 0` 时不写 `map`。
   **为什么必须改**：`hit` 的过期判断是 `time.Since(at) >= c.ttl`（[#L42-L55](../../apps/server/internal/domain/negative_cache.go#L42-L55)），`ttl == 0` 时恒为真，于是**命中永远失败**——功能上「看起来已关闭」。但每次确认 404 仍会往 `m` 里塞一条键，而这条键只会在下次 `hit` 同一路径时才被删除。长期运行 + 大量不同缺失路径（Gradle 反复试错、扫描器、错误配置的客户端）会让 `m` **单调增长且永不回收**，是一个只在重启时才消失的内存增长缺陷。这是「0 = 关闭」最容易被漏掉的一半。
3. **`hit` 增加关闭态早返回**：`ttl <= 0` 直接 `return false`。语义显式，不依赖 `>=` 上的巧合；此时 `m` 应为空，也无需清理。

同时修正两处**已经与实现不符的注释**：`setTTL` 的「<=0 忽略」以及导出方法 [`SetNegativeCacheTTL`](../../apps/server/internal/domain/asset_service.go#L243-L244) 的「测试与调优用；<=0 忽略」。后者有一个必须说清的事实：

> **已核实**：`AssetService.SetNegativeCacheTTL` 目前**全仓只有定义、没有任何调用点**（装配层从未调用它）。也就是说负缓存 TTL 今天是纯死代码常量，运行时不可改。本次改动是它**第一次真正接线**——因此不能假设「把配置接进 setter」就完事，必须同时确认注入发生在 `NewAssetService` 之后、第一个请求之前。

**测试如何覆盖**（新增 `domain/negative_cache_test.go`，直接单测结构体，不经 HTTP）：

- `setTTL(0)` 后 `add` 不写：`len(c.m) == 0` 且 `hit == false`。
- `setTTL(0)` 后连续两次 `add` 同一键，`len(c.m)` 仍为 0（钉住「不再增长」）。
- `setTTL(-1)`：不改变现值（构造后默认 60s 仍是 60s；已设 5s 仍是 5s）。
- `setTTL(1ms)` + 等待过期：`hit` 由 true 变 false（既有过期行为不回归）。
- Service 层端到端：`SetNegativeCacheTTL(0)` 后，同缺失路径连续两次 `Resolve` 都回源（上游计数 = 2），而非第二次命中负缓存。

### 3.5 与 FR-154 的关系：配置项控制的是「确认阶段预算」

FR-154 把 group 成员解析拆成两阶段：**确认阶段**（限时，只判定成员是否持有该制品，拿到响应头即算命中、不落盘）与**落盘阶段**（改用回源整体超时 `JIAN_UPSTREAM_TIMEOUT`，默认 30s）。本 FR 配置化的正是**确认阶段**的预算，语义边界如下：

- 注入点定在 FR-154 定义的**确认阶段预算**。FR-154 落地前对应的是 [asset_service.go#L1338](../../apps/server/internal/domain/asset_service.go#L1338) 的 `context.WithTimeout(groupCtx, groupMemberTimeout)`；落地后该预算不再是成员 `ctx` 的全部，而是同批草拟的 FR-154 规格（[0.13.0-group-two-phase-budget.md](0.13.0-group-two-phase-budget.md)）所述的「`context.WithCancel` + 独立计时器」里那个计时器的时长，且 FR-154 明示**不改该常量的值与可配置性**（把它留给本 FR）。因此本 FR 改的正是那个计时器时长，而不是成员 `ctx` 的整体超时。
- **不得**让该配置项影响落盘阶段的预算。反例：把 15MB 大制品的落盘也压到「确认预算」里，就是 FR-154 要修的那个缺陷；若本 FR 先把「一个 timeout 覆盖成员解析全流程」写进实现，会与两阶段语义打架。
- 因此**顺序依赖是硬的**：FR-154 先定稿 → 本 FR 把可配置值注入确认阶段。若 FR-154 推迟，本 FR 的可行退路是「注入点保持现有 L1338 的 `context.WithTimeout` 位置不变，仅把常量换成可配置字段」，同时在 PRD/CHANGELOG 里注明该项在两阶段落地后会重新对位。
- 文案纪律：本 spec、设置页字段标签与 OPERATIONS 说明一律称「成员确认预算 / 确认阶段超时」，**不**使用「group 成员超时」「成员解析超时」这类会暗示覆盖全流程的说法。

### 3.6 装配与热生效链路

```
环境变量(JIAN_GROUP_MEMBER_TIMEOUT / JIAN_NEGATIVE_CACHE_TTL)
   └─ Load() → Config.GroupMemberTimeout / Config.NegativeCacheTTL
        ├─ 启动播种：setting 表无键时写入初值（seedSettingDefault，模式同 wiring.go#L179-L196）
        └─ 生效值：setting 表优先（NegativeCacheTTLSecs 的 ok 区分缺失与 0）
             ├─ 启动期注入：assetSvc.SetGroupMemberTimeout(...) / assetSvc.SetNegativeCacheTTL(...)
             └─ 设置页保存 → PutSettings → 回调 → 上述两个 setter（热生效，无需重启）
```

`AssetService` 需要新增一个字段承载成员确认预算（当前只有常量），并新增注入方法；`negativeCache` 侧复用已有的 `setTTL`（改造后）。两者都是**可变字段 + 互斥保护**或**启动后只写一次**的选择——`negativeCache` 已有 `mu` 保护 `ttl`，新增字段建议同构（保存时加锁，读取时加锁），避免热改与在途请求的 data race（`-race` 必须绿）。

## 5. 验收标准

### 5.1 单元与集成（须全绿）

**配置解析（表驱动，对齐 FR-43 风格，每项各一组）**

- `JIAN_GROUP_MEMBER_TIMEOUT`：缺省 → `3s`；`"0"` → `3s`；`"-3"` → `3s`；`"3s"`（非数字）→ `3s`；`"   "`（空白）→ `3s`；`"8"` → `8s`；`"  10  "` → `10s`（两端空白被裁剪）；超上限值按 §3.1.1 的最终取舍断言（夹取到 3600s 并留警告，或原样生效——二者必须是测试钉住的**明确**行为，不允许「未定义」）。
- `JIAN_NEGATIVE_CACHE_TTL`：缺省 → `60s`；`"0"` → **`0`（关闭）**；`"-1"` → `60s`；`"60s"` → `60s`；`"   "` → `60s`；`"600"` → `600s`；上限取舍同上。
- `Load()` 确实把两个值带进 `Config`（解析函数绿了但字段没赋值是这类改动的典型静默失灵，须单列，对齐 `TestLoadCarriesCapacityCacheTTL`）。

**负缓存关闭语义**

- `negativeCache.setTTL(0)` 后 `add` 不写：`len(m) == 0`、`hit == false`。
- 关闭态下同一路径连续 `add` 多次，`m` 长度仍为 0（内存不增长，见 §3.4 第 2 点）。
- `setTTL(-1)` 不改变现值（默认 60s / 已设自定义值均保持）。
- `setTTL(1ms)` 后过期行为不回归（`hit` 由 true 变 false）。
- Service 层：`SetNegativeCacheTTL(0)` 后同缺失路径连续两次读**每次都回源**（上游请求计数 = 2），钉住「`JIAN_NEGATIVE_CACHE_TTL=0` 时负缓存完全关闭」。

**既有负缓存测试在默认值下继续通过**（已核实这 5 个存在于 [asset_service_resolve_test.go](../../apps/server/internal/domain/asset_service_resolve_test.go)）

### 5.2 实机验收（需用户确认）

> **硬约束：只在本地与测试站进行，禁止部署正式站。** 本节全部步骤不得在任何承载真实业务的实例上执行；涉及「关闭负缓存」的验证会放大回源压力，尤其不得指向生产上游。

1. **起两个实例观察不同 TTL**：本地分别以 `JIAN_NEGATIVE_CACHE_TTL=60` 与 `JIAN_NEGATIVE_CACHE_TTL=0` 启动，指向同一个不可达/缺失路径的 proxy 或 group 仓库。分别连续请求同一缺失路径 3 次，观察：默认值实例第 1 次慢、第 2/3 次秒级 404；关闭实例 3 次都实际回源（上游访问日志或请求耗时均体现）。**记录两次实例的耗时对比**作为证据。
2. **确认预算可调**：用一个**故意慢**的成员（本地可注入延迟的假上游，或测试站上一个可控的慢端点），分别以 `JIAN_GROUP_MEMBER_TIMEOUT=1` 与 `8` 启动，对同一路径发 group 读；观察短预算实例出现「不可判定/超时跳过」而长预算实例成功命中。**不得**用真实公网上游做这一步。
3. **热生效与失效**：在不重启的实例上，经设置页把负缓存 TTL 调到 `0` 并保存，随后对**先前已被缓存的缺失路径**请求一次——应看到它重新回源（证明热生效且未命中旧负缓存）；再在 group 成员上上传一个此前报 404 的制品，验证成功写路径失效后同路径立即可读。
4. **设置页可用性**：设置页能正确回填两个新值与默认值，`0` 能被保存（不被前端 `min` 拦掉），文案明确说明「0 = 关闭负缓存」，保存后摘要区显示与生效值一致。
5. **回归基线**：默认值（`3s` / `60s`）下，一次常规 group 读与一次 404 路径的行为、耗时与升级前一致（无意外变慢或变快）。
6. 以上 1–5 由用户确认通过后才可标记本 FR 交付；单元/集成全绿**不替代**本节。

## 6. 风险 / 待定

**待拍板**

- **上限夹取与否**（§3.1.1）：推荐「夹取到 3600s + 中文警告留痕」（理由：笔误后果是制品长期 404 且不自愈）。反方意见同样成立——`capacityCacheTTL` 已明确否决「静默改写运维显式给出的值」。若采纳反方，则上限只存在于设置页（`maxConfigSecs` 天然 1–3600），环境变量侧不做任何加工，此时必须在 OPERATIONS 里写清「环境变量可配出比界面更大的值，风险自负」。**该决定直接影响 §5.1 的断言取值，须先定。**
- **解析函数命名**（§3.1）：`groupMemberTimeout()` 与 domain 同名常量分处两包，是否符合读者预期？备选 `groupMemberResolveTimeout()`。
- **`api/openapi.yaml` 是否补 `/api/v1/settings` 契约**（§3.3.2）：现状是设置端点无契约，而 `docs/specs/README.md` §6 要求 API 先改契约。本 FR 推荐**不**顺手补（补齐整个 settings 端点契约是一个独立工作项，塞进本 FR 会让 diff 与验收范围失控），但需要在 PRD 或 specs/README 里留一条「设置端点契约缺口」的登记，否则每次改设置项都要重新争论一次。

**风险**

- **热改与在途请求的并发**（§3.6）：`ttl` 已有 `mu` 保护，新增的成员确认预算字段若不加保护，在设置页保存与在途 group 读之间会构成 data race（`-race` 会抓到，但只在测试恰好并发时才暴露）。实现上必须与 `negativeCache` 同构加锁。
- **关闭负缓存 = 放大回源**：`0` 会让每一个缺失路径请求都真实回源/探测全部 group 成员。这本就是「关闭」的应有代价，但界面文案与 OPERATIONS 必须写明，避免被当成「性能优化开关」误用于大流量站点。
- **关闭态下的既有依赖**：`groupGet` 在「全成员确认不存在」后调用 `negCache.add`（[L1324](../../apps/server/internal/domain/asset_service.go#L1324)、[L1367](../../apps/server/internal/domain/asset_service.go#L1367)），命中检查在 [L920](../../apps/server/internal/domain/asset_service.go#L920)。关闭后这些调用点**全部保留**（由 `add`/`hit` 内部早返回兜住），不要写成在调用点散布 `if enabled` 判断——那会让未来新增调用点再次漏掉关闭语义。
- **设置项播种失败**：若 setting 表写入失败导致键缺失，`NegativeCacheTTLSecs` 的 `ok=false` 必须回退到环境变量/默认值而不是 `0`，否则一次 DB 抖动就会静默关掉负缓存（§3.3.1 的 `(secs, ok)` 设计正是为此）。
- **与 FR-154 顺序倒置**：若本 FR 先于 FR-154 合入并把「一个 timeout 覆盖成员解析全流程」固化，两阶段落地时会出现「配置项语义被悄悄改变」的迁移问题（运维按文档设 8s，实际含义从「全流程」变成「仅确认」）。缓解：文案统一用「确认阶段预算」，并在 FR-154 合入时同步改 OPERATIONS 说明。

**范围外（明确不做）**

- 按仓库 / 按上游 / 按成员的差异化超时（例如「这个 proxy 仓库给 10s，那个给 3s」）。当前配置项是**进程级单值**；差异化需要仓库级配置模型 + 契约 + 页面，属独立 FR。
- 负缓存的持久化或分布式化（跨进程共享、跨节点一致、落库）。负缓存是进程内内存优化，持久化会引入「重启后仍返回旧 404」这类更难排查的问题，且与「重启即自愈」的现有性质相悖。
- TTL 的策略引擎（自适应 TTL、按路径正则、按制品类型/大小区分）。
- 负缓存条目的人工可查/可清理界面——那是 FR-157（代理解析结果可观测）的范围，本 FR 只提供「整体关闭」这一个粗粒度开关。
- 补齐 `/api/v1/settings` 的 OpenAPI 契约（§3.3.2 已说明理由）。
