# 功能规格：回源失败原因五分类

> 状态：草拟　·　关联 PRD：FR-158（增强 FR-155）　·　分支：feature/fr158-upstream-failure-classification　·　依赖：FR-154（上游开始信号）、FR-155（失败分类与阻断判定）

## 1. 背景与目标

### 1.1 问题

FR-155 已把「回源失败」分成两类行为：不可达要阻断、超时不阻断。但从运维与调参角度看，两分法仍然不够——它把三种性质完全不同的情况混成了同一个 `upstream_timeout`：

1. **上游没响应**：连上了但一直不返回响应头。多半是真的挂了或极度过载。
2. **下载速度太慢**：已经拿到响应头（说明上游可达且确实持有该制品），只是 body 传不完。**等一会儿或稍后重试通常就好**，不该按故障处理。
3. **下到一半断了**：已经拿到响应头且有传输进展，但连接被重置或提前关闭（可能是上游主动断、中间设备掐连接、或本地磁盘问题）。

这三种在现有实现里都表现为「504 + 一条 `upstream_timeout`」——**无法据以判断该调超时、该重试、还是该去修上游**。

更具体的现状缺口：**传输阶段的失败根本不经过 `classifyUpstreamFailure`**（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1188-L1204) 的 `putStagedBlob` 失败分支只按 `upstream.IsTimeout` 二分），因此既不记判定事件、也不进任何指标。从 `/metrics` 上看不出「有多少次是下载太慢」，只能看到失败总量。

### 1.2 目标

- 把回源失败细分为**五类**，每类有独立可判定的语义、独立的指标取值与独立的日志类别。
- `slow_transfer`（慢）与 `transfer_aborted`（中途断）必须能与 `no_response`（没响应）区分开，因为**处置动作完全不同**：前者等到带宽恢复即可、后者要查上游是否存活。
- 记录传输进度（已传字节 / 总字节 / 耗时），使「慢」这件事可被量化，而不是只有一个状态码。

### 1.3 判据基础（已核实）

区分「拿到响应头之前」与「之后」是可靠且现成的：FR-154 已在 [fetchProxyAsset](../../apps/server/internal/domain/asset_service.go#L1183-L1187) 的「拿到 2xx 响应头」处调用 `markUpstreamStarted(ctx)`，并在随后的 `putStagedBlob` 之前。因此：

- **未拿到响应头**的失败 → 上游侧问题（不可达 / 没响应）
- **已拿到响应头**的失败 → 传输侧问题（慢 / 中途断）

## 2. 需求（要什么）

### 2.1 五类语义与处置

| 类别                  | 判据                                                         | 含义             | 对外状态码       | 是否阻断                 | 建议处置                                 |
| --------------------- | ------------------------------------------------------------ | ---------------- | ---------------- | ------------------------ | ---------------------------------------- |
| `unreachable`         | 连接 / DNS / TLS 失败、上游 5xx / 401 / 403                  | 真不可达         | 502              | **是**                   | 查上游存活、网络与凭据                   |
| `no_response`         | 未拿响应头即超时，**或已拿响应头但零字节传出**               | 连上了但不吭声   | 504              | 否                       | 查上游是否过载或卡死                     |
| `slow_rate`           | **已拿响应头**、有传输进展、超时                             | 带宽不足         | 504              | 否                       | 等带宽恢复或调大 `JIAN_UPSTREAM_TIMEOUT` |
| `transfer_aborted`    | **已拿响应头**、非超时的连接重置 / 提前 EOF                  | 连接不稳定       | 504              | 否                       | 查中间设备或上游主动断连                 |
| `confirmed_missing`   | 404 / 410                                                    | 确实没有         | 404 / 502（410） | 否                       | 正常回退                                 |
| `local_write_failure` | 本地磁盘写失败（磁盘满 / 权限 / 分片目录不可建）             | **不是上游问题** | **500**          | 否（不记上游事件）       | 查本机磁盘与权限                         |
| `canceled`            | 请求被取消（客户端断连、group 中兄弟成员已成功后取消落选者） | 正常生命周期终点 | 不写响应         | 否（不记事件、不记日志） | 无需处置                                 |

> **三类传输失败（`no_response` / `slow_rate` / `transfer_aborted`）统一对外 504**：对客户端而言三者都是「上游暂时性、可重试」，用同一状态码可避免调用方对 502/504 做无意义的区分；**精确原因由指标 `reason` 与日志 `category` 表达**，而不是靠状态码。这优先于「非超时中断应为 502」的形式化推论——后者会让同一类可重试故障出现两种码，反而增加客户端适配成本。
>
> **`canceled` 必须单列**（实现期补充）：`context.Canceled` 既不匹配超时、也不匹配 EOF/连接重置，若按字面落进 `local_write_failure`，则**每次用户中断大文件下载都会留下一条「本地磁盘写入失败」错误告警**。故它必须在判定链最前面短路：不记上游判定事件、不记传输日志、不记解析失败样本，原样上抛取消（与 `api` 层对 `context.Canceled` 的既有处理一致）。

> **410 的对外语义保持现状**（`ErrUpstream` + `ErrUpstreamGone`，对外 502），不因本 FR 改动——这是 FR-155 已确认的既有行为，为的是不让 Go proxy 客户端链路被改成 502 而失去标准回退能力（见 [asset_service.go](../../apps/server/internal/domain/asset_service.go#L1163-L1169) 既有注释）。

### 2.2 传输进度记录

失败时需记录：**已传字节数、响应头声明的 Content-Length（若有）、耗时、判定类别**。

- 现状障碍（已核实）：[store.go](../../apps/server/internal/blobstore/store.go#L108-L112) 在 `io.Copy` 失败时返回 `size = 0`，把已传字节数丢弃。因此**不能**依赖 blobstore 的返回值。
- 解决方向（不改 blobstore 公共签名）：在 `putStagedBlob` 调用处包一层计数 reader，传输失败时读计数。
- `Content-Length` 来自 `fetchProxyAsset` 已持有的 `header`（`fetch` 返回的第二个值），无需额外请求。

### 2.3 指标

- 新增 `slow_transfer` 与 `transfer_aborted` 两个 `reason` 取值，扩展到既有闭集 `jianartifact_upstream_block_events_total{reason}`。
- **不新增指标族**：复用既有阻断事件族，保持「闭集外取值忽略」与「无样本也输出 HELP/TYPE」的既有行为。
- 既有 `probe_failed` / `upstream_error` / `upstream_timeout` 的语义与样本文本**不得改变**。
- **与 FR-157 的解析结果指标不重叠**：那是「一次解析的结果」（confirmed / uncertain），这是「一次回源失败的判定原因」，两者维度不同、不可相加，口径写进文档。

### 2.4 日志

- 传输阶段失败记一条**结构化中文日志**，含仓库、路径、类别、已传字节、总字节、耗时、上游 host（**不含凭据与完整 URL**）。
- `slow_rate` 与 `transfer_aborted` 必须能一眼区分（不同类别文案 + 不同建议）。
- 404 / 410 不记（正常流量），与 FR-157 的「只对 uncertain 记」口径一致。

### 2.5 范围内 / 范围外

- **范围内**：分类判定、指标取值、进度记录、日志、两条回源链路（`fetchProxyAsset` 与 `ResolveOCIProxy`）共用同一判定。
- **范围外（不做）**：
  - 自动重试（客户端有重试语义，服务端自动重试会放大上游压力且与 single-flight 交互复杂）；
  - 断点续传（`Range`）——上游支持情况不一，属独立能力；
  - 把 `slow_rate` 的判定做成可配置阈值（本 FR 只按「是否有传输进展」二分，不引入速率阈值）；
  - 管理端 UI 展示失败原因分布（本期只做指标与日志）。

## 3. 设计（怎么做）

### 3.1 判定入口与顺序

扩展 [classifyUpstreamFailure](../../apps/server/internal/domain/asset_service.go#L1696-L1707)，但**注意其函数签名只接收 `err`**，无法知道「是否已拿到响应头」。有两种做法：

- **方案 A（推荐）**：新增一个独立的传输阶段判定函数（例如 `classifyTransferFailure(err, transferred, declared)`），**不改** `classifyUpstreamFailure` 的语义与签名。原因：现有函数被两个回源调用点共用，改签名会波及 `ResolveOCIProxy` 且容易把「未拿头」与「已拿头」的判据混淆。
- **方案 B**：给 `classifyUpstreamFailure` 增加 `started bool` 参数。改动集中但会同时动两条链路，回归面更大。

采用方案 A：`classifyUpstreamFailure` 保持现状（负责「拿头之前」的失败），新增 `classifyTransferFailure`（负责「拿头之后」的失败）。两者共享同一个 `upstreamFailureVerdict` 结构与 `settleUpstreamFailure` 收口，避免出现第二套副作用逻辑。

### 3.2 传输阶段判定的具体规则

输入：`err`、`transferred int64`（**已从上游读出的字节数**）、`declared int64`（Content-Length，缺失时 -1）。

```
if errors.Is(err, context.Canceled) { return canceled }   // 必须最先短路
if upstream.IsTimeout(err) {
    if transferred > 0 { return slow_rate }        // 有进展：带宽不足
    return no_response                             // 拿到头却一个字节没传出去，按没响应算
}
if errors.Is(err, io.ErrUnexpectedEOF) || isConnReset(err) || errors.Is(err, io.EOF) && declared > transferred {
    return transfer_aborted
}
// 其余传输错误（含本地磁盘写失败）不得伪装成上游问题
return local_write_failure   → 对外 500，且不计入上游判定事件
```

**`transferred` 的语义是「已从上游读出」，不是「已成功写盘」**：磁盘写满时 `io.Copy` 会先 `Read` 成功、再 `Write` 失败，计数可能已等于完整大小。因此**本地写失败不能靠「有无进展」排除**，只能靠错误值判定，且它必须是判定链的**最后兜底分支**。

**关键区分**：本地磁盘写满 / 权限问题**不是上游故障**，必须与上面几类分开，否则会把「本地磁盘满」误报成「上游超时」，把人引到错误方向排查。这类失败对外应返回 500（内部故障）而非 502/504。

### 3.3 进度获取

在 `putStagedBlob` 外层包计数 reader：

- 新增 `countingReader{r io.Reader; n int64}`，`Read` 累加成功读出的字节数。
- 失败后 `n` 即「已传字节」。
- **不改** `blobstore.Store` 的签名与 `put` 内部逻辑（避免影响 hosted 上传等其它调用方）。

### 3.4 指标与日志接线

- `metrics.go` 的 `knownBlockReasons` 闭集加 `slow_transfer`、`transfer_aborted`；`isKnownBlockReason` 与家族渲染逻辑不变。
- 沿用既有「领域定义接口 + 装配注入、nil 不记录」范式，不直接把 `*metrics.Registry` 塞进领域层。
- 日志用既有中文分级日志设施；**不得**输出凭据、完整上游 URL、内网地址（上游只到 `scheme://host`，见 FR-157 的 `upstreamHost`）。

### 3.5 与既有逻辑的关系

- **不改** FR-155 的「超时不阻断」结论：`no_response` / `slow_rate` / `transfer_aborted` 三类都**不阻断**（它们都不是「上游不可达」的证据）。
- **不改** FR-154 的看门狗与两阶段预算。
- **不改** FIX-1 的返回码分流（Confirmed→404 / 含超时→504 / 其余→502）；本 FR 只是在 504 这一支内部做了更细的原因区分，并新增 `local_write_failure` 的 500 分支。
- **不改** 负缓存写入条件（只有 Confirmed 才写）。

## 5. 验收标准

### 5.1 单元与集成（须全绿）

- **`no_response`**：上游接受连接但永不返回响应头 → 类别为 `no_response`，指标 504 语义不变，**不阻断**。
- **`slow_rate`**：上游立即返回 200 + `Content-Length: 15MB` 后按低速率滴流、最终超时 → 类别为 `slow_rate`，日志记录到 `transferred > 0`，**不阻断**，下次请求仍重试（不写负缓存）。
- **`transfer_aborted`**：上游返回 200 + 声明 15MB，传 1MB 后强制断开 → 类别为 `transfer_aborted`，与 `slow_rate` 可区分。
- **本地写失败不误报**：让 blobstore 写入失败（如只读目录 / 配额耗尽）→ **不得**产生任何上游判定事件，对外 500。
- **`unreachable` 不回退**：连接失败仍阻断，既有 `TestResolveProxyUnreachableStillAutoBlocks` 等用例继续通过。
- **指标**：新两个 reason 计数正确；既有三 reason 文本与计数不变；闭集外取值仍被忽略；无样本仍输出 HELP/TYPE。
- **`-race` 通过**；FR-154 / FR-155 / FR-157 新增用例全部继续通过（不得修改其断言迁就本实现）。

### 5.2 实机验收（需用户确认）

> **硬约束：只在本地与测试站进行，禁止部署正式站。**

手动复验步骤：

1. 上游限速到约 300KB/s（低于 15MB / 30s 门槛），请求该大制品 → 应为 `504`，且 `jianartifact_upstream_block_events_total{reason="slow_transfer"}` 增长、`blocked_repositories` 不增长；日志能读出「已传 X MB / 共 15MB」。
2. 上游端口关闭 → 应为 `502`，`reason="upstream_error"` 增长、`blocked_repositories` 增长。
3. 上游接受连接但不回包（如 `nc -l` 不响应）→ 应为 `504` 且 `reason="upstream_timeout"`，与第 1 步的类别不同。
4. 上游传一半断开（如 `curl --limit-rate` 配合 kill）→ `reason="transfer_aborted"`。

## 6. 风险 / 待定

- **R1**：`transfer_aborted` 与 `slow_rate` 在某些网络环境下难以绝对区分（例如超时恰好发生在传输中途）。判定以「是否因超时触发」为第一优先：`IsTimeout` 为真一律归 `slow_rate`（有进展时），只有非超时的连接中断才归 `transfer_aborted`。这个优先级必须在测试里钉住。
- **R2**：`Content-Length` 可能缺失（chunked 响应）或与实际不符。缺失时 `declared = -1`，判定退化为「只看是否超时与是否有进展」，不因此把类判错。
- **R3**：本地写失败与「上游提前 EOF」都表现为 `io.EOF` / `io.ErrUnexpectedEOF`，需以 `declared` 与实际传输量比对才能区分；无 `Content-Length` 时无法可靠区分，此时**偏向上游断开**（归 `transfer_aborted`）而非 500——宁可让人去看上游，也不要静默报 500 掩盖真实断流。
- **R4**：`ResolveOCIProxy` 的传输路径与 raw/maven 不完全同构（有 manifest 与 blob 两段），接线时需确认其「拿头」时点，不可盲目复用同一判断。若不同构，本期只在 raw/maven 路径生效，并在 spec 与日志中写明 OCI 暂不细分。
