# 功能规格：上游健康历史

> 状态：草拟　·　关联 PRD：FR-159（增强 FR-114）　·　分支：feature/fr159-upstream-health-history　·　依赖：FR-155（失败分类）、FR-158（失败原因五分类）

## 1. 背景与目标

### 1.1 问题

「上游**当前**连接状态」已随 FR-114 交付：`ConnectionStatus` 六态枚举（`READY` / `AVAILABLE` / `AUTO_BLOCKED` / `HALF_OPEN` / `UNAVAILABLE` / `OFFLINE`）+ 仓库列表徽章 + 详情页状态与 online/offline 开关 + 手动重测。但它有三个结构性缺口：

1. **只有一个「此刻」**：状态是内存态，重启归零；没有「过去一小时连通率多少」「昨天挂过几次、每次多久恢复」。
2. **只有汇总计数**：断路器只有 counter `jianartifact_upstream_block_events_total`（累计值、无时间维度），无法还原趋势。
3. **HEAD 探测成功 ≠ 大制品可取**：这正是本次 15MB 故障的教训——POM 200 而 jar 404，慢与不可达被混为一谈。只看探测结果会得出「上游健康」的错误结论。

### 1.2 目标

- **持久化**上游健康的时间序列，可按仓库查看**任意时间窗**的连通率与延迟趋势。
- **两路数据合并**：真实回源请求的结果（反映真实可用性）+ 后台定时探测（无流量时补空窗，且能提前发现上游挂掉）。
- **按失败原因分层**：连通率之外，还要能看出失败里有多少是「没响应」、多少是「慢」、多少是「不可达」——直接复用 FR-158 的五分类，不另造一套词表。
- 展示**最近 N 次请求明细**（时间、结果、原因、耗时、来源是真实请求还是探测）。

### 1.3 范围内 / 范围外

- **范围内**：分钟级采样表、真实请求采样、定时探测补充、查询 API、前端趋势图与明细、保留策略与清理。
- **范围外（不做）**：
  - 跨节点聚合（复制通道已随 FR-138 退役，本 FR 只做单节点）；
  - 上游 SLA 报表导出 / 告警联动（告警仍走既有 `upstream_auto_blocked`）；
  - 按路径维度的健康（只到仓库维度——按路径会让数据量爆炸且无明确聚合口径）；
  - 历史数据回填（新表从启用时刻开始积累，不伪造历史）。

## 2. 需求（要什么）

### 2.1 采样口径

**两路来源写入同一张表**，用 `source` 区分：

| `source` | 触发 | 语义 |
| --- | --- | --- |
| `request` | 每次真实回源请求结束时 | 反映**真实用户可用性** |
| `probe` | 后台定时 HEAD 探测 | 无流量时补空窗，并提前发现上游挂掉 |

- **真实请求采样必须与 FR-158 的分类共用同一判定**（`classifyUpstreamFailure` / `classifyTransferFailure`），不得在采样处再判一次——两处判定必然漂移。
- 采样聚合到**分钟桶**（`bucket_start` 取整分钟），同一分钟内多次请求累加计数、延迟取平均与 p95。**不逐请求落行**——高频回源下会写爆库。
- 探测间隔可配置（默认 60s，与分钟桶对齐），**仅对 `proxy` 类型仓库**（`group` 没有独立上游，`hosted` 无上游）。`offline` 仓库不探测（用户明确要求停用）。
- **探测必须走既有探测链路**（`ProbeWithCredential` / `recheck` 同源），不新造 HTTP 路径——否则会出现「探测说健康、回源却失败」的第二套口径。

### 2.2 数据模型

新增迁移 `0051_upstream_health_minute.sql`（当前最大为 `0050`）：

```
upstream_health_minute(
  bucket_start TEXT NOT NULL,      -- 分钟桶（UTC，'YYYY-MM-DD HH:MM:00'）
  repository_id INTEGER NOT NULL,  -- 关联仓库（仓库删除时级联清理）
  source TEXT NOT NULL,            -- 'request' | 'probe'
  samples INTEGER NOT NULL,        -- 总样本数
  ok INTEGER NOT NULL,             -- 成功数
  timeout INTEGER NOT NULL,        -- no_response 数
  unreachable INTEGER NOT NULL,    -- 不可达数
  slow INTEGER NOT NULL,           -- slow_transfer 数
  aborted INTEGER NOT NULL,        -- transfer_aborted 数
  avg_latency_ms INTEGER,          -- 平均耗时（无成功样本时为 NULL，不伪造 0）
  max_latency_ms INTEGER,
  PRIMARY KEY (bucket_start, repository_id, source)
)
```

- **`source` 进主键**：真实请求与探测是两条独立序列，混在一行会让「连通率」被探测流量稀释，无法分别判断。
- 失败列与 FR-158 的分类对齐；`local_write_failure` / `canceled` **不计入**（前者是本地故障、后者是正常取消，都不是上游健康信号）。
- 索引：`(repository_id, bucket_start)` 支撑按仓库查时间窗。
- **保留 30 天**（对齐 `host_metric_minute` 的既有口径），由 `storage-cleanup` 作业顺带清理，不新增作业。

### 2.3 查询 API

- `GET /api/v1/repositories/{name}/upstream-health?from=&to=&source=`
  返回时间序列（分钟桶数组）与汇总（连通率、各原因计数、平均/p95 延迟）。
- `GET /api/v1/repositories/{name}/upstream-health/recent?limit=`
  返回最近 N 次**明细**（时间、结果、原因类别、耗时、来源）。**明细来自采样表聚合而非逐请求日志**——若需要逐条明细，只能用环形缓冲（内存、重启丢失）或新增明细表；本 FR 采用「分钟桶展开为明细摘要」的保守口径，并在 API description 写清这一限制。
- 均**仅管理员**（含失败原因与上游地址信息，不宜匿名暴露）；非 proxy 仓库返回 400（无上游概念）。

### 2.4 前端

- 仓库详情页新增「上游健康」区块：时间范围选择（复用 `DashboardRangePicker` 的交互惯式）+ 连通率趋势图（复用 `TrendChart`）+ 失败原因分布 + 最近 N 次明细表。
- **必须区分 `request` 与 `probe` 两条曲线**（或可切换），否则「探测 100% 成功但真实请求 60%」这一关键信号会被平均掉。
- 空态必须区分「没有数据」与「上游一直健康」——前者显示「尚无采样」，不能显示 100%。
- 窄屏降级为单列，趋势图可横向滚动。

## 3. 设计（怎么做）

### 3.1 模块与依赖

```
domain（采样记录器：真实请求结果 → 分钟桶累加；复用 FR-158 分类）
  ↓
scheduler（新增 upstream-probe 作业，仅 proxy 且 online）
  ↓
persistence（0051 迁移 + 分钟桶 upsert / 查询）
  ↓
api（两个只读端点 + 契约）
  ↓
web（趋势图与明细，复用 TrendChart）
```

### 3.2 采样写入

- 领域层定义 `UpstreamHealthRecorder` 接口（对齐既有 `RejectionRecorder` 范式：领域定义接口、装配注入、nil 表示不记录）。
- 写入用 **upsert 累加**（`ON CONFLICT DO UPDATE SET samples = samples + ?`），避免读-改-写竞态。
- **异步/批量**：真实请求路径不应为写库阻塞。建议进程内累积到小批量后刷盘（例如每 5s 或每 50 条），**但必须在进程关闭时 flush**，否则丢最后一段数据。若实现代价过高，可退回同步写并记录权衡（每分钟每仓库最多 2 行 upsert，SQLite 单写者可承受）。**该选择交给实现阶段按实测决定，spec 只要求「不阻塞回源主路径」**。

### 3.3 探测作业

- 复用 `scheduler.Register("upstream-probe", interval, run)`。
- 每轮：列出 `type=proxy AND online=true` 的仓库，逐个 `ProbeWithCredential`，结果按 `source='probe'` 写入当前分钟桶。
- **并发上限**（例如 8）避免同时探测大量上游；单个失败不影响其它。
- 探测**不得**影响断路器状态机（不调 `recordFailure` / `recordSuccess`）——它是观测，不是判定。这一点必须写测试钉住。

### 3.4 与既有能力的关系

- **不替换** FR-114 的当前状态展示：那仍是「此刻」的即时判断，本 FR 是它的历史补充。
- **不改** 断路器退避与阻断逻辑（FR-155 / FR-43）。
- **不改** FR-158 的五分类词表，只消费其结果。
- **不新增** Prometheus 指标（历史在库里；指标是聚合趋势，两者用途不同）。

## 5. 验收标准

### 5.1 单元与集成（须全绿）

- **分钟桶累加**：同一分钟多次同源采样累加为一行（samples/ok/各失败列正确），跨分钟分行。
- **两源不混**：同仓库同分钟的 `request` 与 `probe` 各占一行，互不覆盖。
- **分类对齐**：一次 `slow_transfer` 失败计入 `slow` 列，`local_write_failure` / `canceled` **不计入任何列**。
- **探测不改状态**：探测失败后断路器的 `Status` / `BlockedUntil` / 退避档位**均不变**，且不产生 `upstream_block_events`。
- **探测范围**：`hosted` / `group` / `offline` 仓库**不被探测**。
- **延迟口径**：无成功样本时 `avg_latency_ms` 为 NULL（不是 0）。
- **保留清理**：超过 30 天的行被清理，未超期的保留。
- **按仓库隔离**：A 仓库的采样不出现在 B 仓库的查询结果里。
- **保留策略不误删**：清理只针对本表，不影响 `host_metric_minute` 等其它表。
- **`-race` 通过**；既有 FR-154/155/157/158 用例全部继续通过。

### 5.2 实机验收（需用户确认）

> **硬约束：只在本地与测试站进行，禁止部署正式站。**

1. 对某 proxy 仓库发起若干次成功与失败的请求（含一次 DNS 失败、一次真实 404），等待一个探测周期。
2. 查询 `upstream-health?from=...&to=...`：应看到 `request` 与 `probe` 两条序列、连通率与失败原因分布正确。
3. 让上游不可达一个探测周期：`probe` 序列应出现失败点，且**断路器状态不被探测改变**（`blocked_repositories` 不因探测增长）。
4. 前端仓库详情页能看到趋势图与最近明细；空数据仓库显示「尚无采样」而非 100%。
5. 重启服务后历史数据**仍在**（这是与当前内存态状态的核心区别）。

## 6. 风险 / 待定

- **R1（写入压力）**：高频回源下分钟桶 upsert 可能成为写热点。缓解：按分钟聚合（每仓库每分钟最多 2 行）、必要时批量刷盘。若实测仍高，可退化为「先内存累加、定时落盘」。
- **R2（探测加重上游负担）**：每个 proxy 每分钟一次 HEAD。对上游数量多的实例需可配置间隔或关闭（建议提供 `JIAN_UPSTREAM_PROBE_INTERVAL`，0 = 关闭）。**默认值需在实机确认后定**。
- **R3（明细粒度）**：「最近 N 次明细」若取自分钟桶，则同分钟内多次请求只能看到聚合摘要，不是逐条记录。若用户要求逐条，需新增环形缓冲（内存、重启丢失）或明细表（写放大）。**本 FR 采用分钟桶口径，并在 API 文档写清限制**，这一取舍需用户确认。
- **R4（时钟与桶边界）**：分钟桶按 UTC 取整，与 `host_metric_minute` 一致；跨时区展示由前端按浏览器时区渲染（对齐 FR-140）。
- **R5（数据量与磁盘）**：每 proxy 每分钟 2 行 × 30 天 ≈ 86k 行/仓库，可接受；但实例有 100 个 proxy 时约 860 万行，需在实机确认磁盘与查询延迟。
