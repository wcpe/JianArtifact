# 功能规格：上游断路器不复用「回源慢」作不可达判据（FR-155）

> 状态：草拟　·　关联 PRD：FR-155（增强 FR-112）　·　分支：feature/fr155-slow-not-unreachable　·　依赖：FIX-1、[FR-154](../PRD.md)

## 1. 背景与目标

- **问题**：proxy 仓库的 auto-block 状态机把「回源超时」和「上游不可达」当成同一类失败。`fetchProxyAsset` 的错误分流只对 404 与 410 做了豁免，其余错误一律落进 `default` 分支触发仓库级 `recordFailure`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1062-L1080)）。因此一次 15MB 大制品的回源超时——上游只是**慢**，并不是连不上——会让整个 proxy 仓库进入 `AUTO_BLOCKED`。
- **后果**：
  - 阻断是**仓库级**的：窗口内该代理仓库**所有路径**都在 `proxyGet` 的 `shouldBlock` 处零连接快速失败（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L998-L1001)），连本可正常拉取的小制品也一起失败。用户侧表现为「WCPE 代理本身正常，但 JAR 拉不下来 / 缓存写错」。
  - 在 group 场景下危害被放大：group 读对每个成员单独判 `shouldBlock`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1314-L1317)），被误阻断的成员被整轮跳过，group 再把失败折叠成 404（该折叠缺陷由 FIX-1 修正，见 [FR-154](../PRD.md)），最终表现为大面积的**假 404**。
  - 退避窗口每档翻倍（[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L137-L145)），误判会自我加重：一次慢回源的代价按 40s→80s→160s 递增，且要等后台 HEAD 探测成功才恢复。
- **根因判断**：「超时」的语义是**预算内没拿到答案**，不是「连不上」。把它当作不可达证据，等于用「这一次慢了」推断「这个仓库整体不可用」，判据本身用错了层级。
- **目标（对用户）**：
  1. 单个慢 / 大制品的回源超时**不再**让整个 proxy 仓库进入 `AUTO_BLOCKED`，同仓库其它路径不受牵连。
  2. 上游**真正**不可达（连接失败 / DNS 失败 / TLS 失败 / 上游 5xx）仍按既有退避进入阻断，快速失败的保护**不回退**。
  3. 超时从「被误判为不可达」变成**可观测**的独立计数，运维能看出「这个上游一直慢」而不是只看到「一直在熔断」。
- **阶段**：P2，0.13.0 批次的缺陷修正型增强（直接延续 FR-112 → FR-43 的断路器线）。

## 2. 需求（要什么）

### 2.1 错误分类：把「慢」从「不可达」里摘出来

- 回源失败的判定必须**按错误种类分流**，而不是「非 404/410 即不可达」：
  - **超时**（调用方预算耗尽，或回源客户端自身超时）→ **不计入不可达**；
  - **连接失败 / DNS 解析失败 / TLS 握手失败 / 上游 5xx / 401 / 403** → 计入不可达，触发仓库级阻断；
  - **404 / 410** → 维持既有豁免（不阻断）。
- 超时的判定**复用既有 `upstream.IsTimeout`**（[client.go](../../apps/server/internal/upstream/client.go#L252-L266)），不自造第二套超时嗅探。该函数同时覆盖两条来源：
  - `errors.Is(err, context.DeadlineExceeded)`——调用方预算耗尽（含 FR-154 之后 group 成员确认阶段的 3s 预算）；
  - `errors.As(err, &netErr)` 且 `netErr.Timeout()` 为真——回源客户端自身超时（`*url.Error` 实现了 `Timeout()`）。
- **不区分**「谁的超时」：无论预算来自 group 成员窗口、HTTP 请求上下文还是 `JIAN_UPSTREAM_TIMEOUT`（[config.go](../../apps/server/internal/config/config.go#L651-L653)），对断路器而言结论一致——**没有证据表明上游不可达**，只是没在预算内拿到答案。

### 2.2 超时不参与仓库级阻断

- 超时发生时：**不改状态、不推进退避、不启动探测线程**，只做两件事——记录（见 2.3）与**释放半开名额**。
- 必须释放半开名额：`beginUpstream` 已经占住了本轮 `HALF_OPEN` 的探测名额（[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L222-L247)），若超时路径占着不放，后续所有请求会在 `probeInFlight` 处被无限快速失败——这本身就会复现「整仓不可用」。
- 释放沿用既有 `releaseProbe`（[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L253-L260)）：它「不改动状态与退避窗口，只释放名额并收口本轮」的语义**正好**适配「本项失败不构成状态判据」。
- **不写负缓存**：超时既不是「确认不存在」也不是「确认可达」，与现状一致（现状 `default` 分支也不写负缓存）。
- **两个回源调用点都必须改**，否则缺陷只修了一半：
  - `fetchProxyAsset` 的 default 分支（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1075-L1078)）；
  - `ResolveOCIProxy` 的 `recordFailure` 调用（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1155-L1163)）——它只豁免了 `ErrNotFound`，其余（含超时）一律阻断。

### 2.3 指标：超时成为独立可观测类别

- 在既有闭集 `UpstreamBlockReason` 中新增 `upstream_timeout`，使 `jianartifact_upstream_block_events_total{reason="upstream_timeout"}` 能在超时发生时累加（该 reason **不改变阻断状态**，只表示「发生过一次被判为『不快照阻断』的超时」）。
- 闭集机制**保持**：仍由 `knownBlockReasons` 白名单收口，`isKnownBlockReason` 判定不变，闭集外取值**继续被直接忽略**（[metrics.go](../../apps/server/internal/metrics/metrics.go#L130-L147)）——不得退化成自由字符串。
- 既有 `probe_failed` / `upstream_error` 的取值文本、计数语义、输出格式**全部不变**。
- **不与 FR-157 重叠**：FR-157 负责「解析结果维度」（Confirmed / Uncertain、成员、错误类别计数），本 FR 负责「阻断事件维度」（reason 闭集）。两者数据源不同（前者来自 `recordResolveFailure` 的 ctx 记录器，后者来自断路器状态机），不得合并成一个指标，也不得在本 FR 里提前实现 FR-157 的解析结果计数。
- 不新增配置项、不改退避曲线、不改 gauge `jianartifact_upstream_blocked_repositories` 的语义（它仍只数 `AUTO_BLOCKED` + `HALF_OPEN`，[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L264-L274)）。

### 2.4 与 FR-43 的边界（明确不改什么）

- **不改半开闸门语义**：`shouldBlock` / `beginUpstream` / `releaseProbe` 的判定与占位逻辑一行不改。
- **不改退避翻倍规则**：`nextBlock` 仍为「起始 base，每档 ×2」。
- **不改探测线程不变量**：「`AUTO_BLOCKED` / `HALF_OPEN` ⇒ 必有探测线程在跑」保持（[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L340-L346)）。
- 本 FR 只改一件事：**哪些错误会调用 `recordFailure`**。

### 2.5 范围内 / 范围外

- **范围内**：错误分类判定（新增一个共享判定函数）、`fetchProxyAsset` 与 `ResolveOCIProxy` 两个调用点的分流改造、`upstream_timeout` reason、指标文档与测试同步。
- **不做（范围外）**：路径级断路器（见 §3.4）、按错误类别区分的第二套退避窗口、超时阈值配置项、跨仓库聚合阻断指标、FR-157 的解析结果指标。

## 3. 设计（怎么做）

### 3.1 改动面

```
domain/asset_service.go
  ├─ 新增：回源失败分类判定（紧邻 mapUpstreamErr，复用 upstream.IsTimeout）
  ├─ fetchProxyAsset：default 分支前插入超时豁免
  └─ ResolveOCIProxy：把无条件 recordFailure 换成同一判定
domain/proxy_health.go
  ├─ UpstreamBlockReason 常量新增 UpstreamBlockReasonTimeout = "upstream_timeout"
  └─ releaseProbe 的注释口径补上「超时」（行为不变）
metrics/metrics.go
  └─ knownBlockReasons 白名单新增一项（闭集机制不变）
docs/OPERATIONS.md
  └─ reason 取值表加行
```

不新增配置项、不新增状态机入口、不新增指标族。

### 3.2 分类判定

在 `asset_service.go` 中、`mapUpstreamErr` 旁边新增一个**共享判定函数**（本规格只固定语义，标识符在实现时定稿），语义为：

```
输入：FetchWithCredential / 会话读取返回的 error
输出：(reason, block bool)
  block=true  → 调用 recordFailure(repoID, …, reason)   // 进入仓库级阻断
  block=false → 只记事件 + releaseProbe                  // 不改状态
```

判定顺序**必须**与 `mapUpstreamErr` 保持一致，避免两处对同一错误给出不同结论：

| 上游错误                   | 判定依据                               | block  | reason             | 附加动作                                              |
| -------------------------- | -------------------------------------- | ------ | ------------------ | ----------------------------------------------------- |
| 404 `ErrNotFound`          | `errors.Is(err, upstream.ErrNotFound)` | 否     | （不记）           | 写负缓存 + `releaseProbe` + `ResolveFailureConfirmed` |
| 410 `ErrGone`              | `errors.Is(err, upstream.ErrGone)`     | 否     | （不记）           | `releaseProbe` + `ResolveFailureUncertain`            |
| **超时**                   | `upstream.IsTimeout(err)`              | **否** | `upstream_timeout` | `releaseProbe` + `ResolveFailureUncertain`            |
| 连接 / DNS / TLS 失败、5xx | 其余全部（含 `*upstream.StatusError`） | 是     | `upstream_error`   | `recordFailure` + `ResolveFailureUncertain`           |

- 404 / 410 两行是**既有行为，逐字保留**，尤其 410 的豁免是为了不让 Go proxy 客户端链路被改成 502（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1069-L1074)）。
- `*upstream.StatusError`（[client.go](../../apps/server/internal/upstream/client.go#L37-L41)）落进「5xx/401/403 视为不可达」一侧，与既有 `shouldBlockStatus` 的口径一致（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1456-L1460)）。
- 判定函数只做**分类**，不做副作用；副作用（记事件、放名额、写负缓存）留在调用点，便于两个调用点各自决定收口细节。
- **放置位置**：与 `mapUpstreamErr` 同文件（`asset_service.go`，它已 `import` upstream 包并已在做同类错误分流），**不放进** `proxy_health.go`——状态机文件刻意不依赖 `upstream` 包，保持「状态机不认具体错误类型」的分层。

### 3.3 两个调用点的改造

**`fetchProxyAsset`**（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1061-L1080)）：在 `switch` 中新增超时 case（位置在 `ErrGone` 之后、`default` 之前）：

```
body, header, err := s.upstream.FetchWithCredential(...)
if err != nil {
    switch {
    case errors.Is(err, upstream.ErrNotFound):  // 不变
    case errors.Is(err, upstream.ErrGone):      // 不变
    case upstream.IsTimeout(err):               // 新增
        recordResolveFailure(ctx, ResolveFailureUncertain)
        s.health.recordBlockEvent(UpstreamBlockReasonTimeout)   // 只记，不阻断
        s.health.releaseProbe(repo.ID)                          // 必须放名额
    default:                                    // 不变
    }
    return nil, mapUpstreamErr(err)
}
```

- `recordBlockEvent` 是既有私有方法（[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L124-L133)），同包可直接调用，**不需要**新增状态机入口。
- 返回错误路径不变：仍走 `mapUpstreamErr`，超时仍然映射 `ErrUpstreamTimeout` → 504（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1434-L1435)、[handlers.go](../../apps/server/internal/api/handlers.go#L408-L409)）。**对外状态码不改**——本 FR 改的是「要不要因此阻断仓库」，不是「这次请求回什么」。

**`ResolveOCIProxy`**（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1150-L1164)）：当前 `!errors.Is(fetchErr, upstream.ErrNotFound)` 即 `recordFailure`。改为走同一判定函数：

- 超时 → 记 `upstream_timeout` + `releaseProbe`，不阻断；
- 其余非 404 → 维持 `recordFailure(upstream_error)`；
- `NewSession` 失败分支（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1150-L1154)）维持不变：建会话失败属于配置/凭据问题，与「慢」无关。

### 3.4 粒度：**不做**路径级断路器

- 现有闸门是**仓库级**（per repoID），本 FR **不引入路径级抑制**。
- 理由：
  1. 本 FR 的病根是**判据用错**，不是「粒度太粗」。把超时移出阻断判据后，慢路径不再影响任何其它路径，症状已经消失；再叠一层路径级断路器属于为已修好的问题追加机制。
  2. 路径级状态需要 per-path 状态表，key 无界增长（路径空间无界），必须配 LRU / 过期策略，是新的一类内存与淘汰问题；而 singleflight 已按 `repoID+path` 收敛（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1003-L1004)），同一慢路径的并发请求本就已经收敛成一次回源。
  3. 真实不可达天然是仓库级的（连不上就是整个 host 连不上），仓库级阻断对它的粒度是对的。
- 结论写死：**不做**路径级断路器，也不为它预留状态字段。

### 3.5 为什么不选另外两种方案

| 方案                                                    | 结论     | 理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 超时完全不参与仓库级阻断**（推荐）                 | **采用** | 判据正确：超时不能证明不可达。实现面最小——只加一个 case + 复用 `releaseProbe`，不动状态机、不动退避、不动半开闸门。副作用可控：慢上游失去「快速失败」保护，但慢上游本来也没法被快速失败救回来（每次请求都得等预算耗尽），而 `shouldBlock` 带来的收益主要体现在**连不上**的场景，那部分完全保留。                                                                                                                                                                                                                                                                                                                                          |
| B. 超时仍阻断，但阈值更高 / 退避更短 / 只进 `HALF_OPEN` | 不采用   | 现状 `remoteState` 的窗口字段是**单档**的（`blockedUntil` / `curBlock` / `autoBlockSeq`），要「按错误类别用不同阈值」就得拆成两套并行的窗口状态机，或给每个字段加一份超时专用副本；两种做法都会让 `beginUpstream` 的名额判定与 `checkStatus` 的等待逻辑出现「按类别分叉」，与 FR-43 刚固化的半开语义正面冲突。且「只进 HALF_OPEN 而不进完整封锁」在这套状态机里**不成立**：`HALF_OPEN` 的不变量是「窗口到期后试探」，若超时不推进退避却切 `HALF_OPEN`，`checkStatus` 的 `wait := time.Until(st.blockedUntil)` 会立刻为负、直接开探测，等价于「立即探测一次」——那干脆不要新状态，方案 A 用 `releaseProbe` 已经得到同样效果，且零新增状态。 |
| C. 仍阻断，但用独立 reason + 可配置是否参与             | 不采用   | 它只解决了「可观测」，没解决「小制品连带失败」这个真实痛点；把是否误伤交给配置，等于让**默认行为仍然有害**，并额外制造「阻断语义取决于某个环境变量」的运维负担与排查成本。要可配置就得新增 `JIAN_*` 项与非法值回退口径、改 OPERATIONS 环境变量表、写配置解析测试——成本高于收益，而收益只是「保留一个我们判断为错的判据」。                                                                                                                                                                                                                                                                                                                |

### 3.6 指标的闭集扩展

- `domain`：`UpstreamBlockReasonTimeout UpstreamBlockReason = "upstream_timeout"`，紧邻既有两个常量（[proxy_health.go](../../apps/server/internal/domain/proxy_health.go#L53-L58)）。该文件的注释已明确「新增取值必须先改规格并同步测试与 OPERATIONS.md」——本规格即该前置条件。
- `metrics`：`knownBlockReasons` 由两项扩为三项（[metrics.go](../../apps/server/internal/metrics/metrics.go#L59-L66)）；`isKnownBlockReason` 的实现不变，闭集外取值仍被忽略。
- **语义口径需要显式修正**：该族的名字是 `upstream_block_events_total`，而 `upstream_timeout` 按设计**不**产生阻断。处理方式（明确拍板）：
  - **不改指标名**——它刚随 FR-43 交付，改名会断掉运维已配的仪表盘与告警表达式；指标名只作稳定标识，语义以 HELP 文本与文档为准。
  - 在 `docs/OPERATIONS.md` 该族说明中把 `reason` 的语义**明确为「断路器判定事件的类别」**，并直接写清 `upstream_timeout` 是「被判为不阻断」的类别：它出现表示**有慢回源、且已被正确豁免**，不是「发生了阻断」。
  - 该族「即使无样本也输出 HELP/TYPE」的约定保持（[metrics.go](../../apps/server/internal/metrics/metrics.go#L360-L370) 附近的渲染路径）。
- 是否把该族改名为更准确的名字（如 `upstream_health_events_total`）**不在本 FR**，登记进 §6 待定。

### 3.7 与 FR-154 / FIX-1 的关系

- **FR-154（group 回源预算解耦）**：确认阶段 3s 预算耗尽产生的 `context.DeadlineExceeded` 正是本 FR 要豁免的超时来源之一。两 FR 互补：FR-154 让「大制品不再被 3s 预算截断」，本 FR 保证「即使被截断也不会把整个成员仓库打成阻断」。本 FR **不依赖** FR-154 先落地，也不改动 `groupMemberTimeout`（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1242)）。
- **FIX-1（group 把失败折叠成 404 的缺陷修正）**：本 FR 减少了「成员被误阻断 → group 跳过 → 折叠成 404」的发生面，但**不修正**折叠本身。两者必须都到位才能消除用户看到的假 404；本 FR 的验收不依赖 FIX-1 已合并（用单成员 group 或直接对 proxy 仓库断言即可）。

## 5. 验收标准

### 5.1 单元与集成（须全绿）

- **慢制品不牵连同仓库其它路径**：本地限速 / 拖延夹具下，`big.jar` 回源超时后——
  - 该次请求返回 `ErrUpstreamTimeout`（对外 504，语义不变）；
  - `svc.Status(repoID).Status` **不是** `AUTO_BLOCKED` 也不是 `HALF_OPEN`；
  - 紧接着对**同一 proxy 仓库**请求 `small.jar`（夹具对该路径立即 200）**成功**，内容正确，且**真正打到了上游**（夹具计数 +1，证明不是被阻断放行）。
  - 夹具要求：拖延必须发生在**响应头之前**（`<-r.Context().Done()` 或超预算的 sleep）。这是当前会误触阻断的路径；正文慢速（收到头之后再卡住）今日已不触发阻断（`recordSuccess` 在读完正文前就已调用，[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1082)），作为附加用例钉住「仍不阻断」即可。
- **真实不可达仍阻断（不回退）**：上游端口关闭时首次请求失败后 `Status == AUTO_BLOCKED` 且 `BlockedUntil` 非零；第二次请求在窗口内**零连接**快速失败（耗时显著短于首次，且上游无新连接）。
- **410 仍不阻断**：上游返回 410 → `Status` 保持非阻断、`releaseProbe` 被调用（半开名额不泄漏）、负缓存**不写入**。
- **指标**：`upstream_timeout` 在超时发生时计数 +1；既有 `probe_failed` / `upstream_error` 的计数与输出文本不变；闭集外取值（如仓库名、空串）仍被忽略、不产生系列。
- **回归保险（不得修改其断言来迁就新实现）**：
  - [proxy_half_open_test.go](../../apps/server/internal/domain/proxy_half_open_test.go)：`TestResolveProxyHalfOpenBlocksBusinessTrafficBehindProbe`、`TestResolveProxyHalfOpenProbeSuccessRecovers`
  - [proxy_health_test.go](../../apps/server/internal/domain/proxy_health_test.go)：`TestBeginUpstreamAllowsExactlyOneConcurrentProbe`、`TestHalfOpenFailureAdvancesBackoffOnce`、`TestHalfOpenSuccessResetsBackoff`、`TestReleaseProbeFreesHalfOpenSlot`、`TestBlockedCountCountsBlockedAndHalfOpen`、`TestRecordFailureEmitsBlockEvent`
  - [recheck_connection_test.go](../../apps/server/internal/domain/recheck_connection_test.go)：`TestRecheckConnectionFailureToAutoBlocked` 等 4 例
  - [asset_service_resolve_test.go](../../apps/server/internal/domain/asset_service_resolve_test.go)：`TestResolveProxyAutoBlockZeroConnection`、`TestResolveProxyAutoBlockRecovers`、`TestResolveProxyAutoBlockBackoffIncrements`、`TestResolveProxyAutoBlockConcurrent`。**注意**：其中前两条与 `TestResolveGroupFuseSkipsUnreachableMember`、负缓存两例的错误身份断言已随 FIX-1 从「404」改为「502」（连接失败属不可判定、非超时），回归保护的是**阻断状态、窗口内零连接、耗时上界与恢复语义**，不是旧的 404 返回值；本 FR 不得把它们改回 404。
- **`-race` 通过**：`go test -race ./internal/domain/... ./internal/metrics/...`。
- **质量门**：`bash scripts/check.sh` 全绿。

### 5.2 实机验收（需用户确认）

> **硬约束：只在本地与测试站进行，禁止部署正式站。**

- 环境：本地或测试站独立实例，上游指向一个可控的「可连但很慢」源（例如本地起一个对 `/big/*` 延迟响应的静态服务）。
- 手动复验步骤：
  1. 配一个 proxy 仓库指向该慢源，`JIAN_UPSTREAM_TIMEOUT` 调小（如 5s）以便复现。
  2. 拉取一个会超时的大制品：`curl -sS -o /dev/null -w '%{http_code}\n' http://<host>/repository/<proxy>/<big-path>` → 期望 **504**。
  3. **立刻**拉取同仓库一个小制品：`curl -sS -o /dev/null -w '%{http_code}\n' http://<host>/repository/<proxy>/<small-path>` → 期望 **200**（本 FR 的核心判据）。
  4. 打开管理界面仓库列表 / 详情，确认该 proxy 仓库状态**不是** `AUTO_BLOCKED` / `HALF_OPEN`。
  5. `curl -s http://<host>/metrics | grep upstream_block_events_total` → 确认出现 `reason="upstream_timeout"` 且计数 ≥1，同时未被误记为 `upstream_error`。
  6. 反向验证：把该 proxy 上游地址改为不可达端口，重复拉取 → 期望状态变为 `AUTO_BLOCKED`，窗口内后续请求快速失败，`reason="upstream_error"` 计数增长。
  7. 上游恢复后确认自动回到 `AVAILABLE`（既有探测恢复路径不变）。
- 全部 7 步由用户在本地 / 测试站确认通过后，本条才算交付。

## 6. 风险 / 待定

### 6.1 风险

- **慢上游失去快速失败**：整体「接得通但一直慢」的上游不再被自动阻断，每次请求都要各自耗到预算上限才失败。这是方案 A 的**已知代价**，判断上可接受（快慢只有上游自己决定，阻断并不能让它变快，只会让「其它本来也拿不到的东西」提前失败）。观测手段就是新 reason：`upstream_timeout` 持续增长即表示「该上游长期慢」，属于运维该处理的上游容量/网络问题，而不是让断路器去屏蔽。
- **判定顺序错位会把豁免写反**：若把 `IsTimeout` 放在 `default` 之后、或与 `ErrNotFound` / `ErrGone` 的先后搞错，会出现「404 被记成超时」之类的错判。用 §4.3 的表驱动单测把分类表钉死，并让判定函数只有**一处**实现、两个调用点共用。
- **OCI 路径容易被漏改**：`ResolveOCIProxy` 的 `recordFailure` 是第二个调用点，且写法与 `fetchProxyAsset` 不同。漏改则 OCI 仓库仍会被慢回源阻断，验收用例若只覆盖 raw 路径会漏掉。已列为独立任务与独立断言点。
- **`upstream_timeout` 落进「block_events」族的语义张力**：见 §3.6，靠文档口径澄清 + 不改指标名来消化；后续是否改名列入待定。

### 6.2 待定

- **该族指标是否改名**（`upstream_block_events_total` → 更准确的名字）：本 FR 不做，避免断掉既有仪表盘与告警；若要改须走兼容期与迁移说明。建议与 FR-157 一起评估。
- **`context.Canceled`（客户端断连）也落进 `default` 分支**：客户端关页 / 反向代理掐断会让 ctx 被取消，`IsTimeout` 返回 false，今日同样会触发 `recordFailure` → 仓库被阻断。这是与本 FR 同类的另一处误判，但**不在本 FR 范围**；建议另立条目（或与 FR-157 合并评估），本规格只登记事实不做承诺。
- **正文读超时的错误未映射为 `ErrUpstreamTimeout`**：`recordSuccess` 在收到响应头后即调用（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1082)），正文阶段卡死会从 `putStagedBlob` 返回原始错误（[asset_service.go](../../apps/server/internal/domain/asset_service.go#L1083-L1086)），既不改断路器状态也不按 504 映射。属既有缺口，本 FR 不动，登记备查。
- **`ErrCredentialUnavailable` / `ErrUnsafeURL` 仍走 `default` → 阻断**：这两类属于配置问题而非上游不可达，按现状仍会触发阻断。本 FR **刻意不扩大分类范围**（保持最小改动面），是否需要一并豁免列入待定。
- **OCI 路径的 410 与 raw 路径不一致**：raw 路径豁免 `ErrGone`，OCI 路径只豁免 `ErrNotFound`。本 FR 只把超时从 OCI 的阻断分支摘出，`ErrGone` 的差异不统一，登记备查。
- **FIX-1 在 PRD 中没有独立条目**：表头的 `FIX-1` 指 group 不可判定返回码分离（即 group 把失败折叠成 404 的缺陷修正），在 PRD 里以 [FR-154](../PRD.md) 的括注形式登记（「该项属 FR-110 已交付实现的缺陷修正，记入 CHANGELOG 不单列 FR」）。若该缺陷最终单独立号，需回改本表头。
- **与 FR-157 规格的跨规格口径对齐**：[`0.13.0-proxy-resolve-observability.md`](0.13.0-proxy-resolve-observability.md) 的「与阻断事件的边界」目前写的是「一次上游超时可能同时让 `reason="upstream_error"` 加一」——那是本 FR 落地**之前**的口径。本 FR 合并后，超时应计到 `reason="upstream_timeout"`，该处文字需同步改一句（一句话文档改动，随实现提交，不在本规格内执行）。

### 6.3 范围外

- 不改半开闸门（`shouldBlock` / `beginUpstream` / 试探名额唯一性）。
- 不改退避曲线形状（仍为起始 base、每档翻倍、无上限、无抖动）。
- 不做路径级断路器（§3.4）。
- 不做跨仓库聚合的阻断指标。
- 不新增超时阈值 / 是否参与的配置项。
- 不改对外状态码（超时仍 504、上游故障仍 502）。
- 不实现 FR-157 的解析结果计数指标。
