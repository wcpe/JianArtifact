# 功能规格：Maven 版本级清理与资产回收站

> 状态：已交付@未发布　·　关联 PRD：FR-154 / FR-155　·　分支：feat/maven-version-trash

## 1. 背景与目标

一次线上事故暴露了 Maven 聚合仓的**坐标遮蔽**问题：同一个 `group:artifact:version`
同时存在于 releases 与 snapshots 两个成员仓库，聚合仓按成员顺序返回了 releases 里
那份旧制品（2152067 字节），而 snapshots 里才是正确的新制品（2167993 字节，含 5 个新任务类）。
两份大小只差十几 KB，靠"能下载成功"完全发现不了。

排查过程中确认了三件事，构成本规格的出发点：

1. **换聚合仓成员顺序解决不了问题**。它只能把"哪个被遮蔽"换到另一边；真正要做的是
   让该坐标只指向正确来源，前提是先**看得见重复**。
2. **`-SNAPSHOT` 出现在 release 仓是根源**。它在 release 仓里只能是字面文件（覆盖写、
   无构建序号），在 snapshots 仓里则是时间戳构建 + `<snapshot>` 元数据，两种表示互不兼容。
3. **既有回收站接不住这个场景**。`trash_entry` 记录磁盘路径、靠 `os.Rename` 恢复，
   而 Maven 资产是 SQLite 里的 asset 行 + 内容寻址 blob，同一 blob 可能被多个路径共享，
   没有"一个可 rename 回去的原文件"。

目标是：把"删掉某个 Maven 版本（含其全部命名锚点）"变成一次可见、可核对、可恢复的操作，
并能诊断出同一坐标的跨仓重复。

### 关键洞察：命名锚点不需要枚举

同一版本目录下的命名变体会持续增加（主档 / 多种 classifier / 四种校验和 / 版本级 metadata /
SNAPSHOT 时间戳构建 / 字面 SNAPSHOT）。**任何"列后缀白名单"的做法都迟早漏掉新变体**，
而漏掉一个文件会让 metadata 或校验和指向不存在的内容。

因此展开按**目录前缀**进行：`group 路径/artifact/version/` 下的全部文件天然都是该版本的组成。
前缀是可靠边界，命名变体无法穷举。

## 2. 需求（要什么）

- **清理计划（预览）**：按坐标展开版本目录下全部文件，按语义类别（主档 / classifier /
  校验和 / metadata / other）分组，给出文件数、字节、以及 SNAPSHOT 的历史构建列表。
  只读，不产生任何变更。
- **版本级软删除**：把版本移入**资产回收站**，保留 blob，可随时恢复。
  支持整个版本，也支持 SNAPSHOT 只删某一次时间戳构建。
- **资产回收站**：列表 / 恢复 / 彻底清理。恢复还原到与删除前**完全一致**（含时间戳与校验和）。
- **跨仓同坐标诊断**：列出该坐标在哪些 Maven hosted 仓库存在，并给出内容指纹，
  区分"纯冗余"与"真遮蔽风险"。
- **运维口径统一**：资产回收站与既有存储清理回收站**共用同一个保留期、同一个 trash-gc 作业**，
  不新增第二套过期规则。
- 不做（范围外）：其它格式（npm/raw/docker 等）的版本级软删除；自动修复跨仓重复；
  为 group 仓增加"坐标归属"路由规则（留待后续）。

## 3. 设计（怎么做）

### 3.1 数据模型：为什么新建 `asset_trash` 而不复用 `trash_entry`

`trash_entry` 的三条结构性约束决定了它无法承载资产：

| 约束                                          | 对资产的含义                                             |
| --------------------------------------------- | -------------------------------------------------------- |
| `task_id NOT NULL REFERENCES clean_task`      | 资产删除与"存储清理任务"无关，造合成任务会让两套语义纠缠 |
| 恢复靠 `os.Rename(trash_path, original_path)` | 资产没有可 rename 的原文件（共享 blob 尤其没有）         |
| 条目语义是"磁盘路径"                          | 资产要恢复的是**元数据行**，不是文件位置                 |

混用不是"复用"，而是语义污染：`task_id` 与 `trash_path` 会变成恒空的无意义列，
且每次改动都要重新判断"这条记录属于哪种"。

**于是**：数据模型分开（`asset_trash` 独立表，迁移 `0053_asset_trash.sql`），
但**对外只有一个回收站**——统一 API 视图、同一页面相邻 Tab、同一保留期、同一 GC 作业。
数据库干净，界面不分裂。

`asset_trash` 保存 asset 的**完整快照**（含 `sha1`/`md5`/`content_type`/`created_at`/`updated_at`）。
只存 `path + blob_hash` 会让恢复后的制品在排序、时间显示与校验和字段上与原件不同——
用户点的是"恢复"，不是一个"碰巧内容相同的重新上传"。

### 3.2 blob 存活判定：必须把回收站引用算作活引用

软删除保留 blob，但**既有的孤立回收不这么认为**。三处判定点都必须改：

- `AssetMutationRepo.CountBlobReferences`（`RemoveIfUnreferenced` 的判据）；
- `AssetRepo.ListReferencedBlobHashes`（存储体检的孤儿判定）。

若漏改：删除瞬间该 blob 变成"零引用"，随后被孤立回收物理删除，
用户点恢复会得到一条指向已消失 blob 的资产行——**恢复看似成功、下载却失败**，
是最隐蔽的数据丢失形态。

### 3.3 提交路径：为什么需要"保留 blob"的独立入口

协调器在**删除前**调用 `stageUnreferenced` 判定引用并搬移孤立 blob。
软删除走常规路径时，回收站记录尚未写入（它在删除后的 hook 里），
于是 blob 被判成孤立并搬进隔离区——恢复会拿到指向隔离区的资产行。

**修法**：新增 `ApplyWithOperationIDAndHookKeepBlobs`，除"不做孤立隔离"外与常规路径完全一致
（同样走 intent 前置、快照、完成事务与失败回滚）。用独立入口而不是给 `Item` 加标记位，
因为"保留 blob"是整体语义，不可能只对其中一条 item 生效。

安全性：blob 不会被永久泄漏——回收站条目参与引用计数，条目 `purged` 后计数归零，
随后的 `RemoveIfUnreferenced` / 定时 blob-gc 会正常回收。

### 3.4 原子性口径

- **写入回收站与从 asset 表删除在同一事务**：用 `MutationCompletionHook`
  （删除之后、提交之前，同一 tx 内执行）。分开提交会在中间崩溃时留下
  "元数据没了、回收站也没有"的孤儿状态。
- **恢复**：写回 asset 行与标记条目 `restored` 同事务。
- **彻底清理**：顺序必须是"先标记 purged 并落库，再释放 blob"。反过来的话，
  若释放后崩溃，条目仍是 staged 但内容已没了，恢复会报"内容已不存在"——
  那让一次诚实的清理动作变成了数据损坏。
- **分批提交，不受 500 条上限约束**：SNAPSHOT 累积几十个构建后文件数轻易过千，
  沿用 `maxAssetOperationItems` 会让用户永远删不掉最该删的版本。
  每批自身是完整原子操作，**批间不保证原子性**——这是有意的取舍：
  宁可"删了 800/1000 且能看到已完成部分"，也不要"一个都删不掉"。
  残留状态可见、可恢复、可继续删。

### 3.5 恢复绝不覆盖

目标路径已存在时跳过并如实报 `conflicts`。覆盖等于执行一次删除，
而用户点的是"恢复"——反向语义会造成最难排查的数据丢失
（原文件没了，回收站里那份也变成"已恢复"状态）。与既有两个回收站口径完全一致。

### 3.6 分类算法要点

- **构建号识别**支持 classifier 位于构建号前后两种形态
  （`...-3.jar` 与 `...-3-sources.jar`），相邻两段 `<timestamp>` + `<digits>` 才认定，
  避免把 `-rc1` 误判成构建号。
- **校验和文件继承其底层制品的构建号**，否则删单次构建会留下指向已删文件的校验和残骸。
- **metadata 优先于其它类别判定**（它同时也是 `.xml`），否则 `maven-metadata.xml.sha1`
  会被误判成"名为 maven-metadata.xml 的主档"。

### 3.7 跨仓诊断：指纹的含义

指纹 = 按 `path` 排序后对 `path + blobHash + size` 求 sha256 取前 16 位。

- 必须包含 `path`：同一 blob 摆在不同路径下是不同布局，而 Maven 客户端按路径取文件。
- 排序后再累加：保证指纹与遍历顺序无关。
- **指纹相同 = 纯冗余**（删任一副本都安全）；**不同 = 真遮蔽风险**，需人工判定正确来源。

只统计 `maven + hosted`：proxy 的"存在"取决于上游当时状态，group 本身不持有文件，
算进来会产生"同一份内容被数三次"的假重复。

## 5. 验收标准

**清理计划**

- 含 jar/pom/sources/javadoc/4 种校验和/版本级 metadata 的版本，计划条目数 = 实际文件数，一条不漏。
- SNAPSHOT 版本能列出全部时间戳构建，字面 `-SNAPSHOT` 单独成组。
- 含 `..` 或路径分隔符的坐标被拒绝（否则 LIKE 前缀会逃逸到别的目录）。
- 不存在的版本返回 `exists=false` 而非报错。

**软删除**

- 删除后读/搜索/配额均不可见；回收站有对应条目。
- **blob 必须仍存在**（这是可恢复的唯一依据）。
- 回收站条目保存完整校验和与时间戳。
- 部分失败时已完成批次保留并如实上报。
- 回传计划外路径导致整批拒绝，且不影响任何资产。

**恢复**

- 恢复后 blob hash / size / sha1 / content_type / created_at / updated_at 与删除前完全一致。
- 目标路径被占用时保护性跳过并报 `conflicts`，现有内容不变。
- blob 已被回收时如实报 `missing`，不伪造恢复。

**彻底清理**

- 清理前 blob 仍存在；清理后才释放。
- 共享 blob（同内容被其它路径引用）**不得被释放**。

**跨仓诊断**

- 两仓同坐标不同内容 → `identical=false`、`distinctFingerprints=2`、有 warning。
- 两仓同坐标相同内容 → `identical=true`、指纹相同。
- 只统计 hosted，proxy/group 不计入。

**运维口径**

- 资产回收站与存储清理回收站共用同一保留期与同一 trash-gc 作业。
- `retention <= 0` 表示**不自动清理**，绝不能反转成"立即清空"。

**质量门**

- `gofmt` / `go vet` / `go test ./...` 全绿（后端）；`tsc --noEmit` / `vitest run` / `eslint` 全绿（前端）。

## 6. 风险 / 待定

- **回滚需先清空资产回收站**：旧版本代码不认识 `asset_trash`，回滚后其中的 blob
  会被判为孤儿并被 blob-gc 回收。降级前必须先恢复或彻底清理。
  这一点已写入迁移文件的回滚说明。
- **保留期内仍占磁盘**：软删除不释放空间。`Stats()` 返回的字节即"回收站最多能为你省下的量"，
  部署时应据此设置保留期长度。
- **批间不原子**：跨 500 条的删除部分失败会留下已删/未删混合状态。这是为"可删除性"做的取舍，
  结果里有 `batches` 与 `trashed` 供判断。
- **只删单个构建时重建 metadata 采用删除而非改写**：版本级 `maven-metadata.xml` 描述的是
  "当前指向哪次构建"，删掉被指向的构建后整体移除这些文件，让客户端显式拿不到"当前构建"，
  而不是拿到一个 404 的时间戳。若后续需要"回退到上一个构建"，需另行实现重写逻辑。
- **诊断只覆盖 hosted**：proxy 仓的上游状态是时变的，把它纳入会让报告不稳定；
  跨实例（Nexus 上游）的重复不在本功能范围内。
