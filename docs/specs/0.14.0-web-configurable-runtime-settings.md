# 功能规格：运行期策略配置 Web 化（把 13 项环境变量搬上设置页）

> 状态：草拟（待用户审核）　·　关联 PRD：FR-165 / FR-166　·　分支：feat/web-configurable-settings
> 前置：0.13.0（`e27411c`）已合并；本批基于其 `main`

## 1. 背景与目标

### 1.1 现状

仓库共有 **47 个 `JIAN_*` 环境变量**，其中只有 **7 个**能在设置页改（`public_url`、`upstream_timeout`、`group_member_timeout`、`negative_cache_ttl`、备份三项）。剩下 40 个必须「改 env + 重启进程」。

这不只是不方便，是**能力错配**：这 40 个里有 13 个是纯粹的运行期策略——作业多久跑一次、回收站留几天、缓存活多久。它们改完本来就能立即生效，却被锁在「重启才有新值」的启动路径里。运维为了把「storage-cleanup 从每天改成每 6 小时」这种调整，得重启一个承载 11GB 数据、21 个仓库的生产实例。

### 1.2 目标

把 **13 项运行期策略**搬上设置页，环境变量降级为首次播种的初值。沿用 0.13.0 已建立的模型（`setting 表 > 环境变量（仅播种）> 代码默认值`），不发明新机制。

### 1.3 范围外

- 启动期固定项（监听地址、数据目录、TLS、启用格式、连接池）**永不进 UI**——它们要么改完必须重启，要么改错会让实例起不来或连不上。
- 凭据与密钥（`JWT_SECRET`、`MIGRATION_CREDENTIAL_KEY`、LDAP 密码、OIDC secret）**永不进 UI**。
- OIDC / LDAP 的身份提供商配置（14 项）：安全敏感且改错会锁死登录，单开一期。
- 已退役的 `sync_*` 两项：属死配置，本批顺手清理而非搬上 UI。

## 2. 需求（要什么）

### 2.1 迁移清单（13 项）

| 分组           | 环境变量                               | 代码默认 | 语义                                           |
| -------------- | -------------------------------------- | -------- | ---------------------------------------------- |
| **作业间隔**   | `JIAN_BLOB_GC_INTERVAL`                | 86400s   | 孤儿 blob 回收；0 禁用                         |

|                | `JIAN_BACKUP_ORPHAN_CLEANUP_INTERVAL`  | 86400s   | 孤儿备份包回收；0 禁用                         |
|                | `JIAN_TRASH_GC_INTERVAL`               | 86400s   | 回收站保留期回收；0 禁用                       |

### 2.2 生效时机必须如实标注

这是本批最容易做错的地方：**13 项里只有部分能真正"保存即生效"**。

| 生效方式                   | 项目                               | 说明                                           |
| -------------------------- | ---------------------------------- | ---------------------------------------------- |
| **下一轮作业生效**         | 5 个作业间隔                       | 调度器需新增「运行时改间隔」能力（见 §3.2）    |
| **下一次读取生效**         | 容量缓存 TTL、搜索超时、断路器退避 | 这些在请求路径上按需读取，改完立即影响后续请求 |
| **下一次作业运行生效**     | 4 个保留策略                       | 由作业在每轮开始时读取                         |
| **下一次清理前置检查生效** | 回收站上限、保留天数               | 在下一次 cleanup / trash-gc 时判断             |

**要求**：设置页每个字段必须标注真实生效时机，不能一律写「立即生效」。写成"立即"但实际要等下一轮作业，等于给运维一个错误预期。

### 2.3 设置页分区

现有两栏布局塞不下 13 个新字段。新增独立分区「运行期策略」，内含四组（作业间隔 / 保留策略 / 容量与阈值 / 回源与搜索），默认折叠概览、展开编辑。

## 3. 设计（怎么做）

### 3.1 沿用既有模型

```
读取优先级：setting 表 > 环境变量（仅首次播种）> 代码默认值
播种时机：启动时表里无该键，用 env 值写入（seedSettingDefault 已实现，只写缺失键）
```

### 3.2 调度器新增「运行时改间隔」

现状：`Register(name, interval, run)` 在启动时固定 interval，`job.loop` 每轮读 `j.interval`。

改法：给 `job.interval` 加原子读写（`atomic.Int64` 存纳秒），新增
`SetInterval(name string, d time.Duration) bool`：

- 已注册且 d > 0 → 更新，返回 true（**从下一轮起生效**，当轮不中断）
- 未注册或 d <= 0 → 返回 false，不报错（与 `Register` 的「静默跳过」口径一致）

为什么不在运行时重建作业：重建会丢掉 `runs` / `failures` 等历史计数，且与 `Run`（手动触发）的独占状态位存在竞态。改一个原子变量最小且无副作用。

### 3.3 校验口径

对齐既有两类范式，**不发明第三种**：

| 类型                   | 范式                     | 例                                                                             |
| ---------------------- | ------------------------ | ------------------------------------------------------------------------------ |
| 必须为正（无禁用语义） | 夹取到上限 + 中文警告    | 搜索超时、断路器退避                                                           |
| 0 有明确语义           | 0 合法保留，负数回落默认 | 作业间隔（0=禁用）、保留天数（0=不限）、容量上限（0=不限）、缓存 TTL（0=禁用） |

上限**按量纲分组**，不统一用同一个常量：

| 量纲                                                        | 上限                                | 理由                                                                                                         |
| ----------------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 秒级请求预算（搜索超时 / 断路器退避 / 容量缓存 / 成员确认） | `maxConfigSecs = 3600`              | 这些都是「一次请求最多等多久」，一小时已是极端                                                               |
| 作业间隔                                                    | `maxBackupAutoIntervalSecs = 30 天` | **不能复用 3600**：4 个清理作业的默认间隔就是 86400 秒，统一夹到 3600 会让「每天一次」静默变成「每小时一次」 |
| 小时类（宽限期 / 临时文件存活）                             | 8760（一年）                        | 同上，避免默认值被夹                                                                                         |
| 天类（元数据保留 / 回收站保留）                             | 365                                 | 同上                                                                                                         |
| 字节类（回收站上限）                                        | 1 TiB                               | 默认 2 GiB 已超 32 位 int，用 `int64`                                                                        |

> 这条是核实后修正的：规格初稿写「统一 3600」，但那样会把默认值原样回存时夹坏——
> 用户什么都没改、只是点了保存，「每天一次」就变成「每小时一次」。上限的作用是挡
> 数量级笔误，不是把合法默认值改掉。

### 3.4 节点本地分类

13 项全部是**节点本地**（`isNodeLocalSetting`），与既有 `group_member_timeout` 同理由：它们约束的是「本节点怎么用自己的磁盘、多久跑一次自己的作业」，不参与跨节点复制。

### 3.5 死配置清理（FR-166）

`JIAN_SYNC_INTERVAL`、`JIAN_SYNC_PEER_URL`：集群复制已退役（`wiring.go` 多处注明），这两项只剩在设置页回显一个无意义的值——运维看到会去配，配了没有任何作用。

删除范围（四层，缺一层就留半拉）：

- 后端 `config.go`：两个 env 常量、`defaultSyncInterval`、`syncInterval()` 解析函数、`Config` 两个字段
- 后端 `setting_service.go`：`SettingKeyReplSyncInterval`、`SyncIntervalSecs` / `SetSyncInterval`、`SettingsUpdate.SyncInterval` 与写入分支
- 后端 `settings_handlers.go`：`defaultSyncIntervalSecs`、Response/Request 字段、快照回填、校验分支
- 后端 `wiring.go`：播种行
- 前端 `endpoints.ts` / `SettingsPage.tsx`：类型与表单透传
- devmock `store.ts`：类型、初值、`updateSettings` 的 `Omit<...>` 键
- 两处测试桩（`BackupsTab.test.tsx`、`SettingsPage.test.tsx`）

另外顺手删掉 `isNodeLocalSetting` 末尾的 `strings.HasPrefix(key, "repl:")` 兜底：复制退役后没有任何 `repl:` 键会被写入或读取，留着等于给「算不算节点本地」留一条无人使用的旁路。

## 5. 验收标准

### 自动化（必须全绿）

- **播种**：setting 表为空时用 env 值写入；表里已有值时不覆盖（变异验证：改成无条件覆盖，用例须红）。
- **夹取**：0 / 负数 / 超大值按 §3.3 口径处理，超上限打中文警告。
- **热生效**：改作业间隔后**不重启**，调度器下一轮按新间隔（用例用短间隔验证，不依赖 wall clock 长等）。
- **调度器并发**：`SetInterval` 与 `loop` 并发读写 interval 在 `-race` 下无竞态。
- **未注册作业**：`SetInterval` 返回 false 且不 panic。
- **回显**：GET /settings 返回 13 项的新值；缺失时回退默认。

### 实机

- 在测试站改「storage-cleanup 间隔」为 60s，观察调度器状态里该作业的 interval 变化（不重启）。
- 改回收站上限为 0，确认新清理不再被拒。

## 6. 风险 / 待定

- **13 个字段的 UI 密度**：设置页会变长。若不做分区/折叠，用户找不到东西。本批用「运行期策略」独立分区 + 四组分隔缓解，但需实机看效果。
- **生效时机文案是最容易出错的地方**：详见 §2.2。文案写错比不写更糟。
- **作业间隔改小后的负载**：把 `blob-gc` 从每天改成每 5 分钟，会显著增加磁盘遍历。属运维自主决策，但界面应提示「过小间隔会持续占用 IO」。
- **调度器语义边界**：`SetInterval` 只影响下一轮，不打断当轮。若本轮作业本身跑了很久（如 11GB 实例的 blob-gc），新间隔要等它结束后才起算——这是刻意保留的「不自我重叠」语义，需在文档写明。
