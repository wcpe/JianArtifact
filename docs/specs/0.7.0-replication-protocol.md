# 功能规格：节点间复制协议（GET 拉取 + blob 流式）

> 状态：已交付@v0.7.0　·　关联 PRD：FR-84　·　分支：main　·　依赖：FR-83（变更日志引擎）、ADR-0013

## 1. 背景与目标

FR-83 已落地变更日志引擎（repl_change + ReplicationService.Record/Apply/LWW）。FR-84 补齐**节点间传输**：让一个节点（拉取方）能从对端（被拉取方）经 HTTP GET 拉取变更并应用到本地，blob 只传缺失。

核心约束（用户明确 + ADR-0013）：**同步通道全部走 GET 拉取，禁止 PUT 推送**——Cloudflare Tunnel / CDN 的上传体积限制只作用于请求体（上传），对响应体（下载）无大小限制；任何"推送"行为都会撞限制。

目标（对用户）：

- 两个域名两台机器可组主备；备→主直连、主→备经 Tunnel 域名，双向都是 GET 拉取；
- 新节点首启 = `pull?since=0` 重放全部变更日志（全量初始化），blob 按需只拉缺失；
- 复制端点仅专用同步令牌可访问。

## 2. 需求（要什么）

### 服务端（被拉取方，提供数据）

- `GET /api/v1/cluster/sync/pull?since=<seq>&limit=<n>`：返回 `seq > since` 的变更列表（按 seq 升序）与最新 seq。
  - 响应：`{"changes":[...], "latestSeq":N}`，`changes` 元素为 `repl_change` 行（seq/node_id/op/entity_type/entity_key/data/ts）。
  - `since=0` 即全量初始化（重放全部日志）。`limit` 缺省取合理上限（如 500），`changes` 为空也返回 `latestSeq`（供拉取方推进水位）。
- `GET /api/v1/cluster/sync/blob/<hash>`：按内容哈希流式返回 blob 字节；哈希不存在返回 404。
- **鉴权**：以上端点要求请求头 `Authorization: Bearer <token>`，且与实例同步令牌 `JIAN_SYNC_TOKEN` 一致；未配置 `JIAN_SYNC_TOKEN` 时端点整体禁用（404）。与管理登录体系（JWT/API Token）完全独立。
- 端点不进 OpenAPI 契约（与 tree/search/settings 等非契约端点同先例）。

### 客户端（拉取方，消费数据）

- `ReplicationClient`（domain 层新增，HTTP 客户端）：
  - `Pull(since int64, limit int) ([]repository.Change, latestSeq int64, err error)`：GET 对端 pull。
  - `FetchBlob(hash string) (io.ReadCloser, error)`：GET 对端 blob（流式）。
  - `Sync(since int64) (newLatestSeq int64, err error)`：一站式同步——循环 Pull 变更 → `ReplicationService.Apply` → 对 `asset` put 变更检查本地 blob 缺失并 FetchBlob 补拉；返回推进后的最新 seq（供调度器水位 FR-85 用）。
- 对端 URL 与令牌由调用方（FR-85 调度 / FR-86 管理面）提供；FR-84 只提供能力，不做调度。

### 边界

- **不做**：调度 / 对账 / 首启自动触发（FR-85）；管理面配置（FR-86）；变更日志 GC；PUT/POST 推送端点（明确不做）。
- 全量初始化**不单独设 full 端点**：`since=0` 重放日志即全量（FR-83 Apply 按 seq 顺序应用，tombstone 不会被乱序覆盖）。

## 3. 设计（怎么做）

### 3.1 配置

- 新增环境变量 `JIAN_SYNC_TOKEN`（可选）：设置后启用复制端点；未设置端点 404。两个节点各自配置（建议双方共用同一 token 或各自 token——本期要求两端配置相同 token，简化；多 token 留 FR-86）。

### 3.2 模块与依赖

```
protocol（或 httpserver）  注册 /api/v1/cluster/sync/* 路由 + 同步令牌中间件
  ↓
domain.ReplicationClient   Pull / FetchBlob / Sync（HTTP 客户端）
  ↓
domain.ReplicationService  ListSince / Apply（FR-83 已有）
blobstore.Store            Exists / Put（blob 补拉落盘）
```

- 服务端端点实现放 `internal/httpserver`（注册进 `WithProtocolRoutes`），直接调 `ReplicationService.ListSince` 与 `blobstore.Open`（经现有服务组装）。
- 客户端 `ReplicationClient` 放 `internal/domain`（依赖 ReplicationService + blobstore），供 FR-85 调度复用。

### 3.3 同步令牌中间件

- 对比 `Authorization: Bearer <token>` 与 `JIAN_SYNC_TOKEN`（`subtle.ConstantTimeCompare` 防时序）；不匹配 401；未配置 env 端点 404。

### 3.4 Sync 流程（客户端一站式）

```
1. since = 本地水位（调用方传入；首启 0）
2. 循环：
   a. Pull(since, 500) → changes, latestSeq
   b. 对每个 change：ReplicationService.Apply(change)
   c. 若 change 是 asset put 且本地 blobstore 无该 blobHash：
      FetchBlob(hash) → blobstore.Put（流式落盘，验证哈希）
   d. since = 本批最后 seq；若 len(changes) < limit 或 changes 为空 → 结束
3. 返回 latestSeq（调度器存为本地水位）
```

- blob 缺失判定：`blobstore.Exists(hash)`；补拉写入用 `blobstore.Put`（内容寻址，重复写幂等）。
- Apply 失败（如对端仓库尚未同步、用户缺失）：跳过该条并记日志，靠 FR-85 对账兜底（本期不阻塞整批）。

## 5. 验收标准

- **增量拉取**：A 写入制品/用户/仓库/ACL 后，B `Sync` 后元数据一致；`latestSeq` 正确推进。
- **全量初始化**：空库 B 首次 `Sync(0)` 后，与 A 全部数据一致（重放日志 + blob 补拉）。
- **blob 只传缺失**：B 已有某 blob 时再次同步不重复拉取（本地 Exists 命中跳过）。
- **全程无 PUT**：复制链路（pull/blob）无任何写请求；服务端不提供 PUT/POST 同步端点。
- **鉴权**：无 token / 错误 token 401；未配置 `JIAN_SYNC_TOKEN` 时端点 404。
- **安全**：同步令牌不进日志；blob 校验哈希。
- **测试**：服务端端点 handler 测试（pull 分页 / blob 404 / 鉴权 401）+ 客户端 Sync 集成测试（双向同步、首启全量、blob 补拉、全程 GET）。
- **实机（FR-85 落地后整体验收，用户确认）**：两台机器 / 两个域名组主备，双向经 GET 拉取同步一致，大制品（>100MB）经 blob GET 完整传输不触发上传限制。

## 6. 风险 / 待定

- **水位语义**：`latestSeq` 是"被拉取方当前最新 seq"。拉取方每次同步后记住该值；若同步中途失败，下次从上次成功水位重拉（变更按 seq 有序，Apply 幂等 + LWW 兜底）。
- **Apply 跳过缺失依赖**：对端顺序未保证时（如仓库变更晚于其制品到达），Apply 失败跳过，靠 FR-85 对账补——本期记录日志不阻塞。
- **blob 拉取重试**：FetchBlob 失败（网络/404）记日志并跳过该 asset，靠对账兜底；不做复杂重试。
- **多 token**：本期两端共用一个 `JIAN_SYNC_TOKEN`；按节点区分 token 留 FR-86。
