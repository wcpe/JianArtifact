# 功能规格：同步调度（实时触发 + 定期对账 + 首启全量）

> 状态：草拟　·　关联 PRD：FR-85　·　分支：feature/replication-scheduler　·　依赖：FR-83（变更日志）、FR-84（复制协议）、ADR-0013

## 1. 背景与目标

FR-84 已提供复制能力：服务端 pull/blob 端点 + 客户端 `ReplicationClient.Sync`。FR-85 补齐**调度**：让两个节点自动地、实时地、双向地互相同步，无需人工触发。

目标（对用户）：

- **有上传和删除就同步**：本地写操作发生后，短时间内自动拉取对端（双向）；
- **定期兜底对账**：定时强制同步一次，弥补事件丢失 / 断网恢复；
- **配置对端后自动首启全量**：部署时配好对端地址即自动全量初始化，无需手动操作；
- 同步水位持久化，重启不重复拉全量。

## 2. 需求（要什么）

- **复制调度器 `ReplicationScheduler`**（domain 层）：
  - 持有一个对端（URL + 同步令牌）与本地水位（上次成功同步到的对端 `latestSeq`）；
  - `Start()` 启动后台循环，`Stop()` 优雅停止；
  - **触发策略**（实时 + 兜底双通道）：
    - 短轮询检测本地变更：周期性（默认每 2s）对比本地 `repl_change` 最新 seq，发生变化 → 立即触发一次对端拉取（近似"有写入就同步"）；
    - 定期全量对账：每 `interval`（默认 60s）无条件触发一次对端拉取（弥补漏拉 / 断网积压）；
  - **首启全量**：本地无对端水位记录（首次配置对端）→ 从 `since=0` 全量同步；
  - **水位持久化**：每次成功同步后把对端 `latestSeq` 存 `setting`（key 按对端 URL 区分），重启后从该水位续拉。
- **配置**（本期经环境变量注入，运行时管理面留 FR-86）：
  - `JIAN_SYNC_PEER_URL`：对端基址（设置即启用复制调度）；
  - `JIAN_SYNC_TOKEN`：同步令牌（FR-84 已有，两端共用）；
  - `JIAN_SYNC_INTERVAL`：对账间隔秒（默认 60）。
- **双向**：两个节点各自配对方 URL + 令牌，各自跑自己的调度器（A 从 B 拉、B 从 A 拉）；同步令牌两端相同即可互认。
- **不作为**：运行时管理面（web 集群页 / CLI `replication` 子命令，FR-86）；多对端；变更日志 GC；自动失效切换（部署层 DNS 健康检查）。

## 3. 设计（怎么做）

### 3.1 模块与依赖

```
cmd/main 装配：cfg.SyncPeerURL != "" → NewReplicationScheduler(...).Start(ctx)
  ↓
domain.ReplicationScheduler（新文件 replication_scheduler.go）
  ├─ *ReplicationClient   （FR-84：Pull/FetchBlob/Sync）
  ├─ *ReplicationService  （LatestSeq 检测本地变更；NodeID 无需）
  ├─ *repository.SettingRepo（水位持久化）
  └─ 配置：peerURL / token / interval / 轮询间隔
```

### 3.2 水位持久化

- `setting` 键：`repl:watermark:<peerURL>`（peerURL 含特殊字符不影响，作为字面 key）。
- 值：对端 `latestSeq`（十进制字符串）。读取失败 / 缺失视为无水位 → 首启全量 `since=0`。

### 3.3 触发与循环（单 goroutine 内统一调度）

```
run(ctx):
  lastLocal := 本地 LatestSeq
  if 无水位 → syncOnce(0)（首启全量）；记录水位
  tickerA = 每 2s：本地 LatestSeq != lastLocal → lastLocal = LatestSeq; syncOnce(lastWatermark)
  tickerB = 每 interval：syncOnce(lastWatermark)   // 兜底对账
syncOnce(from):
  newSeq = client.Sync(from)   // 拉变更 + Apply + 补 blob（FR-84）
  成功 → setting.Set(水位键, newSeq)
  失败 → 记日志（保留旧水位，下次重试；对账兜底）
```

- 同一时刻只跑一个 `syncOnce`（互斥），避免并发重复拉取。
- `client.Sync` 内部已循环到最新（见 FR-84），`from` 用当前水位即可（Sync 返回推进后 latestSeq 存为水位）。

### 3.4 配置接入

- `config.go` 加 `SyncPeerURL string`（`JIAN_SYNC_PEER_URL`）与 `SyncInterval time.Duration`（`JIAN_SYNC_INTERVAL`，秒，默认 60）。
- `wiring.go` / `main.go`：`cfg.SyncPeerURL != ""` 时构造 `ReplicationScheduler`（client 用 `cfg.SyncPeerURL` + `cfg.SyncToken`）并在 `run()` 启动（随 context 优雅退出）。

### 3.5 边界

- **不引入事件总线**：短轮询检测本地 seq 变化实现"有写入就同步"，延迟 ≈ 轮询间隔（2s），对制品仓库实时性足够；避免为写路径引入侵入式事件通知（保持 FR-83 最小改动）。
- **不做**：多对端调度、对账冲突合并策略（沿用 LWW）、失败重试退避（对账天然兜底）。

## 5. 验收标准

- **有写入就同步**：A 写入制品/用户后，B 在 ≤ 轮询间隔 + 同步耗时内可拉到（集成测试用可控间隔验证）。
- **定期对账兜底**：人为让一次同步失败（如 B 暂不可达），恢复后 A/B 在下一个对账周期自动补齐。
- **首启全量**：无水位的新节点启动调度器后自动 `since=0` 全量初始化，数据与对端一致。
- **水位持久化**：同步后重启，`setting` 中水位存在，续拉而非重拉全量（blob 不重复拉）。
- **双向**：A 的写入到 B、B 的写入到 A，两节点最终一致。
- **测试**：调度器集成测试（首启全量 / 写入触发 / 对账补齐 / 水位持久化 / 双向）+ 既有测试全绿。
- **实机（FR-86 落地后整体验收，用户确认）**：两台机器 / 两个域名组主备，配 `JIAN_SYNC_PEER_URL` 后自动双向同步，断网恢复自动补齐。

## 6. 风险 / 待定

- **轮询 vs 事件**：短轮询（2s）非严格"事件驱动"，但复杂度低、对制品仓库足够；如需亚秒级可后续改事件通知（不破坏本设计）。
- **单对端限制**：本期一个调度器一个对端；多对端留 FR-86。
- **时钟 / LWW**：沿用 FR-83/ADR-0013 决策；调度器不参与冲突裁决。
- **同步令牌两端相同**：`JIAN_SYNC_TOKEN` 两端配一致即可互认；按节点区分令牌留 FR-86。
