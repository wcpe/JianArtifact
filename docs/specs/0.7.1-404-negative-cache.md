# 功能规格：proxy/group 404 负缓存

> 状态：已交付@v0.7.1　·　关联 PRD：FR-111　·　分支：feature/404-negative-cache

## 1. 背景与目标

FR-110 后 group 缺失制品返回 404 仍需 6-9s（并行探测所有未熔断 proxy 成员）。对**同一个缺失路径的反复请求**（如 Gradle 反复尝试缺失子模块），每次都重新探测一轮，浪费且延迟高。借鉴 Nexus `NegativeCacheHandler`：对明确 404 做短窗缓存，后续同路径请求秒级返回 404。

目标：同缺失路径连续请求，首次 6-9s，后续 <1s（负缓存命中）。

## 2. 需求（要什么）

- **404 负缓存**：proxy/group 读路径对**明确 404**（所有成员确认不存在，非上游故障）做短窗缓存（TTL 60s），同路径后续请求直接返回缓存 404，不再回源/探测。
- **上游故障不缓存**：上游连接失败/超时/5xx（非 404）导致的错误**不写负缓存**，避免把上游故障误缓存成"永久不存在"。
- **复制请求跳过**：复制同步（ReplicationClient）请求跳过负缓存，避免对端同步被缓存 404 误导。
- **成功失效**：同路径后来成功（上传/同步进来）时失效负缓存。
- **键粒度**：按 `(repoID, path)`；仅 GET/HEAD；内存态。
- **范围内**：读路径负缓存；不涉及 blob/元数据缓存。
- **不做（范围外）**：分布式负缓存、持久化、LRU 上限之外的复杂策略。

## 3. 设计（怎么做）

- `domain/asset_service.go` 新增 `negativeCache`（`sync.Mutex` + `map[string]time.Time`，键 = `repoID\0path`）：
  - `Resolve`/`groupGet`/`proxyGet` 入口先查负缓存：命中 → 直接 `ErrNotFound`（不再回源）。
  - 明确 404 时写负缓存（TTL 60s）；错误（非 404）不写。
  - 写路径（`Put`/`Delete`/复制应用）失效对应负缓存键。
- **不可判定 404 不写负缓存（M-1，关键）**：group 层写负缓存前须判定本次 404 是否「确认不存在」。若存在成员被熔断（FR-110 fuse）、auto-blocked（FR-112）或 offline（FR-113）**跳过**，则该 404 是「不可判定」（可能只是全部成员暂时不可用），**不写负缓存**，避免把上游故障误缓存为永久不存在。
  - 实现：`groupGet` 返回带原因的 404（附「是否有成员不可判定」标志，如 `ErrNotFoundUncertain` 或附带 context 标记）；`proxyGet` 的 auto-block 阻止窗口快速失败同样不写负缓存。
- 与 `proxyFuse`（FR-110）/ `proxyHealth`（FR-112）区分：fuse/health 跳过不可达成员，负缓存跳过整个 path 的探测。
- **负缓存失效联动（M-1，后续修订见 §7）**：auto-block 恢复（FR-112 后台探测成功 → AVAILABLE）时，若之前因「不可判定」未写负缓存则无残留；复制/上传成功仍须失效。**此处原先「对已写的『确认不存在』负缓存不因 auto-block 恢复而失效」已被 §7.2 推翻**——恢复 AVAILABLE 现在会级联清掉该仓库及其父 group 的负缓存。

## 4. 任务拆分

- [ ] domain 负缓存结构 + 读路径接入（Resolve/groupGet/proxyGet）
- [ ] groupGet 返回「不可判定 404」标志；有跳过成员时不写负缓存
- [ ] 写路径失效（Put/Delete/复制应用）
- [ ] 复制请求跳过负缓存
- [ ] 测试：命中/未命中/上游故障不缓存/**有成员被熔断或 offline 跳过时不缓存**/成功后失效/复制跳过
- [ ] 文档同步：ARCHITECTURE、CHANGELOG

## 5. 验收标准

- 同缺失路径连续请求：首次 6-9s，后续（TTL 内）<1s 返回 404。
- 上游 5xx/超时导致的错误不写负缓存（下次仍尝试回源，不误判不存在）。
- **有成员被熔断/auto-blocked/offline 跳过时，group 404 不写负缓存**；上游恢复后同路径立即重试成功，不返回缓存的过期 404。
- 同路径成功上传/同步后负缓存失效，可立即读到新制品。
- 复制同步请求不受负缓存影响。
- 测试全绿（含 -race）。

## 6. 风险 / 待定

- TTL 内新制品可能延迟可见（最长 60s）——可通过"成功失效"缓解，属可接受权衡。
- 键粒度 `(repoID, path)` 简单直接；group 的 404 在 `groupGet` 层缓存（整个 group 探测结果），proxy 的 404 在 `proxyGet` 层缓存。

## 7. 后续修订：毒缓存加固（对应 PR #112）

线上事故促使本机制做了一轮加固，全部为**追加**语义，不改变「只缓存确认不存在」这一根本判据。

### 7.1 Maven 同坐标「有 pom 无 jar」守护

Maven 生态里 `.pom` 与 `.jar` 分两次发布，构建先拿 POM 再拿 JAR。若上游（或中间代理）对 JAR 返回瞬时 404，
把该路径写进负缓存会让构建死锁——`maven.wcpe.top` 的 `com.mojang:logging` 事故即属此类。

现规则：写入负缓存前检查**同坐标 POM 是否已本地缓存且 `packaging` 非 `pom`**；命中则不写。
`-sources.jar` / `-javadoc.jar` / `-test-sources.jar` 等可选附件、以及 `packaging=pom` 的模块仍正常负缓存
（它们本就常常不存在，不该牺牲 IDE 探测延迟）。

查找范围要**超出本条仓库**：客户端通常经 group 拉 POM，POM 会落在最先服务它的成员上。
只看本 proxy 的缓存会让「POM 在兄弟成员」时守护失效，因此自身未命中时再向所有父 group 找一次。

SNAPSHOT 必须单独处理：协议层已把 `.../1.0-SNAPSHOT/foo-1.0-SNAPSHOT.jar` 改写成
`foo-1.0-20260317.215705-3.jar`，按 `artifactId-version` 拼前缀永远匹配不上。
SNAPSHOT 分支直接用文件名去 `.jar` 换 `.pom`。

### 7.2 父 group 级联失效

负缓存键是 `(repoID, path)`，而 group 的 404 与成员的 404 是两套独立的键。
成员修复后（重新上传、恢复上线、`RecheckConnection` 转 AVAILABLE、手改配置）必须同步清掉所有父 group 的同路径条目，
否则「成员已经好了，聚合仓还在返回 404」。级联覆盖直接与嵌套父 group。

**这推翻了 §3 的原条**：原设计认为「已写的确认不存在不因 auto-block 恢复而失效」，
实践中这恰好是毒缓存最难自愈的一环，现改为恢复即失效。

两条实现约束：

- 建父边时必须**同时收主名与别名**（group 成员允许写别名，只按主名建边会静默丢边）；
- `List()` 不填充 `Aliases`，需用 `ListAliasesByRepos` 批量补齐，避免逐仓 N+1。

### 7.3 失效是热路径成本

级联失效挂在**每次 proxy 冷回源成功**与**每批发布**上（一次 500 依赖的构建即 500 次）。
父边反查要读一遍仓库表并解析每个 group 配置，属固定成本，因此优化为：
负缓存为空时直接早退（O(1)），非空时才做反查。批量操作按「全部受影响路径 × 一次父边解析」处理，不按条目数放大。

### 7.4 仓库级 TTL 覆盖的口径

新增 `negativeCacheTtlSeconds`（proxy 仓库级）：继承全局 / `0` 关闭 / `1–3600` 自定义。

**口径统一为「只能更短，不能更长，也不能重新打开」**：

- 全局 `TTL=0`（运维的绝对关闭开关）下，仓库级正数覆盖**不得**把它重新打开；
- 仓库级覆盖值大于全局时按全局取值，避免单仓把条目钉得比全局更久；
- group 层取「所有可回源 proxy 成员的覆盖值最小值」，与全局取更短者。

### 7.5 客户端强刷透传

识别 `Cache-Control: no-cache` / `max-age=0` 与 `Pragma: no-cache`
（Gradle `--refresh-dependencies`、`mvn -U`），命中时跳过负缓存直读上游。语义是「跳过读、仍更新写」。

**只在已认证主体上生效**：该头零成本、可任意构造，而制品读路径没有独立限流。
若匿名请求也能触发，任何对不同 path 反复带该头的客户端都能让每次读穿透 group 全部成员回源，
把负缓存这道唯一减速带关掉。当前仅接入 raw 与 maven 两个读 handler。

### 7.6 group 成环的写入侧拒绝

group 允许嵌套 group 后，读路径会按成员递归下发。若允许 `A→B` 与 `B→A` 共存，
单个请求会在 16 层深度内按分支因子指数放大（2-环约 2^16 个 goroutine 与同量级本地查询），
构成可被配置触发的自我 DoS。写入侧现拒绝成环（沿成员链 DFS，触及自身即成环），
读路径另带 visited 集合兜底历史脏数据。
