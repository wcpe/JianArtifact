# 功能规格：group 聚合读性能（并行回源 + 短超时 + 不可达熔断 + IPv4 优先）

> 状态：开发中（实现已完成并实机验证，待随 0.7.1 发布）　·　关联 PRD：FR-110　·　分支：feature/group-read-latency

## 1. 背景与目标

`maven-public` 等 group 仓库聚合大量 proxy 成员（实测生产节点 maven-public 曾含 22 成员、18 个 proxy）。旧 `groupGet` 对不存在的制品**串行**遍历每个 proxy 成员，每个不可达成员消耗 `groupMemberTimeout=10s`，导致缺失制品 20+ 秒才返回 404（经 CDN 甚至超时）。Gradle 把超时当"仓库故障"而不回退下一仓库。

本 FR 让 group 对缺失制品**快速返回明确 404**（Gradle 可正常回退）。

## 2. 需求（要什么）

- **并行探测**：group 读先串行快查全部成员本地缓存（hosted/已缓存 proxy 命中即返回，保持成员顺序语义），本地全未命中则对未熔断的 proxy 成员**并行回源**（首个成功即取消其余）。
- **短超时**：`groupMemberTimeout` 10s → 3s。
- **不可达熔断**：proxy 回源失败（连接失败/超时/5xx，非 404）进入短窗熔断（30s 内跳过该成员）。
- **IPv4 优先回源**：`upstream.Client` 用 tcp4 Dialer，规避无 IPv6 出口宿主被 DNS AAAA 优先拖慢。
- **范围内**：仅 group 读路径；不改变 hosted/proxy 语义。
- **不做（范围外）**：404 负缓存（FR-111）、auto-block 主动探测恢复（FR-112）、offline 开关（FR-113）、状态展示（FR-114）——均为后续 FR。

## 3. 设计（怎么做）

- `domain/asset_service.go`：
  - `groupGet` 改为两阶段：阶段一串行 `localGet` 快查（不触发网络），阶段二对未熔断 proxy 成员并行 `resolve`（`sync.WaitGroup` + `context.WithCancel`，首个成功取消其余；成功者关流，后续按成员顺序 `localGet` 返回缓存）。
  - `groupMemberTimeout` 10s → 3s。
  - 新增 `proxyFuse`（`sync.Mutex` + `map[repoID]time.Time`）：失败 `trip`（TTL 30s），`tripped` 判断是否熔断。
- `upstream/client.go`：`newUpstreamHTTP` 用 `net.Dialer` + `DialContext("tcp4")` 构造 Transport，`NewClient`/`SetTimeout` 使用之。
- 清理生产节点 maven-public 不可达/无效成员（运维数据，非代码）。

- [x] 现有 group/proxy/single-flight 测试全绿，新增并行/熔断测试通过（含 -race）。

## 6. 风险 / 待定

- 剩余 6-9s 来自"group 须等全部成员探测完才能确定 404" + 个别慢但可达上游（如 maven-central 回源 2-4s）的语义开销，属正常；不可达成员熔断后不再反复拖慢。
- 熔断为固定 30s TTL（无主动探测恢复）——由 FR-112 增强为 Fibonacci 退避 + 后台 HEAD 探测。
