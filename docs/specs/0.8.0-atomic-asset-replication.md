# 功能规格：集群原子制品操作复制

> 状态：开发完成，待用户验收　·　关联 PRD：FR-105　·　目标版本：v0.8.0（尚未发布）　·　依赖：FR-104、FR-115、FR-121　·　决策：ADR-0020、ADR-0023

## 1. 背景与目标

本地目录删除或 Raw 路径迁移必须整批原子，对端也不能在同步中读取到只删除了一半或只移动了一半的目录。级联树增加 relay standby 后，operation 还必须经过一个或多个中继保持完整，不能因为中继重新编号或只保存逐项变更而出现半批次状态。

## 2. 需求

- operation envelope 承载当前 hosted 仓库内的 `asset` 项；PyPI、NuGet 发布还必须同批携带其 `format_metadata` 项，保证制品和索引元数据在父节点与所有级联下游同时可见。每项保留独立接收审计，并携带 UUIDv7 `operationId`、根源节点、stream generation、统一版本元组、排序实体键、项目数和清单 SHA-256；逐项变更只属于 operation envelope，不独立占用根源复制流的 `seq`。
- 根 primary 的 completed outbox 与本地完成状态同事务提交并分配根源 `seq`；relay 只保存同一根源 record 的入站/转发状态，不将上游数据重新写成自己的业务 change 或 operation outbox。
- `protocol=v2` 将根源 outbox 或 relay 可转发日志作为联合 records 流中的不可分割 envelope 返回，响应为 `{records,latestSeq,hasMore}`。中继只有在收齐、校验清单、依赖关系与缺失 blob，并完成本地原子应用后才能向直接下游提供；watermark 只能在完整 envelope 成功后推进，`hasMore` 是唯一翻页依据。
- v1 继续只承载普通 `repl_change[]` 兼容；若范围包含 operation，必须 409 拒绝而不能越过其 seq。级联树不允许通过 v1 绕过中继完整性。
- 父节点与直接下游必须先协商 v2 和中继能力；任一直接边能力不足时返回 `409 cluster_peer_upgrade_required`，不产生本地业务操作、不创建本地业务 outbox，也不推进该边 watermark。
- 根 primary 的状态对所有下游权威；relay 的更高本地遗留版本必须由直接父节点的根源 operation 整批覆盖，不能生成 successor、普通变更或回传记录。相等版本元组而资产逻辑内容不同视为损坏并拒绝该批，不修改正常读视图或 watermark。
- relay 日志必须按根源 stream generation、source node、source seq 和 operationId 幂等；同 stream/seq 的不同载荷必须拒绝。接收端以不可变 receipt 固化原始 generation/source/seq/operationId/manifest，普通 change 与 operation envelope 的根源身份、版本、清单和依赖在所有层级保持不变。
- 不做 PUT 推送、跨操作强一致、跨节点共享事务、跨分支合并或由中继重新裁决业务版本。

## 3. 设计

在既有 GET pull 变更流上保持 ADR-0020 的 v2 联合 records、操作 outbox、完成边界和 `operation_item(type,key,data,blob_hashes,depends_on)`。根 primary 在完成业务操作的同一 SQLite 事务中写入 outbox；relay 在本地入站事务中登记接收与可转发状态。

中继流程固定为：

1. 直接下级以自己的边 watermark 拉取父节点；
2. 父节点只从根源 outbox 或已完整应用的 relay 日志返回 records；
3. 下级校验 generation、seq、operation 清单、依赖和 blob 哈希；
4. 下级在本地完成原子应用，并登记接收审计；
5. relay standby 在每条本地应用成功后写入不可见 inbox，只有整轮分页、应用和 blob 补齐全部成功后才推进 `forwardable_seq`；
6. 只有直接下级成功推进其 watermark 后，父节点才可根据所有直接下级的最小确认水位回收 relay record/blob。

operation 仍最多包含 1000 个 wire item（一次最多 500 个实际制品，移动为每个制品产生 delete+put 两项）。普通 change 与 operation envelope 使用同一根源序列排序，分页不能拆 operation，watermark 不能跨越未完整交付的 record。

接收端先取得全部依赖和 blob，再通过 FR-104 协调器在单个本地事务中应用；PyPI、NuGet 的格式元数据与制品同事务可见。完成前不进入正常资产读视图，也不能进入下游 relay 流。接收审计保留本地复制服务身份、来源节点和原始操作者快照，不复制任何凭据。

- [x] 实现中继接收、blob 保守保留、原子应用与成功后可转发状态转换。
- [x] 扩展 v2 capabilities/pull/blob 响应和直接父子能力协商。
- [x] 保证普通 change、operation envelope、接收审计和重复拉取在多级中继中保持根源身份。
- [x] 补充分支下级、四跳链路、跨边凭据和父节点失败的自动化测试；真实断网/重启/重新挂接仍需环境验收。
- [x] 同步 PRD、ARCHITECTURE、API、OPERATIONS、CHANGELOG。

## 5. 验收标准

- 两节点间的目录删除和 Raw 多项移动在对端一次性可见，不出现半批次状态。
- 四层级联链路和一个 relay 挂两个直接下级时，目录删除、Raw 多项移动、普通 change、PyPI/NuGet 格式元数据和 blob 均能逐层一次性可见。
- 两个直接下级独立拉取时，各自 watermark、接收审计和失败状态独立；一个下级落后、断网或撤销凭据不影响另一个下级继续同步。
- 中继转发后的 `sourceNode`、stream generation、seq、operationId、manifest、依赖和 blob 哈希与根 primary 一致；中继不产生本地业务 change/outbox，不生成 successor。
- relay 只向下级提供已经完整校验和原子应用的记录；当前 blob 保守保留，慢下级恢复不会因父节点提前回收而丢失数据。按直接子边最小确认水位回收仍未开启。
- 重复拉取、并发下级、普通 change 与 operation 交错、分页边界、缺失 blob、损坏清单、相等版本内容不一致和父节点断网均不导致半应用或错误 watermark。
- operation 完成事务一旦提交，资产/格式元数据、outbox 或 receipt、实体版本和逐项审计即为权威结果；其后的回滚快照删除失败只能保留为可重试清理，不能补偿回滚业务状态。standby 在完成前崩溃时只恢复 `received` intent，恢复后同 receipt 可重试、不同 receipt 拒绝。
- fresh 下级从水位 0 重放时，若历史 put/move 所需 blob 已按 FR-104 回收，且该 operation 的全部 put 目标均被后继 put/delete 或仓库删除覆盖，则仅将这些历史 put 记为 `skipped_superseded`，同批 delete 仍须原子应用后再继续推进；原始 receipt、执行子集和全部 applied/skipped 审计须同事务提交，任一审计失败整批回滚并允许同 ID 重试，不同 manifest 必须拒绝。多文件 move 中一个 blob 仍可用、另一个已回收时不得残留任一旧源路径，无关实体删除也不能被误当成覆盖。
- stream generation 变化、人工重新挂接和人工提升后，旧 watermark/旧 relay 历史不会污染新流；旧节点以全新数据目录重新建立复制。
- 复制全程无 PUT/POST 推送；下游不能通过复制凭据访问管理、协议写入或业务写入。
- 后端单测、集成测试、竞态测试、OpenAPI/devmock 校验通过；本地真实进程覆盖单 relay 双 child、operation/blob、一个 child 断网而兄弟继续、恢复追平、逐跳凭据轮换、relay/child 重启，以及含已回收历史的 fresh relay→child 从水位 0 重建。外部网络、Linux arm64、远程 CI 与发布仍需独立验收。

## 6. 风险

- 中继日志和未确认 blob 会增加磁盘占用；回收必须以直接下级确认水位为边界，不能使用无条件 GC 破坏慢下级恢复。
- 级联层数越深，延迟和故障传播范围越大；不以定期对账掩盖中继丢失或 operation 半应用。
- v1 兼容只适用于不含 operation 的历史普通流；级联 relay 不得通过旧协议绕过 v2 完整性。
