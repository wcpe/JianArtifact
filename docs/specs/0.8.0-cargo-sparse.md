# 功能规格：Cargo sparse registry

> 状态：开发完成，待用户验收　·　关联 PRD：FR-26　·　分支：当前工作区　·　依赖：FR-32、FR-104、FR-105、FR-109；决策：ADR-0010、ADR-0015、ADR-0017

## 1. 背景与目标

Cargo 的 sparse registry 将 crate 索引拆为按 crate 名定位的 JSON Lines 文件，下载 URL 与发布 API 又由根 `config.json` 声明。它不是 Raw 目录树：仅保存 `.crate` 文件不足以让 `cargo build` 发现版本、校验 checksum 或识别 yanked 状态。

本功能提供 hosted、proxy、group 三类 Cargo sparse registry。客户端只需把 registry index 指向 `<base>/cargo/<repo>/`；下载 URL、索引与发布 API 均由本节点生成，既不暴露上游 URL，也不要求改 Cargo 客户端的解析工作流。

## 2. 需求（要什么）

- **根配置与索引**：
  - `GET /cargo/<repo>/config.json` 返回 sparse 配置，`dl` 指向本仓 `/cargo/<repo>/api/v1/crates/{crate}/{version}/download`；hosted 的 `api` 必须为节点对外基址的 `<public-base>/cargo/<repo>`，由 Cargo 再追加标准 `/api/v1/...` 路径，不能预先附加 `/api/v1`。`auth-required` 必须按当前仓库是否允许匿名 read 动态生成：匿名可读为 `false`，否则为 `true`，三种仓库类型一致；hosted publish 无论该字段均强制 API Token 认证。proxy/group 不声明 API 以防写入。
  - `GET /cargo/<repo>/<index-path>` 依 Cargo sparse 索引路径规则返回一个 crate 的 UTF-8 JSON Lines，每行一个版本记录；请求路径与 crate 名映射不匹配返回 404，而不是目录列举。
  - `GET /cargo/<repo>/api/v1/crates/:crate/:version/download` 流式回传对应 `.crate`，并设置长度、类型与 ETag。
- **hosted 发布**：实现 `PUT /cargo/<repo>/api/v1/crates/new` 的 Cargo publish 二进制帧（metadata JSON 长度 + metadata + crate 字节长度 + crate 字节）。校验 crate 名、版本、索引路径、包字节 sha256 和 metadata 一致性；同一仓库/crate/version 只能首次创建，重复发布返回 Cargo 可识别的冲突。成功后原子写入 crate、版本记录与索引可见状态，返回 `{"ok":true}`。
- **hosted yanked 状态**：实现 `DELETE /cargo/<repo>/api/v1/crates/:crate/:version/yank` 与 `PUT .../unyank`，只改该版本的 `yanked` 索引字段，不删除 `.crate`。两者均要求该仓库写权限，且受 FR-109 的 Release 不可变策略约束：Release 仓库拒绝 yank/unyank，开发仓允许且完整审计。
- **proxy 与 group**：
  - Cargo proxy 的 `remoteUrl` 是上游 sparse index 根地址。首次取 `config.json` 时读取其 `dl` 模板并只在服务器内部保存；对外仍返回本仓 `dl`。索引未命中从上游拉取、校验 JSON Lines、缓存版本记录；下载按已记录的上游 `dl` 模板流式回源、校验 checksum 后缓存。
  - group 按成员顺序合并同 crate 的版本记录，版本号相同则首成员胜出；下载按该记录所属成员解析。group 的 `config.json` 使用 group 自己的本地下载 URL，且不可发布、不可 yank。
- **认证、发布策略、审计与复制**：读写复用仓库 ACL；Cargo 发布使用其原生 registry token 通道，统一解析为 ADR-0015 的 API Token principal，不宣称标准 `cargo publish` 可携带 Basic 用户名口令。除这一裸 token 兼容通道外，Basic 只接受账号口令或 API Token，Bearer 仅接受 `jat_` API Token，Web JWT Bearer 在 Cargo 协议端点统一为 401。不可变 Release 的原生 Cargo publish/yank/unyank 一律不得覆盖既有逻辑对象，即使主体为管理员；仅未来统一管理 API 携带 `overrideReason` 时才可执行格式感知覆盖。发布账户路径前缀以规范化 crate 名匹配；额度计数以新版本与 `.crate` 字节为准。发布、yank、unyank、代理缓存的可复制元数据均写审计与复制记录，审计保留稳定用户 ID、用户名快照、认证方式、IP、User-Agent、请求 ID 与结果，不记录口令或令牌明文。
- **范围外**：Git index、crates.io 用户/所有者 API、搜索、下载统计、替换/删除已发布 crate、任意 `dl` URL 转发、私有上游明文凭据或任意环境变量引用、SemVer 重排序、UI 发布表单不在本 FR。私有上游仅可使用 ADR-0022 的逻辑 `credentialRef`。管理端删除不覆盖 Cargo，另立格式感知生命周期需求。

## 3. 设计（怎么做）

### 3.1 路由、配置与认证

- 新增 `protocol/cargo.go`，由 FR-32 的格式注册表按 `cargo` 开关注册 `/cargo/:repo/*rest`；先匹配 `config.json` 与 `api/v1`，再匹配 sparse index catch-all，防止 crate 名路径吞掉 API。
- 仓库 format 增加 `cargo`；OpenAPI、前端/devmock、usage、迁移发现同步扩展。Cargo proxy 的 `remoteUrl` 必须是无凭据的 `http/https` sparse 根地址。上游下载模板、token 与最终下载 URL 只能保存在 Cargo 专属持久化字段或运行时凭据解析器中，不能回写到公开 repository.config。
- 在 `auth` 增加窄的协议凭据解析接口：仅 Cargo 路由接受 Cargo 的裸 `jat_` Authorization 值，并与协议 Basic、`jat_` Bearer 输出同一种 principal；协议路由拒绝 Web JWT Bearer。该扩展不得改变管理 REST 的认证语义，也不得把任意裸 Authorization 当作会话凭据。

### 3.2 数据、发布与索引

- 新增 `cargo_crate_version`：仓库 ID、规范化 crate 名、版本、crate asset 路径、sha256、完整 Cargo index JSON、yanked、上游下载模板/来源标识、创建/更新时间；同仓/crate/version 唯一。`.crate` 字节作为现有 blobstore 的 asset 保存到保留路径 `cargo/crates/<crate>/<version>/<filename>`。
- `CargoService.Publish` 先流式将请求 payload 中的 crate 部分写入同盘暂存并计算 sha256，再校验 metadata 与索引记录；随后以一个 SQLite 事务写 asset、版本行和完成状态。索引响应按版本创建顺序以 JSON Lines 流式输出，不能把整份索引文件加载入内存或作为可被任意 PUT 覆盖的 Raw asset。
- yank/unyank 只在事务中切换 `yanked` 后生成索引；任何失败不改变下载字节。FR-104 的引用回收必须承认 Cargo crate asset 仍由版本行引用，禁止因索引状态改写误删 blob。

### 3.3 回源、group 与复制

- `CargoUpstreamClient` 读取上游 `config.json`、按索引路径拉取 JSON Lines，并把 `dl` 模板映射为单个 crate/version 的绝对下载地址；模板替换只支持 Cargo 规范变量，不接受客户端给出的任意 URL。`remoteUrl`、`dl` 与重定向均须经统一出站安全策略，拒绝环回、链路本地、私网、云元数据地址，并在连接时重新校验 DNS。下载完成后 sha256 必须与 index `cksum` 一致，否则返回 502 且不缓存。
- proxy 冷拉和 group 同 crate 请求以 `(repo,crate,version-or-index)` single-flight 收敛；上游 404→404、超时→504、无效索引/校验失败→502。group 合并不做 SemVer 择新，严格按成员顺序保留首次出现的同版本记录。
- `cargo_crate_version` 与 yanked 状态定义为复制实体；发布的一份 crate 与其版本记录使用 operationId 及完成边界，接收端先取缺失 blob 后在同一事务中公开索引记录。复制完成前 node B 不得让 index 出现不可下载版本。

## 5. 验收标准

### 自动化

- 以 Cargo 官方 sparse 索引格式夹具验证 `config.json`、2/3/4/多字符 crate 名索引路径、JSON Lines、依赖字段、checksum、重复版本冲突与 yanked 字段；断言 hosted `api` 为 `<public-base>/cargo/<repo>`，真实 publish 请求只追加一次 `/api/v1/crates/new`；public/anonymous 与私有 hosted/proxy/group 的 `auth-required` 正确；坏路径、坏帧、坏 checksum 均无新增 asset/版本行/blob。
- hosted 集成测试发布 `.crate` 后使用 index 和 download 端点完整往返；yank 后旧版本仍可按锁文件下载但新解析不选中，unyank 后索引恢复。Release 与发布账户策略的拒绝路径、JWT Bearer 401 路径须有审计。
- proxy httptest 覆盖 config `dl` 重写、上游 index/download 404/超时/5xx、下载 sha256 不符、缓存命中与 single-flight；断言响应与持久化中没有上游 URL 或凭据泄露给客户端。
- group 覆盖成员优先、同版本冲突、跨成员版本并集、下载定位到正确成员；proxy/group 写请求返回一致的只读冲突。
- 双节点测试发布/yank/unyank 的 operationId：对端在缺 blob 时不展示该版本，补齐后索引、下载、审计和复制水位一致；断网恢复无半版本。

### 真机验收（须用户确认）

- 使用真实 stable Cargo，在临时项目配置 `[registries]` sparse index 后执行 `cargo publish`、全新 `CARGO_HOME` 下 `cargo build`、`cargo update`、`cargo yank`/`cargo unyank`；记录并断言 publish 实际请求为 `/cargo/<repo>/api/v1/crates/new`（无重复 `/api/v1`），确认动态 `auth-required`、下载 URL、凭据、checksum 与 yanked 行为均被 Cargo 接受。
- 使用真实公开 sparse 上游与一套私有上游凭据引用完成 proxy 首拉、离线缓存读取和 group 解析；上游停止后已缓存 crate 仍可构建，未缓存 crate 返回明确上游错误。
- 在双节点真实部署从 A 发布后在 B 使用新 `CARGO_HOME` 构建；断网阶段 B 不得解析到不可下载版本，恢复后无需手工修复索引或 blob。

## 6. 风险 / 待定

- Cargo publish 线协议使用标准 registry token，不能假定 `cargo publish` 可传递 HTTP Basic 用户名口令；其与 ADR-0015 的协议账号密码规则共同构成客户端兼容边界，必须以真实 Cargo CLI 验证，不能在 handler 中临时拼接认证头。
- 上游 `dl` 模板可以指向不同域名且含变量，错误替换会形成 SSRF 或缓存投毒；只使用从已配置上游 `config.json` 解析出的 `http/https` 模板，并做 host/scheme、变量和 checksum 校验。
- Cargo 的版本选择由客户端的 SemVer 规则完成，服务端只保留索引记录；group 同版本首成员优先是确定性来源选择，不代表“最新版本优先”。
