# 功能规格：Linux arm64 发布二进制

> 状态：计划　·　关联 PRD：FR-33　·　分支：main　·　依赖：ADR-0001、ADR-0005、ADR-0006

## 1. 背景与目标

JianArtifact 的交付形态是内嵌管理端资源的单个静态二进制。Linux arm64 主机（如 ARM 云实例与常见 ARM 服务器）不能运行 linux/amd64 资产，因此正式发布必须提供可校验、可实际启动的 Linux arm64 二进制。

现有发布脚本已包含 `linux arm64` 交叉编译调用，但 Go Task 的 `release` 仍是占位任务，且没有 arm64 原生运行验收。本 FR 将其收敛为受 CI 验证的正式发布能力；交叉编译成功不等同于 arm64 可运行。

## 2. 需求

- 每个 main 预览发布与正式 `vX.Y.Z` Release 必须包含 `jianartifact-<version>-linux-arm64`，与现有发布资产目录和命名规则一致。
- 二进制必须以 `CGO_ENABLED=0 GOOS=linux GOARCH=arm64`、`-trimpath` 及发布版本 ldflags 构建，内嵌与同次构建一致的管理端 `apps/web/dist`。
- `SHA256SUMS` 必须包含该文件，且在 Linux arm64 环境可用 `sha256sum -c` 校验通过。
- 顶层 `make release` 和后端 Task `release` 必须调用同一份发布清单，不能保留成功退出的 TODO 占位；Windows 原生入口必须为 PowerShell 或 Go 工具，Linux/macOS 可使用 shell 入口，二者不得要求 WSL，并保留默认 amd64 兼容行为。
- CI 必须先在常规发布构建中验证生成文件是 ELF 64-bit AArch64/ARM aarch64，不能只依赖文件名；随后在真实 Linux arm64 runner 上下载同一发布资产，完成校验和、`help`、启动服务和 `/readyz` 冒烟。
- arm64 冒烟使用临时数据目录、随机空闲端口和超时清理；不得调用外部仓库、不得输出环境变量或凭据。
- 范围外：Docker 多架构镜像、Windows arm64、macOS arm64 的新增承诺、远程部署脚本自动识别架构、性能基准和专门的 ARM 优化。已有其他平台资产不得因本 FR 被移除或改名。

## 3. 设计

- 发布资产使用一份受版本控制的目标清单：Windows 原生入口由 PowerShell 或 Go 工具执行，Linux/macOS shell 入口只负责转发；两端共享同一目标、版本注入、embed 和输出约定，避免 Bash-only 入口或两套构建逻辑。
- 构建命令显式传入版本，产物名使用该版本；正式 tag 与根 `VERSION` 的一致性仍由 release workflow 的既有元数据门校验。
- 发布 workflow 在 `build-assets` 后增加 arm64 验证依赖：构建侧以 `file` 或 `readelf -h` 检查 ELF 架构，并以 `readelf -d` 断言没有 `NEEDED` 动态依赖；原生 Linux arm64 runner 下载同名 artifact 后先校验 SHA256，再启动二进制并探测 `/readyz`。该原生 job 是 GitHub Release 前置依赖，失败时不得上传 Release 资产。
- 由于 ADR-0001 禁止 CGO，arm64 兼容性由纯 Go 依赖与静态交叉编译保证；依赖升级或重新引入 CGO 时，构建和 native smoke 必须立即失败。
- Docker 镜像仍按现有 Dockerfile/Buildx 行为构建，本 FR 不宣称镜像已支持 `linux/arm64`；二进制验收与容器平台矩阵分开记录。

## 4. 任务拆分

- [ ] 收敛发布构建入口：后端 Task、顶层 Makefile、Windows 原生入口和 Unix shell 入口共享同一发布清单的版本、架构和输出约定。
- [ ] 为发布脚本增加/固化 linux arm64 文件存在、ELF 架构、静态链接和 `SHA256SUMS` 覆盖校验。
- [ ] 扩展 release workflow：发布资产构建后运行 Linux arm64 原生 smoke，并让 GitHub Release 依赖该门。
- [ ] 补构建脚本与 workflow 测试/检查，覆盖版本注入、缺失资产、错误架构和校验和失败。
- [ ] 文档同步：PRD、ROADMAP、部署说明、CHANGELOG 与发布资产清单。

## 5. 验收标准

- Windows 原生环境执行 `make release` 不依赖 WSL；产物目录含 `jianartifact-<version>-linux-arm64` 与其 `SHA256SUMS` 行；`readelf -h` 或等效检查确认目标为 AArch64，且 `sha256sum -c SHA256SUMS` 通过。
- 该文件由 `CGO_ENABLED=0 GOOS=linux GOARCH=arm64` 构建，`file` 或等效检查确认其为 Linux arm64 ELF 静态二进制，`readelf -d` 不含 `NEEDED`；版本字符串与本次发布版本一致。
- CI 的 Linux arm64 runner 下载构建 job 产出的同一文件，执行 `jianartifact help` 成功；以临时数据目录启动 `jianartifact run` 后 `/readyz` 返回 200，并在超时内可靠关停。
- main 预览版与正式 tag 都执行上述架构检查和原生 smoke；任一失败均阻止 GitHub Release 发布，其他现有发布资产仍保留。
- **真实设备验收（需用户确认）**：在独立 Linux arm64 主机上下载正式 Release 二进制，校验 `SHA256SUMS`、启动服务并经浏览器访问内嵌管理端及 `curl /readyz`；记录 CPU 架构、版本和结果，不能以 amd64 交叉编译绿替代。

## 6. 风险 / 待定

- GitHub arm64 runner 的可用性、配额或组织策略可能影响 CI；若不可用，必须配置受控的 Linux arm64 自托管 runner，不能删除 native smoke 门。
- 现代纯 Go SQLite 及未来协议依赖可能在编译期支持 arm64 但在运行期暴露问题，因此保留独立真实 arm64 启动门。
- 当前 Docker 镜像没有在本 FR 中声明多架构 manifest；用户在 arm64 主机上应先使用本 FR 产出的二进制，镜像支持需另立需求与验收。
