# 功能规格：回源 Token 校验（安全防护）

> 状态：开发完成，待用户验收　·　关联 PRD：FR-130　·　分支：feature/fr130-origin-token-guard

## 1. 背景与目标

EdgeOne 免费版无"源站防护"(无法获取回源 IP 段做安全组白名单),Host 头可伪造,现有域名白名单(FR-129)挡不住恶意直连。目标是提供**应用层回源来源校验**:只有携带 CDN 回源注入的密钥 Token 的请求才被放行,直连源站(无 Token)一律 404——不依赖回源 IP、不依赖付费功能。

阶段：P1(源站访问防护,与 FR-131 TLS 共同闭环)。

## 2. 需求（要什么）

- 后台「设置 → 安全防护」区块：
  - **启用开关**(默认关闭)
  - **请求头名**(可编辑,默认 `X-Jian-Origin-Token`,即 CDN 回源时注入的请求头名)
  - **Token 值**(一键随机生成 32 字节 + 复制,供粘贴到 EdgeOne 回源请求头规则)
- 全局中间件(置于现有 Host 白名单之后,认证之前)：
  - 未启用：完全放行(行为不变)
  - 启用后：**非回环请求必须携带 `请求头名: Token值` 且完全匹配**,否则 404;回环仅按服务端看到的 TCP 对端地址判定，不能由可伪造的 Host 声明
  - 与 Host 白名单**并存**(两层都查:白名单挡误访问、Token 挡伪造直连)
- Token 为**节点本地**设置(不参与复制);重新生成后旧 Token 立即失效(无历史窗口)。
- 范围内：设置页安全防护区、全局校验中间件、单测与前端测试。
- 不做（范围外）：Token 过期/轮换策略、IP 白名单、与 TLS 的强制绑定、多 Token。

## 3. 设计（怎么做）

- **存储**(`apps/server/internal/domain/setting_service.go`)：
  - 新增设置键:`origin_token_enabled` / `origin_token_header` / `origin_token_value`(**节点本地**,加入 `isNodeLocalSetting`,不参与复制)。
  - 方法：`OriginTokenGuard() (enabled bool, header, value string)` 与 `SetOriginTokenGuard(enabled bool, header, value string)`;并入 `SettingsUpdate` 与 `settingValues`。
- **设置端点**(`apps/server/internal/api/settings_handlers.go`)：
  - `SettingsResponse` 增 `originTokenEnabled` / `originTokenHeader` / `originTokenValue`;`SettingsRequest` 对应可选字段。
  - 校验：请求头名必须为合法 HTTP 头名(无空白/冒号);开启时 Token 非空;Token 长度下限(≥16 字符)。
- **全局中间件**(`apps/server/internal/httpserver/`)：
  - 新 `originTokenMiddleware(provider func() (bool, string, string)) gin.HandlerFunc`:只按 `RemoteAddr` 解析实际 IPv4/IPv6 回环来源并放行，不信任 Host 或转发头;未启用放行;启用后 header 值恒定时间比较,不匹配 → 404。
  - `Server` 增 `WithOriginTokenGuard(provider)` option,`Handler()` 中置于 hostFilter 之后。
- **wiring**(`apps/server/cmd/jianartifact/main.go`)：provider 直读 `settingSvc.OriginTokenGuard()`(运行时生效,无需重启),注入 httpserver。
- **前端**(`apps/web/src/pages/SettingsPage.tsx` + `api/endpoints.ts` + `i18n/zh.ts`)：设置页新增「安全防护」卡片:开关、请求头名输入、Token 输入 +「生成」(crypto.getRandomValues 32 字节 hex)+「复制」。

## 5. 验收标准

1. 设置页「安全防护」可见,默认关闭;开启后可编辑请求头名(默认 `X-Jian-Origin-Token`)、生成并复制 32 字节随机 Token。
2. 关闭时：一切行为与现状完全一致(无 Token 也放行)。
3. 开启后：
   - 无 Token 直连源站(任意 Host,含伪造白名单域名)→ **404**;
   - 携带正确 `请求头名: Token` 的请求 → 放行(模拟 CDN 回源);
   - 实际 TCP 对端为回环(IPv4、IPv6 或 IPv4-mapped IPv6)的请求 → 恒放行(健康检查/本机 CLI 不受影响)，外部对端伪造 `Host: 127.0.0.1` 仍 → **404**;
   - Host 白名单仍独立生效(非白名单 Host 即使带 Token 也 404,因白名单先于 Token 检查)。
4. 重新生成 Token 后,旧 Token 请求 → 404。
5. 节点本地:在 103 配置不影响 108/测试站;复制不会同步该设置。
6. **真机验收(需用户确认)**:EdgeOne 规则引擎为 maven.wcpe.top 加「修改回源请求头」`X-Jian-Origin-Token: <值>`;103 开启防护后:公网经 CDN 上传 → 201;公网直连 IP(伪造 Host、无 Token)→ 404;主备复制(108→103)正常。

## 6. 风险 / 待定

- Token 在 HTTP 回源链路明文传输(EdgeOne→源站):回源链路受信任,风险低;FR-131(TLS 回源)落地后 Token 随 TLS 加密,风险消除——两 FR 配合使用。
- EdgeOne 免费版「规则引擎/修改回源请求头」可用性:需用户在控制台确认(基础功能,免费版一般可用)。
- 同机反向代理或隧道若通过回环连接转发外部流量，应用只能看到代理的回环地址并命中本机例外；此类部署必须让代理连接服务的非回环监听地址并用防火墙限制来源，不能通过信任 `X-Forwarded-For` 等可伪造头规避。
