# 功能规格：主备级联树单向复制与受控人工提升

> 状态：已退役@v0.8.0（FR-138；主备级联树复制通道已整体移除，本文仅作历史证据与验收记录）　·　关联 PRD：FR-115　·　目标版本：v0.8.0　·　决策：ADR-0023（已由 ADR-0027 取代）　·　依赖：FR-105、FR-121

## 1. 背景与目标

现有主备实现是“每个 standby 直接从 primary 拉取”的一主多备星型拓扑。它已经保证 primary 唯一可写、standby 只读和 GET-only，但当备用节点数量、地域或网络层级增加时，primary 需要直接服务所有下级，且页面只能表达单一 primary/standby 关系。

本规格把主备复制扩展为有向级联树：根节点是唯一 primary；每个非根节点只有一个直接上级；每个节点可以挂零个或多个直接下级。下级始终主动从直接上级拉取，节点只知道直接邻接关系，不要求任何节点掌握全局拓扑。

## 2. 需求

- 业务角色仍为 `primary`、`standby`、`disabled`。primary 是唯一业务写入源；所有 standby（包括中继 standby）拒绝业务、管理和协议写入；disabled 不参与复制。
- standby 可显式启用中继能力。中继 standby 在保持业务只读的同时，为直接下级提供已经完整接收、校验并原子应用的上游复制流；叶子 standby 不对外提供复制源。
- 每个非根节点只能配置一个直接父节点；每个父节点可配零个或多个直接子节点。配置和管理只涉及直接邻接边，不展示或编辑孙节点、祖先链或全局拓扑。
- 每条父子边只使用 v2 的 capabilities、records pull 和 blob GET；上级不向下级发起连接，不提供 PUT/POST 复制接口，不因下级请求开放业务写权限。
- 复制中的普通 change 和 operation envelope 必须保持根源 `sourceNode`、stream generation、`seq`、`operationId`、版本元组、依赖和 blob 清单不变；中继不得将其重新登记为本地业务变更。
- 中继必须拥有独立的持久化 relay/inbox 记录。记录只有在依赖就绪、blob 校验成功、本地状态原子应用完成后才进入可转发状态；整轮失败时 record 与预取 blob 均不得被下级看到。
- 每条父子边维护独立 watermark、stream generation、valid 围栏和观测状态。三者须原子保存，失效围栏跨重启保持；watermark 只能推进到连续完整成功的根源记录，非零 watermark 缺少 generation 时拒绝续拉。父节点必须按直接下级确认的 watermark 保护仍可能被下级需要的 relay record/blob。
- 父节点只为直接下级创建、验证、撤销和轮换逐跳凭据；下级凭据不能跨边复用，也不能访问管理、协议写入或业务写入。
- 父节点不可用、能力不兼容、凭据撤销、记录缺失或 blob 校验失败时，下级停留在明确的失败/过期状态，不跳过父节点连接更高层，也不推进 watermark。
- standby 的 received intent 在 prepared/staged/committing 阶段崩溃后，重启只按首次落盘的原始 receipt 身份恢复并允许同 ID 重试；旧角色的 local intent 不得由 standby 自动执行。凭据撤销与并发校验以条件更新实际命中为准，撤销完成后进入竞态窗口的请求也必须拒绝。
- 人工提升或重新挂接时必须先围栏旧写入源，核验水位和内容摘要，生成新的 stream generation，并按受控回填重新建立该边；旧 watermark、旧凭据和旧 relay 历史不得自动跨流复用。
- 不做自动选主、自动换父、双主写入、跨分支合并、全局拓扑控制和把节点主机指标跨层汇总。

## 3. 设计

### 3.1 拓扑与配置

```text
                 ┌── child-1 standby
root primary ─── relay standby
                 └── child-2 standby
                       └── grandchild standby
```

图中每条箭头表示下级主动向上级发送 GET pull 请求。应用配置使用直接父节点语义：standby 配置唯一 `JIAN_REPLICATION_PRIMARY_URL`；该变量名为历史兼容而保留了旧名，但在级联树中表示直接上级，不代表必须直连根 primary；是否允许直接下级由显式中继能力开关控制。（该通道与变量均已随 FR-138 退役。）

节点本地保存：本节点 ID、直接父节点绑定、直接子节点凭据摘要、父边 watermark、子边已确认 watermark、stream generation 和邻接观测状态。不存在要求 primary 保存全树节点列表的控制面。

### 3.2 复制流与中继日志

根 primary 的业务写入继续产生根源 `repl_change` 和 v2 operation outbox。standby 拉取父节点时，父节点从自己的可转发 relay/inbox 记录读取；根 primary 从本地业务源日志读取。

中继接收流程固定为：

1. 从直接父节点按 watermark 拉取 v2 records；
2. 校验 stream generation、来源序号、operation 清单、依赖和 blob 哈希；
3. 在本地完成 operation 或普通 change 的原子应用；
4. 同一事务写入原始 operation receipt、实体版本和全部逐项接收审计；
5. 每条成功后登记不可变 inbox record，整轮分页、应用和 blob 补齐成功后推进 `forwardable_seq`；
6. 仅向直接下级提供该连续前缀内的 record 与 blob；
7. 直接下级成功确认后，按所有下级的最小确认水位回收可安全删除的 relay 记录和 blob。

relay 日志不能复用表示“本节点业务写入”的 `repl_change`，否则会把入站数据伪装成本地源变更并形成回路。转发必须保留根源版本和 operation 身份；同 stream/seq 只允许同一不可变载荷幂等重试，换 source 或改 payload 必须拒绝。

### 3.3 流代次、断点与环路

每条根源复制流具有不可复用的 stream generation。primary 受控提升、人工重新挂接或重建流时生成新代次；子节点发现代次变化必须停止旧 watermark 续拉，进入要求重新配对/回填的状态。

节点配置必须拒绝直接自环；能力协商携带受保护的 lineage/loop proof 和 hop 边界，父节点不能向已出现在祖先证明中的节点提供复制源。该证明只用于协议防环，不在页面展示完整祖先列表。

### 3.4 父子凭据

父节点为直接子节点创建一次性凭据，父节点保存加盐不可逆摘要，子节点用本地独立密钥 AES-GCM 密封保存。凭据绑定父 node ID、子 node ID、父基址和 stream generation。

中继节点可以使用本地 CLI 为直接下级创建凭据，但不能读取或转交自己的上游凭据。轮换必须先由子节点导入并验证新凭据，再撤销旧凭据。

### 3.5 故障、人工提升与重新挂接

- 直接父节点短暂不可用：子节点保留旧数据和 watermark，重试恢复，不产生业务写入。
- 上游 blob 已回收或丢失（blob GET 稳定 404）：同一记录连续 ReclaimedSkipAfterRounds（3）轮 404 后按「上游数据丢失」跳过该记录并推进水位，整轮不再被单条记录永久卡死（FR-115 验收发现：原实现整轮失败无限重试，且每条缺 blob 记录触发逐页向流末尾的服务端前向扫描，整体 O(N²)）；跳过与失败证据保留在接收审计（apply_log）中，跨页后继覆盖判定改为顺序流缓冲（O(N)），不再向服务端重复扫描。
- 中继节点不可用：其全部直接下级显示该父边失败/过期；不得自动越级连接祖父节点。
- 重新挂接：先停止旧边，人工确认新父节点是同一合法流或执行全量重建；清除旧边 watermark，使用新父边凭据和 stream generation。
- 提升：先围栏旧 primary/父节点，再核验目标节点水位、接收审计和抽样 SHA-256；目标节点切为 primary 后执行受控回填；旧节点以全新数据目录重新挂接为 standby。

## 4. 任务拆分

- [x] 修改配置模型：直接父节点 URL、中继能力、邻接边和 stream generation。
- [x] 新增 relay 日志持久化模型，并按根源 stream/source seq 保持可转发顺序。
- [x] 扩展复制源能力协商、records pull、blob GET 和根源 watermark。
- [x] 扩展 v2 operation 接收，使中继不拆批、不重写根源身份、不产生本地业务 outbox。
- [x] 扩展逐跳凭据创建、校验、撤销/轮换和 GET 权限白名单。
- [x] 实现 stream 代次匹配、来源自环拒绝、父节点不可用和旧配置隔离保护；自动换父/人工重新挂接仍按运维流程执行。
- [x] 同步 API、集群页面、集群监控、运维手册、架构和 CHANGELOG。

## 5. 验收标准

- 自动化集成夹具已覆盖根 primary → relay standby → relay standby → leaf standby 的首启源流、增量拉取和 operation 续传；本地四进程已验证 relay 强制停止后同目录重启可续传新制品，真实网络断网窗口和人工重新挂接仍待用户环境验收。
- 一个 relay standby 同时挂两个直接下级时，两个下级都能独立拉取并最终达到相同根源 watermark；一个下级落后或离线不阻塞另一个下级。
- primary、relay standby、leaf standby 的业务写入均符合角色边界；中继不产生本地业务 `repl_change`、operation outbox 或回传变更。
- 普通 change、删除 tombstone、v2 operation、PyPI/NuGet 格式元数据和 blob 经两级以上中继后，根源身份、序号、operationId、清单和 SHA-256 一致；不出现半批次可见。
- relay 只向下级提供整轮确认前缀内已完整应用的记录与 blob；当前 relay blob 采用保守保留策略，不会因中继提前清理造成慢下级丢失；按所有直接下级确认水位定向回收仍是发布前运维增强项。
- 0.8.0 未发布开发库升级到不可变 relay 记录时，旧 inbox/frontier 与父边 lineage 强制清空并从水位 0 重建，不能让旧版可改写行被新 frontier 直接信任。
- 重复拉取、并发下级、父节点短暂断网、父节点能力不足、错误凭据、撤销/轮换和 stream generation 变化均不推进错误 watermark，不产生业务副作用。
- 来源自环、stream 代次不匹配和跨边凭据复用被拒绝；完整协议 lineage 环路探测和绕过父节点的越级验证仍需真实多节点验收补足。
- 人工重新挂接和提升后，旧 watermark/旧 relay 历史不污染新流；旧节点以全新数据目录回接并重新完成同步。
- 集群页面和集群监控准确展示本节点、直接父节点、直接子节点和每条边的状态；不声称掌握孙节点状态，不展示凭据、环境变量、内部地址或主机跨节点指标。
- 后端单测、集成测试、竞态测试，前端类型检查/测试/lint/build，以及本地四进程 root→relay→relay→leaf 初始传播验收均通过；真实断网/重启/重新挂接和浏览器路径仍未完成，测试绿不替代完整级联验收。

## 6. 风险 / 待定

- 级联层数越深，延迟和故障传播范围越大；第一版需提供当前节点到直接邻接边的清晰健康状态，不承诺全局实时视图。
- relay 日志和未确认 blob 会增加磁盘占用；必须提供安全的子节点移除/重新配对和保留清理边界，不能用无条件 GC 破坏慢下级恢复。
- stream generation 已进入非契约复制能力响应和 relay 记录；lineage proof、人工重新挂接和按子边确认回收仍是待定发布项。
